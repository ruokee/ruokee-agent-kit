# 一致性（Consistency）

一致性模型、事务边界和冲突处理的工程方法。适用于跨服务数据操作的方案选择、双写问题的修复、事件与状态的可靠性设计。

## 问题：事务边界被网络剪断

单机时代，一个 `BEGIN…COMMIT` 让扣库存、建订单、发优惠券要么全成要么全败。这三件事散落在三个服务三个库后，没有任何单个本地事务能同时框住它们。扣了库存、建了订单，优惠券没发出去，数据只做成一半。

把三个库重新框进一个事务的方案是两阶段提交（2PC）：协调者先问所有参与者是否准备好（投票），全 yes 才提交。代价大到核心链路避之不及：投票到提交之间所有参与者锁住数据干等，一个慢全体被拖住；协调者在 commit 命令发到一半宕掉时，参与者阻塞在进退两难的 in-doubt 状态直到协调者恢复——持久化的事务日志和恢复后的协调者可以完成决定（如 PostgreSQL 的 prepared transaction 经 WAL 持久化、崩溃后保留，https://www.postgresql.org/docs/current/two-phase.html），协调服务本身也可以做冗余，但阻塞和恢复依赖是它的核心风险；要求所有参与者在线，把多个服务的可用性串联，与 CAP 的 A 正面对立。

2PC 不是不能用：单个数据库内部或紧耦合的少数资源间（如同库多分片）仍有位置。横跨多个独立服务且要扛高并发时，主流答案不是把事务做得更强，而是放弃跨服务强事务，改用容忍中间态的最终一致方案。

## Saga：一串本地事务加补偿

把大事务拆成一串本地事务，每步只在自己服务的库里跑。失败时不靠回滚，而是反向执行补偿动作抵消已做的事：钱已打给商家，补偿是发起退款留一条反向记录；邮件已发出收不回，补偿是发更正邮件；库存已扣，补偿是加回去，但此刻可能已被别人买走，这是补偿的固有麻烦。

**补偿不是数据库回滚。** 回滚是事务未提交、数据库当无事发生；补偿是上一步已提交甚至已有对外副作用，删不掉历史，只能再做一个反向操作。Saga 把一致性从数据库保证搬到业务流程保证——省了跨服务锁，多了必须操心的状态机：在第③步没跑完时，系统真实处于"订单已建、库存已扣、未确认"的语义锁定期，业务上要回答此时用户看到什么、能不能取消、半成品订单会不会被别人看到。

两种串联风格怎么选：

- **编排（Orchestration）**：控制流集中在编排器，看得见全貌，可观测性强，一处就能看到卡在第几步。适合步骤多、补偿复杂、要强监控的关键长流程；风险是编排器膨胀成上帝服务。
- **编舞（Choreography）**：控制流分散在事件接龙里，无中心，但可观测性弱，排障像拼图。适合步骤少、参与方少的轻量流程；风险是步骤一多就变事件意大利面，没人讲得清全流程。

朴素法则：当你必须翻好几个服务的日志才能拼出一笔订单发生了什么时，就该上编排器。Uber 在《Announcing Cadence 1.0》（2023-06-22，https://www.uber.com/us/en/blog/announcing-cadence/）介绍了自建的持久化工作流平台；DoorDash 在《Building Reliable Workflows: Cadence as a Fallback for Event-Driven Processing》（2022-10-21，https://careersatdoordash.com/blog/building-reliable-workflows-cadence-as-a-fallback-for-event-driven-processing/）记录了采用 Cadence 兜底可靠异步流程的实践。把 Saga 编排器做成平台级基础设施，是两家的共同路线。

## Outbox：双写问题的事务性解法

一个服务处理完请求，既要改自己的库又要对外发消息。这两件事落在数据库和消息中间件两个系统里，没有事务能同时框住。先写库再发消息，中间崩溃就丢消息；先发消息再写库，写库失败就出幽灵消息。这个问题的阴险之处在于：测试环境几乎不出现，却在生产的尾部概率里持续制造数据库和下游对不上的灵异事件。

解法是事务性发件箱（Transactional Outbox）：不发真消息，改往同一个库的 outbox 表插一行，和业务数据用同一个本地事务提交，两者原子地同生共死。然后独立的投递器读这张表把消息真正发出去：

- **轮询发布。** 定时 SELECT 未发出的记录，发出后标记为已发。简单，有轮询延迟。
- **事务日志拖尾（CDC）。** 直接读数据库 binlog/WAL，outbox 表有新提交立刻捕获发出（如 Debezium 的 Outbox Event Router），零轮询、保顺序。数据库的事务日志本身就是记录发生过什么的真相流。

遇到"改了库又要发消息"，默认考虑 Outbox 或数据库事务日志 CDC（而不是写完库接一行 `kafka.send()`），若有不采用的理由（如两者落在同一事务资源、用原生事务消息）需在决策中说明。注意 Outbox 给的保证是 at-least-once（投递器可能发了没标记就崩溃导致重发），必须和幂等消费配套。

## 幂等三件套

跨外部副作用的系统通常选择 at-least-once 投递，加上网络重试处处都在，同一操作被执行两次是分布式里的常态不是异常。幂等即同一操作执行 1 次和 N 次对系统状态的影响完全一样。`SET 余额 = 100` 天生幂等；`余额 = 余额 + 100` 做两次就多加一次，天生不幂等——而加减、发货、发钱、发消息这类不幂等操作偏偏最不能出错。

改造三件套：

1. **幂等键。** 每个操作带全局唯一 ID（如 `pay_order_12345`）。
2. **去重表。** 消费端记下处理过的键。
3. **同事务执行。** 处理业务和写入幂等键在同一个本地事务里提交。先执行、再写 key，分成两步，中间崩溃就留下钱扣了但 key 没记的破绽，重试又扣一遍。

**重试和幂等必须成对出现。** 写下"失败了就重试"时先问：被重试的操作幂等吗？不幂等配自动重试等于随机重复扣款机。Stripe 在 API 文档中把 `Idempotency-Key` 做成一等公民请求头（https://docs.stripe.com/api/idempotent_requests），正是因为客户端网络一定会重试，服务端就必须幂等。

## 事件溯源与 CQRS

两件重武器，绝大多数 CRUD 系统用不上，硬上是添堵。会判断什么时候轮到用即可。

**事件溯源。** 不存当前状态，存导致状态的一串事件：不存余额 100，存"开户 +0、存 80、存 50、取 30"，余额是重放算出来的。复式记账（账本只增不改，记错只能冲正）和 Git（存 commit 序列，checkout 即时间旅行）都是这个思想。买到的：完整审计（每次状态变化都是不可变事件）、时间旅行（重放到任意时刻）、一份事件多种解读（新需求写新投影，不改历史）。代价：查询难（事件流没法直接 WHERE，这正是 CQRS 解决的问题）；事件 schema 演进是硬仗（事件永不删改，老事件要能被新代码重放，跨数年向后兼容）；重放成本（要定期存快照，像游戏存档点）。适合审计和可追溯压倒一切且业务天然是一串事件的领域（账务、订单状态机、协同编辑历史）。先问：真的需要过去每一刻的完整历史吗？不需要就老老实实存状态。

**CQRS。** 写用一套模型，读用另一套，靠事件投影持续更新读模型。像餐厅后厨和菜单分家：后厨只管做对记准，展示层只管一眼看明白，各自优化，服务员传话保持大致同步（菜单的售罄标签可能慢半拍，即最终一致）。微服务里最实际的用途：database per service 后跨服务 join 做不了，建一个读视图库订阅各服务事件，把数据预先拼好摊平存进去。甜头：读写独立优化扩展（读多写少时读侧疯狂加副本写侧不动）、一个写模型投影任意多个定制读模型、复杂查询不拖累写库。苦头：读模型最终一致（刚下单在列表里看不到，产品要正面处理）、组件和运维复杂度翻倍、多一条要不丢不乱的投影链路。值得的场景很窄：读写负载严重不对称，或同一份数据被列表、详情、搜索、报表四种方式查。朴素判断：当为报表查询不得不在核心写库建一堆奇形怪状的索引还拖慢下单时，CQRS 才开始回本。

## Schema 与契约演进

逻辑好改、数据难改，在事件驱动世界里被放大：schema、事件结构、API 契约一旦被别人依赖（别的服务、攒了三年的老事件、未升级的老客户端），就不能想改就改。滚动升级期间新旧代码同时在线：新代码要读懂老数据（后向兼容），老代码忽略新数据时至少要保证不崩（前向兼容）。

安全迁移的套路是 expand-contract（平行变更），直觉像在旧桥旁边先架新桥：两桥并行通车（Expand，新旧字段共存），车流平稳走上新桥（Migrate，双写搬数据），再拆旧桥（Contract，删旧字段）。全程没有一刻断路。直接 RENAME/DROP 列的瞬间，未升级的旧实例集体崩溃。

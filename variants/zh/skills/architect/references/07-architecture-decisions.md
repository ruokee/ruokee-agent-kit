# 架构决策（Architecture Decisions）

记录候选方案、取舍、后果和重审条件的方法。适用于做出重要架构决策后的留痕，以及判断既有决策是否还成立。

## 最先丢失的永远是为什么

代码和架构图能告诉你系统是什么：有哪些模块、怎么调用、数据怎么流。这些随时能从系统本身读出来。但为什么这么选、当初放弃了什么、在拿什么换什么，读代码读不出来，只活在做决定那个人的脑子里。

会议里讲过的原因，会在三次会议、两次离职、一年时间后蒸发。等需要它时，只剩一个看起来莫名其妙的设计和一群不敢动它的人。接手者面对没有"为什么"的系统只有两种错误可选：要么不敢动（不知道动了会不会出事，系统僵化），要么乱动（删掉看似多余的双写，三周后线上炸了，因为当年有监管要求写入不可篡改存储的背景）。

由此立一条原则：**好的文档不重复解释代码做了什么，因为代码自己会说；好的文档解释代码为什么这么做，因为代码永远不会说。** 把记录的力气花在一旦丢失就再也找不回来的东西上。

## 记录的内容

一条架构决策记录回答六件事：

| 栏目 | 填什么内容 | 少了会怎样 |
|-|-|-|
| 标题 | 一句话说清决策是什么 | 方便检索 |
| 状态 | 草稿/已采纳/已废弃/被取代 | 让读者知道这条还算不算数 |
| 背景 | 当时面临什么问题、什么约束 | 后人最缺的就是当时的处境 |
| 决策 | 最终决定怎么做 | 代码里也能看到，但写下来才完整 |
| 其他选项 | 还想过哪些方案、为什么没选 | 放弃了什么是记录独有的价值 |
| 取舍与后果 | 好处、代价、已知债务 | 让后人清楚地继承这份有意的取舍 |

三条纪律：

- **一个决策一份，保持轻。** 几分钟能读完，才有人读。
- **追加，不修改。** 决策变了写新的一份，把旧的标记为被取代。团队曾经怎么想、后来为什么改，本身就是宝贵信息，保留历史而不是抹掉历史。
- **和代码放在一起。** 随代码版本管理、可搜索、可评审，而不是放 Wiki 的角落里腐烂。

**服从项目现有记录约定。** 不同项目已有自己的决策记录机制，本技能只讲记录方法，不另建格式。在本仓库中，决策记录使用 Agent Note（见 [`.agents/notes/README.zh.md`](../../../../../.agents/notes/README.zh.md)）：proposed 状态记录未被维护者接受的决策，implemented 记录已实施且现行的决策，Decision owner 和 Draft writer 字段已覆盖决策者信息。

## 技术债的记账

技术债借自金融：为了现在更快拿到价值，有意识地选了将来要偿还的权宜方案。借钱本身不是错，关键是你知不知道自己借了、打不打算还。

分清两种债：

- **有意识的债（健康）。** "为了赶上发布先做最简单的方案，记下来，下季度重构。"是理性的商业权衡，写成决策记录并排期偿还。
- **无意识的债（危险）。** "我也不知道为什么这里这么写，反正能跑。"是失控，欠了债都不知道，哪天爆雷完全没准备。

MVP 故意欠技术债常常是正确的：短链第一版的单存储单机发号换来快速验证需求，划算。错的是不知道自己欠了债、欠了不记录、永远只借不还。处理纪律三条：有意识地借（明确这是权宜之计）；记下来（一笔债就是一条决策记录，背景说明为什么暂时这样做）；安排偿还时机（定下"当 X 发生时就还"的触发条件，而不是有空再说）。

## 何时重审决策

架构该不该动了，不凭感觉（"这代码看着丑"不是理由，不影响质量属性的丑可以忍），不凭跟风（别人的瓶颈不是你的瓶颈，照搬大厂成熟期架构套自己的成长期是头号过度设计）。用两把尺子量：

1. **瓶颈。** 某个质量属性是不是已经被架构卡住了：数据库读到冒烟、加缓存也压不住；一个模块改动总是连累一片、发布越来越慢。真实的、量出来的瓶颈才是升级信号。
2. **质量目标的变化。** 业务对"做多好"的要求上了台阶：可用性从 99% 提到 99.99%；用户量进入下一个量级。

不是架构旧了丑了就升级，而是某个真正在乎的质量属性被当前架构卡住、且这个卡点已经量出来，才升级。每次升级本身就是一个该记录的重大决策：背景写什么瓶颈逼着动，决策写升成什么，其他选项写还能怎么扛，取舍写付出什么。

# 系统分析（System Analysis）

从代码、配置和运行证据拆解一个陌生系统。适用于接手遗留系统、审查既有架构、理解依赖服务，或为迁移和拆分做前期摸底。

## 读图是设计的逆过程

正向设计是约束 → 方案 → 图；分析是图和代码 → 反推约束与取舍。两者的判断框架相同，方向相反。

认字和读懂是两回事。认字是看到有网关、有编排层、有向量库、有 GPU；读懂是对每个部件能回答三问：

1. 它在服务哪个质量属性或约束？
2. 它放弃了什么？
3. 规模涨 100 倍，这里会先裂吗？

答不出这三问，说明只是认识了框的名字，还没有理解系统。

## 四步分析法

**① 抓本质。** 一句话业务是什么；最重的两条质量属性是什么；最硬的一条约束是什么。功能人人看得到，质量属性和约束才是把系统塑造成当前样子的力量。

**② 看全景。** 找到灵魂数据流：系统存在的意义所系的那条请求路径，从入口跟到存储再回到响应。跟完一条真实请求（比如一笔退款查询），比读十遍目录结构更能建立全景。

**③ 挖取舍。** 找出两到三个"选了 X、放弃 Y、因为约束 Z"的判断。取舍藏在关键组件的选型里：为什么用消息队列而不是同步调用，为什么读写分开存储，为什么自己部署而不是买服务。

**④ 找死穴。** 第一个规模化瓶颈在哪（负载涨百倍时哪个部件先死），以及一个常见反模式（这个系统里最容易犯的错）。

四步的产出是一页笔记，不是一个完整文档。笔记的价值在于强迫你回答问题，而不是归档。

## 从代码和配置取证

架构图会过期，代码不会。分析一个系统时，用仓库事实校准认知：

- **入口和边界。** 从部署配置、路由定义、公开接口找系统边界。外部调用进来第一站是什么，边界内有哪些部署单元。
- **数据流。** 从 schema、migration 和数据访问层找真实的数据归属。哪些服务写哪些表，跨服务读表通常意味着边界泄漏。
- **依赖方向。** 从 import、依赖清单和服务间调用找依赖箭头。双向依赖、循环依赖是边界不清的直接证据。
- **状态位置。** 哪些组件无状态可以随意扩，哪些有状态（数据库、缓存、队列、本地磁盘）决定了演进的难度。
- **配置和基础设施代码。** 部署单元、环境变量、网络策略往往比文档更真实地反映架构现状。

运行证据同样重要：日志、链路追踪、监控指标能回答"图上画的路径实际走不走、走多频繁"。代码里的死路径和监控里的大流量，都是纸面分析看不到的。

## 分析产出中必须区分的东西

- **事实与推断。** "这个服务每秒约 200 次调用，来自监控"是事实；"这个服务是核心链路，因为调用量大"是推断，可能有别的解释（比如健康检查刷出来的量）。分析报告里两者必须分开陈述。
- **现状与好坏。** 先描述系统是什么样，再评价哪里好哪里坏。跳过描述直接下判断，读者无法核对结论。
- **设计意图与历史包袱。** 一个奇怪的设计可能是深思熟虑（有当时的约束），也可能就是没人敢动。区分两者的办法是找记录（ADR、commit 历史、注释），找不到记录时明确说"原因不可考"，而不是编一个合理的故事。

## 遗留系统的特殊注意

- **不要带着洁癖读遗留系统。** 目标是理解它为什么活到现在，而不是罗列它违反了多少最佳实践。活着的系统必然做对了一些事，先找到那些事。
- **接口即承诺。** 遗留系统最宝贵的资产是它已经稳定的接口。分析时标出"外部依赖这些接口"的清单，这是后续演进（见[演进与迁移](./12-evolution-and-migration.md)）的护栏。
- **数据是最难的约束。** schema 是遗留系统里最难改的部分，数据归属和生命周期决定了拆分和迁移的可行边界（见[数据与状态](./05-data-and-state.md)）。

## 用分析结论校准判断

分析的终点不是笔记，是对后续工作的输入：

- 要接手开发，先确认死穴和反模式，避免在别人摔过的地方再摔。
- 要审查（见各主题文档），用四步笔记作为审查的事实基础，避免凭图审查漏掉真实数据流。
- 要演进（见[演进与迁移](./12-evolution-and-migration.md)），用接口清单和数据归属划定第一步的安全边界。
- 分析 AI 系统时，在质量属性和取舍两栏额外盯三个新约束：成本（每次调用烧 token）、非确定性（同输入未必同输出）、上下文（模型工作内存有限且昂贵）。判断每个部件是在省钱、防出错，还是在管上下文（见 [AI 时代的架构判断](./ai/01-ai-era-judgment.md)）。

# 演进与迁移（Evolution and Migration）

根据演进触发信号和技术债证据规划拆分、迁移、回滚和退役。适用于改造运行中的系统：拆分单体、更换组件、迁移数据、下线旧实现。

## 推倒重写几乎注定失败

每个接手烂摊子的工程师都冒过"推倒重来"的念头，它几乎总是错的，不是旧代码好，而是重写这个动作物理上赢不了：旧系统不会停下来等你，它一边被重写一边还在被改 bug 加需求，目标在移动；那些又脏又怪的代码里沉淀着多年踩坑换来的隐性知识（某个莫名其妙的 if 是绕过某客户的脏数据，某段重试是兜住第三方的抽风），重写一遍血泪清零，同样的坑再踩一遍。

重写最大的成本不是重新写一遍代码，而是重新踩一遍坑，而且期间很难继续交付。Netscape 把浏览器从头重写，近三年没有可用新版本，IE 吃光市场份额。对于持续运行、仍在演进的系统，默认优先渐进改造：新旧并存，旧的块块萎缩，新的块块长出，任何一步能停、能回滚，系统始终在线。系统足够小、尚无真实流量，或完整替换的总成本明确低于渐进迁移时，重写仍可能合理。

## 触发信号：先量再动

升级架构是"被真实信号触发的、有据可查的决策"，不是"定期重构的仪式"。数字是经验启发式（来自常见工程实践的粗略数量级，未经本项目验证）不是铁律，真正的依据永远是某个质量属性被真实瓶颈卡住且量出来了，且归因到具体工作负载（哪类查询、哪条路径），而不是只见 CPU 数字就跳到方案：

| 信号类别 | 可观测信号 | 常见破解 |
| --- | --- | --- |
| 数据层 | 主库 CPU 持续超 70%、读排队；缓存命中率跌破 90%；单表行数过千万到亿、单库容量过几百 GB；写 QPS 接近单库上限 | 先做查询归因（等待事件、慢查询、调用方、读写占比），常见结果是索引缺失、报表扫描或锁竞争；读副本、缓存调优是证据指向读路径后的选项；分片是归因到写容量且其他手段用尽后的最后手段（慎选分片键） |
| 延迟 | P99 持续超标而 P50 还好；用户干等数秒的同步操作；规律性尖峰 | 治尾延迟；异步化削峰；弹性扩缩 |
| 可用性 | 可用性要求上台阶；组件一挂全瘫（SPOF）；一次故障波及面大、恢复慢 | 冗余、故障域隔离、限流降级熔断 |
| 组织效率 | 改一处牵动一片、发布越来越慢；多团队在一个代码库互相阻塞；新人上手要数周 | 先理模块边界（未必要拆服务）；这才是微服务的真正信号，但先看团队边界 |

纪律：先量再判断，没有监控数据就谈升级都是拍脑袋；一次只解一个瓶颈，别一次重构全家桶；每次升级写一条决策记录，背景栏全是信号；没触发就别动，没信号还要升级十有八九是过度设计或跟风。

## 绞杀者模式：在旧系统外围拦截

在旧系统外面加一层门面/路由，逐步把流量引向新实现：路由表里"走新实现"的条目越来越多，旧单体越来越少被命中，直到一条流量都收不到，被绞杀下线。

与 big rewrite 的根本区别：新旧始终并存，流量逐块切换，每块切过去都是一次小而可回滚的发布，而不是攒一个大版本赌命。整个模式的命门是那层门面——所有外部请求必须先经过它，才有资格决定走旧还是走新。没有它，连"把某功能悄悄切到新实现"的开关都没有。绞杀者不追求快，常常要并存维护两套一段时间，但它把一次性赌上整个系统的巨型风险，拆成一次切一小块的可控风险序列。

## 抽象分支：在抽象层之后换实现

当要换的是系统内部被无数地方调用的核心组件（换缓存层、换 ORM、换模型 provider）时，不可能在外面拦一层。新手的本能是开长命特性分支躲进去改两个月——分支活得越久和主干差异越大，最后那次合并是灾难，且期间主干无法发布这部分。

抽象分支反过来：不开长命分支，所有改动在主干上，靠一层抽象让新旧并存。五步：①在要替换的组件前插入抽象接口；②所有调用方改成依赖抽象（行为不变）；③在抽象层背后写出新实现（开关控制，先不放量）；④逐步切开关，出问题随时切回；⑤新实现稳了删旧实现。"开分支慢慢改"是规模化重构最贵的反模式——制造一颗合并核弹，引信时间由别人决定。多写一层抽象的成本，买的是随时能停、能发、能回退的安全感。

AI 系统中的例子：模型 provider 迁移牵动很多调用方时，把调用收进共享 `ModelClient`，在它背后适配新旧实现、路由流量并保留回退开关。这层接缝有明确用途，也有账单：多维护一个接口，还可能把 provider 的专有能力磨成最低公分母。只有一个 provider、一个调用点的小工具，直接调用就行，别为了想象中的搬家先修一条高速公路。出现具体迁移或反复的跨调用需求，再判断共享边界是否划算；AI 网关另算一笔取舍，不随 `ModelClient` 附赠。

## 并行运行：用真实流量当裁判

绞杀者和抽象分支给了切换开关，真正扳下去前，还得拿出相信新实现的依据。单元测试和契约测试守住明确不变量，真实流量补上测试作者没想到的刁钻情况。AI 输出也要分开比：金额、权限和结构化契约该精确就精确，开放式摘要换个说法仍可能同样好，比较的是语义质量。测试通过之后，还要知道用户真正会怎么用。发布判据见[评测驱动架构](./ai/05-evaluation-driven-architecture.md)。

并行运行（影子流量/暗发布）：新旧两套对同一批真实请求同时跑，旧实现的结果返回用户（无感知），新实现的结果背后悄悄比对、记录差异。等不一致率（或质量退化率）降到够低，才真正切流。纪律：旧实现结果永远返回用户；候选实现的异常全部吞掉（绝不让实验代码搞挂线上）；随机打乱执行顺序以暴露顺序依赖。

重构关键路径最大的恐惧是"我以为等价，其实不等价"。并行运行把恐惧变成可量化的数据——用真实流量当裁判，不用自信当裁判。它特别适合逻辑复杂、错了代价极高、说不清有多少边界情况的核心计算（计费、权限、风控）。代价是同时跑两套系统的开销；它是关键路径的重器，不是日常工具。GitHub 重构权限判断时开源的 Scientist 库是活样板（GitHub Engineering 博客，2016-02-03，https://github.blog/2016-02-03-scientist/）；AI 时代它价值不降反升：AI 快速产出新实现，并行运行用数据审判它对不对——速度交给模型，信心交给数据。

## 零停机数据迁移

数据最难改：代码能蓝绿回滚，数据只有一份，改坏救不回。涉及换库、改表结构、拆库时走 expand-contract 五步，每步可回滚：

1. **双写。** 新数据同时写旧存储和新存储，读还走旧的。退路：停掉对新存储的写。
2. **回填。** 存量历史数据批量搬进新存储。退路：只写新库的批处理，随时可停。AI 系统的特殊代价：向量库回填要把历史文档全部重新 embedding，既花钱又花时间，要分批限速、当成本来规划。
3. **影子读校验。** 读请求两边都读，返回用户的仍是旧存储那份，比对新旧是否一致（就是并行运行）。退路：只比对不切流。
4. **切读。** 一致率够高，读切到新存储，此时仍在双写。退路：读切回旧存储，它一直被双写依然新鲜。
5. **清理。** 观察稳定后停掉双写，下线旧存储。唯一不可逆的一步，放最后、留足观察期。

前四步旧存储始终是权威且新鲜的，都能瞬间退回去。数据迁移的灾难几乎都源于一刀切：半夜停服、跑迁移脚本、上线、祈祷。

## 拆单体：先模块化，再按需抽服务

把拆微服务当进步本身是新手最常见的错。正确的战略顺序：

一坨泥单体 → 模块化单体（一个部署单元，内部强制模块边界）→ 只在确有瓶颈时按需抽离微服务。

先在进程内把边界划清（改边界近乎零成本，改错重划就行）；等缝被真实业务捶打稳定了，只为确实需要独立伸缩、独立发布或故障隔离的那块，支付分布式的代价，抽成服务；不需要独立的留在模块化单体里就是好归宿。模块化单体把"边界设计"和"分布式部署"解耦：先拿到微服务最值钱的部分（清晰边界），把最贵的部分（分布式运维）推迟到非付不可。

缝沿业务能力的自然边界找（DDD 限界上下文），不按技术分层拆。判断先抽哪块：哪块最需要独立伸缩、独立发布或故障隔离？服务数量从来不是目标，它是为某个具体质量属性付出的代价。

Segment 的警钟：为故障隔离把系统拆得过碎（一个数据目的地一个 worker，改一次公共库花一周），最后回退到单体。拆过头和盲目拆同样致命。

新旧模型打架时用防腐层：在新服务和旧系统之间架一道翻译隔离墙，新服务只跟翻译干净的接口打交道，旧模型的腐烂渗不进来。

## 防腐化：适应度函数

费力划好的边界，别在后续几百次提交里又揉回一坨泥。把重要且能可靠验证的约束写成会失败、能卡 CI 的测试：订单模块不准 import 计费内部，指定负载下 p99 超标就 fail，API 契约被破坏就 fail。如果项目已因迁移等实际需要采用共享模型边界，也可用依赖检查阻止绕过。先有值得守的边界，再让测试守住；别为了凑一条检查，反过来硬造抽象。

架构不是画完图就定型的雕像，是要持续维护的活系统，活的东西没有免疫系统必然腐化。适应度函数就是架构的免疫系统：不阻止系统长大，只阻止它在长大的过程中烂掉。没有它，今天辛苦划清的每道边界，都只是在等一个赶时间的下午被人捅穿。

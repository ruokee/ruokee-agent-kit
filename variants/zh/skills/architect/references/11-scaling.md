# 规模化（Scaling）

根据负载证据识别瓶颈并选择扩展方式。适用于容量规划、过载分析与修复、扩展性设计评审。

## 加机器不是一个均匀的动作

"扛不住就加机器"有两条路：垂直扩展（换更猛的单机）简单、代码不用改，但有物理天花板、单点和不划算的溢价；水平扩展（一堆普通机器）容量上限高得多，但代价是从管一台变成管一群，且并非无限：共享瓶颈、协调开销、分片数量上限都会设限，增加节点本身也不等于已经具备冗余和正确的故障处理。垂直扩展是在买时间：系统还小时升一台机器永远比改架构便宜，别急着上分布式。

关键分水岭是无状态好扩、有状态难扩。无状态层（Web/API）加 10 台是配置改一行；有状态层（数据库/缓存）加 1 台可能意味着重新分片、搬迁 TB 级数据、几周的迁移窗口。规模化的第一步永远是先把状态从计算里挤出去，让瓶颈几乎总是落在这种挤压后残余的有状态部分。当有人说"加机器就行"，先问：加的是哪一层？

## 分片策略

两大流派：范围分片按 key 区间切，范围查询高效（时序、按时间翻页），但易热点（按时间分片时今天的数据全压一片）；哈希分片按 hash(key) 切，分布均匀天然防热点，但范围查询废了（相邻 key 散到各片）。选择取决于查询形态，不是哪个更好。

朴素哈希 `hash(key) % N` 的致命缺陷是把节点数写进公式：加一台机器 N 变了，几乎每个 key 的归属都变（从 N 变 N+1 时平均要搬迁约 N/(N+1) 的数据，例如 4 变 5 时约 80%），集群被再平衡流量打瘫。

**一致性哈希**解决它：把哈希空间想象成一个钟面，节点和数据都哈希到钟面上，key 顺时针找到的第一台机器负责它。新加一台等于插一个新钟点，只有新钟点到前一钟点之间那一小段数据需要换东家。加/减一个节点平均只搬 1/N 的数据，从"全集群地震"变成"局部微调"，是大规模分布式存储平滑扩容的地基。

朴素一致性哈希还有节点分布不均的问题（某节点挂了负载全压给顺时针邻居）。解法是**虚拟节点**：每个物理节点在环上放几百个分身，大数定律抹平随机性，一台挂了负载被打散分给所有其他节点，异构机器也能按强弱配分身数量。选了哈希且要弹性扩容，一致性哈希加虚拟节点几乎是标配。

## 热点

分片的前提是负载均匀，现实负载遵循幂律：少数 key 占绝大多数流量。热点的可怕在于**分片本来是来救你的，热点让分片失效**——加再多机器，流量还是全压在持有那个热 key 的那一台上（顶流发帖、秒杀单件商品、突发新闻）。

识别靠监控按 key 维度的流量分布，不是只看总量。打散的核心思路只有一个，把一个点变成一片：

| 手段 | 做法 | 适合 |
| --- | --- | --- |
| 加盐 | 热 key 拆成 `key#1`…`key#N` 散到多片，读时聚合 | 写热点（计数器） |
| 本地缓存 | 应用进程内存缓一份，大部分读不出本机 | 读热点（配置、热门内容） |
| 只读副本 | 给热点数据多几个副本分摊读 | 读多写少的热点 |
| 请求合并 | 同一瞬间的 N 个请求只放一个查后端，其余等结果 | 读击穿 |

Twitter 的写时扇出（发推推进所有粉丝的缓存）碰上千万粉丝的顶流就是灾难（一条推等于几千万次写入）。解法是混合策略：普通用户走写扇出，少数大 V 走读时拉取。对热点，把写时打散到千万处换成读时从一处拉取。

## 多级缓存与踩踏

真实的大规模系统是 CDN → 边缘 → 应用本地 → 分布式缓存 → DB 的多级结构，每层挡掉一批流量。层级越多 DB 越轻松，但每多一层副本，一致性就多一道难题（改了 DB，五层怎么一致地失效）。

最凶险的是**缓存踩踏**：超热 key 过期的瞬间，一万个并发请求同时发现"没了"，一起涌向 DB 重建同一个值，DB 瞬间被同一查询打一万次。它比缓存宕机更隐蔽——不是缓存坏了，是缓存正常过期这件事在高并发下成了同步的洪峰。三道防线：

1. **请求合并（single-flight）。** 同一 key 的并发重建只放第一个去查 DB，其余订阅它的结果。一万次查询塌缩成一次（Discord 工程博客《How Discord Stores Trillions of Messages》，2023-03-06，https://discord.com/blog/how-discord-stores-trillions-of-messages）。
2. **过期时间加随机抖动。** 别让一批 key 同一秒集体过期。
3. **逻辑过期/提前异步刷新。** key 不真删，后台快过期时悄悄刷，读端永远命中。

好的缓存设计，一半是命中率，另一半是失效时别让所有人同时扑向 DB。

## 尾延迟与扇出放大

平均延迟把少数极慢稀释没了，而那 1% 恰恰是最该在意的体验。延迟是分布不是数字，对外承诺和内部 SLO 都用 p99/p999。

真正的杀手是**扇出放大**：一个用户请求扇出成几十上百个子调用，要等最慢的回来整个请求才算完成。像一桌 100 个人点的菜，等最后一道上齐才能开饭。单个子调用 p99 慢的概率只有 1%，但 100 个子调用全部快的概率是 (99%)^100 ≈ 36.6%——63% 的概率整个请求撞上至少一个慢子调用。**在大扇出系统里，整体的 p99 趋近于子调用的 p999 甚至 p9999。** "子组件偶尔慢一下无所谓"这个直觉在扇出面前是错的。

对冲请求（hedged requests）治尾延迟：同一请求发两个副本，谁先回用谁。全发两份负载翻倍，聪明做法是延迟对冲——先发给副本 A，A 在 p95 时间内没回才补发 B。只对最慢的 5% 请求发第二份，额外负载约 5%，砍掉一大截长尾。

## 排队：为什么逼近满载会爆炸

系统在 70% 利用率一切正常，加一点流量到 95%，延迟突然飙升十倍。因为请求到达是随机的（有波峰波谷），高利用率下系统没有余量消化突发：波峰一来请求排队，队列又拖慢后面的，正反馈。排队论给出直觉（以 M/M/1 这类简化模型为前提，真实系统会有偏离，但趋势方向成立）：平均排队时间与 1/(1−ρ) 成正比——ρ=50% 时因子 2，90% 时因子 10，99% 时因子 100，曲线在逼近 100% 处近乎垂直拉起。

**留余量是设计不是浪费。** 闲着 30% 的服务器买的是应对突发的能力和可控的尾延迟；压满利用率省的机器钱，会在第一波尖峰里以雪崩形式十倍奉还。开售即洪峰的系统必须按峰值而非均值预留容量。

Little 定律（队列请求数 = 到达率 × 平均停留时间）用于从并发/吞吐反推延迟或估容量。加机器提容量还有最后一盆冷水：机器之间对齐状态、互相协调的开销随规模增长（USL），收益递减甚至变负——像往一个厨房塞厨师，塞到某个点大家开始抢灶台，再多反而更慢。无状态、少协调的设计能近线性扩展，重协调强一致的设计加到一定规模就撞墙。架构师的活是尽量减少需要协调的部分：让加进来的机器尽量不需要互相说话。

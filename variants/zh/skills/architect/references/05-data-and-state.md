# 数据与状态（Data and State）

状态归属、数据生命周期和存储边界。适用于任何涉及"数据放哪、怎么一致、怎么扩"的架构判断，这是系统设计中最难也最值得早想清楚的部分。

## 状态是难点，也是价值

把系统里的东西分两种：

- **无状态。** 不记得任何事，输入进、输出出、算完就忘。想扩容直接复制实例，流量随便分。
- **有状态。** 记得事情且随时间变化：余额、购物车、在线状态。想复制就要回答两份记忆怎么保持一致，这是一切麻烦的根源。

由此有一条反复出现的架构动作：把状态从计算里挤出去，集中放进少数专门管理状态的地方（数据库、缓存），其余组件保持无状态、可以随便复制。系统的大部分轻松水平扩展，难搞的状态收拢到可控的几处专门伺候。

状态同时是产品的全部价值所在：用户数据、订单、关系、记忆。架构师的工作不是消灭状态（消灭不了），而是把它管理得明明白白：放哪、多强的一致、怎么扩、故障时怎么不丢不乱。

## 为访问形态选存储

"我会用某个数据库就拿它装一切"是常见误区。正确思路是先看数据长什么样、怎么被访问：

|存储类型|适合的访问形态|
|-|-|
|关系型|结构清晰、关系复杂、需要事务和强一致的核心数据（用户、订单、账户）|
|文档型|结构灵活、自包含、按 ID 整取整存（文章、配置、会话记录）|
|键值|极简按 key 取 value、要求极快（会话、计数、缓存）|
|列存|海量数据上的分析聚合（报表、统计）|
|图|重点是关系网络本身（社交、风控关联、知识图谱）|
|向量|按语义相似度检索（embedding、RAG、推荐）|
|对象存储|大块、不可变、按 ID 整取（图片、视频、模型权重、备份）|
|搜索引擎|全文检索和复杂条件过滤排序（商品搜索、日志检索）|
|时序|带时间戳、只追加、按时间聚合（监控指标、计费流水）|

多存储（polyglot persistence）是被证据逼出来的代价，不是成熟度勋章：每多一种存储，就多一份同步链路、一致性边界和运维对象。默认从一种关系库起步，只在某类数据的访问形态明显偏离主库擅长方向、且被真实负载证据证实过不去时，才为它引入专门存储。判断时问三个问题：这份数据的读写形态是什么；需要多强的一致性；会长到多大、访问多频繁（决定要不要考虑复制和分片）。选型细节见[数据存储](./technology-selection/03-data-stores.md)。

## 一致性谱系

"强一致"是含义宽泛的总称，不是精确术语：讨论具体方案时要写清到底是线性一致（所有操作看起来按某个全局顺序即时生效）、可串行化（事务并发结果等价于某个串行执行顺序）、严格可串行化（在可串行化之上还要求尊重真实时间先后）、read-your-writes（自己写的自己立刻读到），还是最终一致（经过不一致窗口后对上）。日常口语说"强一致"可以，落到方案和验收标准时必须指名具体模型，见[一致性](./09-consistency.md)。

CAP 用大白话讲：网络故障把系统切成联系不上的两半时（分区迟早发生，不是你能选的），只能在两件事里二选一——继续服务但可能给不一致的数据（选 A），或为不出错而拒绝服务（选 C）。

哪些数据要更强的保证，是业务判断不是技术判断，标准只有一个：**短暂不一致会破坏什么业务不变量？**

- 先写不变量，再选方案：账户余额的不变量是"任何时刻余额不为负且流水守恒"，守住它的手段可以是事务、条件更新（扣减带 WHERE balance >= x）、可串行化隔离或事后对账，不必预设某个一致性术语；库存的不变量是"不超卖"，唯一性约束本身就是不变量。
- 可以最终一致：点赞数、浏览量（差几秒没人在意）、社交动态流（粉丝晚几秒刷到可接受）、通知和已读状态。

强一致很贵，配额花在真正会出事的地方。把点赞数也做成全网强一致的系统，是在为不需要的严谨支付高昂的性能和可用性代价。一致性模型的系统展开见[一致性](./09-consistency.md)。

## 事务与设计取向：ACID、BASE、CAP 各管一段

几件事必须要么全成要么全不成时，需要事务。转账 A 减 100 和 B 加 100 绝不能只成一半。ACID（原子性、一致性、隔离性、持久性）描述单个事务的执行与恢复保证；BASE（基本可用、软状态、最终一致）是一组偏爱可用性与扩展的设计取向；CAP 描述网络分区时分布式服务在一致性与可用性之间的可观察保证。三者处在不同层级，不能互相映射：不存在"ACID 偏 CP、BASE 偏 AP"这种换算，一个单机 ACID 数据库根本不涉及 CAP 的取舍，一个分布式系统也可以在部分操作上给 ACID 事务、在另一些操作上给最终一致。它们可以组合使用：核心交易走本地 ACID 事务，统计、通知、流式数据走最终一致，跨服务的组合用[一致性](./09-consistency.md)的 Saga 与 Outbox 拼起来。

## 扩展数据的三张牌

|手段|解决什么|代价|
|-|-|-|
|复制（主从）|扩读；顺带冗余容错|主从同步延迟（读到旧值）；写没被扩展；主库是写的单点，故障切换复杂|
|分片|扩写、扩存储容量|跨分片事务和 join 基本告别；分片键选错造成热点分片；再分片要搬海量数据|
|缓存|降读延迟、减数据库读压|一致性问题；新组件要维护；冷启动时流量全打数据库|

一句话区分：**复制扩读、分片扩写、缓存降延迟并扩读**。别指望加从库解决写瓶颈，那得靠分片。

分片要尽量晚做、想清楚再做。分片键几乎是一旦定下就很难反悔的决策：按地区分片但八成用户在一个地区，就会一台被打爆其余闲着；想加机器改规则，要搬迁海量已铺好的数据。

## 缓存的三个坑

缓存用一致性换速度，三个坑几乎人人踩：

1. **失效与一致性。** 数据库改了缓存还是旧的。常见做法是更新库后删缓存让下次重新加载，但高并发下两步之间的时序有各种微妙的不一致。没有完美解，只有取舍：用了缓存就主动接受了某种程度的不一致，要做的是把窗口控制在业务能接受的范围内（比如合理的 TTL）。
2. **穿透、击穿、雪崩。** 缓存的使命是替数据库挡流量，这道墙漏的瞬间洪水直冲数据库。穿透（大量请求查不存在的数据，常被恶意利用）用空值缓存或布隆过滤器挡；击穿（热点 key 恰好过期，海量请求同时涌向数据库）用重建加锁只放一个请求去查库；雪崩（大量 key 同时过期或缓存整体宕机）用过期时间加随机抖动、缓存本身做高可用。
3. **副本的本质。** 前两个难题最终指向同一件事：缓存是数据的第二份副本，只要有副本就有两份对不上的风险。与主从延迟、分片不一致本质同类——**为了性能和扩展复制数据，一致性就成了必须管理的成本。天下没有免费的扩展。**

## 数据模型是最难改的决策

逻辑好改，数据难改。逻辑代码无状态：写错了改几行重新部署，旧代码消失得干干净净。数据有状态有惯性：数据模型（实体划分、关系、分片键、一致性级别）一旦定下，海量真实数据按它的样子躺着且每天增长。改它意味着设计新旧共存的兼容方案、写迁移脚本搬海量数据、期间不能停服务、出错要能回滚但数据可能已被改了一半。以周甚至月计，工程界公认的高危操作。

由此得出的优先级：**该懒的地方懒，逻辑可以先糙后精；该较真的地方必须较真，数据模型要尽早想透。** 在需求、约束、质量属性的推导里，数据怎么建模、放哪、多强一致、怎么扩，应该是最早最认真思考的部分。不是预支未来，而是改起来代价百倍于代码的决策值得多花时间在白板上。

## 数据生命周期

除了"放哪"，还要回答数据的一生：怎么产生、被谁读写、保留多久、怎么归档和删除。合规（GDPR 的删除权）和成本（无限增长的对象存储账单）都挂在这条时间线上。AI 系统里数据生命周期多了两环：训练数据要版本化（否则没法复现），评测集要随业务演进（否则评的是过时目标），见[评测驱动](./ai/05-evaluation-driven-architecture.md)。

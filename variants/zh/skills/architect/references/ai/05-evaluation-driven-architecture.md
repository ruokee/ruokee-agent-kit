# 评测驱动架构（Evaluation-Driven Architecture）

非确定性输出无法逐字断言，只能衡量质量分布：eval 集打分 + 统计门禁防退化。适用于含 LLM 的系统中"够好"的量化与守门。

## 逐字断言不足以覆盖非确定性输出

传统断言建立在确定性上：`assert summarize(x) == "预期的那一句"`，二元对错能精确断言。LLM 抽走了这块地基：温度、模型版本、上下文一变，两次输出字面就不同，两次都算对，`assert ==` 必然误报。注意这不是说传统测试作废：系统里确定性部分（退款幂等、状态机、鉴权）有唯一正确答案，照样用 assert 测试；eval 只管非确定性输出的质量分布。

更糟的是**退化无声**：把模型从旧版升到新版、或改了句系统提示，某类问题的答案悄悄变差了——没有任何测试会红，只能等用户投诉。从"断言单条正确"转向"衡量一个质量分布"：不再问这一条对不对，问这一批代表性输入整体质量分是否够好、有没有比上一版退。

## eval 三件套

**eval 集**：一批代表性输入 + 每条的期望要点。注意是要点/判据，不是逐字的标准答案。例：用户问"上周买的鞋开胶了能退吗"，期望要点是引用了质保政策、给出明确的能/否、没编造不存在的政策、口吻得体——评要点中了几条，不逐字比对。

**评分**：谁来判够不够好。

|方式|适合|代价|
|-|-|-|
|规则/程序判定|有客观判据（含不含关键词、格式、有没有引用）|便宜稳定，只能判硬标准|
|LLM-as-judge|主观质量（答得好不好、相不相关）|灵活，但裁判本身也非确定、也会错、也烧 token|
|人工抽样|校准前两者、兜底高价值场景|适合定义标准和校准，但受标注者一致性、领域能力和成本限制|

实务：规则能判的先用规则，主观的用 LLM-as-judge，定期人工抽样校准裁判——别盲信模型裁判，它也是个会出错的模型（比如偏好长答案）。

**门禁**：光跑 eval 不够，接进 CI。换模型、改提示、改检索策略前，CI 自动跑 eval 并按下述统计条件判定，防的就是悄悄退化。"总分低于基线一律拦截"过于粗糙：一个总分可掩盖高风险类别的退化，一次随机跑分偏低也可能只是噪声。至少定义：

- 固定模型/提示/数据版本与解码参数，只让被测变更成为变量；
- 高风险类别（碰钱、安全、关键业务）设硬门槛，不看总分；
- 总体指标设容忍带而非单线；
- 对含随机组件的环节（采样温度、LLM 裁判）重复运行取均值或成对比较；
- 报告效应量和置信区间，区分真实退化与运行方差；
- LLM 裁判用人工标注集校准并监测偏差（如偏好长答案）。

## 从小步、从真实失败攒起

新手一听评测集就想攒几千条，然后永远没开始。正确姿势：

1. **种子来自线上真实 bad case。** 每一条用户投诉、每一个答错的截图都是最值钱的样本——它们是真实失败，不是想象的失败。先攒十几二十条就能跑起来。
2. **离线 + 在线两条腿。** 离线 eval：固定数据集进 CI，把关上线前。在线 eval：对真实流量抽样打分或影子运行打分，把关上线后——真实分布永远比数据集刁钻。
3. **持续加 case。** 每次发现新的失败模式就固化成一条 eval，和写回归测试一个道理。eval 集是活的，随系统长大。

别等完美的评测集，先用粗糙的把循环跑起来。

## eval 不替代传统测试，是新增一层

AI 系统里确定性的部分照样用传统测试：退款幂等、状态机、鉴权、API 契约，有唯一正确答案，`assert ==` 照样有效。eval 只管非确定性输出的质量分布。两套并存各管一段。

把不确定性挡在副作用之外的设计在这里又兑现了一次：确定的部分还能用确定的方法测。

## eval 的成本与陷阱

把 eval 当架构组件，就要像对待任何组件一样看代价：

- **烧钱耗时。** 每条样本真实调用模型，LLM-as-judge 每评一次又多一次调用。eval 集越大跑得越勤成本越高，要在覆盖度和成本之间权衡。
- **裁判会错。** LLM-as-judge 非确定、有偏见，要人工抽样校准，别把它的分当圣旨。
- **过拟合与老化。** 盯着固定 eval 集调久了会为考高分而优化，对集外样本未必好；业务变了旧 eval 集会过时。持续更新，过时的 eval 比没有更糟。

eval 是 AI 系统的质量适应度函数：它之于答案质量，正如适应度函数之于架构边界——把你在乎的东西变成一道会失败、能卡 CI 的自动检查。区别只是架构边界能精确断言，答案质量只能看分布。把够好写进 eval、接进门禁，才敢放心升级模型迭代提示——否则每次升级都是闭着眼睛赌它没变差。

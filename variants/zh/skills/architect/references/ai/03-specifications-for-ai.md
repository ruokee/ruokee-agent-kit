# 面向 AI 的规格（Specifications for AI）

把架构约束落成持久形式，并交给运行时或调用方加载；能自动验证的，再下沉为检查或门禁。适用于 AI 协作开发（vibe coding、agent 编码）中守住架构边界：决策记录、AGENTS.md 类规则文件、适应度函数的分层落位。

## 别让架构约束靠聊天续命

代码可以交给 AI 产出，规格、约束和验收标准仍要有人说清楚。聊天时说一句"退款记得加幂等"，这轮上下文里有，压缩后还在不在？换个会话、换个同事，谁知道这句话说过？需要跨越这些过程的约束，应写进项目维护的记录，再通过运行时支持的机制加载，或由调用方显式注入。约束得有个比聊天窗口更长寿的住址。

例如，退款请求要携带幂等键，重复请求返回原结果，执行前还要验证授权。把这些写清楚，再拿实现和测试逐项核对。AI 可能推断出你没写的要求，也可能漏掉你强调过的要求，不能拿默契当验收。能精确测试的不变量落实为检查，具体怎么查见[审查 AI 产出](./04-reviewing-ai-output.md)。

## 规格金字塔

约束按可执行程度分三层，越往下越硬、越绕不过：

| 层级 | 载体 | 约束什么 | 给谁看 |
| --- | --- | --- | --- |
| 决策记录 | 使用项目现有格式的文档 | 为什么这么定、取舍 | 人 + AI（理解意图） |
| AGENTS.md 类规则文件 | 项目根的常驻规则 | 做什么 / 不做什么 | AI（运行时支持并配置后自动加载，否则由调用方显式注入） |
| 适应度函数 / lint / CI | 自动化测试 | 红线（违反即拦） | 机器 |

三层各管一段：为什么当年选择双写、准备拿什么换什么，留在决策记录；退款必须幂等这类反复适用的指令，写进规则文件；领域层不准 import web 层，交给依赖检查。小工具未必需要三层齐全，别把维护文档本身变成最大的工程。重要、反复执行且维护成本合理的检查，尽量让机器接手。文档解释为什么，自动检查在违规时亮红灯，两者各有用处。

## 怎么写好规则文件

`AGENTS.md` / `CLAUDE.md` 放项目根，运行时支持并配置该机制时每次对话自动加载，是 AI 的长期记忆。多数人写成正确的废话：

```
- 写高质量、可维护、可扩展的代码
- 遵循最佳实践
- 注意性能和安全
```

AI 看到这些什么也做不了——高质量到底多高？最佳实践是谁的？有用的写法要具体、可执行、带为什么、有反例：

```
## 数据与一致性
- 凡是动钱的接口（扣款、退款）一律携带幂等键；同一请求再来一次，
  返回上次的处理结果，绝不二次执行。背景见 ADR-003。
- ❌ 不许把支付 API 直接交给模型调用；模型的产出止步于退款提议，
  真正动手的是确定性的退款服务。

## 韧性
- 所有外部调用（模型 API / 第三方）必须设超时；只对可恢复错误，
  在幂等、时间预算和重试预算内退避重试。
  理由：依赖一定会抽风；但永久错误、认证失败、配额耗尽和
  不可幂等的副作用调用不应自动重试。

## 边界
- 领域层禁止 import web 层 / 框架。违者 CI 会 fail。
```

五条纪律：

1. **具体到可执行。** 不说"注意安全"，说所有外部输入入库前必须校验、用户内容当不可信输入（含提示注入）。
2. **带上为什么。** 像 ADR 一样给理由——AI 和人知道理由，才不会在规则显得多余时把它删掉。
3. **给反例。** 容易误用的规则配一个具体错法。例如，只说"退款要安全"不够，把"模型直接调用支付 API，绕过授权检查"写出来，边界才看得见。反例要说明会坏在哪里。
4. **短而狠。** 规则文件是常驻上下文成本，按 token 计费。写最高频、最容易被违反的那几条，别写成小说。
5. **随代码演进。** 过时的规则比没有更糟（它主动误导 AI），规则变了就改。

设计时选了 A、放弃 B，先把取舍留在决策记录；其中需要反复执行的约束，再提炼进规则文件并链接依据。AGENTS.md 写清 AI 动手时要守的边界，详细论证留在主要文档。别把整本决策史塞进常驻上下文，每次问个小问题都要带着它按 token 付费，多份副本还会各自长出一套说法。

## 能机器强制的，就别只写文档

金字塔最底层最硬。约束的归宿按能不能被机器验证分流：

| 约束 | 落成什么 |
| --- | --- |
| 领域层与框架解耦 | CI 依赖检查不过即拦截 |
| 退款接口要求幂等 | 规则写进规则文件，契约测试缺幂等键即失败 |
| 项目已采用共享模型调用边界 | 依赖检查拒绝绕过既定边界的调用 |
| p99 上限 200ms | 性能测试超标即失败 |
| 为什么用 RAG 不用微调 | 决策记录（只能人读，无法机器验证） |

把靠人提醒的约束变成会亮红灯的检查。CI 不在乎代码是人写的还是 AI 写的，覆盖到的违规一视同仁地拦。但一片绿灯只说明已写的检查通过了，漏写的检查不会自己举手。审查仍要追踪未覆盖的行为，并核对检查的前提是否成立。

## 规格即架构

把约束写清楚、放到 AI 读得到的地方，是架构工作的一部分。"退款要安全"留下了太多空白，"先校验授权，同一幂等键只执行一次"才给实现和验收提供了共同依据。含糊处会留下选择，让模型默默填空，就可能把尚未作出的业务决定藏进代码。把这些选择找出来，由负责人判断，再用检查守住可验证的部分。

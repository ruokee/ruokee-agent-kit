# 分布式系统（Distributed Systems）

网络、时间、并发和部分失败给设计带来的硬约束。适用于任何跨机器、跨服务、跨进程协作的架构判断——这些约束决定了哪些方案根本行不通。

## 单机的三个奢侈

写单机程序时习以为常的三件事，跨过两台机器全没了：

|单机世界|分布式世界|
|-|-|
|函数调用必达|网络不可靠：丢包、乱序、重复、延迟、分区|
|全世界一个"现在"|没有全局时钟：每台机器的表都不一样，"同时"是幻觉|
|要么成功要么失败|部分失败：有的节点成了、有的败了、有的不知道死活|

部分失败最致命。你给另一台机器发请求，等两秒没回音：它没收到？在算？算完回包丢了？还是整台宕了？**你无法区分它死了和它只是慢**（灰色失败）。唯一的武器是超时，而超时本质是猜测：猜短了把只是慢的节点误判为死、重试雪上加霜；猜长了故障恢复迟钝。分布式系统的可靠性设计，很大程度上就是在跟"分不清死与慢"搏斗。

思维翻转：单机时代默认调用会成功；分布式时代默认每次跨网络调用都可能失败、超时、重复送达，然后问"这种情况下我的系统会怎样"。这是入门和进阶的分水岭。

## 一致性是光谱，每档都有价目表

强一致到最终一致之间有中间档，每往强升一级都在支付延迟和可用性：

|档位|保证|适用|
|-|-|-|
|线性一致|任何人在任何节点读，立刻读到最新值，像只有一台机器|ATM 余额、唯一性分配|
|顺序一致|大家看到的顺序一致，但可能不实时|配置下发|
|因果一致|有因果关系的操作顺序不乱，无关并发不强行排序|群聊消息、评论|
|最终一致|迟早一致，中间窗口各看各的|点赞数、浏览量|

因果一致是很实用的中间档：你回复了我的消息，这类有因果的操作对所有人顺序一致；两个陌生人各发各的，谁先谁后无所谓。它比线性一致便宜得多，又避免了"先看到回复、后看到原帖"的荒谬。

判断不是尽量强，而是先问这份数据配得上多强。把宝贵的强一致配额花在真正会出事的地方。

## PACELC：你天天在付的账

CAP 说网络分区时只能选 C 或 A。但 PACELC 补全了漏掉的一半：绝大多数时候网络是好的，这时你在付什么账？

- 分区时（PAC）：要正确（C）还是要在线（A）。
- 不分区时（ELC，99% 的时间）：要低延迟（L）还是要强一致（C）。

就算网络一切正常，强一致依然要钱：让所有副本同意一个值，得等节点间往返协调。一致性不是出事才付的意外险，而是天天在付的水电费——每一次决定要不要等所有副本确认，都是在拿延迟换一致性。

## 没有全局时钟，就用因果

每台机器的物理时钟有偏差，网络延迟不确定，靠对比两块表的读数判断谁先谁后不可靠（表本身对不齐）。办法是放弃物理时间，改用因果关系：不问几点几分，只问这件事是不是因为那件事才发生的。

逻辑时钟让每条消息携带发送方计数，收到的人把自己的计数调到更大，因果顺序就被钉死。Lamport 时钟给所有事件排出全序但分不清真回复和恰好并发；向量时钟能识别并发写冲突（两人同时编辑同一行，系统知道撞车了，让人决定留谁）；混合逻辑时钟（HLC）把物理时间和逻辑计数缝在一起，现代分布式数据库做一致性快照常用它。

多数业务系统用不上逻辑时钟，别为显得高级而引入。但系统要保证因果正确时它绕不开：实时协同文档的合并顺序、即时通讯的消息时序、分布式数据库的一致性快照。

## 共识最贵，别滥用

一组机器对某件事达成铁板一块的一致（谁是主库、日志第 100 条是什么、锁归谁），靠共识协议（Raft/Paxos）。它买到的东西很硬核：部分节点宕机时，存活多数派仍能达成唯一决定，是分布式世界里单一权威真相的来源。

代价同样直白：每个决定都要走一轮多数派投票，一来一回是延迟；至少三五个节点；写吞吐受限于单一 leader；成员变更微妙易出错。共识像董事会表决，适合重要决定，不适合日常群聊。

只用在必须有唯一权威顺序的少数地方：选主、集群元数据、分布式锁、复制日志。把每条业务写入都塞进共识组的系统，是在为不需要的全局唯一顺序支付高昂代价。反模式是把 Raft 集群当通用数据库使。

## 端到端 exactly-once 不能只靠消息传输

对任意外部副作用的端到端恰好一次，消息传输层保证不了：发出消息没收到 ack，只有两种选择：重发（至少一次，可能重复）或不重发（至多一次，可能丢失）。这不是某个产品的缺陷，是物理限制。

限定条件下传输层可以有恰好一次语义：如 Kafka 在 consume-process-produce 边界内，用幂等生产者、事务、原子提交 offset 和 read_committed 消费隔离，提供流处理语义上的 exactly-once（Kafka 官方设计文档，https://kafka.apache.org/43/design/design/）。但这只覆盖它管得到的边界——一旦消息的消费要写外部数据库、调第三方 API，那些副作用仍可能重复或丢失。

跨外部副作用的真正解法是换个地方解决：**at-least-once 投递 + 消费端幂等 = 业务效果上的恰好一次。** 幂等的实现通常是给操作一个幂等键，消费端用去重表记下处理过的键，重复到来直接跳过。别指望传输层的 exactly-once 语义覆盖外部副作用，把正确性下沉到消费端。

## 案例：43 秒分区乱了 GitHub 24 小时

2018 年 GitHub 更换光纤导致美东数据中心与网络枢纽断联 43 秒（GitHub Engineering 博客《October 21 post-incident analysis》，2018-10-30，https://github.blog/2018-10-30-oct21-post-incident-analysis/）。断联期间美东继续接收写入（它没死，只是失联——灰色失败）；基于 Raft 的编排器按多数派共识自动把主库切到美西；网络恢复后两岸各持有对方没有的数据，成了两个都自认为是主的分叉集群，自动调和有丢数据风险，只能人工修复，服务降级 24 小时。

教训：部分失败让你分不清死与慢；共识能在多数派间达成一致，却可能在分区时完全按规则把系统切进灾难性拓扑。自动化越强，越要想清楚它在极端情况下会做出什么决定。事后 GitHub 禁止编排器跨区域提升主库——一个为单节点故障设计的自动切换，在整个区域分区面前做出了应用层扛不住的决定。

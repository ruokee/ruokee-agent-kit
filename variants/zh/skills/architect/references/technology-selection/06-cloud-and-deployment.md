# 云与部署（Cloud and Deployment）

部署平台选的是运维模型：省心还是控制权、团队能否养住。适用于 PaaS/容器/Serverless/K8s 的选择判断、部署策略设计、演进路径规划。

## 你选的不是机器，是运维模型

新人问"用虚拟机还是容器、Serverless 还是 K8s、自建还是上云"。架构师先问：谁负责发布？谁负责扩容？谁负责告警？新版本坏了谁能回滚？证书、密钥、配置、日志、指标、权限谁管？出事时团队看不看得懂平台？

部署平台不是一台机器或一个控制台，是**从代码变成线上服务的整条路径**：构建、配置、密钥、发布、健康检查、流量切换、自动扩缩、日志指标、故障回滚。

平台越省心，通常越少控制权、越可能厂商绑定；平台越可控，通常越吃团队运维能力。没有高级低级，只有这笔复杂度现在值不值。

## 四个台阶是复杂度价格表，不是成熟度排名

PaaS/托管应用平台最省心，适合 MVP、小团队、标准 Web 应用。托管容器平台仍省心，但有容器和服务边界。Serverless 适合事件驱动、突发流量、后台任务。K8s 控制力最强，也最吃平台能力。

不要把这四层理解成越往后越高级。三人团队用 PaaS 稳稳上线，比自建 K8s 天天修集群更健康；反过来，几十个服务、多个团队、复杂流量治理，继续塞进简单平台也会变瓶颈。选部署平台像选交通工具：去楼下买菜自行车最好，跨城搬家卡车最好，问题不在卡车是不是更先进，在你是不是正在搬家。

## K8s 什么时候值得上

K8s 解决的不是单个容器怎么运行，是怎么管理一群不断变化的容器：调度、扩缩、服务发现、滚动发布、自愈、资源隔离、声明式配置。

值得上的信号：服务数量多（需要统一调度、发布、资源治理）；多团队独立部署（不能互相排队发版）；复杂流量治理成常态（灰度、金丝雀、蓝绿、区域路由）；需要混合云/私有化（跨环境保持部署模型一致）；有平台团队（有人把 K8s 封装成内部开发者平台，而不是让所有业务团队啃配置）。

如果只是一个标准 Web 应用 + 一个数据库 + 一个队列，K8s 多半不是收益而是负担：提前买下证书、Ingress、网络策略、镜像仓库、集群升级、权限控制、节点资源、可观测性一整套复杂度。

## Serverless 的限制

价值：按需扩缩，低流量时成本低；适合事件触发（上传文件后转码、定时任务、Webhook 处理）；团队少管机器。

代价：冷启动（长时间不用后首次请求慢）；运行时限制（执行时间、内存、网络、依赖包大小）；可观测性和本地调试更难；厂商绑定更强。

适合短、散、事件驱动的任务。把复杂长流程硬拆成几十个函数，没有工作流编排、trace 和重试纪律，会变成另一种难维护。

## 部署策略本身就是架构

评估平台不能只看能不能跑，要看坏版本上线时怎么收场：健康检查（平台怎么知道实例真的能接流量）、回滚（新版本坏了能不能快速回到旧版本）、渐进发布（能不能灰度/金丝雀/蓝绿切流量）、配置与密钥（是否和代码分离、可审计）、基础设施即代码（线上资源可版本化、可审查、可重建）。

GitOps 把线上目标状态从人工点控制台变成版本化、可审查、可回滚的声明。一个不能快速回滚、不能定位版本、不能解释配置来源的平台，会把每次上线都变成赌博。

## 最稳的演进路径

| 阶段 | 形态 |
| --- | --- |
| MVP/单体 | 托管应用平台 + 托管数据库 + 简单 CI/CD |
| 多服务 | 容器化 + 托管容器平台 + 标准日志/指标/密钥 |
| 多团队 | 托管 K8s + 平台团队 + GitOps + 服务目录 + 权限治理 |
| 强监管/私有化/混合云 | K8s 或私有云平台，接受更高运维成本 |

先让业务跑起来，再把反复出现的运维复杂度收敛成平台能力，按真实痛点决定复杂度投入。

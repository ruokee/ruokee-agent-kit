# API 与通信（API and Communication）

服务间通信的边界判断：同步/异步/流式、内部/外部、契约强度，然后才是 REST/gRPC/GraphQL/Webhook 的选择。适用于设计服务边界、对外 API、第三方集成。

## 通信方式决定耦合方式

同样是"订单通知库存扣减"，可以同步调 REST、同步调 gRPC、发布事件异步消费、GraphQL 按需查询、Webhook 回调。每种都能工作，但耦合方式完全不同：同步调用结果清楚，但调用方可能被对端拖慢或拖死；异步事件解耦，但结果不立即可知，一致性更复杂；GraphQL 客户端灵活，但服务端治理和性能更难；Webhook 适合外部通知，但重试、签名、幂等必须做。

**先定交互语义，再定协议。** 不要先说要用 gRPC，先判断这条链路是否必须同步知道结果。

## 第一刀：同步还是异步

|通信方式|适合|代价|
|-|-|-|
|同步请求/响应|调用方当场等结果、要即时校验、失败必须马上知道|链路每多一环尾延迟就叠一层，任一依赖故障沿链扩散|
|异步消息/事件|允许稍后完成、需要削峰、一份数据多个下游消费|状态推进变复杂，要补幂等、补偿和积压治理|
|流式通信|边生成边输出、实时状态刷新、长任务进度回报|要处理连接保活、背压和断线续传|

经验规则：用户必须马上知道能不能继续 → 同步；只需要知道已受理 → 异步；要持续看见变化 → 流式。

## 协议各有边界，不是替代关系

|方式|更适合|不适合|
|-|-|-|
|REST|对外开放 API、普通 Web/SaaS、易调试、生态通用|高频内部调用、强类型契约要求极高的场景|
|gRPC|内部服务间调用、低延迟、高吞吐、强 IDL|浏览器直连、公开 API|
|GraphQL|多端聚合查询、字段变化频繁、前端需要灵活组合|写操作复杂、缓存/权限/限流治理弱的团队|
|Webhook|第三方事件通知、支付回调、外部集成|需要同步强结果的核心链路|
|MCP|给 AI agent 暴露工具、资源和上下文|普通业务服务间通信，无 agent 语义的场景|

对外 API 优先易理解、稳定、可版本化；内部高频调用优先强契约和性能；前端多端聚合考虑 GraphQL 但要有治理能力；第三方回调必须考虑签名、幂等、重放攻击；agent 工具接口要把权限和人审写进协议边界。

## 契约比协议更重要

API 最大的风险不是 HTTP 还是 protobuf，是**契约不清楚**：输入输出（字段含义、必填/可选、单位、枚举）、错误语义（哪些可重试？哪些是用户错误？哪些是系统错误？）、幂等性（同一请求重放两次会怎样？幂等键在哪里？）、版本策略（字段怎么新增/废弃？旧客户端多久兼容？）、限流与配额（谁可以调多少？超过后返回什么？）、安全边界（鉴权、授权、签名、审计）。

没有契约治理，REST 变成乱七八糟的 URL，GraphQL 变成随意暴露数据库，gRPC 变成强类型的泥球。

## 内部通信：别让调用链无限变长

微服务最常见的性能问题不是单个服务慢，是调用链扇出：用户请求 → A → B/C → D/E/F/G。每多一跳，增加网络延迟、超时和重试风暴、依赖故障传播、trace 排障成本。

内部 API 要配套三件事：**超时预算**（上游 500ms，不能给每个下游都 500ms）；**重试纪律**（只重试幂等请求，加退避和抖动）；**降级策略**（非核心依赖失败时返回部分结果或兜底）。

## 外部 API：稳定性比优雅更重要

对外 API 一旦发布就是承诺：向后兼容（新增字段通常安全，删除/改含义危险）；错误码稳定（客户会写逻辑依赖你的错误语义）；文档与示例（外部开发者看不懂，再优雅也没用）；签名与防重放（特别是支付、Webhook、agent 工具调用）；审计与速率限制（出问题能追踪，被滥用能限制）。

平台型产品的 API 不是实现细节，是产品的一部分，版本和兼容策略就是架构边界。

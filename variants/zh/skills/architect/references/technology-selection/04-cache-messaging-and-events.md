# 缓存、消息与事件（Cache, Messaging, and Events）

三类中间层的语义区分与选型：缓存只加速不篡位、队列削峰转异步、事件传播事实。适用于读热点、写洪峰、跨边界协作的压力分析。

## 三个东西经常被混用

很多架构图里 App → Redis → MQ → Kafka → Worker 一条龙，然后说有缓存、有队列、有事件驱动很高级。真正要问的是：Redis 里放的是可丢的缓存还是不该丢的业务状态？MQ 是为了削峰还是为了让两个服务异步协作？Kafka 里的消息是命令（让别人做事）还是事件（告诉别人发生了什么）？消费失败、重复消费、乱序、积压怎么办？

**中间层的价值不在名字，而在它改变了什么质量属性**：延迟、吞吐、可用性、耦合度、一致性、恢复成本。它们解决的是三类不同压力：读热点、写洪峰、跨边界协作。

## 缓存：只加速，不篡位

适合解决读热点。三个最常见的错：把缓存当事实源（缓存丢了数据就丢）、不设计失效策略（用户看到旧数据、脏数据）、所有请求一起穿透（主库被打爆）。

| 错误 | 正确姿势 |
| --- | --- |
| 缓存当事实源 | 主库是事实源，缓存可重建 |
| 无失效策略 | TTL、主动失效、版本号 |
| 缓存穿透 | 空值缓存、请求合并、限流、预热 |

缓存类型按数据形态选：本地缓存适合配置、字典、低频变化数据（注意多实例不一致）；分布式缓存（Redis）适合热点对象、会话、计数、限流（注意网络开销、容量、淘汰策略）；CDN 适合图片、视频、静态资源、公开页面（注意失效延迟）。

判断句：**缓存丢了，系统应该变慢而不是变错。变错，说明你把业务状态偷偷放进缓存了。**

## 消息队列：把必须现在做的改成可以排队的

最常见价值是削峰填谷：瞬时压力变成可控排队。典型场景：抢票锁座后的出票通知、下单成功后的发券短信邮件、文档上传后的解析索引、视频上传后的转码。

但队列引入后，同步世界变成异步世界，必须回答五个新问题：重复消息（消费者幂等吗？同一消息处理两次会怎样）；消息丢失（生产、存储、消费确认链路怎么保证）；消息乱序（需要同一业务键内有序吗）；队列积压（用户看到什么？系统如何降级）；死信（失败消息去哪里？谁来修？）。

队列不是一加就稳定，是把问题从请求延迟转成了**异步一致性与恢复**。

## 事件系统：记录发生了什么，不是命令别人做什么

| 类别 | 指什么 | 举例 | 结果由谁兜底 |
| --- | --- | --- | --- |
| 命令 | 请你做某事 | `CreateOrder`、`SendEmail` | 接收方要执行成功或失败 |
| 事件 | 某事已经发生 | `OrderPaid`、`TicketLocked` | 订阅方按需反应 |

事件适合跨边界传播事实：订单服务发布 `OrderPaid`，库存确认扣减、通知发短信、数据平台更新报表、风控记录行为，订单服务不需要知道所有下游。代价：事件 schema 一旦发布下游会依赖，升级要兼容；下游处理失败时事实已经发生，不能简单回滚；事件太细会淹没系统，太粗表达不清；事件链太长排障变难，必须有 trace。

## 产品选型：先选语义再看名字

选型时先归入四种语义，再挑产品：

- **任务队列**（RabbitMQ、Celery、Sidekiq 一类）：像派活给 worker，每条消息被消费即完。后台任务、发邮件、图片处理。
- **日志型事件流**（Kafka、Pulsar 一类）：像一本可回放的事实日志，消费位移可重置。事件总线、数据同步、审计、流处理。
- **轻量消息/流**（Redis Streams、NATS 一类）：像一条简单快速的异步通道，运维轻。中小规模异步、低延迟内部消息。
- **云托管队列**（SQS、Pub/Sub 一类）：像把运维外包出去的可靠队列。云上业务、团队不想自运维。

选型时问四件事：需要消息**可回放**吗（需要就偏事件流）？需要复杂路由和投递确认吗（任务队列更合适）？团队能不能运维集群（不能就托管）？消息是不是核心审计事实（是的话持久化、保留周期、schema 治理都要严肃对待）？

## Outbox：写事实和发事件别分裂

最经典的坑：写订单成功、发送 `OrderCreated` 失败——主库里有订单，下游永远不知道；或反过来消息发出成功、写订单失败——下游收到一个不存在的订单。

Outbox 模式：同一个本地事务里写业务表 + 写 outbox 表，后台投递器扫描 outbox 发消息并标记已投递。避免写事实和发事件两步分裂。代价是多一张表、一个投递器、幂等和重试逻辑，换来跨服务一致性可控。

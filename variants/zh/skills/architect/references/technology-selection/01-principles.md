# 选型原则（Selection Principles）

技术选型的统一决策框架：要不要引入、处在哪个阶段、会先死在哪、团队能否养住、能否退出。适用于任何"要不要上 X"的判断，是 technology-selection 目录其余七篇的总纲。

## 根节点不是 A 还是 B

选型的第一个问题从来不是"PostgreSQL 还是 MongoDB""REST 还是 gRPC""PaaS 还是 K8s"，而是：**我们真的需要引入新技术吗？**

现有技术栈能在目标性能、成本、可靠性和交付周期内解决问题，默认沿用现有栈。任何新技术都带来学习成本、集成成本、运维成本和未来迁移成本。这和能单体就别微服务、能工作流就别 agent、能托管 API 起步就别自建 GPU 是同一种克制。架构师把选型理解为：**为一个明确问题支付一笔明确成本。**

## 第一刀：现在处在哪个阶段

同一个系统不同阶段答案完全不同：

| 所处阶段 | 主要矛盾 | 由此偏向 |
|-|-|-|
| MVP | 验证速度 | 组件越少越好，主流栈、托管优先，迁移成本先不考虑 |
| 成长期 | 可控增长 | 先把可观测和灰度补上，边界划清，局部能扩 |
| 规模期 | 效率与成本 | 才值得为单位成本做深度优化和平台化 |
| 关键期 | 稳定与合规 | 审计、隔离、容灾、SLO 和事故流程成为硬要求 |

一个技术在成熟期是正确答案，在 MVP 可能就是过度设计。验证需求时优先少组件，支撑增长时优先可控，优化规模时才值得为单位成本和深度定制付出复杂度。

## 第二刀：系统会先死在哪里

确认现有栈不够后，不要马上找工具，先定位失败模式：

| 你最怕哪种失败 | 先查哪里 |
|-|-|
| 数据出错、各处状态对不齐 | 检查数据模型与事务边界是否吻合，幂等和 Outbox 是否到位，有没有对账兜底 |
| 读流量集中烧穿主库 | 评估缓存层、读模型隔离、CDN 分流、入口限流 |
| 瞬时写入洪峰冲垮后端 | 引入队列缓冲、背压传导、削峰填谷、非关键路径异步化 |
| 深调用链放大尾延迟 | 审视 API 边界划分、各层超时预算、降级手段、trace 定位 |
| 每次发布都心惊肉跳 | 补部署平台能力、灰度发布、快速回滚、配置治理 |
| 出了事半天找不到原因 | 检查指标、日志、链路追踪的覆盖，SLO 告警是否指到责任方 |
| AI 输出质量悄悄变差 | 建 eval 基线、trace 观察、RAG 检索评测、模型路由回退 |
| 团队经常互相等互相卡 | 划模块边界、评估平台工程投入、理顺服务归属 |

**工具只是答案的外壳，失败模式才是选型的题目。**

## 第三刀：团队能不能养得起

很多技术在 benchmark 里很好看，但团队不一定养得起：会不会部署？会不会排障？有没有监控？线上坏了谁能修？版本升级会不会炸？有没有足够多的人理解它？

一个"性能更强但没人会修"的系统，在生产里常常输给"性能够用但团队熟悉"的系统。选型不是实验室比赛，是长期运营合同。不把可运维性和关键人员风险写进判断，选中的不是技术，是未来事故。

## 第四刀：能不能退出

成熟的选型一定有退出方案：新数据库的数据怎么迁移、双写如何校验、回滚到哪里？模型供应商的 API 能否适配、提示和 eval 能否复用？业务逻辑是否被框架吞掉、能否分层隔离？消息系统的 topic/schema/消费位点如何迁移？云平台的镜像、配置、密钥、存储、网络能否移走？

没有退出路线的选型，就是把未来绑死。重要技术进生产前，至少要有 Spike（小实验）、灰度计划、回滚方案和决策记录。

## 统一决策树

要不要引入新技术？
1. 现有栈能满足目标 → 沿用 + 局部优化。
2. 不能，但现在处在 MVP → 选最少组件、最快验证、低迁移成本。
3. 失败模式是什么？数据/一致性 → 先看存储与事务边界；延迟/吞吐 → 先看缓存、批处理、扩展方式；可用性/失败 → 先看冗余、降级、隔离；AI 质量 → 先看 eval、RAG、模型路由；团队协作 → 先看模块边界、平台能力。
4. 候选方案能否被团队养住、能否退出？不能 → 换轻一点的方案。能 → Spike 验证 → 写决策记录 → 灰度采用。

## 选型决策记录的要点

决策记录的重点不是格式，而是把"为什么选"和"选错怎么退"写清楚：背景（现状与痛点，最好带数字）、目标（要解的失败模式）、候选（至少两条，各自的代价）、选择与放弃（换来什么、付出什么）、复审条件（什么信号出现时重新评估）、退出方案（怎么移走）。

## 七个领域的"先问什么"

| 领域 | 不要先问 | 先问 |
|-|-|-|
| 语言/框架 | 哪个语言更先进 | 团队、生态、运行时、业务复杂度匹配吗 |
| 数据库/存储 | 哪个数据库最强 | 事实源是谁，查询形态是什么 |
| 缓存/队列/事件 | 要不要上 Kafka | 是读热点、时间错配，还是业务事实广播 |
| API/通信 | REST 还是 gRPC | 同步/异步、内部/外部、契约强度是什么 |
| 部署平台 | 要不要 K8s | 团队是否需要并养得起平台能力 |
| 观测/可靠性 | 用哪个监控工具 | 用户 SLO 是什么，事故怎么收场 |
| AI 基础设施 | 要不要自建 GPU | 稀缺资源是模型、上下文、成本、质量还是可控性 |

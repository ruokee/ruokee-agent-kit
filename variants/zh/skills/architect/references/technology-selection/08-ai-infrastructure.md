# AI 基础设施（AI Infrastructure）

AI 技术栈的五层拆解与升级信号：托管 API 默认起步、网关、RAG/向量库、自建推理、训练与微调、守门层。适用于含 LLM 系统的基础设施选型。

## 你到底在自建什么

一听 AI 基础设施就想到 GPU、向量库、agent 框架、模型网关、推理引擎、训练微调、评测平台。但第一步不是列清单，是问：**你是真的在建基础设施，还是只是在做一个 AI 应用？**

早期产品 MVP 阶段最合理的默认答案：调用托管模型 API，加最小日志和成本监控，先把业务闭环跑通。只有遇到明确触发信号——成本失控、数据不能出域、延迟不达标、供应商单点不可接受、模型需要深度定制——才值得下沉到网关、自建推理、GPU 池。

AI 基础设施不是越底层越高级。越底层拿回的控制权越多，同时接下的账单也越多：成本、容量规划、故障恢复、安全隔离、团队运维能力。

## 五层拆解

|层|组件|
|-|-|
|入口治理|模型网关、鉴权、限流、成本记录、模型路由|
|上下文|RAG、向量库、文档权限、重排、引用|
|推理|推理服务、GPU、KV cache、批处理|
|训练与微调|数据版本、任务编排、检查点、实验追踪、验证与晋级|
|守门|可观测、eval、trace、人工审批|

五层不是一开始都要有。正确顺序是**先看见不可省的风险，再补对应的层**：看不见成本，先补网关或用量日志；检索质量决定答案上限，先补 RAG eval；多个团队都调模型，再补统一网关；GPU 成本超过 API 成本，再考虑自建推理；确有需要改变模型行为的场景，才考虑微调或训练；agent 能执行副作用，必须补权限、人审和审计。

## API 还是自建推理：成本账不是面子账

|方式|优势|代价|
|-|-|-|
|托管模型 API|起步快、运行稳定、运维少，新模型随手可用|被供应商锁定，数据必须走对方的路径，量大后单位成本可能反超|
|自建推理|模型、数据、成本结构、部署环境全部自己控制|GPU、显存、批处理、扩缩容、故障、容量都得自己背|
|混合路由|简单任务用便宜模型，难任务才上强模型|路由策略、评测、回退、成本核算都更复杂|

分叉不问"哪个更先进"，问四个问题：数据能不能出域？延迟目标托管 API 能不能满足？调用量大到自建更便宜了吗？团队会不会运营 GPU 服务？只中一个通常不足以上自建；同时命中两三个，基础设施下沉才有意义。

## RAG、长上下文、微调：分清补知识还是补行为

|路线|解决什么|适合|
|-|-|-|
|RAG|答案基于当场检索到的外部资料|知识库大、内容常更新、答案要给引用、要做权限过滤时选它|
|长上下文|把材料整段放进窗口一次读完|材料体量有限、一次性任务、窗口容量够用时选它|
|微调|调整模型默认行为、输出风格与固定格式|输出格式要求死板、领域语汇稳定、手里有高质量样本时选它|

最常见的误判：检索没做好就怪模型笨，或把本该 RAG 解决的"知识更新"问题拿去微调。判断句：**知识用检索，行为才谈微调。** 要引用、要更新、要权限，优先把 RAG 做对。

## 训练与微调：何时托管、何时自建

训练基础设施不是推理的延伸，是另一套账本：数据管道（清洗、去重、许可合规、版本化——否则实验无法复现）、任务编排（长跑任务要可中断可恢复）、GPU 与互联（多卡训练对卡间带宽和存储吞吐敏感，和推理的硬件画像不同）、检查点与模型制品（断了能续、版本可追溯）、实验追踪（超参、数据集、指标对齐到一次运行）、验证与晋级（离线指标达标才准上评测集，评测集达标才准进候选发布）。

分叉判断：**能托管微调（API 提供的微调服务）满足需求时，默认托管；只有训练任务高频到自建集群更划算、或数据/模型不能出域、或需要训练流程的深度定制时，才自建训练基础设施。** 多数做 AI 应用的团队永远不需要后者。自建前还要问：有没有人懂分布式训练的排障？练一次的成本多大、多久迭代一次？这些和推理自建的判断是同一套账，但门槛更高。

## Agent 框架：先工作流，再自主

第一个问题仍然是：能用确定工作流解决吗？能 → 工作流优先（更可预测、可测试、可审计）；不能 → agent，但必须配权限、预算、人审、trace、eval。

agent 框架选型重点看：工具权限能否分级？是否支持人工审批？能否记录每步 trace？能否限制预算和最大步数？能否做上下文压缩和任务恢复？

## 守门层是生产门槛

AI 系统和传统系统最大的不同是输出不稳定、质量会漂移。上线后只看接口成功率不够，还要看：prompt 和上下文是什么？检索到了哪些片段？模型调用成本多少？工具调用有没有越权？最终答案有没有引用、有没有胡编？换模型或改提示后质量有没有退化？

系统碰钱、碰用户数据、碰自动操作时，eval 不是"以后再补"，是架构的一部分。没有 eval，每次换模型、改提示、换检索策略，本质上都是闭眼上线。

## 选型速查

| 判断问题 | 起步选择 | 触发升级 |
|-|-|
| 只是验证 AI 产品 | 托管模型 API 加基础日志起步 | 等到多应用共用、成本看不清、供应商故障影响面大再补网关 |
| 多模型/多团队都在调模型 | 模型网关统一入口 | 需要统一鉴权、限流、计费、故障转移时 |
| 要用私有知识作答 | RAG 加简单向量检索 | 检索质量不稳、权限复杂、知识库变大时 |
| 向量规模还小 | pgvector 或单机向量检索 | 到百万级以上、过滤复杂、延迟吃紧再上专用向量库 |
| 模型调用成本高 | 模型路由、缓存、配额 | API 成本高于自建总成本、或数据不能出域 |
| 需要自动行动 | 确定性工作流 | 步骤开放、必须动态规划才上 agent |
| 要稳定迭代 | trace 加小 eval 集 | 生产级、碰钱、换模型频繁时扩到完整门禁 |
| 要改变模型行为 | 托管微调服务 | 训练高频到自建更划算、数据/模型不能出域、需深度定制 |

# 语言与框架（Languages and Frameworks）

语言、运行时、框架三层的选型判断：业务复杂度、性能、生态、团队、演进五把尺子。适用于新项目选栈、评估是否换语言/框架。

## 语言、运行时、框架分别影响什么

新手常把三件事混在一起。语言决定表达方式、类型系统、生态入口，架构上要看团队熟悉度、长期维护、错误能否早暴露。运行时决定并发模型、内存、启动速度、部署形态，要看延迟、吞吐、资源成本、冷启动。框架决定约定、组件组合、开发节奏，要看交付速度、可测试性、插件生态、团队一致性。

只问"用 Java 还是 Go"不是完整问题，完整的问题是：在当前团队、当前业务、当前质量目标下，需要什么样的**运行与交付模型**。

判断标准：一个语言/框架选择会显著影响质量属性，它就是架构决策；如果只是代码风格不同，就别上升到架构战争。选语言不是投票，"我喜欢 Go""招 Java 容易"这些理由是线索不是决策，要继续问：这条业务链路的瓶颈是什么？团队最缺交付速度、运行效率、稳定性还是招聘可得性？生态里有没有成熟的库、调试工具、监控方案？三年后新人能不能读懂、改动、上线？

## 五把尺子

| 量尺 | 该问什么 | 倾向哪种答案 |
| --- | --- | --- |
| 业务复杂度 | 规则多、状态多、权限多吗 | 类型系统强、工程约定强、测试生态成熟 |
| 性能与资源 | CPU、内存、P99 尾延迟是不是核心 | 运行时开销低、并发模型清晰 |
| 生态成熟度 | 支付、鉴权、ORM、消息、监控有没有现成方案 | 生态深、文档多、社区稳定 |
| 团队能力 | 团队会什么？招人容易吗 | 团队主语言，或学习成本可控的新语言 |
| 交付与演进 | 快速迭代还是长期高可靠 | 框架约定清晰、迁移路径明确 |

不要只因为语言看起来更先进就换栈。只有新技术能明确换来某个质量属性，且愿意支付学习、运维、招聘、迁移成本时，才值得进入候选。

## 常见后端语言的取舍

不是排名，是帮助形成判断：

| 技术 | 常见优势 | 常见代价 | 适合场景 |
| --- | --- | --- | --- |
| Java/Kotlin + JVM | 生态成熟、企业库多、性能稳定 | 项目偏重、启动慢、框架复杂度高 | 中大型业务系统、金融、电商、SaaS 后台 |
| Go | 部署简单、并发模型直接、资源占用低 | 工程抽象包袱较多 | 网关、基础设施、微服务、实时链路 |
| Python | AI/数据生态强、原型快 | 运行性能和并发模型要小心 | AI 服务、数据平台、低 QPS 后台 |
| TypeScript/Node.js | 前后端同语言、I/O 并发友好 | CPU 密集不合适 | BFF、中小 SaaS、实时轻服务 |
| Rust | 性能和内存安全强 | 学习曲线高、交付速度慢 | 存储、代理、引擎、性能敏感组件 |

一个系统不一定只用一种语言：业务主服务 Java/Go/TS，AI 推理与数据处理 Python，高性能代理或存储引擎 Rust/Go，前端与 BFF TypeScript。但多语言有**认知税**：构建、部署、监控、调试、招聘、代码审查都变多。小团队给每个模块选"最合适的语言"引入五种栈，通常是在提前透支组织能力。

## 框架：默认选成熟，除非有明确反证

框架本质上是替团队约定做法：它提供路由、依赖注入、配置、数据访问、鉴权、测试和可观测性入口；代价是自由度降低、学习和升级成本增加，调试也可能不够透明。MVP 阶段优先降低交付风险；长期多人维护优先降低协作风险。很多时候，成熟而稍显笨重的框架比看起来酷但全靠团队自律的轻框架更稳。

第一轮筛选：团队新人多、多人长期维护 → 约定强、文档好、生态成熟的框架；极快试错、业务未定 → 轻量框架 + 清晰模块边界；大量企业集成、事务、权限 → 成熟企业框架；高并发网关 → 运行时开销低的框架；AI/数据密集服务 → 靠近 Python 生态，外层用稳定 API 包起来。

## 什么时候换语言/框架

不要因为看起来旧就换，换栈由触发信号推动：P99 长期超 SLO 且瓶颈来自运行时（不是写法问题，是模型不匹配，把热点链路拆到更合适的运行时）；团队交付越来越慢、框架约定挡路（先模块化再局部迁移）；生态缺失导致大量自研（换到更成熟的栈）；招聘和代码审查困难（收敛语言）；安全与合规要求变高（关键组件单独升级）。

换栈也要像拆单体一样做：不要大爆炸重写，先抽边界、并行运行、影子流量、逐步切换。

## 选型结论的写法

决策记录里不要只写"我们选择 Go，因为 Go 很快"，要写清楚为什么只把入口层切出去、承认了什么代价：背景（下单入口是 I/O 密集链路，P99 目标 200ms，团队已有 Go 运维经验）、选择（入口层 Go，业务状态机留在 Java 订单服务）、放弃（单语言仓库的简单性，多一条构建链路）、换来（入口部署轻、可独立扩容和限流）、复审条件（入口逻辑变成复杂业务编排、或团队 Go 维护能力不足时回收进主业务栈）。

# 数据存储

数据存储（Data Stores）：按数据生命周期和查询形态选存储：事实源默认关系型，搜索/分析/向量是读模型。适用于主存储选型、读写分离、RAG 存储设计、拆存储时机判断。

## 别用一个数据库扛所有问题

MVP 用一个关系库扛交易、报表、搜索、附件、向量，没错。问题是业务长大后这些数据的访问方式完全不同：订单要强一致不能丢；报表扫大量历史数据不能拖垮主库；搜索要相关性排序不是 `LIKE`；图片视频要便宜存、能走 CDN；RAG 要向量召回和权限过滤。

架构判断不是问哪个数据库最好，是判断**哪类数据该用哪种存储模型承载**。一个系统常常需要多种存储，但每多一种，就多一份同步链路、一致性边界和运维对象，也增加排障成本。

## 先画数据生命周期

选数据库之前，把一类数据从出生到归档画出来：写入 → 校验 → 事务提交 → 查询/检索 → 分析/报表 → 归档/删除。回答五个问题：

- 读多还是写多，决定是否需要读写分离、缓存和索引模型。
- 事务边界在哪里，决定能不能用关系库的事务兜住。
- 查询形态决定一切：主键查、范围查、全文搜索和向量相似度是四种完全不同的东西。
- 数据增长多快，决定分区、冷热分层和归档策略。
- 出错时会怎样，决定一致性、备份、审计和恢复等级。

先算数据量、读写比、保留周期，再谈工具。

## 关系型仍是主存储的默认起点

- 关系型存储，比如 PostgreSQL 和 MySQL，适合交易、订单、权限、租户和账务这类需要事务的数据；不适合极大规模分析、全文搜索和海量非结构化文件。
- 文档数据库，比如 MongoDB，适合结构经常变化、整篇文档读写、关系较弱的数据；不适合强事务、多表复杂关联和严格报表。
- 键值存储，比如 DynamoDB 和持久化 Redis，适合按 key 高速读写、结构简单、超大规模的场景；不适合复杂查询和灵活关联。
- 列式和分析数据库，比如 ClickHouse 和 BigQuery，适合报表、聚合、日志分析和行为分析；不适合高频小事务写入。

默认建议：先用关系库把核心交易数据放稳，等报表、搜索、日志、向量检索真的变成独立压力，再把对应读模型拆出去。不要一上来为了现代感把每类数据塞进不同数据库。

## 读模型不是主库附属品

当查询形态偏离主库擅长方向，就考虑读模型：

- 全文搜索引擎，比如 Elasticsearch、OpenSearch 和 Meilisearch，换来相关性和倒排能力；代价是维护索引同步，并接受最终一致。
- 报表分析引擎，比如 ClickHouse、BigQuery 和 Snowflake，列存扫描与聚合很快，但扛不了交易写入。
- 对象存储，比如 S3、OSS 和 GCS，存文件便宜且持久，但别拿它当数据库做条件查询。
- 向量数据库，比如 Milvus、Qdrant 和 pgvector，相似度检索强，但权限过滤、召回质量和成本都要评估。
- 时序数据库，比如 Prometheus 和 InfluxDB，擅长指标时间线查询，不适合普通业务对象。

最容易犯的错是把读模型当事实源。正确关系：主库 = 事实源，搜索/分析/向量库 = 从主库或对象存储同步出来的读模型。读模型可以落后，但要说清楚**能落后多久、怎么补偿、怎么重建**。用户改了资料只改搜索索引、主库不知道，就是事故。

## 向量库不是 RAG 的唯一答案

RAG 很容易被压扁成"文档切块 → 向量库 → topK → LLM 回答"。真实系统还包括：原文对象存储、解析切块、元数据主库、关键词索引（混合检索）、权限/租户过滤。

选型时问：权限过滤在检索前做还是检索后做（后过滤可能召回不够）？只做向量召回还是混合检索？原文和引用存在哪里（向量库不该是唯一事实源）？索引坏了能不能从原文和元数据重建？成本能不能随文档量和查询量线性增长？

向量库解决相似度召回，不解决权限、事实源、引用、评测的全部问题。不要把一个 RAG 系统压扁成一个库。

## 拆存储的触发信号

- 报表查询拖慢交易库时（OLTP 与 OLAP 互相干扰），把数据同步到分析库。
- 搜索相关性差、LIKE 扫描慢时，建搜索索引。
- 附件或图片撑爆数据库时，迁到对象存储并接 CDN。
- 单表增长导致索引和备份变慢时，分区、归档或做冷热分离。
- RAG 召回质量不稳时，用混合检索、重排和 eval。

反面：数据量小、团队少、故障代价低时，一套关系库 + 合理索引 + 定期备份，往往比过早引入五种存储更健康。

## 选型结论的写法

关键是说清楚**哪个读模型拖垮了哪个事实源**，而不是"ClickHouse 很快"。例：背景是月度报表扫 2 亿行历史事件，交易库 P99 从 120ms 升到 900ms；选择是主库继续当事实源，Outbox 事件同步到分析库，报表只查分析库；放弃报表强实时性，允许 1 分钟内延迟；换来交易链路与报表链路隔离；复审条件是报表必须秒级实时或同步延迟超业务可接受时重新评估。

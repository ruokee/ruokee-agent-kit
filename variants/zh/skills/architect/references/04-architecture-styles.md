# 架构风格（Architecture Styles）

比较常见架构风格的适用条件与取舍。适用于为新系统选择总体结构、评估现有结构的演进方向、审查风格选择是否匹配约束。

## 模式是工具，不是目标

同一类问题在无数系统里反复出现，被验证过的解法沉淀成模式。学模式的价值：遇到问题手里有牌，不必从零硬想；沟通有共同词汇，一个词省半小时解释。

但模式没有高级和低级之分，只有合适与不合适。一个用对了的单体，远比一个用错了的微服务高级。评估任何风格时都要回答三件事：它解决什么问题，它长什么样，它的代价是什么。看不到代价，等于没学会这个模式。

## 各风格的适用条件与代价

**分层（Layered）。** 按关注点横向切层，每层只与相邻层打交道：表现层、业务层、数据层。解决"别把所有东西搅成一锅粥"，是关注点分离的最朴素形式，几乎永远适用。代价是穿透成本：一个简单查询要穿过每一层，产生只是传数据的样板代码。注意分层是代码组织方式，不代表每层都是独立部署的服务，别把分层误当成分布式。

**单体（Monolith）。** 整个应用一个部署单元，模块之间是函数调用不是网络调用。解决"用最低协作和运维成本先把东西做出来"。单体内部完全可以、也应该分模块（模块化单体）；单体不等于一团乱麻，只是模块部署在一起。代价：改一行重新发布全部；无法对单个模块单独扩容；一个模块崩溃拖垮整个进程；边界不清时退化成大泥球。这些大多是产品成功后才需要面对的成长烦恼，没验证产品有没有人用之前就为此买单是过度设计。

**微服务（Microservices）。** 多个可独立开发、部署、扩容的小服务，各自拥有数据。它首先解决组织问题，其次才是技术问题：当多个团队在一个单体里互相踩脚、每次上线全公司排队时，微服务让每个团队有自己的服务和发布节奏。代价是把函数调用变成网络调用，引入一整座分布式复杂度：超时重试幂等、跨服务事务近乎不可能、运维复杂度爆炸（服务发现、链路追踪、统一日志、编排）、本地调试要同时起多个服务。三个前提最好同时满足再考虑：组织规模够大到互相阻塞；有明确的独立部署需求；平台能力（监控、CI/CD、编排）已经就位。五人团队拆十几个微服务每天排查服务间为什么调不通，不是先进，是给自己上刑。

**事件驱动（Event-driven）。** 组件通过"发生了什么"协作而不是"你去做什么"命令。订单服务广播"订单已支付"，短信、积分、物流各自订阅，发布者不知道谁在听。解决解耦和扇出：每加一个下游动作，改订阅方而不是下单代码。代价：整体流程看不见，逻辑打散到一堆订阅者里，排查像破案；还要面对事件重复、乱序、丢失和最终一致的短暂不一致。流程简单、调用关系清晰时硬上事件驱动，是把直路绕成迷宫；需要立刻拿到结果的同步场景也不适合。

**消息队列/异步处理（Message queue）。** 生产者和消费者之间放缓冲水池：削峰填谷、异步解耦（耗时活儿不让人干等）、可靠投递（消费者挂了任务还在队列里）。代价：多一个必须维护且不能挂的关键基础设施；用户拿不到即时结果，产品要设计"处理中"状态；消息可能被消费两次，消费逻辑必须幂等；队列积压本身成为新的监控对象。没有峰值压力的小任务量，加队列只是徒增运维负担。

**CQRS（读写分离）。** 写和读拆成两套模型：写模型规则严谨、强一致；读模型为查询预先优化、可反范式、可缓存。适用于读远多于写且读写诉求严重不对称（如商品详情页，一次修改千万次浏览）。代价：复杂度翻倍，两套模型加一条要可靠的同步通道；读写之间通常异步同步，写完读到的可能还是旧数据。绝大多数系统不需要 CQRS，它是常规手段压榨干净之后的重武器。

**发布-订阅（Pub/Sub）。** 与队列的关键区别在投递语义：队列一条消息只给一个消费者（分活儿），Pub/Sub 每个订阅者各收一份（广播）。解决"一件事通知很多方且通知方不想知道有谁"。代价：全局流程难追踪，扇出成本随订阅者上升，投递语义（至少一次、至多一次）必须想清楚。

**BFF（为前端裁剪的后端）。** 每种前端一个贴身后端，把后端零散数据裁剪聚合成该端最顺手的形状。适用于多端且各端差异大、后端是多个服务。代价：多一层中间人，团队不大时几个 BFF 容易重复代码，BFF 自己可能膨胀成小单体。只有一种前端或各端诉求一致时，通用 API 就够。AI 对话产品里的编排层某种程度就是一个重型 BFF，把推理、检索、工具、会话裁剪成前端要的那段流式对话。

**管道-过滤器（Pipeline）。** 处理任务拆成首尾相接的步骤，前一站输出是后一站输入，每站可独立开发、测试、替换、扩容。适用于线性数据加工（ETL、媒体转码、RAG 的召回-重排-生成）。代价：整条管线受最慢一站拖累；一站失败要想清楚整条链路的回滚；站间序列化有开销；不适合需要站间来回交互的逻辑。

**微内核/插件化（Microkernel/Plugin）。** 最小稳定内核加可插拔插件，内核只提供基础能力和插件接入契约。适用于核心稳定、外围多变、要让第三方扩展的系统（浏览器、IDE）。代价：插件契约一旦定下很难改；插件质量参差可能拖垮内核，需要隔离或沙箱；内核预留扩展点本身设计难度高。没有外部扩展需求的系统搞插件化是过度设计。

## 选择顺序

1. **能不用就先别用。** 最简单的分层单体能不能解决？能，就这样。
2. **对症，不对时髦。** 代码搅成一团，分层/模块化；一件事扇出通知很多方，事件驱动/Pub/Sub；耗时任务或削峰，消息队列；读写严重不对称，CQRS；多端差异大，BFF；线性数据加工，管道；核心稳定要外人扩展，微内核；多团队互相阻塞，慎重微服务。
3. **付得起代价才上。** 代价付不起或问题还没真出现，先记一笔"以后可能要"，别预支复杂度。

三条心法：从简单开始，由真实痛点驱动演进；模式可以组合，真实系统几乎都是分层单体打底、局部用事件驱动和异步；永远能说出引入一个模式换走了什么，说不清代价大概率是在跟风。

## 反转案例是校准器

Amazon Prime Video 把视频质量监控从微服务和 Serverless 改回单体，成本降约九成（Prime Video Tech 博客，2023-03）；Segment 把 140 多个微服务合回单体后，从每天半次宕机变成一个工程师几分钟部署（Segment 工程博客 "Goodbye Microservices"，2020-07）。教训不是微服务错了（Netflix 用得很好），是跟风错了。判断一个风格选择是否合适，永远回到当前项目的六问答案和约束，而不是行业声量。

# Python 专项代码质量指南

本参考资料集中保存设计原则、编程范式和重构主题在 Python 中的具体应用。

## 设计原则

### 组合优于继承（Composition over Inheritance）

Python 支持多重继承，mixin 是一种常见的惯用模式：小型类向宿主类添加一部分行为。使用得当时，
mixin 应该小型、无状态、命名清晰，并且仅依赖宿主有文档记录的接口。使用不当则会引起真正的麻烦：

- **隐式状态和初始化顺序。** 一个设置属性或期望 `super().__init__()` 按特定顺序调用的 mixin
  会以隐式方式耦合宿主和其他 mixin。方法解析顺序（MRO）决定了何时运行什么，包含多个 mixin 的类
  可能难以推理。
- **名称冲突。** 多个 mixin 定义或期望相同的属性或方法名会通过 MRO 以微妙的方式交互。

保持 mixin 小型、无状态，并以它们添加的内容来命名。如果一个 mixin 需要大量状态或特定的
初始化顺序，那就是该使用组合的信号。

- 默认使用函数、构造函数参数、Protocol、策略对象和委托来实现复用和变化。
- 将继承保留给异常层次结构、框架钩子、真正稳定的抽象，以及少数小型、清晰的 mixin。
- 对于共享代码，优先选择模块级辅助函数或组合的协作者，而不是仅为了持有共享方法而存在的基类。

### 领域驱动设计要点（Domain-Driven Design Essentials）

- 小项目可以不使用完整的分层架构，仅借用通用语言、值对象和不变量思维。
- 值对象可以很好地映射为 `dataclass(frozen=True)`、`attrs`、Pydantic 模型或普通类。
- 实体不一定是 ORM 类。当持久化关注点扭曲模型时，将领域模型与持久化模型分离。
- 仅当你确实需要事务边界、存储的测试替身或与 ORM 的隔离时才引入仓库和工作单元，而不是默认这样做。

### 深模块与信息隐藏（Deep Modules and Information Hiding）

- Python 没有强制的 `private`。使用命名约定（`_internal`）、模块结构、`__all__`、明确设计的
  公共 API、`property` 和 `Protocol` 而非访问修饰符来表达边界。
- 优先让模块的内部稍微长一些但局部清晰，而不是将逻辑分散到读者需要追踪的十几个浅辅助函数中。
- 适配器层是天然的深模块：它通过一个小的接口隐藏第三方库的细节，同时仍然暴露调用者必须考虑的
  错误和性能特征。这是防腐层和适配器模式
  的结构基础。

### 依赖反转与依赖注入（Dependency Inversion and Dependency Injection）

Python 很少需要 DIP 在其他生态中获得的那种重型装置。轻量级工具通常就足够了：

- **构造函数和函数参数。** 传入协作者。`def process(orders, repository, clock):` 无需仪式
  即可反转三个依赖。
- **`typing.Protocol`。** 结构化地定义策略需要的窄能力；任何具有正确方法的对象都符合条件，
  无需继承任何东西。这使接口符合性与继承关系保持分离。
- **普通可调用对象。** 当依赖负责提供某个值，例如时钟、ID 生成器或通知器时，普通函数或
  `Callable` 往往比接口对象更轻量。
- **常见情况的默认参数。** `def fetch(url, client=httpx.get):` 保持了实际默认值的方便，
  同时为测试传递 fake 留有接缝。

在同一个地方装配具体接线：`main()`、Web 应用的启动代码、框架入口点。这个*组合根*
（composition root）是高层策略遇到具体细节的地方；其他所有地方都依赖于抽象。

- 优先选择构造函数参数、函数参数、默认参数、小型 Protocol 和工厂函数。
- 在单一组合根中装配具体依赖。
- 将外部客户端包装在适配器中；让核心依赖于 Protocol 或可调用对象。
- 使用上下文管理器管理依赖生命周期（连接、文件、锁），将其保持在领域逻辑之外。

### DRY: 不要重复自己（Don't Repeat Yourself）

- 首先去重领域概念、schema 和协议，而不是局部代码形态。
- 对于重复的 schema/API/模型定义，使用单一真实来源：`dataclass`、`TypedDict`、Pydantic、OpenAPI 规范或代码生成。
- 对于实现相同但有不同业务原因的两个函数，允许重复直到变化方向明确。
- 优先使用模块级函数、表驱动映射、`Protocol` 和策略函数，而不是构建类层次结构来共享代码。
- 表（table）和分发映射（dispatch map）是折叠真正重复知识（每个案例一行）的绝佳方式，无需发明继承树。

### GRASP: 通用职责分配软件模式（General Responsibility Assignment Software Patterns）

行为靠近拥有它的数据（信息专家）。CLI 和 API 处理器保持为薄控制器，规则放在核心中。服务、适配器、映射器和策略函数都是合理的纯虚构。一旦真正识别出变化点，保护变化通过 `Protocol`、适配器或深模块来实现。在整个过程中，平衡低耦合与高内聚，而不是单独最大化其中任何一个。

### KISS: 保持简单（Keep It Simple）

- 默认使用清晰的数据结构、直接的控制流、标准库以及少量命名良好的函数。
- 当复杂度不可避免时，将其隔离在模块、适配器或深模块（deep module）内部，使调用方保持简单。
- 不要为单个调用点创建抽象，也不要把所有东西塞进一个巨型函数：两者都是向相反方向对简单的背离。
- 让格式化工具和 linter 处理风格问题，以便人类注意力集中在边界和行为上。

### 迪米特法则（Law of Demeter）

- 根据结构知识和变更传播来判断，而不是点的数量。
- 给领域对象语义查询：`order.shipping_postal_code()`、`invoice.is_overdue()`，
  而不是暴露嵌套字段供调用者遍历。
- 让 DTO、dataclass 和 JSON 类似的数据被透明地遍历。
- 将测试中的深层 mock 视为信号：如果测试必须 patch `a.b.c.d`，生产代码可能对该路径知道得太多。

### 三的原则（Rule of Three）

- 第一次出现：直接编写内联代码。
- 第二次出现：允许少量复制粘贴；抵制提取的冲动。
- 第三次出现，或已经看清变化方向：提取。通常使用参数明确的模块级函数、表驱动映射或小型 `Protocol`，不一定要用类。
- 当你后来意识到抽象得太早时，优先选择内联/扁平化/再次复制，然后寻找真正的变化轴。这是正常的重构操作，而非失败。

### 测试驱动开发（Test-Driven Development）

- `pytest` 非常适合小步 TDD；保持 fixture 直接，避免在其周围构建不可见的框架。
- 对于原型、UI 和复杂的外部集成，先做试验性项目，然后补充特征描述测试或合约测试。
- `monkeypatch` 很方便但容易过度使用。优先在边界传入 fake 或 stub，而不是修补深层内部；
  需要深层修补是一个依赖本应被注入的信号。

### 告诉，不要问（Tell, Don't Ask）

- 给领域对象语义命令方法：`invoice.mark_paid()`、`order.cancel()`、`account.debit(amount)`。
  这些方法在内部维护状态转换和不变量。
- 让数据载体、API schema、ORM 行和配置对象直接暴露属性。
- 使用 `property` 统一存储值和派生值，但要保持廉价且无副作用：不要在其后隐藏 I/O。
- 在函数式核心中，行为不必须是方法：一个接受数据并返回决策的命名函数
  （`def can_debit(account, amount) -> bool`）将逻辑和数据放在一起，而不强制面向对象。
  告诉，不要问是关于将规则和数据放在一起，而不是坚持使用方法。

### YAGNI: 你并不会需要它（You Aren't Gonna Need It）

- 先用普通函数、显式参数、`dataclass` 或简单映射来满足真实的调用点。
- 在第二个真实变化点出现之前等待抽象；在提取之前，设想一下未来的重构会有多便宜：通常便宜到值得等待。
- 对于公共 API、持久化 schema 和外部协议，提前稳定边界是可以的；那不是投机性功能。
- 移除未使用的扩展点比保留"可能有用"的抽象更符合 YAGNI。

## 编程范式

### 面向数据设计（Data-Oriented Design）

- 对纯数据记录优先使用 `dataclass`；当记录是没有身份的值对象时，使用 `frozen=True`（参见 stdlib 参考资料中的 dataclass 指南）。
- 当数据以字典形式到达（JSON、配置）并且你想要形状检查而不转换为对象时，使用 `TypedDict`。
- 保持这些结构作为数据：避免将繁重的业务工作流附加到 dataclass 上；那就是"意外贫血，然后过载"的反模式。如果出现真正的不变量，升级到带有方法的类。
- 为每个 schema 建立单一事实来源，而不是在类型、运行时验证和文档中重复声明相同的形状。
- 转换属于模块级别的处理数据的函数，可以组合成管道，而不是方法（除非行为是类型固有的）。

### 声明式编程（Declarative Programming）

- 为每个声明式结构提供一个单一的事实来源。不要为类型检查器写一次模式，为运行时验证再写一次，为文档再写第三次：尽可能进行派生或生成。
- 在边界处将外部配置解析为类型化对象（`dataclass`、Pydantic 模型），然后让其余代码使用具体类型而不是原始字典。
- 复杂的规则表仍然需要测试。声明式并不意味着免测试；转换表或权限矩阵需要覆盖其行及其被拒绝的情况。
- 对于隐藏控制流的声明式机制，装饰器、路由注册、信号处理器，确保实际执行路径仍然可追踪，避免注册关系变成不可见连接。
- 保留一个命令式逃生口。最好的声明式设计允许罕见的不规则情况回退到普通代码，而不是迫使每个异常都塞入声明的词汇表。将路径映射到处理器的路由表保持声明式；而增长出一个 `condition` 微型语言来表达"仅限周二的高级用户"的路由表，已经开始糟糕地重新发明编程语言了。声明常规情况，让普通函数处理不规则情况。

### 事件驱动架构（Event-Driven Architecture）

- 进程内：一个简单的 `event_name -> list[callable]` 字典通常就足够了；不要为本地解耦引入消息代理。

```python
from collections import defaultdict
from collections.abc import Callable

class EventBus:
    def __init__(self) -> None:
        self._subscribers: dict[str, list[Callable]] = defaultdict(list)

    def subscribe(self, event: str, handler: Callable) -> None:
        self._subscribers[event].append(handler)

    def publish(self, event: str, payload: object) -> None:
        for handler in self._subscribers[event]:
            handler(payload)   # 生产者从不命名消费者
```

这就是最小尺度上的整个模式：发布者知道事件名称和负载，从不了解处理器。更大规模的实现，例如消息代理、持久化和异步投递，都沿用同一结构，只是增加了基础设施。

- 框架提供信号/钩子（Django 信号、Flask 信号、pytest 钩子）：在其中工作时优先使用框架的机制而不是自制的。
- 使事件负载成为纯数据（`dataclass`/`TypedDict`），具有稳定、版本化的模式；这是生产者和消费者之间的契约。
- 设计消费者为幂等的，并记录足够的上下文（事件 ID、关联 ID）以追踪失败。
- 对于异步工作流，发出的事件通常变成一个任务；保留所有权并观察其生命周期和失败，不要触发后就置之不理。
- 不要把记录事件本身等同于可靠审计。如果事件是你的事实来源，就要像维护数据库 schema 一样维护事件 schema。
- 抵制将事件用于实际上是直接请求-响应的流程。如果生产者需要结果、阻塞等待它或只有唯一一个消费者，普通函数调用比事件往返更清晰。

### 函数式核心，命令式外壳（Functional Core, Imperative Shell）

- 入口层可以使用 argparse、Click、Typer、FastAPI 或 Django，但核心业务函数不应依赖框架对象：跨边界传递纯数据。
- 在边界处使用 `dataclass`、`TypedDict`、Pydantic 模型或普通字典承载数据，根据项目的复杂性选择。
- 将不稳定的依赖项，时钟、随机性、文件系统、HTTP 客户端、数据库会话，作为函数参数、构造函数参数、小型 `Protocol` 或通过组合根注入，而不是在核心内部获取它们。
- 核心应接受纯数据并返回纯数据；外壳拥有 `with`/`async with` 资源生命周期。

### 命令式/过程式编程（Imperative / Procedural Programming）

- 在显式的入口点中承载命令式胶水代码，例如 `main(argv: Sequence[str] | None = None) -> int`，并通过 `if __name__ == "__main__":` 将其隔离。
- 让入口层解析参数、加载配置、配置日志、构建依赖，并将异常转换为退出码。核心逻辑接收显式参数，并保持可导入和可测试。
- 对外部资源使用 `with`/`async with`，而不是依赖垃圾回收来释放它们。
- 当一个过程增长到难以阅读时，按阶段将其拆分为命名步骤（`load_config()`、`build_client()`、`run_job()`），而不是直接引入框架。线性的、命名良好的步骤是一种特性，而不是坏味道。
- 抵制将简单的三行序列包装到类或管道抽象中的冲动；直截了当的命令式代码通常就是 KISS 正确的答案。

### 面向对象编程（Object-Oriented Programming）

- 对于简单的数据载体使用 `@dataclass`；当存在真正的不变量或需要管理的生命周期时，才使用普通类。
- 对于跨边界的可替代性，优先使用小的 `typing.Protocol`（结构类型化）而不是名义基类。协作者只需提供正确的方法。
- **数据模型（dunder 方法）** 是对象接入语言的方式：值对象使用 `__repr__`、`__eq__`、`__hash__`；容器使用 `__iter__`、`__len__`、`__contains__`；资源使用 `__enter__`/`__exit__`；可调用策略使用 `__call__`。只有当对象确实具有该语义时才实现它们：不要发明未文档化的 dunder。
- `property` 用于隐藏存储差异或暴露轻量级派生值，而不是用于隐藏昂贵的副作用，如 I/O、网络调用或数据库查询。
- **描述器（Descriptor）**（`property`、方法、ORM 字段、验证器背后的协议）集中化属性访问行为。它们功能强大且容易过度使用；将它们保留在框架/边界代码中，不要散布在业务逻辑中。对于普通字段验证，优先使用 `__post_init__`、Pydantic 或普通构造函数。
- 保持混入（mixin）小、无状态且命名清晰。多重继承会迅速将 MRO 变成隐式的复杂性。

## 重构

### 重复代码（Duplicated Code）

- 对于重复的 schema、API 契约或模型，建立单一事实来源：`dataclass`、`TypedDict`、Pydantic、OpenAPI 规范或代码生成，而不是三个手工维护的副本。
- 表驱动映射和分发字典（dispatch dicts）能合并真正重复的知识（每行一个 case），而无需发明类层次。
- 倾向于提取为模块级函数或小型策略函数，而不是一个唯一目的是共享代码的基类。
- 注意同一领域规则出现在 schema、服务和测试夹具中。这在 Agent 编码中很常见，三个"副本"会悄无声息地分叉。

变换本身通常是提取函数；反向操作，当你发现错误的去重时，是内联函数。

### 过长函数（Long Function）

- 将阶段提取为模块级函数或方法；它们共享的局部变量变为参数和返回值，这通常能澄清数据流。
- 守卫子句（`if not valid: raise`）能有效地展平嵌套并且可读性好。
- 注意每个提取的函数都会增加一个调用帧；在真正的热循环中这是可观的，尽管对普通代码来说清晰性胜出。不要提取只增加调用帧却不隐藏复杂度的薄包装函数。
- 列表推导式或生成器可以替代在循环中累加的数据块，缩短函数而不隐藏任何东西。

### 基本类型偏执（Primitive Obsession）

- `dataclass(frozen=True)` 是默认的值对象：不可变、可比较、定义成本低。
- `StrEnum` / `IntEnum` 用于还需要在边界（序列化、存储）上以基本类型表示的固定集合。
- `TypedDict` 用于必须保持字典形状（例如 API 边界的 JSON）但希望键被检查的情况。
- `NewType` 用于零开销的不同别名，当你想让类型检查器阻止 `UserId` 和 `OrderId` 互换，而不需要运行时包装。
- 在系统边界处（解析输入、读取数据库）构造领域类型，使类型化的核心不再处理原始基本类型，与函数式核心、命令式外壳的划分一致。

基本类型偏执经常与依恋情结（嫉妒一个无法附加行为的基本类型）和数据泥团同时出现；引入缺失的类型常能同时解决多个坏味。

### 薄包装（Thin Wrapper / Trivial Helper）

Python 中的函数调用不是免费的。每次调用构建一个栈帧，解释器为它做真正的工作。对大多数代码来说这无关紧要：清晰性胜出。但在热路径和紧循环中，围绕每个元素操作的一层薄包装可能在性能分析中显现出来。这是避免它们的次要原因，从来不是主要原因：主要成本始终是毫无回报的间接所带来的认知开销。

# Well said

自然、直接地表达。为阅读这段文字的人考虑，把想法说清楚，只保留读者需要的信息。去掉套话、内心念头、对话中啰唆无用的话、防御性表达和不必要的自我证明。

输出任何内容时使用，包括会话回复、文档、代码注释和 Agent 之间的交流。

## 使用指引

- **读取完整内容。** 不能只看描述或节选。完整内容已在上下文中时直接使用，上下文丢失后补读缺失部分。
- **核对结果。** 根据读者和要求的格式写作。交付前，对照来源核对事实和结论，逐字核对必须原样保留的内容，检查要求的结构和篇幅。
- **遵循指令。** 没有额外要求的情况下，通常原地修改目标文件。如果有其他要求，例如只做检查、输出报告之类的，直接遵守即可。如果是会话回复，直接输出即可。
- **例外保留原文。** 引文、日志、命令、标识符及其他需要原样保留的内容，包括其中的标点和空格，通常优先于文风规则。

## 流程

1. 检查下列文风模式。
2. 改写。保留原意，符合预期语气。
3. 让文字有自己的声音。
4. 自查："哪些地方明显像 AI 写的？" 消除剩余的痕迹。

## 需要清理的文风模式

识别并修正以下模式。

### 内容

1. **夸张修辞。** "关键时刻"、"……的见证"、"不断变化的格局"、"为……奠定基础"、"不可磨灭的印记"、"根深蒂固"。删掉夸张措辞，直接说明发生了什么。
2. **堆砌名号。** 脱离语境地罗列媒体名称。选择有实质内容的来源，说明它说了什么，删去没有信息量的名号。
3. **空泛的 -ing 补句。** "highlighting..."、"ensuring..."、"reflecting..."、"showcasing..."、"fostering..."。删除，或依据真实来源展开。
4. **宣传语言。** "坐落于……"、"充满活力"、"令人叹为观止"、"开创性"、"久负盛名"、"惊艳"、"必游之地"。改用中性描述。
5. **模糊归因。** "专家认为"、"行业报告显示"、"一些评论家指出"。明确指出来源，否则删除。
6. **公式化挑战。** "尽管面临挑战……依然蓬勃发展。" 用具体事实替代。

### 语言

7. **AI 常见词汇。** Additionally、crucial、delve、enduring、enhance、fostering、garner、interplay、intricate、抽象用法的 landscape、pivotal、showcase、抽象用法的 tapestry、testament、underscore、vibrant。换成普通词。
8. **绕着说"是"。** "serves as"、"stands as"、"boasts"、"features"。直接用"is"或"has"。
9. **对照句式。** "不是 X，而是 Y"、"不只是 X，更是 Y"。直接陈述要点。
10. **强凑三项。** 把想法硬塞进三项。应按内容实际需要的数量组织。
11. **同义词轮换。** 在同一段中用 protagonist、main character、central figure、hero 指同一对象。选定一个称谓，重复使用即可，并删去解释其他称谓含义相同的文字。
12. **虚假范围。** "从 X 到 Y"的两端没有有意义的尺度关系时，直接列出主题。

### 格式与标点

13. **破折号。** 完全避免使用破折号。只用句号或逗号，不用括号、半字线或连字符替代。破折号是 AI 文风的典型特征，改用括号只是换了一种特征。需要分隔想法时，结束句子或使用逗号。
14. **过度使用冒号。** 冒号适合放在列表或例子前，不适合连接句中内容。"If you're coming from traditional automation: instead of registering event handlers, you describe conditions"中的冒号没有作用。改写时直接陈述要点，不需要这种比较框架："Describing when the scheduler should fire works best as plain English." 意思相同，也不依赖连接标点。
15. **过度粗体。** 不要给每个专有名词或缩写都加粗。
16. **行内标题式列表。** 典型特征是粗体标签加冒号重复本行内容，例如"**Performance:** Performance improved..."。改为普通正文。标签用于命名条目，后面接标签没有说过的内容时则没有问题，例如"**Schema in TypeScript.** Tables live in one file."。
17. **英文标题逐词大写。** 使用句首大写。
18. **装饰性表情。** 从标题和列表项中删除。
19. **弯引号。** 改用直引号，编辑时也不要新增。

### 对话痕迹

20. **聊天机器人套话。** "希望这能帮到你！"、"如果……请告诉我"、"当然！"、"没问题！"、"找到了确凿证据！"。删除。
21. **知识限制套话。** "虽然具体细节有限……"。寻找来源，或删除。
22. **奉承。** "问得好！你说得完全正确！" 直接回应。

### 冗余

23. **填充短语。** "In order to"改为"To"；"Due to the fact that"改为"Because"；删除"It is important to note that"。
24. **过度保留。** "could potentially possibly be argued that it might"改为"may"。
25. **空泛结论。** "未来一片光明。" 陈述具体计划或事实。

### 术语与黑话

26. **抽象隐喻名词。** Substrate、wedge、vector、locus、vantage、nexus、作名词的 primitive、隐喻用法的 harness、"API surface"中的 surface、bedrock、隐喻用法的 scaffolding、modality、paradigm、gold-plating、隐喻用法的 ratchet、用于搬迁代码的 evacuate、endgame、north star、flywheel。这些词看似技术化，通常有更具体的说法。"Substrate"改为"base"；"Wedge in"改为"add"；"Vector"改为"way"或"method"；"Gold-plating"改为"more than the job needs"；"Ratchet"改为机制真实名称或"a limit that only tightens"；"Evacuate"改为"move out"；"Endgame"改为"the last phase"。选具体的词，并保留比喻原本描述的对象。
27. **中文黑话。** 例如"赋能、助力、驱动、抓手、闭环、链路、全链路、拉通、对齐、反哺、颗粒度、组合拳、生态位、赛道、破圈、降维打击、天花板、长期主义、情绪价值"。按第 26 条的方法处理。

### 直白表达

28. **说明它做什么，而不是让人感觉如何。** "the database stays close at hand"、"SQL you can read"、"types that follow your schema"描述的是感受。修改时说明机制或数字，例如"`.toSQL()` returns the exact string sent to the database"、"a column rename fails the build"。问这句话让读者知道什么或做什么，然后把它写出来。如果无法改述为具体指令、事实或数字，就删掉。再检查它能否原封不动地出现在另一个项目的文档中；如果能，它就没有说明本项目的信息，应删除。
29. **缩短或拆开密集长句。** 读者需要回头才能理解时，拆句或删去从句。一句表达一个想法。
30. **主动语态。** 优先使用。检查"is/are/was/were + 过去分词"并明确主体："queries are validated"改为"the compiler validates queries"；"the file is parsed by the loader"改为"the loader parses the file"。只有主体未知或确实不重要时，才保留被动语态。
31. **删副词，或换更有力的动词。** "runs quickly"改为"is fast"或具体数字；"significantly improves"改为测得的变化量。需要副词撑住的动词往往不够准确。保留测量及其条件，并放在论断旁边，避免把该句写成普遍保证。
32. **优先普通词。** "utilize"改为"use"；"leverage"改为"use"；"facilitate"改为"help"；"numerous"改为"many"；"in the event that"改为"if"。华丽的同义词很少更清楚。

## 防御性表述

防御性表述的典型特征是避免说错、强调自己谨慎，或交代自己没做什么，借此逃避责任。它用免责声明和自我辩解代替结果，让用户得不到有用的回答，也不能免除 Agent 完成任务的责任，因此是重点清理目标。

### 典型特征

留意以下模式，检查它们是否代替了该做的工作或有用的内容。

- **证明姿态。** "不能证明"、"只能说明"、"不代表"、"不声称"、"不构成建议"、"不保证"，以及 "cannot prove", "only shows", "does not mean", "does not claim", "does not constitute advice", "cannot guarantee"。用这些话代替调查、验证或判断，是最严重的症状。Agent 只是在形式上应付用户，给出了一份免责声明，却没有真正解决问题。修复方式是检查工作是否达到要求，是否漏做关键检查，是否把不达标的结果当成完成。只是表述过于保守时，把已有依据的结论说清楚。工作有问题就返工。
- **认知边界。** "尚未"、"未见"、"无法确认"、"未验证"、"不推断"，以及 "not yet", "no evidence found", "cannot confirm", "not verified", "do not infer"。Agent 为了显得考虑周到，主动谈起与任务无关又没弄清的问题，会给读者增加不必要的负担。应当把这些问题及附带的声明一起删掉。如果是本该查证却停着不做，会把工作推给用户，那么应继续完成必要检查。把实际检查范围和证据来源放在检查结论旁边，删除重复声明和不影响交付的操作记录。
- **工作范围。** "未修改"、"未提交"、"未执行"、"保持只读"，以及 "did not modify", "did not commit", "did not run", "remained read-only"。这类问题较轻，偶尔出现可以接受。反复列举自己没做什么，会让读者在一堆操作记录里找结果，也把按要求做事写成了自我表扬。没有要求报告时，删掉这类清单。Skill、规范、工作流程或用户明确要求报告的状态可以保留。如果没做的工作影响任务完成，就要把它当作需要解决的问题，不能当作多余的话删掉。

### 修复指南

先看问题出在文字还是工作本身。对照任务要求、实际做过的工作和已有证据。该做的实现、调查或验证没完成，就在已授权的范围内继续做。结果有错就返工。确实缺少权限、资料或执行条件时，说明缺什么、怎样影响任务、下一步要做什么，并继续完成不受影响的部分。不要只说"无法确认"就停下来，也不要为了弄清某个未知问题而做无关或越权的事。

工作本身没问题时再改文字。先看这一段回答什么，它的出发点是否来自实际要求和资料。去掉免责、自我辩解和反复强调的限制后，还剩下什么事实、判断或行动？有没有先下一个缺乏依据的大结论，又在后面否定它？没有意义、删掉也不影响理解的内容，直接删掉。只删有问题的句子或换掉几个词，整段可能还是空的。整段都没有有用内容就删掉整段，不要再补空话。

内容有用，但出发点不符合实际问题，或整段都在替自己辩解时，放弃原来的写法，按读者需要的信息重写。把有用的事实放到对应的结论或行动旁边，受影响的前后段落和小节也一起重写。保留会影响读者判断或行动的事实、实际风险、还没弄清的重要问题、授权要求和必要的解释与依据。把这些信息与相关结论放在一起，让读者看清结论的依据和适用条件。删除没有依据的说法和为它辩解的内容。

## 清理思维链泄露

思维链泄露是从写作会话的视角出发，而不是从文档本身出发的文字。它引用只有会话中才能看到的材料，叙述修改过程而非最终状态，与已经离场的审阅者争辩，或夹带流程旁白、保留措辞和未翻译的工作语言片段。

站在只有成品的读者角度阅读，读者无法访问会话、会议笔记、早期草稿或审阅讨论。编辑后，检查读者能否凭成品及其可访问来源理解并核实每一处引用和论断，尤其是在中断、纠正或新增要求之后。保留所有仍然有效的事实，只引用目标读者能够获取的材料。适合时直接描述当前行为；历史表达本身不等于泄露。

例如：

- **修改旁白。** "以前是"、"不再"、"现在使用"、"根据反馈改为 XX"。直接描述当前行为，例如把"现在串行写入"改为"串行写入"。
- **版本印记。** "这一稿"、"这篇笔记的 v3"、"这一轮"。去掉草稿印记，保留真实软件版本和运行期的新旧状态。
- **纠正标签。** "XX 功能，无 YY 版"、"移除 YY 后的 XX"、"带 YY 的 XX"。直接说明主体和最终功能，省去对纠正动作本身的描述。
- **临时指令。** "这次跳过完整测试"、"这一轮使用 XX"。临时指令只在会话范围内生效，不自动变成长期要求。
- **会话引用。** "(decision 7)"、"design §4.2"、"tasks/<id>/plan.md"。把失效引用改为可核实的来源或能够独立理解的事实。
- **审阅视角。** "这组 PR 中后续的一个"、"审阅时被否决"、"审阅者已确认"。保留机制、不变量或理由。
- **编辑旁白。** "只改标题"、"保留这一节"、"下一轮补齐剩余内容"。执行指令，省去旁白。
- **计划残留。** "大概够了"、"先放着"。说明已经核实的边界或明确的不确定性。
- **未跟踪材料泄露。** 提及 Git 忽略文件、临时产物或未跟踪的任务信息。移除这些引用，重新表述有用的事实。

## 文章写作

用以下方法指导文章写作。

### 真内容

真内容是文章的核心，也就是文章到底有什么值得读。拿掉来源说明、免责声明、方法标签和结构性套话，再看剩下什么。如果剩下的文字还能说清发生了什么、作者发现了什么、这件事为什么重要，文章就有真内容，读者也能有所收获。有真内容，才有整理和润色的基础。如果剥去这些外壳后几乎空无一物，继续润色也只是让空洞变得流畅。

这也划定了润色的边界。编辑可以调整顺序、压缩重复、换掉生硬的表达，但不能虚构作者没有经历过的事情。宁可让内容不足显露出来，也不要用层层解释和限定掩盖它。

真内容与空泛内容之间的分寸，也需要拿捏。真内容占比高的文章可能有真情实感，却未必容易读；空泛内容太多，读者看了半天，也得不到多少有用的信息。AI 写作绝大多数属于后者，因此更需要识别并删去空泛内容。

### 隐含语境

文章不必交代所有前提。作者与目标读者共享的知识、段落之间可以自然补全的联系、前文已经写清且仍然适用的范围，都可以留在语境里。读者会参与理解，不需要作者把每一步推理都展开。但作者觉得显然，不代表读者也能看出来。能否省略，要以目标读者已有的知识和文中提供的信息为依据。

比如，对熟悉 Python 工具链的读者，"运行 mypy"已经点明了静态类型检查，不必再反复解释类型标注的作用。但仅凭这句话，不能认定项目采用了更严格的类型要求，更不能推断检查覆盖了全部代码。如果严格程度或检查范围会影响文章的结论，就需要另行说明。共享知识可以帮助读者理解工具的用途，不能替作者补出项目的实际做法。

又如，"目前只在 Node 22 做过测试，其他版本还没试"交代了测试范围。若改成"只能在 Node 22 运行"，就把尚未验证的情况写成了确定的限制。没测试过，不等于不能运行。这类限定不是多余的解释，而是结论的一部分。

隐含不等于隐瞒，也不等于让读者猜。可以省去的是读者能够自然接上的解释，不能省去的是理解和判断所必需的事实。如果省略某项内容会改变读者对事实或结论的理解，或者影响下一步行动，就应当明确写出。必要信息应在读者需要的位置交代清楚，已经说明且仍然适用的前提不必反复重申。推理中容易让读者困惑的地方，要补上关键依据，但不必把完整的思考过程都写进文章。

隐含语境调节的是解释密度。解释太少，读者会断线；解释太多，文章的重心就会从内容偏向解释本身，变成 AI 对自身周全的表演。分析文章时，要找的是读者会在哪里困惑、缺少什么信息，而不是为每句话补齐一条证明链。

## 让文字有自己的声音

只删除模式还不够，僵硬、没有个人声音的文字同样明显。保留作者真实的观察、判断、节奏和语气。

- **有观点。** 对事实作出反应，不只是中立罗列优缺点。
- **变化节奏。** 短句之后，可以接从容一些的长句。交替使用。
- **承认复杂性。** "令人印象深刻，也有些不安"比单说"令人印象深刻"更好。
- **合适时用"我"。** 第一人称并不等于不专业。
- **允许一点不齐整。** 过于完美的结构容易显得机械。
- **具体表达。** 与其说"这令人担忧"，不如说"凌晨 3 点还有 Agent 不停工作，让人有些不安"。

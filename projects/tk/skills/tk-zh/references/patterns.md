# 使用模式

以下模式说明如何把普通材料放进任务目录。它们不是 tk 的受管格式。应按实际工作创建文件，不要为了匹配示例预建空目录或占位文档。

## 草稿区

需要随手记录临时内容时，在任务目录中创建 `scratchpad/`：

```text
<task>/
└── scratchpad/
```

`scratchpad/` 内可以放任意文件或子目录，例如临时笔记、命令输出、待整理片段、截图或小脚本。tk 不规定文件名、格式和层级。

草稿区只解决“先放下来”的问题。内容稳定后，将仍有价值的结论整理到合适的普通材料或 `TASK.md`；失效草稿直接删除，避免后续把旧推测当成当前事实。

## 深度调研

下面只是一种可能的目录，不是需要照抄的模板：

```text
research/
├── question.md
├── sources/
├── evidence.md
└── report.md
```

实际结构取决于调研问题、来源类型和交付物。只有一个结论时，一个 Markdown 文件就够了；需要保存原始数据、来源摘录或多轮分析时，再增加相应文件。不要创建没有内容的 `sources/`、`evidence.md` 或 `report.md`。

一份可复核的调研材料通常需要说明：

- 要回答的问题；
- 事实来源和访问时间；
- 能够由证据支持的结论；
- 仍不能确认的部分。

## 实验

下面也只是示例：

```text
experiment/
├── setup.md
├── inputs/
├── runs/
└── result.md
```

按实验本身保存必要材料。一次短命令验证可以只记录命令、环境和输出；涉及样本、脚本或多次运行时，再拆分目录。不要机械复制示例层级。

实验记录至少应让后来者判断：运行了什么、使用了什么输入、观察到什么结果、结论适用于哪些条件。若结果不可复现，应明确缺少的环境、数据或外部依赖。

## 迭代设计

设计工作可以把稳定约束、候选方案和验证结果分开保存。例如：

```text
design/
├── constraints.md
├── options.md
└── verification.md
```

文件数量应跟着实际复杂度增长。没有多个候选方案时，不需要创建 `options.md`；只有一页能说清时，也不需要目录。

`TASK.md` 保留当前目标、已生效决定、重要材料入口和仍有效阻塞。被替代的方案留在普通材料中，且应清楚标为未采用或已失效，避免污染当前状态。

## 决策记录

项目已有 ADR、RFC 或其他正式决策体系时，任务材料可以保存提案草稿、证据和讨论结果，正式决定仍进入项目规定的位置。任务目录不替代项目的决策机制。

记录设计决定时，至少写清：

- 当前决定；
- 促成决定的约束和证据；
- 受影响的行为或接口；
- 尚未解决的问题。

不要把只对当前会话有意义的修改过程、被纠正的旧说法或 Agent 工作记录写进正式决定。

## 材料入口

普通材料可以采用任意格式和目录结构，但重要入口应从 `TASK.md` 链接。链接文字说明材料内容，不要只写“详见这里”。

例如：

```markdown
## 重要材料

- CLI 行为核对：`research/cli-behavior.md`
- 实验结果：`experiment/result.md`
```

WAL 记录发生过什么，普通材料承载可复用内容，`TASK.md` 只保留当前状态。三者不要互相复制整段内容。

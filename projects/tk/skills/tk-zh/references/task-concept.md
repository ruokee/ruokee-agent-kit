# 任务概念

任务身份、路径、内容、关系或生命周期不清楚时阅读本文。日常创建、更新和文件维护规则以 Skill 正文为准。

## 任务模型

### 身份与路径

UUIDv7 是任务的稳定身份。名称和目录用于识别，可以通过 `rename` 改变，不是身份。

顶层任务默认位于：

```text
<task_root>/YYYY/MM/DD-NN--slug/
```

新子任务默认位于父任务目录下配置的 `subtasks_dir`，并使用 `NN--slug` 目录名。`subtasks_dir` 只控制创建位置；发现会根据有效载体识别父任务目录内其他位置的子任务。详细规则见[子任务](./subtask.md)。

名称使用 NFKC 规范化，限制字符，并且最多占 32 个终端显示列。显示列不是 Unicode 字符数。创建或重命名必须使用运行时校验，不自行计算 slug。

### 内容组成

任务目录包含四类内容：

- 受管元数据：身份、名称、状态、时间、关系、schema 版本和 `extra`；
- `TASK.md` 正文：当前目标、范围、约束、稳定决定、重要材料入口和仍有效阻塞；
- WAL：`wal/YYYY-MM-DD.md` 中由运行时追加的活动记录；
- 普通材料：除受管载体和 WAL 外的任意内容，可以使用任何适合工作的文件格式和目录结构。

运行时管理受管元数据和 WAL。Agent 可以维护 `TASK.md` 正文和普通材料，但不能绕过运行时手工改写受管字段，也不能编辑、删除或重排已有 WAL 条目。

WAL 记录已发生的持久事件，例如决定、纠正、可恢复里程碑、验证结果、协作结果和阻塞。它是追加历史，不是当前状态摘要。正文只保留仍有效的信息；较长且可复用的内容放入普通材料，再从正文链接入口。

普通材料不受 tk schema 管理，也不进入任务索引。它可以是文档、代码、数据、图片、命令输出或其他文件。不要使用受管名称 `tk.toml`、`TASK.md` 或 `wal/` 存放普通材料。

### 受管字段

| 字段 | 规则 |
| --- | --- |
| `id` | 必填 UUIDv7，创建后不变 |
| `name` | 必填，只通过 `rename` 修改 |
| `status` | `planning`、`open` 或 `closed` |
| `created_at` | 带时区 RFC 3339，创建后不变 |
| `depends_on` | 同一任务根目录内的 UUID 集合 |
| `related_to` | 同一任务根目录内的 UUID 集合 |
| `extra` | 结构化附加值，按顶层键修改 |
| `schema_version` | 当前受支持的 schema 版本 |

`parent`、关闭原因、历史名称、`actor` 和会话绑定不属于受管字段。父子关系来自目录包含关系，生命周期原因进入 WAL。

### 元数据载体

`split` 模式使用两个文件：

```text
<任务目录>/tk.toml
<任务目录>/TASK.md
```

`tk.toml` 只保存受管元数据，`TASK.md` 只保存正文。

`embed` 模式使用 `TASK.md` 顶部严格的 tk YAML frontmatter 保存受管元数据，frontmatter 之后是正文。缺失、重复、未知字段、错误类型或非规范顺序都可能使载体无效。

项目配置的 `metadata_mode` 必须与磁盘载体一致。不能手工把一种载体改成另一种。项目级转换见[项目和存储](./project-storage.md)。

### 创建输入

顶层创建至少需要名称。tk 运行时在创建 Task 时自动生成 `# <规范化名称>` 作为初始正文。状态默认是 `open`，时间默认是当前时间，关系和 `extra` 默认空。

只有导入历史任务且原始带时区时间戳可靠时，才显式传入 `created_at`。关系目标必须已经存在于同一任务根目录。任务不能引用自身，依赖不能形成环。

## 定位

### 精确引用

精确引用只接受完整 UUIDv7、绝对任务目录、绝对受管载体路径或项目相对任务路径。精确操作不根据模糊名称猜测目标。

完整绝对任务路径或材料路径可以反向定位所属项目，不要求它属于当前工作目录发现的项目。

### 搜索输入

名称、目录基名、UUID 前缀、文本、正则和材料路径是搜索输入。搜索先确定查询类型，不在一种解释失败后自动改用另一种解释。结果按匹配类型、创建时间和 ID 稳定排序。

搜索可以返回零个、一个或多个候选。需要更新、关闭、重命名或追加日志时，调用方应先选定唯一任务。

## 生命周期

### 状态

| 状态 | 含义 |
| --- | --- |
| `planning` | 用户明确希望保存，但仍在形成的想法、调查或计划 |
| `open` | 正在实际处理的工作 |
| `closed` | 工作已经结束，包括完成、放弃、不可行或被替代 |

状态表达事实，不表示优先级。

### 状态转换

允许的转换是：

- `planning` 到 `open`；
- `planning` 到 `closed`；
- `open` 到 `closed`；
- `closed` 到 `open`。

`start` 把 `planning` 改为 `open`。对已经 `open` 的任务重复 `start` 返回无变化。`closed` 任务不能通过 `start` 打开，只能通过 `reopen`。

### 关闭

普通关闭要求：

- 目标尚未 `closed`；
- 所有后代任务都已 `closed`；
- 所有 `depends_on` 目标都已 `closed`；
- 原因非空；
- 已取得本次关闭的真实确认。

存在阻塞时，运行时返回具体后代或依赖，不自动关闭它们。

`force` 只跳过后代和依赖检查。它不关闭这些任务，也不绕过授权、原因、schema、路径、Git、关系或 `closed` 祖先规则。

### 重开

`reopen` 需要非空原因和本次操作的真实确认。存在 `closed` 祖先时拒绝，因为重开会把活动工作藏在关闭树下。

新工作通常创建一个 `related_to` 原任务的打开任务。只有用户确认工作仍属于原任务时才重开。

### `closed` 状态限制

`closed` 任务允许 `read`、`search` 和 `check`。普通元数据修改、追加 WAL、`rename` 和创建子任务都会拒绝。

关闭和重开由运行时写入 WAL。不要再追加内容相同的人工日志。

## 关系

### 依赖

`depends_on` 表示目标任务必须先结束。它是有向关系，不能成环。关闭任务前，所有依赖目标必须已经 `closed`。

### 关联

`related_to` 只表示任务有关联。它不是自动对称关系；写入 A 指向 B 不会自动修改 B。

### 关系约束

两种关系都只能引用同一任务根目录中的 UUID，不能引用任务自身，并按 UUID 去重排序。

修改关系时使用增量操作，不通过重写整个集合猜测并发状态。目标不存在、跨任务根、自引用或形成依赖环时，运行时拒绝整个请求。

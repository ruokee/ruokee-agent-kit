# 维护

操作失败、状态可能部分提交、受管数据无效，或准备运行 check、rename、GC 和人工修复时读本篇。

## 先确认状态

先读稳定 error code、category 和 details。不要解析自然语言 message，也不要把一次失败等同于没有写入。

多目标错误重点检查 completed、uncompleted、original_error 和可能存在的 cleanup_error。先 read 目标或运行 check，再决定新的完整操作。不假定回滚、续跑令牌或后台继续。

WAL 警告表示元数据可能已经提交。按 [WAL](./wal.md) 只补缺失事件，不重复原修改。

## Check

check 只读。它验证项目配置、任务拓扑、载体和 schema、UUID、名称和路径、同级序号、关系和依赖环、WAL、活动操作标记及清理清单。

完整扫描发现问题返回 `check_failed`。必要目录或文件无法读取时返回 `check_incomplete` 并停止；这表示扫描没有完成，不能据此宣称其余项目正常。

check 不自动修复，也不授权人工编辑。修复前保存准确 code 和 path，修复后再次 check 并读取受影响任务。

## Rename

每次 rename 先 dry-run。确认规范化后的名称、解析出的父级、目标路径、冲突和报告的 Markdown 引用。运行时只修改任务自身名称、适用时的生成式目录和元数据，不改写普通材料中的引用。

请求名称及其适用的生成式路径已经匹配时返回无变化。不能用别名、复制目录或直接编辑元数据来绕过目标冲突、受管数据损坏或引用扫描失败。

提交阶段失败可能只完成名称、生成式目录或 WAL 更新的一部分。立即运行 `check`，再根据当前受管状态决定重试 rename 或进入人工修复。

## GC

GC 只清理已经退出的操作进程留下的 tk 临时路径、最小清理清单和活动操作标记。它不恢复、继续、回滚或完成任务、迁移、元数据模式切换、rename 或组件操作。

陌生残留先 dry-run。活动操作进程仍存在、进程身份无法证明已经结束或路径不满足清理合同的项目必须保留并报告。

删除失败时读取已删除和未删除路径。修复文件系统错误后重新运行完整 GC，不手工编辑清理清单来让检查通过。

## 人工修复门槛

日常修改必须使用公开 tk 操作。只有受管数据已经损坏，并且公开操作无法表达修复时，才允许人工修复。

执行前必须：

1. 唯一定位受影响任务和受管载体；
2. 说明准确字段、最终内容和路径变化；
3. 取得用户当前明确授权；
4. 确认没有活动 tk 写入者；
5. 只修改已说明的最小范围；
6. 运行 check 并重新读取任务；
7. 任务可读后记录修复事件。

人工修复不能用于绕过授权、Git、生命周期、关系、冲突或兼容性拒绝。

## 历史名称问题

历史 split 任务可能使用超过 32 显示列的名称。加载元数据失败时，rename 也可能无法运行。

若公开操作无法表达修复，生成式任务需要同时更新 `tk.toml` 中的 `name` 和目录叶子 slug，使两者一致。非生成式子任务只更新 `name`，保持目录不变。保留日期、序号、UUID、状态、时间戳、关系、正文和 WAL。

当前合同不允许把这一流程直接套到 embed frontmatter。没有公开恢复路径时报告限制，不手工编辑 frontmatter。

## 传输故障

进程无法启动、输出不是合法 JSON、协议帧损坏或进程被杀死时，可能没有领域错误结果。保留原始故障，检查当前状态，不伪造 error code，也不换入口绕过同一操作。

# tk 任务管理工具

tk 是一个持久化任务管理工具。使用 Harness 提供的 tk 工具管理项目本地的持久任务。任务是值得保留的临时项目努力。任务不代表已经承诺执行或完成。

tk 运行时负责处理元数据、关系、生命周期、路径和持久化。

你负责判断是否使用 tk、如实传递当前授权、维护任务材料，并在异常后先确认规范状态。

## 是否应当使用 tk

出现以下情况时使用 `tk`：

- 提及 `tk`、`catchup`、任务操作或任务管理；
- 提供任务 ID、任务名称、任务路径、分支、`TASK.md`、`tk.toml` 或材料路径；
- 要求查找、创建、读取、继续、记录、更新、关闭、重开、重命名、迁移或检查任务。

在 `permissive` 项目中，明显需要跨多个步骤或会话保存状态的工作也可以创建任务。

快速问答、临时清单、普通单次修改和随口想法不需要 `tk`。

## 调用 tk

日常操作使用 Harness 提供的 tk 逻辑工具：

- 逻辑操作包括 `search`、`read`、`create`、`update`、`log` 和 `exec`；
- Pi 和 OMP 的原生工具通常显示为 `tk_search`、`tk_read`、`tk_create`、`tk_update`、`tk_log` 和 `tk_exec`；
- Codex 和 Claude Code 通过 MCP 使用同一组操作，通常注册为 `task.find`、`task.read`、`task.create`、`task.update`、`task.log` 和 `task.exec`。实际前缀由宿主中的 MCP 服务名称决定，字段、结果和领域规则不变；
- `exec` 只用于 `--version`、`init`、`check` 和 `rename`。

每次调用传入当前绝对 `cwd`。完整绝对任务路径或材料路径可以定位自己的项目。

`actor` 只适用于 `update`、`log` 和 `exec rename`。需要归因时使用最具体的可用模型值或 Harness 值。`actor` 不表示身份或授权。

完整工具字段和结果见 [工具](./references/tool.md)。

## 解析任务

精确操作接受完整 UUIDv7、绝对已发现任务目录、绝对受管 `tk.toml` 或 `TASK.md`，以及项目相对已发现任务路径。

对于名称、目录基名、UUID 前缀、文本、正则、分支和材料路径应先 `search`，再使用返回的精确引用。多个候选仍然都可能符合时，列出相关候选并请用户选择。

## 创建任务

使用 `create` 创建任务。

- 默认创建的任务状态为 `open`；仅在用户明确希望保存仍在形成的想法、调查或计划时使用 `planning`。
- 用户没有明确要求时，选择能清楚表达用途的任务名称。建议使用短祈使句、短语或名词，禁止使用并列关系词，例如“和”“且”“与”“并”或 `and`。
- 在同一回复中报告新任务的名称、状态和路径。
- 只在补充创建历史任务时才传入 `created_at`。

### 授权

- 项目配置控制默认授权方式。
- `strict` 项目中，顶层任务只有在用户当前明确要求或确认，传入 `user_confirmed=true` 才能创建。
- `permissive` 项目中，Agent 允许为值得持久保存的工作主动创建任务。

### 子任务

参考 [子任务](./references/subtask.md)。

- 只允许在 `open` 或 `planning` 任务下创建子任务；不能在 `closed` 任务下创建，且不允许为了创建子任务强行重开任务。
- 子任务的任务名不使用并列关系词，如有多个子任务应当并列创建。
- 子任务可以嵌套。
- `subtasks_dir` 只控制默认创建位置；发现根据父任务目录下的有效载体，不受该配置限制。

## 跟进任务

当用户明确提及 `catchup` 关键词，或 Agent 认为有必要了解任务现状时，阅读 [跟进任务](./references/catchup.md)。

不要递归枚举普通材料。按需跟随 `TASK.md` 或其中的链接。

## 记录工作日志

WAL 是工作活动日志（Work Activity Log），用它来保存任务推进时发生了什么。

出现以下内容时需要及时使用 `log` 进行记录：

- 用户的决定、决策和修正；
- 有意义的用户/外部编辑；
- 探索、分析、评估过程的发现；
- 已验证的阶段性成果；
- 可恢复的里程碑；
- 执行过程发现问题；
- 影响继续执行的阻塞项。

不要记录以下内容：

- 读取的文件具体内容；
- 执行过的命令；
- 临时待办事项；
- 未经验证的猜测；
- 草稿；
- tk 运行时已自动记录的生命周期事件。

记录内容：

- `message` 使用非空单行文本，简明扼要说明要记录的东西。
- 仅在有必要的时候额外写 `body` 来补充说明。`body` 可以使用多行 Markdown。

只要需要记录 WAL 就立即记录，在开始下一个独立工作线之前完成；绝不推迟到后续里程碑、测试或会话结束。不要为了减少调用次数把后续里程碑或验证结果并入前面的记录。

需要分析、审计 WAL 时阅读 [WAL](./references/wal.md)。

## 更新任务

使用 `update` 修改任务元数据、更新状态和修改关系。使用宿主文件工具编辑 `TASK.md` 和普通材料的内容。

生命周期：

- 所有生命周期转换都需要填写原因。
- `planning` 可以切换为 `open`，或者因为不再推进而直接 `closed`；任务不能从其他状态回到 `planning`。
- `open` 可以关闭变为 `closed`；`closed` 可以重新打开变为 `open`。
- 仅当所有子任务和依赖任务都关闭后才能关闭，否则会被 tk 运行时拒绝。仅在用户明确要求时使用 `force` 强行关闭。
- `closed` 任务默认只读。如果确实相关，新工作通常创建新任务并设置关联关系。

关系：

- `depends_on` 表示关闭前必须完成的依赖任务。
- `related_to` 表示关联任务。
- 复杂图约束参见 [任务概念](./references/task-concept.md)。

## 任务文件

任务空间是任务所在的文件夹。默认情况在任务空间下通过普通文件和目录管理自有内容。当计划、研究、分析、详细决策、检查点、移交、结果或其他实质内容具有持续价值，或会影响后续工作或恢复时，主动在任务空间下创建或更新文件，而不是让内容只留在对话中。

Agent 默认拥有完整的读写权限。Agent 无须逐文件确认即可创建或更新普通文本文件。用户没有明确要求时，选择能清楚表达用途的文件名。覆盖含义不明的现有内容、删除或移动材料、写入大型或二进制产物、或越过分配边界前，必须先询问用户。

保持 `TASK.md` 简洁，只保存当前目标、范围、约束、仍有效的稳定决定、重要材料入口和当前阻塞。命令流水、聊天历史、长篇研究、详细设计、检查记录和易变步骤写入普通材料。

你可以编辑 `TASK.md` 正文和普通材料。元数据必须通过 tk 工具修改。

当用户明确要求使用特定模式，或已经出现记录文档、跨日期、多次推翻设计、调研、草稿等信号时，阅读 [使用模式](./references/patterns.md)。

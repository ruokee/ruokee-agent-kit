# 维护

操作失败、状态可能部分提交、受管数据无效，或准备运行 check、rename、GC 和人工修复时读本篇。

## 先确认状态

先读稳定 error code、category 和 details。不要解析自然语言 message，也不要把一次失败等同于没有写入。

多目标错误重点检查 completed、uncompleted、original_error 和可能存在的 cleanup_error。先 read 目标或运行 check，再决定新的完整操作。不假定回滚、续跑令牌或后台继续。

WAL 警告表示元数据可能已经提交。按 [WAL](./wal.md) 只补缺失事件，不重复原修改。

## Check

check 只读。它验证项目配置、任务拓扑、载体和 schema、UUID、名称和路径、同级序号、关系和依赖环、WAL、活动操作标记及清理清单。

完整扫描发现问题返回 `check_failed`。必要目录或文件无法读取时返回 `check_incomplete` 并停止；这表示扫描没有完成，不能据此宣称其余项目正常。

check 不自动修复，也不授权人工编辑。修复前保存准确 code 和 path，修复后再次 check 并读取受影响任务。

## Rename

每次 rename 先 dry-run，再打开 `report_path`。确认原始旧名称、规范化新名称、任务映射和引用。rename 修复符合范围的无效、为空或实际过宽的字符串名称，以及可识别生成式后缀缺陷。[任务概念](./task-concept.md)所述合法排版差异不需要修复。即使源排版合法，显式 rename 仍达到规范化名称和适用路径。

引用默认保留原文。使用 `--update-references` 显式改写，使用 `--extend-scan` 添加 Markdown 文件或目录。

请求名称及其适用的生成式路径已经匹配时返回无变化。不能用别名、复制目录或直接编辑元数据绕过目标冲突、名称修复范围外的损坏或引用扫描失败。

提交阶段失败可能只完成名称、生成式目录或 WAL 更新的一部分。立即运行 `check`，再根据当前受管状态决定重试 rename 或进入人工修复。

## 引用

rename 和布局命令默认扫描当前任务根。`git_policy=track` 时扫描项目 Markdown 及其他已知任务根。WAL、`.git` 和 `.tk-tmp` 排除，符号链接保持既有跳过规则。必要 I/O 失败及资源上限显式停止规划。embed 只扫描正文。

使用可重复的 `--exclude-scan <path>` 从引用扫描及提交前复查中排除字面文件或目录子树。相对路径从项目根解析，绝对路径可以覆盖外部扩展根。路径按词法归一、排序和去重，允许尚不存在及扫描范围外的排除项。匹配采用完整路径组件，排除优先于默认及扩展输入，在检查或读取被排除目标前生效。其他输入沿用既有失败规则。该选项只控制引用扫描。任务发现及受管变更保持各自规则。被排除的引用保留原文。

显式更新覆盖 Markdown 链接、图片、定义、包含真实任务根路径的完整路径双链和完整路径文本。标签、标题、别名、query、fragment 及编辑区间外字节保留。仅文件名双链保持原文。相对链接根据源文件移动后的父目录及目标移动后的路径计算。子树内链接仍正确时保持原文。

打开 `<task_root>/.tk-tmp/reports` 下的不可变 JSON 报告，读取完整任务映射、引用、扫描范围和诊断。dry-run、无变化及有效项目中的规划失败也保存报告。`scan_complete=false` 标识扫描中断或失败。报告存储失败停止受管写入。报告是扫描快照。执行完成情况由摘要及错误表达。

存在显式排除时，`excluded_paths` 记录其归一后的绝对路径，业务规划失败也保留。没有排除参数时省略该字段。结合 `scan_roots` 减去内置及显式排除后的范围理解 `scan_complete`，整个范围都被排除时也可以完整。批准引用更新前先核对该范围。

## 布局失败

读取错误中的 `completed`、`uncompleted`、`original_error`、`report_path` 和配置状态。布局按目录移动、可选引用替换、最终 switch 配置的顺序提交。migrate 保留配置。rename 按移动、引用、元数据、WAL 的顺序提交。受管写入前复检待改引用、载体、目标和配置。

部分 switch 在最终配置写入前保留源布局配置。已经移动的任务可能暂时从普通读取中消失。解决报告中的阻塞后，为剩余源目录重新规划。此前移动的引用通过前次报告核对。每次调用保存新报告。运行时不自动回滚。

## GC

GC 只清理已经退出的操作进程留下的 tk 临时路径、最小清理清单和活动操作标记。它不恢复、继续、回滚或完成任务、迁移、元数据模式切换、rename 或组件操作。

项目级真实 `.tk-tmp/reports` 目录保留。用户级组件临时目录保持既有清理语义。

陌生残留先 dry-run。活动操作进程仍存在、进程身份无法证明已经结束或路径不满足清理合同的项目必须保留并报告。

删除失败时读取已删除和未删除路径。修复文件系统错误后重新运行完整 GC，不手工编辑清理清单来让检查通过。

## 人工修复门槛

日常修改必须使用公开 tk 操作。只有受管数据已经损坏，并且公开操作无法表达修复时，才允许人工修复。

执行前必须：

1. 唯一定位受影响任务和受管载体；
2. 说明准确字段、最终内容和路径变化；
3. 取得用户当前明确授权；
4. 确认没有活动 tk 写入者；
5. 只修改已说明的最小范围；
6. 运行 check 并重新读取任务；
7. 任务可读后记录修复事件。

人工修复不能用于绕过授权、Git、生命周期、关系、冲突或兼容性拒绝。

## 名称修复

split 和 embed 中符合范围的旧名称损坏，可使用完整 UUID、精确任务目录或精确受管载体调用 `tk rename`。名称修复不容许名称缺失或类型错误、载体不可解析、标记缺失、schema 不受支持、身份损坏、不安全路径、关系或 `extra` 无效，以及无法识别的生成式目录结构。

修复后运行 `tk check` 并读取任务。只有损坏仍在公开操作范围外时，才进入人工修复。

## 进程故障

进程无法启动、输出不是合法 JSON 或进程被杀死时，可能没有领域错误结果。保留原始故障，检查当前状态，不伪造 error code。

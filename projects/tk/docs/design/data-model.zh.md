# 数据模型

[English](./data-model.md)

## 项目配置

项目配置位于 `.agents/tk_config.toml`。配置是相对默认值的稀疏 TOML：

```toml
task_root = ".tk"
subtasks_dir = ""
git_policy = "none"
creation_policy = "strict"
metadata_mode = "split"
task_layout = "monthly"
```

默认值不会写入配置文件。全部使用默认值时可以不存在配置文件。

- `task_root` 是项目相对路径，默认为 `.tk`。
- `subtasks_dir` 是每个父任务下新建子任务的可选默认相对目录，不限制发现范围。
- `git_policy` 为 `track`、`ignore` 或 `none`。
- `creation_policy` 为 `strict` 或 `permissive`。
- `metadata_mode` 为 `split` 或 `embed`，作用于整个项目。
- `task_layout` 为 `monthly` 或 `daily`，选择普通顶层发现布局，默认为 `monthly`。

`init --force` 可以忽略无法解析的旧项目配置，使用本次显式参数和默认值写入新的稀疏配置。它不读取、迁移、移动、删除或改写任务数据，也不处理单个任务的 `tk.toml`。

## 任务目录

顶层任务使用配置选中的布局：

```text
monthly: <task-root>/YYYY/MM/DD-NN--slug/
daily:   <task-root>/YYYY/MM/DD/NN-slug/
```

新建子任务使用稳定的 `NN--slug` 目录，直接位于父任务下或配置的 `subtasks_dir` 下。已有子任务可以位于更深的普通材料目录下。最近的有效祖先任务定义父级，因此目录拓扑仍表示父子关系，元数据不保存 `parent`。

任务根目录没有永久索引或缓存。发现过程按需从文件系统构建一份内存任务图，所有全项目调用方都使用这份图。

两种布局都按日历日期分配两位序号，从已发现的最大序号继续分配，保留空缺。同日序号 `99` 已存在时停止创建。布局转换保留日期、序号、原 slug、UUID、元数据、子树和 WAL。

## 元数据 schema

当前初始 schema 版本是 1。元数据只包含：

- `schema_version`：必填正整数。
- `id`：必填 UUIDv7，创建后不可变。
- `name`：必填、符合任务名称规则的名称，只有 rename 可修改。
- `status`：`planning`、`open` 或 `closed`。
- `created_at`：必填、带时区的 RFC 3339 时间戳，创建后不可变。
- `depends_on`：同一任务根目录内的 UUID 集合。
- `related_to`：同一任务根目录内的 UUID 集合。
- `extra`：可选、可在 JSON 与 TOML 间无损表示的结构化值。

schema 不包含 `parent`、`branch`、`updated_at`、最后关闭原因、`paused`、`archived`、安装时间或会话状态。

未知字段、错误类型、缺失版本和不支持的版本均无效。普通内容即使看起来像任务元数据，也不会成为候选项。

## 元数据模式

split 表示：

```text
任务/
├── tk.toml
└── TASK.md
```

`tk.toml` 保存全部元数据，`TASK.md` 保存正文。

embed 表示：

```text
任务/
└── TASK.md
```

`TASK.md` 以受限 YAML frontmatter 保存全部元数据，结束分隔符之后是正文。运行时拒绝 YAML tag、重复键、未知字段、未闭合 frontmatter 和超过上限的 frontmatter。

修改 embed 元数据时，运行时逐字节保留正文。表示切换作用于整个项目，不允许按任务混用。

## 创建正文

create 不接受正文输入。CLI 没有 `--body` 选项，子任务 item 把 `body` 作为未知字段拒绝。运行时创建任务时自动生成 `# <规范化名称>` 作为初始正文：split 模式下该标题是 `TASK.md` 的全部内容，embed 模式下该标题位于受管 frontmatter 之后。

创建之后由调用方把正文作为普通内容维护。rename 和子任务重试匹配不把正文作为输入或匹配条件。元数据变更逐字节保留正文。显式引用更新可以改写正文中的引用路径。表示切换保留正文。

## 候选识别

普通顶层发现只接受配置选中的 monthly 或 daily 拓扑。两者都要求固定数字宽度、合法日历日期、两位序号、非空 slug，以及按[任务名称规则](#任务名称)与 slug 对应的元数据名称。布局操作可以在专用预检中读取另一种拓扑。发现有效顶层任务后，运行时递归扫描真实后代目录，包括普通材料目录。

后代目录首先需要当前项目 `metadata_mode` 对应的明确标记：

- split 模式以常规 `tk.toml` 为标记。有效任务还必须具有常规的配对 `TASK.md`；
- embed 模式只有在常规 `TASK.md` 以 tk YAML 分隔符和 `schema_version` 头开始时才视为标记，随后必须完整通过 frontmatter 严格校验。

带标记目录只有在载体、schema、UUIDv7 身份、表示和项目路径全部通过校验后才成为任务。生成式 `NN--slug` 子任务还要求按任务名称规则与元数据名称对应；非生成式子任务没有路径与名称一致性要求。普通发现不会返回带标记但无效的目录，`check` 会报告它们。无关 `TASK.md` 和普通 YAML frontmatter 仍是材料。

最近的有效祖先任务是发现出的父级。无效标记目录和普通材料目录不会替换该祖先。符号链接、特殊文件、WAL 目录、`.tk-tmp`、清理数据和任务根目录外路径不参与发现。

普通任务材料可以直接或在嵌套材料目录中使用文件和目录软链接。相对和绝对链接可以指向项目内外。发现和 `check` 不解析或读取目标，包括缺失、不可读或成环的目标。链接目标中的任务标记和重复身份不进入任务图，真实嵌套子任务仍参与发现。材料链接的名称本身不使其成为受管载体或运行时路径。

遍历顺序固定。一次扫描最多接受 100,000 个真实目录和 256 层后代。超过任一上限或遇到必要 I/O 失败时，运行时返回 `task_discovery_limit_exceeded` 或对应存储错误，不返回部分任务图。`check` 把这类扫描报告为不完整。

`subtasks_dir` 只控制新子任务的写入位置。序号分配检查所有已发现的直接子任务，只统计叶子目录具有有效生成式 `NN--slug` 的任务，取最大序号且不填补空洞。新名称继续使用两位序号。序号 `99` 已存在时，创建会在写入前失败。

## 任务身份

UUIDv7 是权威身份。路径是定位符，rename 和布局操作可以改变路径。名称描述任务。

## 任务名称

保存名称必须是 NFKC 文本，至少包含一个字母或数字。只允许字母、数字、普通空格 `U+0020`、连字符 `-` 和下划线 `_`。

保存名称和生成式目录后缀各自最多占 32 个实际终端显示列。对保存字符串中的每个空格、连字符和下划线计宽，不先剥离或规范化字符串。格式化使名称从 32 列变为 33 列时，以 `task_name_too_wide` 拒绝。日期和序号前缀不计入后缀宽度。

生成式后缀遵守相同的字符和非空文字规则，且不含任何空白。合法名称与后缀比较时，只忽略两侧的普通空格、连字符和下划线，其余文字必须逐字相同，包括大小写。例如，后缀 `AI学习` 对应名称 `AI学习`、`AI 学习`、`AI-学习` 和 `AI_学习`。该比较不是身份、搜索别名或任务合并规则。非生成式子任务目录没有名称对应要求。

创建和显式 rename 保留请求规范化，采用 NFKC、受限字符和折叠后的连字符分隔。新生成目录不含空格。普通读取和 `check` 不规范化保存名称或移动目录；元数据更新和表示切换保留合法的保存写法。

子任务创建重试先完整校验保存名称，去掉其中的普通空格，再应用既有创建规范化，与规范化请求名称比较。其余请求字段保留原匹配条件。因此，排版空格不使已有子任务重复创建，而 `AI学习` 与 `AI-学习` 请求仍然不同。

## 关系

`depends_on` 和 `related_to` 只能指向同一任务根目录中的任务。任务不能引用自身，`depends_on` 不能形成环。关系按 UUID 排序并去重。

## 生命周期

- `planning`→`open`：允许，自动追加 WAL。
- `planning`→`closed`：非空原因、当前授权、关闭检查。
- `open`→`closed`：非空原因、当前授权、关闭检查。
- `closed`→`open`：非空原因、当前授权、没有已关闭祖先。

普通关闭要求所有后代和依赖目标已关闭。强制关闭只绕过后代和依赖检查，不绕过授权、原因、schema、路径、Git 或关系验证。

同一次更新组合关系修改与生命周期动作时，校验使用应用这些修改后的候选元数据。新增未关闭依赖会阻止普通关闭；移除最后一个未关闭依赖后，其余检查通过即可关闭。被拒绝的更新不写入元数据，也不追加生命周期 WAL。

一次更新构建一份严格任务图，用它解析目标和关系引用、检查生命周期约束并校验候选关系。任务图仅在当前请求内存在，不提供并发写入同步。

closed 任务默认只读。read、search 和 check 仍可读取它。rename 仍可用，且不改变状态。

## 创建授权

- `strict` 项目的顶层任务只有在用户当前明确要求或确认时才能创建。
- `permissive` 项目允许 Agent 为值得持久保存的工作创建任务，不要求已经承诺执行。
- 创建 `planning` 任务需要用户明确表达保存早期想法、调查或计划的意图。
- 创建默认状态是 `open`，需要 `planning` 时显式传入。
- open 任务树中的普通子任务不需要新的顶层授权。

## 项目发现

Git 项目使用 Git 根和项目配置定位。

非 Git 精确路径使用任务目录结构定位：

1. 从任务、受管文件或材料路径向上寻找符合 monthly 或 daily 规范的顶层祖先目录；
2. 验证日期目录和序号拓扑；
3. `YYYY` 的父目录是候选任务根；
4. 只再检查最多两个祖先目录，用于匹配项目配置和任务根关系；
5. 加载配置选中布局的载体任务图，并要求精确路径位于已发现任务内；
6. 两层内无法确认项目时失败，不继续遍历到文件系统根目录。

普通上下文目录使用有界的就近项目发现。精确绝对已发现任务路径、受管载体或材料路径会先定位其所属项目，因此调用方可以从项目 A 的 cwd 读取项目 B 的绝对引用。

## Git 策略

Git 策略在任务或配置受管写入前检查。辅助扫描报告的创建独立于这项检查：

- `track` 要求任务受管文件没有被忽略；
- `ignore` 要求任务根目录被忽略；
- `none` 不调用 Git 策略命令。

read、search 和纯诊断不会因为 Git 策略被拒绝。tk 永远不修改 `.gitignore`、索引、Git 配置、提交或历史。

## Search 可见性

省略状态过滤器或传入空数组时，搜索 `planning`、`open` 和 `closed` 全部状态。非空状态数组才缩小结果集。文件系统遍历不会在 closed 父任务处停止，结果会报告 closed 祖先。

搜索排序和匹配方式由 [CLI 参考](./cli-reference.zh.md#tk-search)定义。

## WAL

每个任务的 WAL 位于 `wal/YYYY-MM-DD.md`，条目格式为：

```markdown
## 2026-08-31T12:34:56+08:00 · actor

Message

Optional body
```

只有完整匹配 RFC 3339 时间戳、分隔符和 actor 的 `## ` 行才开始新条目。普通 Markdown H2 属于正文。

WAL 是普通辅助 Markdown 记录，不参与领域操作正确性。它不提供重复检测、事务保证或特殊行转义。正文恰好伪装成完整条目头属于极小概率事件，tk 不为此增加长度前缀或新格式。

actor 是单行归因信息，不是身份认证或授权。只有实际追加 WAL 的 update、log 和 rename 请求接受 actor。

元数据先提交，自动 WAL 后追加。WAL 追加失败会返回警告，不回滚已经提交的元数据。

`tk read` 按调用方设置的条目数和字节预算返回最近 WAL。`summary` 省略 WAL 正文，`detailed` 包含正文。预算之外的条目会被静默省略，不返回截断字段、警告或诊断。完整历史仍保存在每日文件中。

`tk check` 使用单独的流式检查器。它按固定顺序读取每个普通的每日 WAL Markdown 文件和其中全部条目，不设置固定的总文件数、总字节数或总条目数上限。必要 I/O 失败或取消会使检查不完整，不能返回成功的部分扫描结果。

## 单文件写入

单文件受管更新使用同目录临时文件和原子替换：

1. 严格读取当前状态；
2. 完成领域验证；
3. 执行写入前 Git 策略检查；
4. 写入并关闭完整临时文件；
5. 原子替换目标；
6. 删除临时内容。

同一文件的并发完整替换由最后完成者决定。

## 多目标操作

批量创建、schema 迁移、表示切换、布局操作、rename 和 CLI Skill 生命周期操作的受管变更遵循同一失败边界：

1. 首次写入前完成全部领域校验；
2. 按确定顺序逐项提交；
3. 普通 I/O 错误发生时立即停止；
4. 返回已完成项、未完成项和原始错误；
5. 不自动回滚，不创建续跑状态，不在进程退出后继续操作。

相同请求可以在调用方确认当前状态后重新执行。每次调用都重新构建发现任务图，并根据当前受管文件重新规划。

批量创建可以跳过已经存在且与请求匹配的项目。schema 迁移跳过已经处于目标版本的载体。

## schema 迁移

正式发布的 schema 版本使用逐级迁移器，例如 1→2、2→3。迁移总是按顺序执行到目标版本。

- 每个已发布版本的迁移器长期保留；
- split 和 embed 都支持逐级迁移并保留正文；
- 首次写入前完成全部选中载体的读取、验证和转换规划；
- 不支持降级；
- 未正式发布的开发格式不构成旧 schema；
- 初始 schema 是 1。

迁移器可以实现为 Rust 模块，也可以作为构建时嵌入的资源文件。代码组织不改变逐级迁移合同。

## 表示切换

表示切换在 split 和 embed 之间转换整个项目：

1. 读取并校验全部已发现任务；
2. 为每个任务生成目标载体；
3. 按确定顺序提交任务；
4. 最后更新项目配置；
5. 中途失败时报告已完成和未完成任务，不自动回滚。

切换不追加任务 WAL。

## 布局转换

`tk switch layout --to <monthly|daily>` 在预检中合并完整源任务图和已有目标布局任务，验证载体、名称、UUID 唯一性、日期序号及关系，按源路径顺序移动顶层目录，最后写入目标配置。已有目标任务保持原位。空根切换更新配置，同布局请求生成无变化报告。

`tk migrate layout --task <path>...` 将当前任务根内显式选择的规范顶层目录适配到配置选中的布局。相对路径以项目根为基准。重复选择和已经适配的选中任务按物理目录去重。预检先合并选中子树和当前任务图，再检查 UUID、序号、目标及关系。配置、元数据表示和 schema 保持原值。

两种操作都保留源编号和 slug。目标已存在或同日序号重复时停止规划。部分 switch 在全部必要移动和引用更新成功前保留原配置。已经移动的任务可能暂时从普通发现中隐藏。后续 switch 根据两种布局重新规划并处理剩余源目录。前次路径映射保留在前次报告中，供人工修复引用。

## rename

即使保存名称和生成式后缀已经按排版比较对应，rename 仍采用请求规范化及具体目标。它也修复无效、为空或实际过宽的字符串名称，以及结构可识别但不符合[任务名称规则](#任务名称)的生成式后缀：

1. 通过完整 UUID、精确任务目录或精确受管载体解析唯一符合条件的候选。可修复候选参与 UUID 唯一性和父级归属判断；祖先结构无法确定时拒绝操作；
2. 规范化新名称，并用替换后的名称完整校验元数据。名称缺失或类型错误、身份损坏、schema 不受支持、关系或 `extra` 无效、不安全路径以及无法识别的生成式结构仍然报错；
3. 非生成式子任务保持目录不变；其他任务保留日期和序号并计算新的 slug 路径；
4. 验证需要移动时目标不存在；
5. 扫描引用并保存扫描报告；
6. 检查项目可写条件和 Git 策略，再复检输入；
7. 生成式目录无覆盖移动，非生成式子任务跳过本步；
8. 显式请求时更新引用；
9. 更新元数据，保留状态及 `name` 之外的全部字段，保留包含引用更新的当前正文；
10. 追加 WAL。

只有保存名称和适用目标路径都精确相等时才返回无变化。名称为 `AI 学习`、后缀为 `AI学习` 时，rename 为 `AI 学习` 的目标名称和后缀都是 `AI-学习`。名称为 `AI-学习`、后缀为 `AI_学习` 时，同名 rename 仍移动目录。

提交前精确比较当前路径、完整元数据、载体字节、配置、目标和引用与计划是否相同。排版等价不会抑制 `stale_rename_plan`。已有步骤提交后失败时，返回已完成和未完成步骤、原始错误及报告路径。中间状态可读仍需重新规划相同请求，完成精确目标。

## 引用更新

rename 和两个布局命令默认保留引用原文。`--update-references` 显式启用改写。可重复的 `--extend-scan <path>` 接受 Markdown 文件或目录，支持项目外绝对路径。相对输入以项目根为基准。

`git_policy=track` 时，默认从文件系统扫描整个项目的 Markdown，独立于 Git 暂存状态。`ignore` 或 `none` 时扫描 `task_root` 下的 Markdown。重叠输入归一去重并排序。符号链接跳过，显式选择链接会被拒绝。合并扫描最多接受 100,000 个真实目录和 256 层。必要 I/O 失败及 `reference_scan_limit_exceeded` 停止规划。

已知任务 WAL、`.git` 和当前任务根的 `.tk-tmp` 被排除。embed `TASK.md` 从受管 frontmatter 之后开始扫描。导入子树和已有目标布局任务的运行时目录也参与排除。

扫描器处理普通 Markdown 链接和图片目的地、引用定义、双链中带任务根的完整路径，以及文本或代码中的完整任务路径。仅文件名的短双链和外部 URI 保持原样。标签、标题、别名、片段及 query 保留原字节。目的地支持转义、括号、尖括号和 URL 百分号编码。匹配要求完整路径前缀及目录组件边界。其他目录下同名的任务根片段属于不同路径。

完整路径双链中的相对路径先以项目根解析，再应用映射。开头的上级目录组件保留其对引用位置的作用。双链按完整路径组件匹配源目录，映射采用最近的真实源目录祖先。文件名中的 `!`、`:` 等字符属于该组件。

令 F 将被移动目录及其后代映射到新路径。文件 S 指向目标 T 的相对链接，替换为从 `parent(F(S))` 到 `F(T)` 的相对路径。这覆盖被搬文件指向外部、外部指向被搬任务、任务间互链及子树内链接。目标按词法组件归一。已经适用的引用保留原写法。

一次扫描准备全部映射。每个待改文件保留一份原文快照及排序后的无重叠 UTF-8 字节区间。提交前重新扫描文件集合和引用，完整比较待改文件原文。每个文件在映射后的位置用同目录原子临时文件替换一次，扩展文件可以位于另一文件系统。

## 扫描报告

有效项目中的每次 rename 和布局调用都保存独立报告，包括 dry-run、无变化请求及规划失败。解析、项目定位、取消和报告存储失败返回各自错误。受管变更开始前，报告使用 `create_new` 新建，写入 UTF-8 JSON，并完成 flush 和 sync：

```text
<task-root>/.tk-tmp/reports/YYYYMMDDTHHMMSS+ZZZZ--<operation>--<UUIDv7>.json
```

operation 为 `rename`、`switch-layout` 或 `migrate-layout`。报告是不可变的执行前快照，包含 `report_version=1`、运行身份和本地时间、操作选项、项目根和任务根、源目标布局、扫描根、完整性、诊断、任务映射及引用。任务项包含 `task_id`、`old_path`、`target_path`、`old_name` 和 `new_name`。引用项包含 `kind`、`old_file`、`target_file`、从 1 开始的 `line`、半开区间 `byte_start` 和 `byte_end`、`original`、`replacement`、`old_target` 和 `target`。

记录中的路径全部为绝对路径。原文与建议相同时无需内容替换。`scan_complete=false` 表示扫描不完整。实际执行状态由 [CLI 摘要](./cli-reference.zh.md#路径变更结果)或错误表达。报告用于人工检查，不作为重放输入。

dry-run 只新增报告，任务数据、引用和配置保留原字节。报告写入失败会停止受管变更，并清理本次不完整报告。已有报告保留至用户主动清理。项目写入门禁、check 和 GC 为真实 `.tk-tmp/reports` 目录保留命名空间，并保留其中的内容。用户级操作目录保持原有语义。

## 最小清理清单

每个需要登记临时内容的操作使用最小清理清单，只记录：

- 清单格式版本；
- 操作进程身份；
- 创建时间；
- tk 创建的临时文件和目录路径。

清单只承担临时内容清理职责，不记录领域状态、内容摘要或提交阶段。

会修改多个项目目标的命令在首次写入前创建活动操作标记。标记记录操作 ID、项目范围、Linux boot ID、PID 和进程启动时间。

- 操作进程仍在运行时，其他项目写操作返回 `operation_in_progress`。
- 操作进程退出后，写操作仍拒绝并提示先运行 GC。
- read、search 和纯诊断不受阻塞。
- 单文件原子替换不创建项目级活动操作标记。
- 两个进程恰好同时创建标记的竞争按极小概率事件处理，不增加锁。

## GC

GC 只处理 tk 临时内容：

- 仍在运行的操作进程对应的清单和路径全部保留；
- 操作进程退出后，对应清单按记录路径清理；
- 路径逃逸、symlink、无法解析的清单和无法证明属于 tk 的内容保留并报告；
- 开发阶段旧清理格式视为未知内容，不解析、不迁移；
- GC 不继续、完成或回滚领域操作；
- 项目真实 `.tk-tmp/reports` 目录中的扫描报告保留；
- GC 不修改任务元数据、正文、WAL、项目配置或 Harness 配置。

删除期间发生 I/O 错误时停止并报告已删除和未删除路径。

## check

check 严格检查项目配置、带标记任务载体、schema、表示一致性、生成式名称与路径一致性、UUID 唯一性、直接子任务序号唯一性、关系、WAL、活动操作标记和临时清单。逻辑同级序号冲突会报告解析出的父级路径。

普通材料链接不产生诊断。任务根、已识别任务载体、每个已发现任务的 WAL 及项目任务根的 `.tk-tmp` 数据仍有各自的受管类型要求。`check` 报告 WAL 和临时运行数据中的链接，不跟随目标。它不检查普通链接有效性，也不为受管存储提供链接别名。

必要目录或文件读取失败、发现过程超过资源上限或扫描被中断时，check 立即返回不完整检查，不继续收集后续诊断。存在失败 I/O 路径时一并报告。有效 WAL 的规模本身不会使检查不完整。完整读取后发现标记载体、格式或领域错误时，检查是完整但失败。check 不修改任何内容。

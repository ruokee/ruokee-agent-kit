# 验证

[English](./validation.md)

本文说明验证 tk 必要行为和实现选择的方法及场景。规格包含完整行为和验收要求，设计解释实现。验证不能因为实现方便而降低其中任何义务。

以下列表是场景要求，不是覆盖报告。自动检查入口为负责 Rust 和组件生命周期检查的 `cargo test --manifest-path projects/tk/Cargo.toml`。生命周期测试用候选 CLI 操作真实临时文件，不使用 Harness 命令。已安装 Skill 和真实 Harness 场景单独运行，每项验证结果记录实际候选、宿主版本、输入、观察及未覆盖项。

## 自动检查前提

使用带 `rustfmt` 的 Rust、Git 和非 root 的 POSIX 环境。在仓库根目录单独准备锁定 crate 依赖，不混入检查：

```sh
cargo fetch --locked --manifest-path projects/tk/Cargo.toml
```

运行 `cargo fmt --manifest-path projects/tk/Cargo.toml -- --check` 检查 Rust 格式，再运行上文的 Rust 测试命令。每个检出保留独立的可写依赖及构建输出。这些命令不改变用户的运行时或 Skill 安装。

## 仓库边界

验证以下静态事实：

- 一个 Cargo package 生成 `tk` 可执行文件；
- Rust 是唯一组件组装器；
- 组件组装只有一条 Rust 产物路径；
- 内嵌分发恰好包含 `tk-cli` 和 `tk-cli-zh` 两个自包含 Skill，不含 Harness 字段；
- 每棵源码树和安装目录都包含自身全部参考资料，两种语言语义对应；
- 评审记录和任务材料不进入产品产物。

## 数据模型测试

覆盖 split 和 embed：

- schema 1 的严格解码、稳定编码和正文保留；
- 未知字段、缺失版本、未知版本、错误类型和受限 YAML；
- 规范顶层发现和后代的模式专用载体标记；
- 直接位于父任务下的子任务、配置目录下的子任务以及普通材料目录下嵌套的子任务，父级为最近有效祖先；
- 带标记无效载体、符号链接、运行时自有路径、发现上限、重复身份和逻辑同级序号；
- UUIDv7、生成式名称与路径一致性、关系去重、跨根引用和依赖环；
- 顶层任务和生成式子任务兼容普通空格、连字符和下划线的排版对应，不折叠大小写或改变文字；
- 名称和生成式后缀分别验证实际 32/33 列边界，计入全部分隔符，生成目录拒绝空白；
- 受管写入和双向表示切换保留合法保存写法，不隐式改名、移动目录或新增诊断；
- 改变 `subtasks_dir` 后的子任务编号、不填补空洞和 `99` 耗尽；
- 非生成式子任务重命名不移动目录，生成式重命名保持序号；
- planning、open、closed 转换和关闭约束；
- 关系修改与关闭组合时校验候选依赖，拒绝时保持元数据与 WAL 不变，强制关闭仍执行授权与关系检查；
- 单次更新的关系引用解析、关闭或重开检查、候选关系校验复用一份发现图；
- strict 与 permissive 创建；
- create 把 `--body` 作为未知 CLI 参数拒绝，并在子任务 item 上把 `body` 作为未知字段拒绝；
- 运行时在 split 和 embed 模式创建任务时写入恰为 `# <规范化名称>` 的初始正文；
- 子任务重试只匹配 create 拥有的字段，忽略新增普通排版空格和已编辑正文，仍区分 `AI学习` 与 `AI-学习` 等不同规范化请求；
- Git `track`、`ignore` 和 `none` 只在写入前预检；
- 绝对已发现任务、载体和材料路径反向定位项目；
- 非 Git 发现的有界祖先检查。

## 搜索测试

覆盖：

- 默认包含 planning、open 和 closed；
- 显式 status 缩小结果；
- 完整 UUID、明确任务路径、材料路径、regex 和 string 的解释顺序；
- 查询类型确定后不回退；
- 最少 8 位 UUID 前缀；
- 匹配类别、`created_at` 降序和 ID 升序；
- `match` 返回 `uuid`、`path`、`regex` 或 `string`；
- 默认 20、最大 100 和有界结果集；
- `search_body=false` 不读取正文。

## WAL 测试

覆盖正常条目编码和解析、actor、消息、正文与预算。WAL 故障不能回滚已经提交的元数据。

不为正文恰好伪装成完整条目头增加转义格式或专项测试合同。

## 写入测试

覆盖：

- 单文件同目录临时文件和原子替换；
- 最后完成的完整替换决定最终字节；
- 多目标操作首次写入前完成全部领域预检；
- 每个提交点注入 I/O 失败，并准确报告完成和未完成项；
- 不自动回滚，不生成续跑状态；
- 批量创建重试跳过已经存在且匹配的项目；
- 仍在运行的操作进程阻止其他项目写入；
- 操作进程退出后，活动操作标记仍阻塞写入直到 GC；
- read、search 和纯诊断在活动标记下仍可用（[最小清理清单](./data-model.zh.md#最小清理清单)）；
- 单文件更新不创建项目活动操作标记。

## 迁移测试

当存在多个正式 schema 时，每条相邻迁移器分别测试，组合链也测试。当前初始版本是 1。

覆盖 split 和 embed 的逐级向前迁移、正文保留、全部目标预检、跳过当前版本、未知版本、缺失转换和拒绝降级。

## 表示切换测试

表示切换覆盖 split→embed、embed→split、配置最后提交、中途故障的完成与未完成项，以及不追加 WAL。

## rename

覆盖名称和路径更新、重复相同 rename 返回无变化、WAL 警告、目标冲突和引用扫描：

- `git_policy=track` 从文件系统扫描项目 Markdown，不受 Git 暂存状态影响；
- `ignore` 和 `none` 扫描 task_root 普通 Markdown；
- split 和 embed 正文均参与；
- closed 任务可以改名和修复，并保持状态；
- 排版兼容的源状态仍达到精确规范化名称及适用路径，包括仅分隔符变化和原样请求显示名称的情形；
- 空名称、实际超宽名称和可识别后缀缺陷仍可修复，提交前精确复检保留 `stale_rename_plan`；
- 真实目录移动后发生元数据 I/O 失败时报告部分完成，中间状态可读仍需重试达到精确目标；
- 仅元数据的 rename 报告引用但不适用路径移动门禁，无变化请求也会报告引用；
- 工作树中已删除但仍在 Git 索引里的文件不会导致扫描失败，未跟踪文件同样参与；
- 引用文件不可读时命令显式失败，扫描超过深度或目录上限时以 `reference_scan_limit_exceeded` 停止；
- 引用只报告，不自动修改；
- 带引用的 dry-run 成功并返回完整计划；
- 带引用的路径移动执行在首次写入前以稳定错误码 `broken_reference_conflict`、`conflict` 类别和退出码 3 停止，details 包含 `old_path`、规范化 `new_name`、绝对 `target_path` 和全部引用路径与行号；
- `--ignore-brokenlinks` 让移动完成，引用文件逐字节保持原样，结果中仍包含引用；
- 无引用的路径移动正常完成。非生成式子任务改名不会移动目录，重复相同 rename 返回无变化；这两种情况都不返回 `broken_reference_conflict`。

## 维护测试

check 测试完整有效项目、领域诊断和必要 I/O 快速失败。必要读取失败后不能继续输出看似完整的诊断集合。

两种元数据模式均通过公开 CLI 验证普通文件和目录链接，覆盖直接与嵌套材料位置、相对与绝对链接、项目内外目标、缺失与真实不可读目标、自环和相互引用。`check` 必须成功且不产生链接诊断，不通过目录链接发现无效载体或重复身份。read 和 search 保持原任务身份与最近父级关系，包括真实嵌套子任务。普通链接名为 `TASK.md`、`tk.toml`、`wal` 或 `.tk-tmp`，不因 basename 获得受管职责。

反例保留任务根与载体规则、表示冲突、WAL 根与条目类型，以及临时根、操作目录、清单和 payload 类型。这些错误与普通链接共存时仍须可观察。保持完整但失败与必要 I/O 导致不完整的退出合同。比较检查前后的链接目标路径、目标原始字节和任务数据，检查不得修改它们。

GC 测试：

- 最小清理清单的版本、进程身份、时间和临时路径；
- 活动进程内容保留；
- 已结束进程内容和标记清理；
- 路径逃逸、symlink、未知清单和无法证明属于 tk 的内容保留；
- 开发阶段旧清理格式不解析、不迁移；
- 不修改任务、WAL、项目配置或 Harness 配置；
- 删除错误时报告已删除和未删除项。

## 接口测试

运行以下 CLI 场景：

- 命令树、help、version、文本与 JSON 输出；
- stdout 和 stderr 分离；
- 当前退出码映射；
- actor 只出现在 update、log 和 rename；
- search 全部默认状态；
- init force 不读取任务数据；
- 两种目标都默认英文，接受两种语言，并报告最终 Skill；
- install 与 uninstall 必须且只能选择 Harness 或 Skill 根目录；
- 组件命令没有本地 source，并拒绝全局 cwd；
- 拒绝未知命令和不属于当前合同的选项。

## 组件组装

重复构建必须产生相同的两个 CLI Skill 载荷、文件字节、`tar.zst` 字节和清单。验证语言、Skill 身份、路径、权限、摘要、缺失项、多余项和 `runtime_compat`。

`TK_SOURCE_REVISION` 有值和无值两种构建均验证。构建脚本不能调用 Git，也不能写出 Cargo 管理目录以外的生成物。

## 安装测试

隔离测试覆盖每个 Harness 根目录映射及自定义根目录的两种语言：

- install、update、选择切换、no_change 和 uninstall；
- 内嵌归档，无网络和本地来源；
- text 和 JSON install 结果中的最终目标、`language` 和 `skill`；
- 固定运行时不存在、不是常规文件或没有执行权限；
- 安装写入所选 Skill、删除另一种语言，不要求 Harness 可执行文件；
- 卸载完整删除两个 CLI Skill 目录，包括修改和额外内容；
- 根目录、其他子项和无关配置保持不变；
- 中途 I/O 失败报告完成和未完成项；
- GC 只清理组件临时内容，不继续生命周期操作。

自定义根目录还覆盖相对与绝对路径及缺失父目录创建。两种目标都覆盖完整载荷收敛、语言切换、dry-run 和 no_change。结果恰好包含 `skill_root` 或 `harness` 之一，卸载省略语言和 Skill。

## 真实 Harness 验证

- Codex：隔离环境真实安装、加载和卸载。
- Claude Code：隔离环境真实安装、加载和卸载。
- Pi：隔离环境真实安装、加载和卸载。
- OMP：隔离环境真实安装、加载、通过 CLI 操作任务和卸载。

每个 Harness 都验证两种语言的普通 Skill 放置、发现和卸载。

真实测试必须观察 Harness 的实际加载结果和卸载后状态，不能只检查组装文件。

## Skill 测试

Skill 场景覆盖 strict/permissive 创建、planning/open 选择、任务解析、catchup、WAL、人工修复授权、close/reopen、四种材料模式和 CLI 命令使用。两个 Skill 身份必须呈现相同的模式语义，且各自保持自包含。

四种模式共通：建议以已经出现的信号为前提，并说明模式会增加什么、需要维护什么；用户采用后才在 `TASK.md` 中声明。反例只排除主动建议；用户明确请求采用某种模式时该请求本身就是授权，不受反例阻拦。

材料模式场景观察：

- 记录：同日工作或仅计划以后继续时不主动建议；第二个本地自然日有实质活动后可以建议。材料保留当时判断，后续更正写入后续材料而不是改写先前材料，也不补造过去活动或未来日期的记录；记录、WAL 与 `TASK.md` 各自保持分工。
- 深度调研：只读一个已知文档或回答普通 API 问题时不主动建议，收集、保存或交叉核验外部来源的工作可以建议。材料把关键主张与来源对应起来，并保留来源访问日期、来源之间的冲突、仍不能核验的部分和结论边界。
- 迭代设计：新的大幅改版开启下一轮，普通修正留在当前版本；每轮自包含，被替代的版本保留内容，`TASK.md` 只暴露一个当前设计入口。
- 草稿纸：无需留存的简短问答不建立材料；临时内容留存，稳定内容整理到普通材料，失效内容保持可区分；没有删除或移动材料的授权时不执行清理。

采用模式不增加元数据、schema、`extra`、状态或命令，也不扩大任务创建或生命周期授权。项目已有布局可以覆盖默认目录。任何场景都不要求创建空材料。

Markdown 与 Rust 基线检查不能单独证明 Agent 行为；模式通过安装候选 Skill 后的 Harness 场景核验。

## 文档测试

公开文档检查英文和中文页面的语言链接、语义对应、术语和自然度。使用仓库现有检查和人工审查，不增加自定义文档结构检查器。

# Skill 行为

[English](./skill.md)

本文规定 Agent 使用 tk 时的理想行为。运行时负责强制执行元数据、路径、生命周期、关系、Git 和持久化规则。Skill 不复制第二套规则。

## 何时使用 tk

用户明确提到任务 ID、任务名称、任务路径、任务分支或 tk 操作时使用 tk。

在 permissive 项目中，Agent 也可以为明显值得跨步骤或跨会话持久保存的工作创建任务。快速问答、普通 TODO、一次性小改和随口想法不需要任务。

任务是值得持久保存的临时性努力。创建不代表用户或 Agent 已经承诺执行或完成。

## 安装后的 Skill 身份

tk 提供四个相互独立的自包含 Skill：

| 模式 | 英文 | 中文 |
| --- | --- | --- |
| tools | `tk` | `tk-zh` |
| CLI | `tk-cli` | `tk-cli-zh` |

tools Skill 的 search、read、create、update 和 log 使用 Harness 逻辑操作，exec 只接受 version、init、check 和 rename。公开 CLI 只用于没有逻辑操作的支持命令。逻辑操作缺失、拒绝请求或执行失败时，按集成或传输故障报告，不通过直接 CLI 重试。

CLI Skill 的所有任务操作都使用公开 `tk` CLI，并在自身目录中包含所需的完整现行命令参考。它不比较入口，也不依赖集成发现。

同一模式的英文和中文 Skill 具有对应的语义覆盖。四个目录均可独立安装和理解，不依赖其他仓库组件。

## 生命周期含义

- `planning` 保存仍在形成的想法、调查或计划。
- `open` 表示正在实际处理。
- `closed` 表示该努力已经结束，可以是完成、放弃、不可行或被替代。

状态描述事实，不是优先级。

## 解析任务

每个新会话默认不绑定任务。

1. 用户提供完整 ID、精确名称、路径、目录名或分支时，先 search 或 read。
2. 完整引用唯一时直接 read summary。
3. 名称、UUID 前缀、文本和材料路径先 search，再使用返回的完整引用。
4. 多个候选无法根据用户信息唯一选择时，展示候选并询问。
5. 持续对话可以在当前会话中保留已经解析的任务，但不把绑定写入任务。

普通 catchup 是只读操作：读取 summary、`TASK.md` 入口和必要材料，报告当前目标、状态、依赖、已形成结论、阻塞和下一步，然后停止。只有用户同时要求继续工作时才继续。

## 创建

### strict

strict 项目的顶层任务只有在用户当前明确要求或确认创建时才创建。Agent 不能把“这个问题可能很重要”当成确认。

### permissive

permissive 项目允许 Agent 为值得持久保存的工作主动创建任务，不要求已经承诺执行。Agent 根据语境选择状态：

- 内容仍在形成，且用户明确希望保存早期材料时使用 planning；
- 已经开始实际处理时使用 open。

创建后在同一回复报告任务名称、状态和路径。

### 子任务

open 任务下的真实工作单元可以作为子任务创建，不需要重新取得顶层创建授权。不能在 closed 父任务下创建子任务，也不能隐式重新打开父任务。

批量创建只用于同一个父任务下相互独立的真实工作单元，不用于导入整个 backlog。

## `TASK.md`

`TASK.md` 保存紧凑的当前事实和重要入口：

- 目标；
- 范围和约束；
- 已采用的稳定决定；
- 重要材料链接；
- 当前仍有效的阻塞。

它不保存逐步聊天记录、命令流水、长篇研究正文或已经被替代的计划。详细材料写入任务目录中的普通文件，再从 `TASK.md` 链接。

Agent 可以编辑 `TASK.md` 正文和普通材料。受管元数据必须通过 tk 操作修改。

## 日志

事实一旦成为持久决定、纠正、可恢复里程碑、验证结果、协作结果或阻塞，就立即写 WAL，再开始下一条工作分支。

每条日志使用非空单行摘要，细节放在 Markdown body。actor 使用当前可获得的最具体模型或 Harness 信息。actor 只表示归因，不表示身份或授权。

不要记录例行读取、临时计划、工具流水和仍在形成的猜测。

## 更新、关闭和重新打开

更新前读取当前任务。关系、extra 和生命周期通过 tk update 完成。

关闭前确认：

- 工作确实已经结束；
- 后代和依赖满足普通关闭规则；
- `TASK.md` 只保留当前结果和入口；
- 需要保留的验证或决定已经记录。

close 和 reopen 都需要非空原因和当前用户确认。closed 任务默认只读，但允许 rename 和修复。新工作通常创建相关任务，只有用户明确确认新工作仍属于原任务时才重新打开。

## 人工修复 `tk.toml`

日常修改始终使用 tk 公开操作。

当 `tk.toml` 已损坏，且 tk 无法表达修复时：

1. 精确说明要改的字段和最终内容；
2. 取得当前对话中的明确授权；
3. 只做说明过的最小编辑；
4. 运行 `tk check`；
5. 任务恢复可用后，用 WAL 记录人工修复事件。

不能手动编辑元数据、清理清单或 Harness 配置来绕过运行时拒绝。

## 错误处理

先读取稳定错误码、类别、详情以及已完成和未完成项。必要时重新 read 或 check 当前状态，再决定是否重试。

多目标操作失败后不假定运行时会回滚或续跑。Agent 根据当前规范状态和用户目标发起新的完整命令。

真正需要用户选择时明确说明选择影响。能够从工具、项目文件或现有材料确定的信息不向用户追问。

## 材料模式

四种模式用于组织任务中的普通材料。它们都是可选项，一个任务可以组合使用，也可以都不使用。项目说明可以补充或覆盖这些默认路径。

| 模式 | 建议采用的信号 | 默认材料 |
| --- | --- | --- |
| 记录 | 实质调查、实施、验证或决策活动已经发生在第二个本地自然日 | `records/YYYY-MM-DD-topic.md` |
| 深度调研 | 工作要求收集、保存或交叉核验外部来源，或已经存在来源清单和来源材料 | `research/report.md`、`research/README.md` |
| 迭代设计 | 出现两次以上相互替代的大幅改版、旧方案被整体推倒，或主要边界持续变化 | `revision_<N>/README.md` 及该版本目录内的材料 |
| 草稿纸 | 尚未整理的片段、笔记、输出、小脚本或其他临时文件需要持久保存 | `scratchpad/` 下的文件和子目录 |

每种信号也有对应的反例：同日任务和仅计划以后继续的工作不需要记录；只读一个已知文档或回答普通 API 用法问题不需要深度调研；增量补充、措辞调整和普通评审修正不产生新版本；无需留存的简短问答不需要草稿纸。

主动建议某种模式前，先确认信号已经出现，并说明它会增加哪些材料、以后需要维护什么。用户采用后，在 `TASK.md` 正文中简要声明并链接已有入口材料；用户明确要求采用某种模式时，该请求本身就是采用授权。只为已经发生的工作创建材料：不预建空目录、不补造过去活动、不创建未来日期的记录，也不为匹配示例迁移已有任务。

维护让这些模式保持有效：

- 记录保存有实质活动的日期对应的背景、动作、证据入口和当时结论。保留先前判断，后续更正写入后续材料，`TASK.md` 指向仍然适用的结论。记录不替代 WAL 或正式决策记录。
- 深度调研持续维护来源来历与访问日期、关键主张对应的证据、来源之间的冲突、仍不能核验的部分和结论边界。`TASK.md` 提供报告的直接入口。
- 迭代设计让每轮版本自包含，并让被替代的版本保留当时状态；只有新的大幅改版才创建下一轮，普通修正继续编辑当前版本。`TASK.md` 只把当前版本作为设计入口。
- 草稿纸中的内容稳定后整理到合适的普通材料，失效内容与当前事实保持可区分。

模式只组织普通文件，不增加运行时状态、元数据、schema 字段或命令。采用模式不授予删除或移动材料、创建任务或改变其生命周期的权限。正式决定遵守项目指定的机制和位置。

# 澄清

遵循已加载的[入口](../SKILL.md)，解析材料前读取[任务归属](../references/task.md)。Clarify 包括目标讨论、必要调研、设计和规划，可以维护普通分析材料及必要临时文件，不授权实现、配置、Git 或托管元数据变更。

## 解析请求

读取所属 Task、当前目标、相关决定、既有材料和项目规则。区分初步讨论、设计问题、形成 Plan 和修订请求。使用已确定信息，不重启完成的访谈，仅补充缺失的问题、预期结果、范围、约束和停止条件。

选方案前判断工作是否有用、可行。遵守仅讨论、仅设计、不做 Plan、暂停、不写入等明确限制。

## 调研

先读项目事实和惯例，缺少事实时使用本地或公开研究。先读既有研究摘要，必要时追溯原始来源。研究、诊断、架构或访谈 Skill 仅在适用时使用。

对尚未确定的重要选择说明备选、证据、建议和所需决定。使用获准访谈方式，允许时可以结构化提问。不替用户决定优先级，不把 Agent 提议当作要求。

## 维护材料

复用所属 Task 的既有文件：

- `goal.md`：用自然语言表达已确认要求、预期结果、相关情形、约束、排除项，以及完成或合理停止的条件。不写实现方法和代码细节。
- 可选 `design.md`：如何利用现有系统和最小充分改动达成目标。按需包含重要备选、归属、依赖、失败行为、算法、数据结构或实现细节。
- 可选诊断：症状、实际条件、证据及有依据或尚不确定的原因。修复方法和建议写入设计，不写入诊断。
- 可选研究：有可追溯来源的摘要，区分观察、结论和假设。
- 可选 Grill，通常为 `grill.md`：记录访谈讨论，不替代当前要求和决定。
- `plan.md`：下文定义的完整工作安排，包括可执行单元及必要的子任务澄清。进入 Execute 前必需，单单元任务也不例外。

验收对应已确认要求或必要证据，不添加效果指标、迁移、安装或实验。仅设计请求可以只维护设计，不强制形成其他材料或 Plan。

工作不可行、不必要或用户决定不继续时，在记录许可内保存有依据的结论并结束，不强制形成 Plan。适合关闭时遵循 tk 和项目许可；在此停止既不禁止关闭，也不授权关闭。

## 形成 Plan

目标和必要设计已明确，拟形成可执行合同的工作所涉及的可预见重要用户选择已解决时，在同次 Clarify 中形成 Plan 并自检。遵守仅讨论、仅设计、不做 Plan、暂停和写入限制。不额外要求用户声明执行意愿，也不例行确认是否开始规划。准备不授权实现。

形成 Plan、安排依赖和解决许可时读取[执行约束](../references/execution.md)。Clarify 保留获准访谈方式。在当前讨论解决能够确定的选择，不例行推迟。真正阻塞在 Plan 中明确保留，与已就绪的实施合同分开。即使部分或全部子任务的实施合同尚未就绪，父 Plan 也覆盖已确认的完整范围。

保留单元标签、已完成结果和有效证据。Plan 可混用内联单元和 tk 子任务链接。父 Plan 保留范围内的每个子任务，写明目标、材料归属、当前环节、依赖或阻塞及材料链接。详细合同和证据归子任务。其他位置的任务索引或讨论不能替代此处的完整安排。按 tk 许可创建子任务，不为取得目录而创建。

子任务需要单独讨论或准备时，列出明确命名的 Clarify 环节，写明输入、预期形成的目标、必要设计和 Plan 材料、完成条件，以及如何接回父 Plan 中的剩余工作。链接现有材料，不创建空子计划或编造实施合同。未决用户选择使该环节保持阻塞，不能仅因记录了问题就算完成。准备结束后，读取结果并在实施前更新父计划的下一步、依赖和链接。准备完成不等于子任务最终结果完成。只有有效用户决定才能改变已确认范围。

每个已就绪单元定义完整且可独立评估的结果、目标与设计依据、改动与非目标、前提、可观察验收、检查、权限需求及材料归属。安排真实依赖，识别独立工作。允许时使用已验证前序候选，并区分真正必需的部署、服务或已发布产物。不把未授权集成设为开发前提，不在缺少要求和许可时增加交付或昂贵试验。

## 检查材料

Plan 形成后读取[自检](../references/self-check.md)，启动检查时按其链接读取角色与协作规则。检查当前目标、设计、Plan、链接细节、讨论决定、项目规则、依赖、可预见权限及写作。逐项对照已确认范围、子任务和父 Plan：即使尚不能实施，缺少对应澄清环节仍是遗漏。检查各环节的产物和后续承接，不把范围完整视为实施就绪。这不是工具或环境预检，不安装依赖、不改变 Git 状态、不格式化授权材料以外的文件。

每轮 Clarify 是独立的准备阶段，拥有独立的准备自检计数。上一轮 Clarify 返回后，因新的请求、从 Verify、Execute、Supervise 或 Ship 返回的材料或设计缺陷，或因需求、依据变化再次进入 Clarify，开启新一轮。轮次仍在进行时收到的新请求、材料修订、修复、复检或独立准备反馈仍属同一轮。会话恢复、上下文压缩或由另一 Agent 继续本轮也仍属同一轮。仅为获得新计数而宣布的轮次仍属同一轮。计数由自检 Reference 拥有。在准备记录中保存本轮触发依据、候选、次数与上限。

自动检查保存到既有准备自检记录，通常是 `plan-check.md`，不写入 `material_check.md` 或 `verification.md`。作者按共享自检规则修复，未解决的重要需求返回讨论。

独立准备审查只按用户请求启动，不因自检次数耗尽而启动。需要时读取[角色选择](../references/roles.md)和[协作](../references/collaboration.md)，冻结材料并分派 [Verify](./verify.md)。核验者按该操作确定报告，独立准备审查使用 `material_check.md`。没有请求时不创建空报告。

审查请求覆盖范围内作者修复和同一合适核验者的必要复查，直到当前通过或出现真实阻塞；单轮、只报告或更窄限制优先。核验者只读，作者修复，无法判断不等于通过。

## 返回

保存获准结果，保留早期失败及对应范围和候选。返回材料路径、已确定结果、自检次数与结论、按请求完成的独立结论，以及实际阻塞。在可恢复状态中保留当前 Task、依据、材料版本、自检次数与上限、有效限制和下一步。

在 Clarify 内结束，不邀请、建议或询问是否开始执行。只有用户同时实际请求执行时，才按该操作自己的范围和许可进入 Execute。完成准备或审查不等于实现。

# 澄清

完整读取[公共合同](../SKILL.md)，将本操作应用于用户的实际请求。Clarify 包含目标讨论、必要调研与设计、规划，不授权实现。

## 解析请求

读取所属 Task、当前目标、相关决定、已有材料及项目规则。确定用户需要初步讨论、特定设计问题、直接生成 Plan，还是修订现有材料。沿用已清楚的内容，不因入口相同就重做已完成访谈。

新想法先明确问题、预期结果、范围、约束及停止条件。选择方案前判断行动是否有用、可行。目标已明确时，直接开展请求的设计或 Plan 工作。遵循只讨论、只设计、不做 Plan、暂停及不写入限制。

## 调研

先读项目事实和现有模式。事实不足时开展本地或公开资料调研，优先使用已有 Research 汇总，需要核对时再追溯具体证据。按各自启用条件使用相关调研、诊断、架构或访谈 Skill，不把每种活动变成必经步骤。

诊断记录症状、实际条件、证据及有依据或尚不确定的原因，不在该报告写修复建议。用户需要时，由设计讨论修复方式。区分测量和观察、结论及假设。

未决用户要求或重要取舍需要说明选项、证据、建议及所需决定。采用适用访谈方法，只在许可时使用结构化问答。先核对可获取事实，不替用户决定优先级，不把 Agent 建议变成已确认要求。开展访谈时保留讨论记录。

## 定义结果

用自然语言将已确认要求保存在 `goal.md`：预期行为、重要场景与约束、当前范围外事项，以及完成或合理停止的条件。实现细节放入可选 `design.md`。每项验收条件都对应已确认要求或必要证据，不为显得完整而增加收益指标、迁移、安装或实验。

必要设计在 Clarify 内完成。依据现有系统及最小充分变更说明如何达到目标。只在需要时写重要替代方案及实际取舍、归属、依赖、失败行为和实现细节。只请求设计时，可以维护 `design.md`，不强迫补齐其他材料或规划。

不可行、无需行动或用户决定不再继续时，保存结论及依据。不为补齐阶段而创建 Plan。适合结案时，按 tk 和项目的生命周期许可处理；停在 Clarify 既不禁止关闭，也不自动授予关闭许可。

## 形成计划

用户决定推进执行后，在 Clarify 内自然形成必需的 `plan.md`，不为从目标讨论转入规划另问一次例行问题。这是执行准备，不是开始执行的许可。明确限制仍有效，真正未决的选择必须处理，不能藏进 Plan。

每个执行任务都有 Plan，即使只有一个简短单元。修订时保留既有标识、已完成结果及有效证据。改变父任务合同前读取链接子任务。需要时混用正文单元和 tk 子任务链接；创建任务遵循 tk 的适用许可，不仅为取得材料目录而建任务。

每个单元给出可独立评估的结果、目标与设计依据、变更及非目标、前置条件、可观察验收、必需检查、所需许可和材料归属。链接单元可以将细节留在子任务，父 Plan 保留目标、依赖和链接。单元应有足够结果价值承担独立 Verify，也应能完整实现和审阅。

安排真实依赖并识别独立工作。区分可由已验证前序候选提供的代码依赖，以及确实需要存在的外部部署、服务或发布产物。项目允许使用已验证依赖分支时，不把未获授权的合并设为开发前置。没有要求及相关许可，不增加交付、安装或昂贵的真实模型实验。

Plan 应让另一 Agent 无需虚构产品选择即可执行。准备阶段处理可预见的用户决定，不以“待决定事项”清单充当执行合同。确实缺决定时，在可执行 Plan 之外说明阻塞并保留已确定工作。

## 检查材料

Plan 形成后，按公共检查合同主动开展前期材料自检。比较当前 Goal、Design、Plan、链接子任务材料及相关讨论决定。检查变更要求是否同步、能力或条件是否遗漏、单元是否完整、依赖能否使用，以及可预见许可或产品决定是否处理。按需检查写作与项目文档规则。

这是材料检查，不是工具、环境或文件可用性预检。分析许可不授权安装依赖、改变 Git 状态，或运行会写入授权材料之外的格式化程序。

作者修订范围内材料问题，未达所选上限时使用新的只读检查。严格遵循公共合同的通过提前结束、累计计数及上限处理规则。未决要求或重要选择回到讨论，不虚构答案。

前期材料的独立 Verify 不自动启动。用户请求后冻结当前材料，向所选独立核验者提供所属 Task、材料范围、候选位置及回复对象。用户请求涵盖范围内作者修订及同一核验者的复查，直到当前材料通过或遇到实际阻塞。明确的一轮、只给报告或更窄限制优先。Verify 始终只读，不接管作者修订。无法判断不是通过。

## 返回

保存获准的材料及检查结果。返回路径、已确定结果、检查次数及结论、按请求开展的独立 Verify 结果，以及真实未决选择或阻塞。保留之前失败记录的原范围与候选，不把 Goal、Design、Plan 或材料审查完成当作实现完成。

在 Clarify 内结束。前期请求的结尾不邀请、建议或询问启动执行。只有用户实际同时请求执行时，才按执行自身的范围和许可处理。

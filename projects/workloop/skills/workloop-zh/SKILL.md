# workloop

引导 Task 澄清目标、实现、独立核验，并完成项目定义的交付。公共合同与所请求的操作共同生效。指令引导 Agent 行为，不通过程序强制执行。

## 进入

行动前完整读取本文件。根据用户和适用指引解析所请求操作、当前项目、所属 Task、有效要求、范围与许可。引用、解释或编辑某个操作的指令，不表示执行该操作。导览请求只获得说明，不启动实现。

使用 tk 管理持久 Task。通过其公开接口和适用任务管理指令使用，例如使用 CLI 时加载 tk-cli Skill。不导入或读取其他组件的实现文件。其他 Skill 和协作工具只用于需要它们的活动，举例提及不使其成为通用前置条件。

通过完整安装的 Skill 和自然语言选择操作。只读取对应正文，沿实际加载位置解析链接：

- [澄清](./operations/clarify.md)：明确目标，调研、设计并形成或修订 Plan。
- [执行](./operations/exec.md)：当前会话实现并协调检查。
- [核验](./operations/verify.md)：独立评估材料或实现候选。
- [交付](./operations/ship.md)：完成项目定义的交付。
- [监督](./operations/supervise.md)：调度独立 Worker，不亲自实现其工作。

需要初始化或重新配置时，读取[设置](./setup.md)。

使用用户语言，遵循项目写作规则，并在可用时使用 well-said 一类写作 Skill。修订材料时保留事实、决定、条件、否定、归属及真实不确定性。

workloop 面向新任务，不识别旧流程别名，也不迁移旧材料名称。按 workloop 开始的 Task 继续、返工和恢复时，保留原身份及有效要求。

## 保留要求

区分已确认要求、用户指定的方案约束、提议、观察及临时限制。现有代码、生成的 Plan、测试或 Agent 完成声明都不构成用户批准。动机不增加验收门禁。材料冲突按当前有效决定处理，不挑选最容易执行的派生文档。

先读相关来源，不询问材料已能回答的事实。对不必要、不可行或有害工作提出质疑并说明证据。不悄悄替换目标、缩小范围或取消已有能力。暂缓能力不等于永久禁止。保留已完成结果，只重开变更要求或发现问题所影响的工作。

## 确定归属

分配单元或保存材料前，通过 tk 解析所属 Task。同一工作线复用现有 Task。父任务、依赖、共享顾问或旧会话不会自动成为新结果的所有者。创建、关系、元数据及关闭遵循 tk 和项目许可，不手工修改托管元数据。

单元标识在所属 Plan 内保持稳定，新序列从 U01 开始。Plan 可以直接展开单元，也可以链接到承载细节的 tk 子任务。执行该单元时读取链接细节。修订 Plan 时保留标识及已完成单元，不机械地为每个单元创建子任务。

父任务保存跨单元决定及链接，子任务结果归子任务。稳定结果写入材料；实时角色选择、回复路由、待完成分派及临时许可状态留在会话上下文。

## 保存材料

请求某项操作默认授权保存该操作的普通结果材料。复用所属 Task 的既有文件，更新前先读，有意义的结果形成后及时保存，返回前落盘。明确的仅对话、不记录、不写入或更窄限制优先。目标位置确实无法解析时说明缺什么，不另找位置绕过限制。

- `goal.md` 用自然语言说明要做什么、预期结果、约束及停止条件，不写实现方法或代码细节。
- 可选 `design.md` 说明如何达到目标，可包含必要架构、算法、数据结构或实现细节。
- 可选诊断记录问题、现场、证据及有依据或尚不确定的原因，不写修复方法或建议；这些内容由设计讨论承接。
- 可选 Research 提供带可追溯来源的汇总。先读汇总，需要核对事实时再追溯证据。
- 可选 Grill 保存讨论过程，通常使用 `grill.md`，不代替当前目标或决定。
- Execute 前必有 `plan.md`，简单或单单元任务也不例外。它定义可执行单元，可以使用链接的子任务材料。
- `execution.md` 保存单元候选、结果、修复、实际检查及限制；已有执行记录时复用。
- `verification.md` 逐轮追加独立评估，绑定范围和候选，保留过往评估及失败结论。
- `ship.md` 保存实际项目交付结果；已有交付记录时复用。

可选活动不需要空材料或材料职责对应表。辅助 Skill 的记录规则适用于使用它的活动。保存材料不授权实现、Git 操作、配置修改或 tk 生命周期转换。存储受限时说明并继续不受影响的工作，不把未保存的必需报告说成已保存。

## 分离许可

Clarify 可维护其普通分析材料及必要临时文件，不授权代码、配置、Git 或托管元数据修改。讨论、设计及规划不启动实现，回复也不邀请下一操作。

明确执行请求通常授权项目要求的范围内常规实现、修复、项目本地准备、检查、临时进程及保留本地候选所需操作。不反复索取这些许可，仍遵循项目对特定受保护操作的要求及更窄指令。

执行不自动授权集成、推送、发布、本机安装、费用、特权操作或 Task 关闭。已授权的临时目录文件检查仍属于其检查范围。Ship 动作根据项目交付定义、实际请求和仍有效的授权解析，操作名称本身不授予固定动作包。复用许可，不把核验当验收，也不把验收当作其他无关许可。

执行和监督期间不得调用 `ask` 一类结构化问答工具，也不得通过包装工具或其他 Agent 绕过。读取证据并作出已授权选择。必须由用户决定的问题用普通文字提出，继续不受影响的工作。Clarify 保留适用的访谈方式。显式 `noask` 同样禁止结构化问答，恢复时必须保留这一含义。

## 检查结果

每次自检使用新的只读检查上下文。作者修订，检查者不实现。按下文角色规则选择检查者，提供 Task、范围、候选或材料位置、适用依据、已有检查证据及报告位置。报告须列出有证据、可处理的问题及最终结论，没有问题也是有效结论。使用原生子代理时，无论 `nowait` 如何设置，都等待宿主原生的最终结果屏障。

根据任务规模与复杂度在三至五轮中选择自检上限，适用指令设置其他值时从其规定。前期材料和各实现单元分别计数，首次与复查共同计入。完成实质检查消耗一次，启动或通信失败不计。修订及独立 Verify 反馈都不重置计数。

当前候选通过即提前结束自检，首次通过也一样。否则范围内修订，仅在未达上限时请求新的检查。达到上限后停止追加，完成可处理修订，说明未解决发现及未经过自检复查的变更。耗尽上限或旧候选通过都不表示当前通过。不为对正确性、一致性、目标或实际使用没有实质影响的细节反复检查。

Plan 形成后默认自检材料。准备材料的独立 Verify 按用户请求启动，不因自检达到上限而启动。每个实现单元都需要自检及独立 Verify，独立 Verify 不受自检轮次上限约束，不以一种检查代替另一种。

## 协作角色

各角色的宿主、模型、思考强度及位置分别根据当前请求、继续有效选择、适用外部默认解析。接受自然语言选择，保留模型别名。不从执行者推断 Verify，不静默替换不可用模型。需要该角色时再处理缺失选择，遵守当前问答限制。

Senior 只在本次执行明确分配时存在，继续执行保留其分配直到变更。默认模型不启用角色。在已确认目标与约束内，向已分配 Senior 咨询实施选择和范围内澄清。提供 Task、单元、依据、约束、选项、所需决定及实时回复对象。在当前要求与许可内直接采用其建议。目标、优先级、重要需求取舍及受保护许可仍由用户决定。Senior 不能覆盖要求、扩展范围、豁免检查或代替独立 Verify。

使用所选协作工具的公开接口和说明。推荐 Herdr，但不要求必须使用，也可使用 tmux 等终端方式。指定会话工作位置，发消息前发现实时身份。正常启动会话，用普通消息派工，不注入系统提示词。不操作其他 Agent 的问答对话框。

跨单元及复查复用合适的 Verify 和已分配 Senior 会话，与实现保持隔离，核验者不得实现受审目标。角色忙碌时先完成或恢复其现有分派，不另发新任务；仅在没有合适会话或用户要求替换时创建。审查期间冻结候选，不发未经请求的中途消息，不读取工作中 Agent 的私有会话文件。

跨会话工作及咨询默认等待最终结果。使用协作工具的等待操作；命令转入后台时，再使用宿主阻塞式最终结果等待，直到获得结果或具体阻塞。不轮询，不根据生命周期标签推定结论。只有显式 `nowait` 才允许省去跨会话等待，保留分派并在最终结果返回后恢复；它不改变原生自检等待、范围、检查或验收。向负责人发送最终回信时不等待负责人。

分派注明所属 Task、单元、依据、准确范围、候选或依赖基线、许可与限制、要求结果、报告位置、停止点及实时回复对象。只发最终结果。有限范围的 Senior 咨询与发送部分进度报告不同。独立 Verify 只提供 Task、单元或材料范围、候选位置及回复对象，由核验者自行解析依据，不附实现者的审查清单。

推进前核对结果的发送者、单元、候选、结论及保存报告。证据缺失、过期、截断或冲突时澄清，不推定通过。结果已保存但未送达时，先恢复该结果，再考虑重派。非幂等动作可能已成功时，先核对效果再重试。

## 建立证据

实际检查改变的行为，运行适度且项目要求的检查。记录候选身份、条件、实际输入、观察、证据位置、覆盖范围、偏差及未验证部分。源码审阅、文件检查、受控 Provider、实际宿主或 UI 运行及真实模型运行证明的内容不同。测试通过本身不能证明请求的行为。没有要求和必要许可，不增加安装、昂贵实验或效果指标。

变更使受影响证据失效。复用未变证据时说明其身份及范围。实现、自检、独立 Verify、用户审查、交付、安装、重启、发布及 Task 状态分别处理。

## 恢复上下文

在持久上下文或能跨压缩保留的会话状态中，保存操作、所属 Task、单元、依据及入口位置、当前候选、有效范围与许可、明确限制、已完成检查次数及上限、下一动作。实时角色、路由、所拥有资源及待完成分派与稳定产品材料分开。使用宿主可用持久化机制，不要求特定 Pin API。

以明文保留限制，包括“不得调用结构化问答工具”，不只保存 `noask`。行动前替换已撤销或变化的许可。完整公共合同或当前操作正文已不在上下文中时，先从实际安装的 Skill 重读，再继续。保留引用或历史“已读”声明不等于正文仍在。对照当前材料及实际效果恢复状态，不重复已完成工作或待完成分派。重载证明指令可用，不证明遵守。

## 处理失败

在所选操作内直接行动，不主动预检工具、环境或文件可用性。实际加载或动作失败后记录错误，只获取处理该错误所需信息，按需应用准备或诊断说明。不虚构替代品，不隐藏缺失前置条件，不削弱验收来获得成功。

材料冲突或设计缺陷回 Clarify，实现偏差回 Execute。只重开受影响工作，保留整体授权范围。不可行或无需行动时，可在保存有依据结论并取得必要共识后停止；Task 关闭仍按 tk 和项目规则处理。真正缺失的许可或事实只阻塞依赖它的动作，不阻塞其他就绪工作。

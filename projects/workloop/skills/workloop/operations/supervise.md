# Supervise

Apply the loaded [entry](../SKILL.md), then read [Task ownership](../references/task.md), [execution constraints](../references/execution.md), [role selection](../references/roles.md), and [collaboration](../references/collaboration.md). Coordinate the Plan through independent Workers. Do not implement their changes or act as their independent verifier.

## Resolve the Plan

Read the owning Task's goal, mandatory `plan.md`, linked unit details, dependencies, effective decisions, candidates, reports, and project rules. Return only the scope affected by incomplete preparation to [Clarify](./clarify.md), not an under-specified Worker. Apply the shared execution constraints to mixed readiness in a parent Plan.

Apply execution constraints to the selected scheduling scope, continuous progress, permissions, and prohibition on structured questions. A Worker's scope is not the overall Plan scope. Supervision activates no Senior and grants no integration. Resolve Worker, checker, Verify, and an explicitly assigned Senior independently under the role rules.

Keep Task, basis, scheduling scope, grants, restrictions, unit states, and next actions recoverable. Collaboration owns live identities, routes, pending assignments, editing ownership, and resource locations; do not put them in durable product materials.

## Assign work

Choose dependency-ready units delivering complete results. A Worker usually handles one unit at a time but may complete several serially within an explicit assignment. Use separate Workers for independent units only when scope and project rules permit. Do not manufacture parallelism across shared edits or unresolved prerequisites.

Assign through the workloop [Execute](./exec.md) operation, which owns implementation, exercised checks, self-check, independent Verify, and execution evidence. Do not load or duplicate its self-check algorithm to perform the Worker's checks yourself.

Under the collaboration contract, supply Task, unit and Plan basis, working location, editing boundary, grants and restrictions, dependency candidate/base, required checks, authorized materials, expected result, stopping point, and live reply owner. Include an assigned Senior's scope and route when present. Carry the prohibition on structured questions in plain language, not only `noask`. Do not delegate an ungranted action or add a stop contradicting effective scope.

## Coordinate candidates

Use one editing owner for shared files or logic, freeze candidates under review, and reuse suitable isolated Verify and assigned Senior sessions through the collaboration rules. A busy role finishes or recovers its current assignment before receiving another.

Preserve each completed candidate under project commit and branch conventions. Use verified dependencies under the execution constraints, keeping predecessors frozen, bases traceable, and descendants refreshed when a predecessor changes. External dependencies still require their actual state.

## Process results

Validate each final result's sender, Task/unit, candidate/base, changed scope, checks, self-check count and outcome, independent verdict and saved report, and limits. Read the report. Lifecycle state, implementation claims, and self-check success are not independent Verify.

Return in-scope findings to the responsible Worker without resetting inspection counts. Require affected checks and independent recheck with the same suitable verifier. For `unable to determine`, resolve the specific evidence or capability gap within the grant. Recover saved results after communication failure instead of duplicating work.

Material or design defects return affected work to Clarify. Do not redesign through an implementation assignment. Consult an assigned Senior only within its role boundary. State genuine user-only blockers in ordinary text and continue independent ready work.

After each current pass, save the result and schedule the next authorized ready unit without another continue instruction. When the selected scope is verified, return its candidates together for user review or already-authorized delivery. Do not integrate merely to keep scheduling moving.

## Return

Save substantive scheduling outcomes in the owning execution record: units, bases, candidates, report links, coverage, repairs, and blocked dependencies. Subtask evidence stays with its owner; the parent links it.

Return concise per-unit implementation status, self-check count, independent verdict/report, candidate/base, review and delivery state, and concrete remaining blockers. Preserve the whole selected scope if some units remain blocked. Supervision completion implies no merge, installation, publication, or Task closure.

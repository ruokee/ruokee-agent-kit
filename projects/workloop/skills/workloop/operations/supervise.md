# Supervise

Read the [common contract](../SKILL.md) in full. Coordinate the resolved Plan through independent Workers. Do not implement their changes or use this session as their independent verifier.

## Resolve the Plan

Read the owning Task's goal, mandatory `plan.md`, linked unit details, dependencies, accepted decisions, existing candidates, reports, and project rules. If preparation is incomplete, return the affected work to [Clarify](./clarify.md), not to an under-specified Worker.

A named subset limits scheduling. Otherwise continue the remaining Plan from the resolved starting point. Scheduling scope, each Worker's assignment, protected permissions, and parallelism are separate. The supervision entry does not enable Senior or grant integration. Execution is continuous by default and prohibits structured question tools. `confirm` requests item-by-item confirmation without removing required checks or enabling structured questions.

Resolve Worker, self-check, Verify, and any explicitly assigned Senior separately under the common role rules. Preserve live identities, pending assignments, ownership, and resource locations in recoverable runtime state, not Task materials.

## Assign work

Choose dependency-ready units with complete results. A Worker usually handles one unit at a time; it may complete multiple units serially within an explicit assignment. Independent units may run through separate Workers when the requested scope and project allow parallel work. Do not manufacture parallelism across shared edits or unresolved prerequisites.

Provide each Worker the owning Task, unit and Plan basis, actual working location, editing boundary, effective grants and restrictions, dependency candidate/base, required checks, authorized materials, expected result, stopping point, and live reply owner. Include the explicitly assigned Senior's advisory scope and route if one exists. Carry the prohibition on structured questions in plain language, not only `noask`.

Assign implementation through the workloop Execute operation, so the Worker implements, exercises behavior, obtains self-check and independent Verify, saves evidence, and returns a final result for its assigned scope. The Worker's unit boundary does not cancel the owner's authorization to continue the overall Plan. Do not delegate an ungranted action or add a stop condition that contradicts the user's effective scope.

Use normal session startup and ordinary messages through the selected collaboration mechanism. Apply shared final-result waiting; explicit `nowait` permits pending cross-session work but does not remove native self-check barriers. Do not inspect private working-session files or send unsolicited mid-work messages. Consult an assigned Senior only through a bounded request with a clear decision and current reply route.

## Coordinate candidates

Give shared files or logic one editing owner at a time. Freeze a candidate during any review. Suitable isolated Verify and assigned Senior sessions are reused across units; a busy verifier completes or recovers its current assignment before another is sent. Coordinate independent work without turning implementation context into verification context.

Preserve each completed candidate using the project's local commit and branch conventions. A verified unintegrated predecessor may supply a later unit's development base; pending user review or integration alone does not block that dependency. Keep predecessor candidates frozen and record each unit's identity and base. Refresh descendants and affected checks when a predecessor changes. External-state dependencies still need their actual prerequisites.

## Process results

For each final result, verify sender, Task/unit, candidate/base, changed scope, exercised checks, self-check count and outcome, independent Verify verdict and saved report, and known limits. Read the report. A lifecycle label, an implementation claim, or quick-check success is not independent verification.

On in-scope changes required, return the concrete findings to the responsible Worker, preserve its existing inspection count, and require the affected checks and independent recheck. Reuse the existing suitable verifier. On unable to determine, identify the exact missing evidence or capability and resolve it within the grant. Recover saved results after communication failure instead of duplicating completed work.

A material or design defect returns affected work to Clarify. Do not redesign the goal through an implementation assignment. Senior may settle implementation choices and in-scope clarification under the common role contract, but cannot override requirements, waive Verify, or authorize protected actions. State genuine user-only blockers in ordinary text and continue independent ready work.

After each current pass, save the result and schedule the next authorized ready unit without another continue instruction. When all selected units are verified, return their candidates together for user review or an already-authorized delivery. Do not perform integration just to keep scheduling moving.

## Return

Save substantive scheduling outcomes in the owning execution record: completed units, bases and candidates, report links, check coverage, repairs, and blocked dependencies. Keep routing and pending communication in runtime state. Subtask evidence stays with its owner; the parent links it.

Return compact per-unit status with implementation result, quick-check count, independent verdict/report, candidate/base, review and delivery state, and concrete remaining blockers. Preserve the full selected scope if some units remain blocked. Supervision completion does not imply merge, installation, publication, or Task closure.

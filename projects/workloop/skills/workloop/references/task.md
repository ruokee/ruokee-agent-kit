# Task ownership

Read before resolving or saving Task materials in Clarify, Execute, Verify, Ship, or Supervise. Setup and orientation do not need this reference.

## Resolve ownership

Use tk's public interface and applicable task-management guidance before assigning units or saving materials. Reuse the Task for the same effort. A parent, dependency, shared adviser, or earlier session does not automatically own a new result. Apply tk and project permissions to creation, relationships, metadata, and closure; never edit managed metadata by hand.

Continue, repair, and recover a workloop Task under its existing identity and effective requirements. Keep stable unit labels in its Plan, starting a new local sequence at U01. Do not mechanically create a subtask for every unit. Read linked unit details when executing or changing their parent contract.

A parent keeps cross-unit decisions and links; subtask results belong to the subtask. Stable results belong in ordinary materials. Live role choices, routes, pending assignments, owned runtime resources, and temporary permission state belong in recoverable session context.

## Save results

An operation request normally authorizes its ordinary result materials. Use the established files, read before updating, and save meaningful results as they settle and before returning. The operation body owns its material formats. Auxiliary Skills retain their recording rules for the activities that use them.

Conversation-only, no-record, no-write, or narrower limits take precedence. If the destination is genuinely unresolved, identify what is missing without writing elsewhere to evade the limit. A storage limitation blocks the required saved result, not unrelated ready work; do not claim an unsaved report exists.

Optional activities need no empty files or material-to-role matrix. Saving materials does not grant implementation, configuration, Git operations, or tk lifecycle transitions. Apply those actions' own effective permission.

## Bind evidence

Exercise changed behavior and run proportionate project-required checks. Record the scope, candidate identity, conditions, actual inputs, observations, evidence location, coverage, deviations, and unverified areas. Distinguish source and file checks, controlled providers, host discovery, actual UI or model runs, and user outcomes. Automated success alone does not prove the requested behavior.

A change invalidates affected evidence. Reuse unchanged evidence only with its author, candidate, conditions, result, and scope stated; do not claim it was independently rerun. Do not add installation, expensive experiments, or success metrics without a requirement and permission.

Implementation, self-check, independent Verify, user review, delivery, installation, restart, publication, and Task status remain distinct. Ending an operation does not close its Task.

# ADR 决定：只由组件模板渲染系统提示词策略

Decision owner: Ruokee
Decision writer: OMP Claude Opus 5.5
Reverses: [由宿主模板渲染系统提示词策略](../archived/2026-09-30-render-system-prompt-from-host-template.zh.md)
Archived: 2026-10-07
Reversed by: [保留即将弃用扩展的模板功能](../decision/2026-10-07-retain-system-prompt-template.zh.md)

[English](./2026-10-04-use-system-prompt-template-only.md) | 中文

## 动机

`@ruokee/omp-system-prompt` 只对宿主渲染的组件自有模板应用策略，模板由用户作为可选步骤自行选择；其他系统提示词一律交给宿主处理，不报告诊断。

该扩展把 OMP 指令块中的策略文本替换为自有文本，并追加按模型匹配的规则文档。它原先支持两条路线：由宿主渲染组件模板，以及识别宿主默认块并用组件模板重建的转换。该转换只识别 OMP 18.3.0 以前使用的身份行。在 18.3.0 及以后的宿主上，它找不到主块，每轮报告一次失败，宿主提示词保持原样，因此没有选择模板的用户既得不到策略文本，每个会话还会收到一条诊断。

按照[宿主内组件按共同的 OMP 下限维护](../decision/2026-10-04-raise-omp-host-floor.zh.md)，面向 OMP 的组件现在共用维护下限 OMP 18.5.0，没有任何受维护的宿主仍会用到该转换。模板路线在每个受维护宿主上都能完成这项工作；没有组件模板的轮次属于组件不服务的会话，而不是失败。

## 分析

在模板路线上，宿主依据所选来源渲染指令块，并生成自己的页脚块；该页脚块仍以 `<project-context>` 开头，并携带上下文文件、工作区数据和追加文本。Provider 的缓存断点落在第一个 `<project-context>` 块之前的最后一个块上，因此标记本身、块顺序，以及静态前缀与工作目录相关块之间的划分属于宿主的缓存布局，而不只是排版。

模板会收到会话的实时数据，包括可见 skills、rules、always-apply rules、tool inventory、internal URLs、设备列表、tool references 和任务设置，但不会收到插件设置。因此像 `renderDelivery` 这样的组件偏好无法在模板内部表达，渲染出的文本也不能证明选择者是谁。

在 18.5.0 中，[`discoverSystemPromptOverride`](https://github.com/can1357/oh-my-pi/blob/v18.5.0/packages/coding-agent/src/system-prompt.ts) 先查项目级，再查用户级；同一级别内，字面 `SYSTEM.md` 优先于 `SYSTEM_TEMPLATE.md`。命令行显式指定的模板或提示词优先于发现的文件。选中 `SYSTEM.md` 时，宿主用自己的自定义提示词模板包装其内容，`<project-context>` 块照常追加。

## 决定

### 只识别一种指令块

扩展只识别一种指令块形态：会话选择了组件自有模板时的渲染结果。扩展依据组件自有的模板文本加上经过校验的骨架来识别它，而不是仅凭宿主提供模板机制。识别依据是自有的静态骨架：每个锚点两端去空白、保持顺序、首锚位于块首、末锚位于块尾；模板动态槽位的渲染正文不参与校验。因此，复制完整静态骨架、只改这些动态槽位正文的第三方模板同样会被认领，这一边界是接受的取舍，不再用额外校验继续收窄。

当前轮的主块不能被识别为组件模板的渲染结果时，扩展不修改任何块，包括 `<project-context>` 页脚，也不报告诊断。这包括没有模板、使用 `SYSTEM.md`、使用 `--system-prompt`、使用他人模板以及渲染骨架损坏的会话。宿主按自己的默认逻辑工作。扩展不猜测结构，也不会报告策略已应用。

扩展不识别、也不改写宿主默认系统提示词的结构。它不保留默认块路线、路线之间的优先顺序、旧 `PROJECT` 页脚的处理，也不保留只由默认块路线执行的 skill description 单行化。

### 选择组件模板

组件以 `host-template.hbs` 提供其模板，这是由自有策略文本生成的维护中产物。选择该模板是可选的安装步骤。中英文 README 的安装指引说明两种启用方式：单次运行时传入 `--system-prompt-template <host-template.hbs 的路径>`，或者把文件放为项目级或用户级的 `SYSTEM_TEMPLATE.md`。指引写明宿主的选择顺序：命令行参数优先于发现的文件，项目级优先于用户级，同一级别内 `SYSTEM.md` 优先于 `SYSTEM_TEMPLATE.md`，因此存在更优先的 `SYSTEM.md` 时，安装的模板不会生效。

组件不写入用户配置、不写入已安装宿主文件、不复制宿主自带模板。它不写入、不复制、不选择模板文件，也不修改、删除用户的任何系统提示词输入。

读取失败的模板由读取它的那条路径负责。作为严格参数传入的模板若缺失、不可读、为空或格式错误，会在扩展运行前导致该会话启动失败，扩展既无输入可保留，也没有需要报告的内容。模板发现遵循宿主自己的优先级，因此为空的候选会被跳过，宿主继续查找，只有在没有其他候选时才回落到自带提示词。扩展只对最终到达其 handler 的那个块做分类：在跳过空候选之后仍然生效的组件模板照常处理；它无法校验的块一律不改写。

### 模板路线上扩展负责的内容

- **指令块。** 模板渲染结果在其位置逐字节保留，其中的工具、设备、`xd://` URI、skill、规则和运行时区段已经带有宿主的实时数据。
- **Delivery。** 每个受覆盖 turn 都通过公开设置 API 读取有效 `renderDelivery`，并由它决定自有 Delivery 章节是否作为独立块紧跟已识别的模板块插入。其内容、默认值、失败回退取值和逐轮刷新保持原有含义。占据该位置的他人块属于其他写入者：扩展保留该块，并报告自己的章节未插入。
- **页脚。** 扩展修正外层加载说明并删除固定的外层 critical 尾部，同时 `<project-context>`、上下文正文、路径列表、workstation 数据、工作区数据、活动仓库文本和追加文本逐字节保留。页脚合同在已校验的外层边界识别精确已知的主代理及子代理 critical 尾部。未知尾部或无法唯一确定的边界使整个页脚保持不变，并报告该修正未应用。页脚不存在时无需处理也不报告。
- **模型规则。** 第二个 handler 把匹配的规则文档追加到该 turn 已有的数组，匹配方式、顺序和逐字节正文都不变。追加不依赖模板；替换步骤未改动的 turn，追加步骤仍然可以扩展传入数组。
- **Skill 文本。** 模板绑定宿主提供的可见 skill 数据。扩展不从命令元数据重新推导 description，不恢复宿主缩短过的 description，也不向可见集合添加 skill。

上述每一步各自报告自己的有界结果。某一步失败不会抑制其他步骤，任何一步成功也不代表其他步骤成功。

### 页脚归属标记

没有加载说明的页脚，其 append 以完整已知 critical 块开头时，需要转换状态信号。删除原生尾部后，append 占据与未处理尾部相同的文本位置。Delivery 关闭时，两种身份的完整块数组可以相同，但一种要求保留，另一种要求删除，仅凭文本无法区分。有加载说明的页脚在转换后已有自有加载行。

仅在三个条件同时成立时插入中性、无策略指令的归属注释：有效页脚没有加载说明、本次转换移除了精确识别的原生 critical 尾部、append 开头为完整已识别的原生 critical 块。注释位于外层 `<project-context>` 内，但在 workstation 数据、上下文正文、路径列表、工作区数据、活动仓库文本及 append 字节之外。相对于原完整输出，注释及其必要分隔符是逐字节一致要求的唯一例外。普通 append 和有加载说明的页脚不新增标记；这一例外不允许改写不透明数据或策略指令。

通过自有加载说明或位于已校验结构位置的注释识别已转换页脚，不从不透明数据中的标记文字判断归属。保持 `<project-context>` 块首、数组位置及静态前缀缓存边界，不使用进程内归属缓存或新增设置。识别仍依赖文本，不是来源证明或安全边界。

[projects/omp-system-prompt/README.zh.md](../../../projects/omp-system-prompt/README.zh.md#工作机制) 维护具体页脚合同，并区分 API 回归与真实宿主 Provider 观察。观察必须覆盖需要标记及无需标记的形态，包括普通子代理，不声称宿主全面认证。

### 重复 turn 与设置变更

模板路线是幂等的。输入已经携带模板块、位于预期位置的自有 Delivery 章节和已修正页脚的 turn 会被识别，且在没有实际变化时不返回替换，因此设置不变时重复处理保留完整块数组。`renderDelivery` 在 turn 之间变化时只增减该章节，页脚已被转换过的提示词同样适用。

### 兼容边界

兼容对象是扩展而不是宿主。组件的维护下限是[宿主内组件按共同的 OMP 下限维护](../decision/2026-10-04-raise-omp-host-floor.zh.md)记录、并在组件 README 中声明的共同 OMP 下限。宿主 peer 仍以无限制范围声明，扩展不读取宿主版本来决定资格、激活、转换、诊断或回退，兼容边界仍然是依据 turn 输入的结构识别。组件不内置宿主自有提示词文本，并说明自动检查所渲染的 fixture，以及每条观察来自哪个版本。

### 沿用此前决定中的规则

系统提示词此前决定中的以下规则保持原意：

- 只分发一个自包含扩展，仅使用未经改动的宿主发行版和公开 API，不改写已安装文件，不为用户写入提示词文件。
- 每个受覆盖 turn 都处理当前 `event.systemPrompt`，不使用启动快照。
- 只识别一个受支持的输入结构，不假定固定数组下标，把内嵌正文视为不透明数据，校验后输出若无变化则不返回替换。
- 每轮通过公开设置 API 读取 `omp.settings.renderDelivery`；只有精确的 boolean `false` 才省略该章节；读取失败或非 boolean 取值保持启用并报告一条有界诊断。
- 失败时保持开放，诊断有界且不包含提示词正文、skill 名称、私人路径或会话上下文，按会话去重，包含 `unexpected-error` 边界与激活期模板失败。
- 保留已记录的覆盖边界与证据边界，要求以 provider 侧内容作为证据，而不是仅凭 handler 返回值。

## 考虑过的替代方案

**扩展现有转换器去识别升级目标的默认块。** 在讨论如何让策略继续在新宿主上生效时考虑过。它保留一条不需要用户配置的路线，但组件要持续维护一个针对宿主自有提示词文本的解析器，宿主每次改写该块都会重现同样的失败。

**改用纯文本自定义提示词路径而不是模板。** 在比较受支持路径时考虑过。纯文本安装更简单，但该路径会依据宿主的纯文本自定义模板渲染会话数据，而不是依据组件自有的文本，因此维护中的工具、设备、internal-URL 和运行时区段无法保留。

**把 Delivery 章节写进模板。** 在决定该章节位置时考虑过。这样无需逐轮插入，但模板无法读取插件设置，文档化的开关及其逐轮变更会丢失。

**随包提供一个无需用户操作即生效的默认模板。** 这是替换默认块路线时最初的方向。它能为什么都不选的用户恢复策略文本，但组件必须写入或选择宿主提示词文件，这是本决定排除的做法，也会覆盖宿主留给用户的选择。

**未识别到模板渲染结果时继续报告诊断。** 这是本决定之前的行为。它能提示模板未能匹配的用户，但使用 `SYSTEM.md`、`--system-prompt` 或没有模板的用户，会因为组件本不服务的路径收到失败报告。

**为每个已转换页脚加标记，或在提示词之外携带转换状态。** 设计页脚归属标记时考虑过。为全部无加载说明页脚加入标记会不必要地改变普通输出。在提示词之外携带来源或处理状态能保留提示词字节，但需要独立的接口及生命周期设计。有条件注释将状态保留在已校验页脚内，把 Provider 可见变化限定在歧义形态。

## 结果

模板未生效时不会有提示。模板被更优先的 `SYSTEM.md` 覆盖、使用的 `host-template.hbs` 副本已过期，或者其静态骨架被编辑过，用户都会得到宿主提示词，没有诊断，并可能以为策略已经生效。只改动动态槽位正文的编辑仍会被认领，因为槽位正文不在识别依据之内。

没有选择模板的用户得到宿主自己的策略文本。组件的策略只在完成可选安装步骤后生效。

模板路线把组件文本作为宿主直接读取的文件发布出去。由于模板绑定宿主侧的区段，宿主改写这些区段或更改字段时需要同步更新组件的模板；在那之前，渲染结果会继续携带旧区段文本，而不是直接失败。

接受宿主预览并汇总过的 skill description，意味着旧转换此前保留的一项激活约束可能在没有诊断的情况下从提示词中消失，因为宿主侧的缩短属于预期行为。

归属注释会在歧义页脚形态下改变 Provider 可见的输出，要求完整字节一致的消费者仍可能拒绝这一输出。在已校验位置之外识别标记可能留下原生策略，因此不透明文本不能参与归属判断。

文本识别仍然不是来源证明或安全边界。真实宿主验证只能证明观察到的行为，组件文档必须继续标明所验证的 fixture 与每条观察的范围，而不是承诺精确的宿主兼容性。

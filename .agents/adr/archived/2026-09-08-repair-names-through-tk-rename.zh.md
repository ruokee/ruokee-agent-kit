## 动机

本决定记录带载体发现的完整 tk Task 数据模型，并扩展 rename，使其修复已有的字符串名称和可识别的生成式目录后缀。[tk 产品架构](../decision/2026-08-21-define-tk-product-architecture.zh.md)把项目文件作为唯一权威的 Task 状态。

载体发现把有效 Task、普通材料和损坏的受管数据区分开，普通操作要求目标通过严格发现。若要求旧名称先完整通过校验，运行时就无法执行这项修复，而 UUID 仍是身份，路径仍只是定位器。

## 决定

### 项目、路径与表示

项目使用 `.agents/tk_config.toml` 中的稀疏配置，选择一个项目相对 Task 根目录、默认子 Task 创建目录、Git 策略、创建策略和元数据模式。默认 Task 根目录是 `.tk`。`subtasks_dir` 只控制后续子 Task 的创建位置，不限制发现，也不移动已有数据。

顶层 Task 使用规范的 `YYYY/MM/DD-NN--slug` 拓扑。新建子 Task 在父 Task 或其配置的 `subtasks_dir` 下使用稳定的两位 `NN--slug` 目录。已有子 Task 可以位于有效顶层 Task 下的任意真实后代目录。最近的有效祖先 Task 定义父级，元数据不保存 `parent`。

生成式直接子 Task 的序号分配检查所有已发现且叶子目录具有有效 `NN--slug` 的直接子 Task，取最大序号且不填补空洞。配置的创建目录只决定目标位置。序号 `99` 是可生成的最后一个同级编号，耗尽时在写入前失败。

项目统一使用 split 或 embed 元数据模式。split 把元数据存入 `tk.toml`，把正文存入 `TASK.md`。embed 把相同元数据存入受限 YAML frontmatter，并保留下方正文的原始字节。一个项目不会让不同 Task 混用表示形式。

Schema 1 包含不可变 UUIDv7 `id`、规范化 `name`、`planning`、`open` 或 `closed` 状态、不可变且带时区的 `created_at`、同一 Task 根目录内的 `depends_on` 和 `related_to` 关系，以及可选且可无损表示的 `extra`。schema 不存储父级、分支、优先级、分配对象、更新时间、关闭原因或会话身份。

每个正式发布的 schema 转换都保留相邻的前向迁移器。迁移按顺序应用这些迁移器，同时支持 split 和 embed，并保留 Task 正文。不提供降级、schema 0 或未发布开发格式的兼容合同。

### 载体发现、身份与生命周期

顶层发现首先要求规范拓扑、合法日历日期、非空 slug，以及与 slug 一致的元数据名称。后代发现随后遍历每个有效顶层 Task 下的真实普通目录。

后代目录只有通过项目元数据模式对应的标记才成为结构候选。split 模式以常规 `tk.toml` 为标记，有效 Task 还必须具有常规的配对 `TASK.md`。embed 模式要求常规 `TASK.md` 以可识别的 tk frontmatter 开头，其首个元数据键为 `schema_version`。完整载体必须通过严格的 schema、身份、表示和安全路径校验。

生成式 `NN--slug` 子 Task 必须让元数据名称与 slug 一致。非生成式子 Task 没有路径与名称一致性要求。带标记但无效的目录作为受管错误交给 `check`，普通发现不会返回。无关 `TASK.md`、普通 YAML frontmatter、符号链接、特殊文件、WAL、`.tk-tmp`、清理数据和 Task 根目录外路径不会成为 Task。除运行时自有路径外，普通目录和无效目录仍在最近有效祖先下继续遍历。

发现顺序固定。一次扫描最多接受 100,000 个真实目录和 256 层后代。超过任一上限或遇到必要 I/O 错误时，扫描失败且不返回部分任务图。

UUIDv7 是权威身份。路径用于定位 Task，名称用于描述 Task。重复 ID 仍是任务图诊断，并使 UUID 解析产生歧义。关系只能存在于同一个 Task 根目录内。Task 不能关联自身，`depends_on` 不能形成环。关系会去重并按 UUID 稳定排序。

`planning` 保存用户希望保留的早期想法、调查或计划。`open` 表示正在处理 Task。`closed` Task 可以读取，除此之外保持只读。关闭和重新打开都需要非空原因和当前明确授权。正常关闭还要求所有后代 Task 和依赖项均为 closed。强制关闭只绕过这两项检查。

严格模式项目创建顶层 Task 时需要当前明确授权。宽松模式项目可以保存值得持久记录的工作，不把创建视为执行承诺。创建 planning Task 仍要求用户表达保存这项早期工作的意图。

### 发现任务图、精确引用与 Git 策略

Task 根目录不维护永久索引或缓存。每次操作按需构建一份按载体发现的任务图。搜索、普通精确路径解析、父级和后代检查、关系校验、`check`、schema 迁移、元数据模式切换和序号分配使用严格任务图。

精确读取和普通修改接受完整 UUIDv7、绝对已发现 Task 目录、绝对受管载体，或当前项目中的相对已发现 Task 路径。rename 接受相同的精确形式来定位唯一修复候选。该候选的载体必须可解析，唯一容许的旧状态缺陷是 rename 修复范围内的字符串名称或可识别生成式后缀。绝对材料路径可以定位所属项目，但不是精确 Task 引用。Git 项目使用 Git 根目录。非 Git 项目通过规范顶层祖先和有界项目检查发现，不会一直遍历到文件系统根目录。

search 只把查询分类一次，类别依次为 UUID 或显式 Task 路径、现有材料路径、显式正则表达式或字符串，分类后不再回退。search 默认包含全部三种状态，并按 `uuid`、`path`、`regex`、`string` 的匹配类别顺序排列。同一类别按 `created_at` 降序、ID 升序排列。默认限制为 20，最大为 100。结果根据严格发现任务图报告 closed 祖先。

Git 策略只在持久写入前运行。`track` 要求受管 Task 文件不被 Git 忽略，`ignore` 要求 Task 根目录被忽略，`none` 不调用 Git 策略命令。tk 不修改 Git 配置、忽略规则、索引、提交或历史。

### 持久化与维护

受管单文件变更先在同目录写入完整临时文件，再原子替换目标。普通写入不使用锁、租约、compare-and-swap 或自动合并。并发完整替换由最后完成的操作决定结果。

WAL 是按日保存的普通 Markdown 活动记录。元数据先提交，再自动追加 WAL。WAL 失败会返回警告，但不会回滚已经提交的元数据。actor 是归因文本，不表示身份或授权。

多目标操作先完成全部领域预检，再按确定顺序提交，在第一个错误或取消点停止，并返回已完成项、未完成项和原始错误。操作不会自动回滚，也不会写入续跑状态。后续调用重新构建发现任务图，并根据当前受管文件重新规划。

多目标项目写入会在首次持久写入前创建活动操作标记。标记记录操作、项目范围、Linux boot ID、PID 和进程开始时间。操作进程仍在运行时，其他写操作保持阻塞。操作进程退出后，其他写操作仍保持阻塞，直到 GC 删除标记。read、search 和纯诊断仍然可用。活动操作标记不是通用锁。

清理清单只包含格式版本、操作进程身份、创建时间和 tk 临时路径。GC 只删除可以证明由 tk 创建的临时内容，以及已经结束的活动操作标记。它不会继续、回滚或修复 Task、迁移、rename 或组件操作。

rename 执行普通改名，也修复已有字符串名称不规范、为空、规范化后为空或超过当前显示宽度限制的问题。它还修复具有可识别结构、非空后缀与元数据不一致的生成式目录。新名称、身份、schema、日期、状态、关系、`extra`、项目归属和最终路径必须通过校验。名称缺失、字段类型错误、载体不可解析、标记缺失、schema 不受支持、身份损坏、不安全路径、日期或序号损坏，以及无法识别的生成式结构仍然报错。

修复扫描沿用普通表示标记、路径边界、遍历顺序和资源上限。可修复候选参与 UUID 唯一性和结构归属判断。名称损坏的副本不能消除 UUID 歧义。候选位于无效的受管祖先之下且无法确定父级时，rename 拒绝该候选。其他命令继续使用严格发现。

rename 只修改 Task 名称和适用的生成式目录，再追加正常 WAL 事件。它保留 UUID、状态、创建时间、关系、`extra`、正文字节、已有 WAL、日期、序号和父级位置。非生成式子 Task 保持目录不变。生成式子 Task 或顶层 Task 保留序号并更新 slug 路径。rename 报告原始旧名称、解析出的父级、旧路径、目标路径和 Markdown 引用，不改写引用。`git_policy=track` 扫描 Git 跟踪的项目 Markdown；`ignore` 和 `none` 扫描 Task 根目录下的普通 Markdown。dry-run 不写入。仅修复路径也属于变更。

`check` 在不修改内容的前提下校验带标记载体、生成式名称与路径一致性、UUID 和直接子 Task 序号唯一性、关系、WAL、活动操作标记与清理数据。它报告带标记的无效载体和解析出的逻辑父级。必要 I/O 失败或发现上限会停止扫描并报告检查不完整。只有 tk 无法表达修复、Agent 已说明具体编辑且用户在当前对话中明确授权时，才允许人工修复。Task 恢复可用后，Agent 再次运行 `check` 并用 WAL 记录修复事件。

完整格式和操作细节见[数据模型](../../../projects/tk/docs/design/data-model.zh.md)与[工具 API](../../../projects/tk/docs/design/tool-api.zh.md)。

## 考虑过的替代方案

**只支持 split 或 embed。** split 便于直接检查元数据，embed 可以把一个 Task 保存在单个文件中。两者能够承载相同 schema，不需要把其中一种降为次要表示。

**使用锁、事务或持久恢复计划。** 这些机制会增加协调逻辑和第二个操作状态机。原子替换、完整预检、明确的部分提交结果、活动操作标记和从当前受管文件重试已经覆盖目标工作方式。

**rename 时自动改写 Markdown 引用。** 自动编辑可能修改无关文本或有意保留的历史内容。只报告引用可以保持 Task 变更精确，并把内容决定交给调用方。

**继续只在 `subtasks_dir` 下发现子 Task。** 这种方式缩小扫描范围并保证生成式路径，但改变放置偏好会隐藏有效载体，使导入的子 Task 无法访问。

**要求先人工修复名称再运行 rename。** 这会让负责名称修复的运行时操作无法加载修复目标，也会让 split 和 embed 具有不同的恢复路径。

## 结果

Task 状态保持人类可读，并能跨接口移植。改变 `subtasks_dir` 不再改变可见性，导入或重新组织后的有效子 Task 载体仍然可用。

Task 下完全有效的载体即使原本只是示例，也会成为 Task。仓库不应把完整受管载体复制到普通材料中。把有效载体移动到另一个有效 Task 下，也会在不修改元数据的情况下改变推导父级、关闭阻塞项和同级编号。`check` 和 rename 会显示解析出的父级与路径，便于诊断。

递归发现会比配置路径发现读取更多目录。固定深度和目录上限避免无界工作，但大型或不可读材料树可能让全项目操作以显式错误失败。由于没有永久索引，发现、check、关系校验、迁移、表示切换和修复计划可以使用与候选数量成比例的内存。

rename 可以恢复符合条件的名称，但不会让 read、search、update、生命周期、迁移或表示切换获得宽松加载权限。修复计划需要维护第二种校验模式，且只容许旧名称和可识别后缀缺陷。无效受管祖先可能让后代候选因无法安全确定父级而不能修复。

普通并发写入采用最后完成写入者语义。多目标失败可能留下合法的部分结果，调用方必须检查已完成项和未完成项后再重试。目录已移动但元数据失败时，活动标记清理后根据当前受管文件重新规划。进程退出后不存在隐藏续跑状态，也不自动回滚。

每个正式发布的 schema 转换都会成为长期维护代码。支持两种表示也要求两条路径具有等价的验证、迁移、正文保留和名称修复行为。

## 变更

### 2026-09-05：创建不再接受正文输入

`TASK.md` 仍是由 Agent 维护的普通内容，因此 create 接口不接受通过 `tk create task --body`、顶层 create 请求或子 Task item 传入的正文。运行时创建 Task 时自动生成 `# <规范化名称>` 作为初始正文：split 模式下单独存在，embed 模式下位于受管 frontmatter 之后。创建之后由调用方维护正文，rename 和子 Task 重试匹配不把正文作为输入或匹配条件。调用方在创建完成后用普通文件操作写入 `TASK.md`。`tk log --body` 保持不变，因为 WAL 条目不属于 Task 正文。持久元数据 schema 和组件格式均未变化。

### 2026-09-05：rename 防止断链引用

会移动 Task 路径的 rename 在发现旧路径引用时，于首次持久写入前以 conflict 错误停止。错误 details 中包含旧路径、规范化后的新名称、绝对目标路径，以及每个引用的路径和行号。`--ignore-brokenlinks` 允许此次移动且不改写引用。dry-run 报告计划和引用，不写入内容。扫描边界保持不变，包括 Git 跟踪的项目 Markdown、Task 根目录下的普通 Markdown，以及 split 和 embed 正文。

### 2026-09-05：区分有界 WAL 读取与完整检查

`tk read` 按调用方设置的预算返回最近 WAL，上限为 50 条、16000 字节；字节数按紧凑 JSON 的 UTF-8 编码计算。`summary` 默认使用 5 条和 4000 字节，并省略 WAL 正文。`detailed` 默认使用 50 条和 16000 字节，并包含 WAL 正文。两种视图都返回完整的当前 Task 正文。`minimal` 不读取正文或 WAL。运行时从最新条目开始选择完整的返回条目，静默省略其余条目且不返回截断标记，最后按时间正序返回。完整历史仍保存在普通的 `wal/YYYY-MM-DD.md` 文件中。

`tk check` 不再通过有界读取路径校验 WAL。流式检查器按固定顺序读取每个普通的每日 WAL 文件并校验其中全部条目，不设置固定的历史总量上限，也不在内存中保存完整 WAL 历史。必要 I/O 失败和取消会使检查不完整，有效 WAL 的规模本身不会产生错误。

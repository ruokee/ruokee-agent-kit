# ADR 决定：由宿主模板渲染系统提示词策略

## 动机

记录 `@ruokee/omp-system-prompt` 支持的两条指令块路径：由宿主渲染组件自有模板，以及既有的宿主默认块转换。

该扩展把 OMP 默认指令块中的固定策略文本替换为自有文本，并追加按模型匹配的规则文档。它依据渲染结构识别默认块，并用扩展自有模板重建。当前升级目标中的宿主版本改写了该块，其结构不再匹配：在这些版本上，自有策略、Delivery 配置和页脚修正停止生效，而在仍可识别的宿主上继续生效。

宿主现在为同一件事提供了受支持的路径。用户通过宿主自身的机制选择 Handlebars 模板，宿主用与自带模板相同的实时数据和 helper 渲染指令块。该路径把组件自有文本放进块中，而不是重建宿主自有的提示词文本，因此契约需要说明各路径上扩展负责的内容。

## 分析

在模板路径上，宿主依据所选来源渲染指令块，并生成自己的页脚块；该页脚块仍以 `<project-context>` 开头，并携带上下文文件、工作区数据和追加文本。Provider 的缓存断点落在第一个 `<project-context>` 块之前的最后一个块上，因此标记本身、块顺序，以及静态前缀与工作目录相关块之间的划分属于宿主的缓存布局，而不只是排版。

模板会收到会话的实时数据，包括可见 skills、rules、always-apply rules、tool inventory、internal URLs、设备列表、tool references 和任务设置，但不会收到插件设置。因此像 `renderDelivery` 这样的组件偏好无法在模板内部表达，渲染出的文本也不能证明选择者是谁。

页脚仍由宿主依据自己的来源生成，并与其他路径一样以文本形式出现在块数组里传给扩展。

## 决定

### 识别两种指令块

扩展识别两种指令块形态，而不是一种。

1. 宿主默认块，turn 输入仍然携带它时适用。该路径保持既有行为：重建已识别的主块，并沿用既有的页脚转换。
2. 组件自有模板的渲染结果，会话选择了该模板时适用。扩展依据组件自有的模板文本加上经过校验的骨架来识别它，而不是仅凭宿主提供模板机制。识别依据是自有的静态骨架：每个锚点两端去空白、保持顺序、首锚位于块首、末锚位于块尾；模板动态槽位的渲染正文不参与校验。因此，复制完整静态骨架、只改这些动态槽位正文的第三方模板同样会被认领，这一边界是接受的取舍，不再用额外校验继续收窄。

其他形态一律保持输入不变并给出一个有界原因，包括扩展无法完整校验的宿主默认块，以及未按顺序在块首块尾复现自有锚点的骨架。扩展不猜测结构，也不会报告策略已应用。

### 路径优先级

两种形态都可能描述 turn 输入时，只要默认块路径仍能重建输入、且输入尚未把自有 Delivery 章节作为独立块携带，就由默认块路径作答。这保持了既有行为：章节仍留在旧路径重建的那个块内。模板路径处理其余输入：已经以独立块携带该章节的渲染结果，以及任何默认块重建都无法复现的输入，例如页脚已被转换过的混合形态。此后 `renderDelivery` 在 turn 之间变化时，只在持有该输入的那条路径上增减该章节。

### 选择组件模板

组件以维护中的产物形式提供其模板，该产物由其自有策略文本派生。用户通过宿主既有模板机制选择该文件，例如单次运行的命令行参数，或项目、agent 目录中可被发现的模板文件。组件不写入用户配置、不写入已安装宿主文件、不复制宿主自带模板，也不自行选择模板。

读取失败的模板由读取它的那条路径负责。作为严格参数传入的模板若缺失、不可读、为空或格式错误，会在扩展运行前导致该会话启动失败，扩展既无输入可保留，也没有需要报告的内容。模板发现遵循宿主自己的优先级，因此为空的候选会被跳过，宿主继续查找，只有在没有其他候选时才回落到自带提示词。扩展只对最终到达其 handler 的那个块做分类：在跳过空候选之后仍然生效的组件模板依然可以被正常报告；它无法校验的块，包括骨架与自有骨架不一致的他人模板、形似正文、缺少标识或骨架损坏的渲染，一律不改写，并报告为无法识别而不是已适配。

### 模板路径上扩展负责的内容

- **指令块。** 模板渲染结果在其位置逐字节保留，其中的工具、设备、`xd://` URI、skill、规则和运行时区段已经带有宿主的实时数据。
- **Delivery。** 每个受覆盖 turn 都通过与旧路径相同的公开设置 API 读取有效 `renderDelivery`，并由它决定自有 Delivery 章节是否作为独立块紧跟已识别的模板块插入。其内容、默认值、失败回退取值和逐轮刷新保持原有含义。占据该位置的他人块属于其他写入者：扩展保留该块，并报告自己的章节未插入。
- **页脚。** 扩展修正外层加载说明并删除固定的外层 critical 尾部，同时 `<project-context>`、上下文正文、路径列表、workstation 数据、工作区数据、活动仓库文本和追加文本逐字节保留。边界无法唯一确定时整个页脚保持不变，并报告该修正未应用。页脚不存在时无需处理也不报告。
- **模型规则。** 第二个 handler 与旧路径相同，把匹配的规则文档追加到该 turn 已有的数组，匹配方式、顺序和逐字节正文都不变。替换失败时追加步骤仍然可以扩展传入数组。
- **Skill 文本。** 模板绑定宿主提供的可见 skill 数据。扩展在该路径上不从命令元数据重新推导 description，不恢复宿主缩短过的 description，也不向可见集合添加 skill。description 单行化只保留在旧路径。

上述每一步各自报告自己的有界结果。某一步失败不会抑制其他步骤，任何一步成功也不代表其他步骤成功。

### 重复 turn 与设置变更

模板路径是幂等的。输入已经携带模板块、位于预期位置的自有 Delivery 章节和已修正页脚的 turn 会被识别，且在没有实际变化时不返回替换。`renderDelivery` 在 turn 之间变化时，只在持有该输入的那条路径上增减该章节，页脚已被转换过的提示词同样适用。旧路径保持其整体替换契约，两条路径都不匹配的 turn 原样保留输入并给出有界替换诊断。

### 兼容边界

兼容对象是扩展而不是宿主。宿主 peer 仍以无限制范围声明，扩展也不读取宿主版本来决定资格、激活、转换、诊断或回退，兼容边界仍然是依据 turn 输入的结构识别。组件不要求宿主保留旧的默认块，不把模板路径回溯到不具备该机制的宿主，不内置宿主自有提示词文本，也不提高维护下限。组件文档化的维护声明仍按[宿主内组件随宿主升级保持适配](./2026-09-28-adapt-components-to-host-upgrades.zh.md)记录，组件也说明自动检查所渲染的 fixture，以及每条观察来自哪个版本。

### 沿用归档决定中的规则

归档决定中仍然有效的规则在本决定下保持原意：

- 只分发一个自包含扩展，仅使用未经改动的宿主发行版和公开 API，不改写已安装文件，不为用户写入提示词文件。
- 每个受覆盖 turn 都处理当前 `event.systemPrompt`，不使用启动快照。
- 每条路径只识别一个受支持的输入结构，不假定固定数组下标，把内嵌正文视为不透明数据，校验后输出若无变化则不返回替换。
- 每轮通过公开设置 API 读取 `omp.settings.renderDelivery`；只有精确的 boolean `false` 才省略该章节；读取失败或非 boolean 取值保持启用并报告一条有界诊断。
- 以事件目录作为可见 skills 的权威来源，命令元数据只作为 description 边界的有序候选；无法建立对应时逐字节保留目录，外层边界不可靠时按结构失败处理。
- 失败时保持开放，诊断有界且不包含提示词正文、skill 名称、私人路径或会话上下文，按会话去重，包含 `unexpected-error` 边界与激活期模板失败。
- 保留已记录的覆盖边界与证据边界，要求以 provider 侧内容作为证据，而不是仅凭 handler 返回值。

## 考虑过的替代方案

**扩展现有转换器去识别升级目标的默认块。** 在讨论如何让策略继续在新宿主上生效时考虑过。它只需要一条路径，也不需要用户配置，但组件要持续维护一个针对宿主自有提示词文本的解析器，宿主每次改写该块都会重现同样的失败。

**改用纯文本自定义提示词路径而不是模板。** 在比较受支持路径时考虑过。纯文本安装更简单，但该路径会依据宿主的纯文本自定义模板渲染会话数据，而不是依据组件自有的文本，因此维护中的工具、设备、internal-URL 和运行时区段无法保留。

**把 Delivery 章节写进模板。** 在决定该章节位置时考虑过。这样无需逐轮插入，但模板无法读取插件设置，文档化的开关及其逐轮变更会丢失。

## 结果

支持两条路径意味着同一行为有两套识别与步骤实现。改动只应用到旧转换而未应用到模板（或反之）时，两条路径会产生不同的策略文本或页脚文本且没有任何报错，因此对自有策略、页脚修正或 Delivery 章节的改动都需要覆盖两条路径的检查。

模板路径把组件文本作为宿主直接读取的文件发布出去。用户若编辑该产物的静态骨架，或把宿主指向未复现该骨架的其他模板，会得到扩展不予认领的渲染结果，该 turn 保留宿主提示词并给出有界的“无法识别”原因，而不是静默应用部分策略。只改动动态槽位正文的编辑仍会被认领，因为槽位正文不在识别依据之内。由于模板绑定宿主侧的区段，宿主改写这些区段或更改字段时需要同步更新组件的模板；在那之前，渲染结果会继续携带旧区段文本，而不是直接失败。

在该路径上接受宿主预览并汇总过的 skill description，意味着扩展此前保留的一项激活约束可能在没有诊断的情况下从提示词中消失，因为宿主侧的缩短在该路径上属于预期行为。

文本识别仍然不是来源证明或安全边界。真实宿主验证只能证明观察到的行为，组件文档必须继续标明所验证的 fixture 与每条观察的范围，而不是承诺精确的宿主兼容性。

## 变更

### 2026-10-03：有条件的页脚归属

模板页脚合同在已校验的外层边界识别精确已知的主代理及子代理 critical 尾部。未知尾部和有歧义的外层结构保持既有保留及诊断行为。旧 `PROJECT` 路径的严格合同不变。

没有加载说明的页脚，其 append 以完整已知 critical 块开头时，需要转换状态信号。删除原生尾部后，append 占据与未处理尾部相同的文本位置。Delivery 关闭时，两种身份的完整块数组可以相同，但一种要求保留，另一种要求删除，仅凭文本无法区分。有加载说明的页脚在转换后已有自有加载行。

仅在三个条件同时成立时插入中性、无策略指令的归属注释：有效页脚没有加载说明、本次转换移除了精确识别的原生 critical 尾部、append 开头为完整已识别的原生 critical 块。注释位于外层 `<project-context>` 内，但在 workstation 数据、上下文正文、路径列表、工作区数据、活动仓库文本及 append 字节之外。相对于原完整输出，注释及其必要分隔符是逐字节一致要求的唯一例外。普通 append 和有加载说明的页脚不新增标记；这一例外不允许改写不透明数据或策略指令。

通过自有加载说明或位于已校验结构位置的注释识别已转换页脚，不从不透明数据中的标记文字判断归属。设置不变时，重复处理保留完整块数组，不返回替换。Delivery 切换只改变该章节。保持 `<project-context>` 块首、数组位置及静态前缀缓存边界，不使用进程内归属缓存或新增设置。识别仍依赖文本，不是来源证明或安全边界。默认块路径、有界失败行为、策略、模板产物、模型规则、维护下限及按结构判断的适用边界保留原合同，不新增宿主版本门禁或修改已安装宿主。

曾考虑为全部无加载说明页脚加入标记，但这会不必要地改变普通旧输出。也考虑过在提示词之外携带来源或处理状态，它能保留提示词字节，但需要独立的接口及生命周期设计。有条件注释将状态保留在已校验页脚内，把 Provider 可见变化限定在歧义形态。要求完整字节一致的消费者仍可能拒绝这一输出。在已校验位置之外识别标记可能留下原生策略，因此不透明文本不能参与归属判断。

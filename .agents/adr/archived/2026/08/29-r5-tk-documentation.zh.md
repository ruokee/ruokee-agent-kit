## 动机

通过完整规格、独立可用的组件指导和一致的双语文档，维护 tk 的四种材料模式。

这套共同规则让 Agent 和用户对模式会增加什么、需要维护什么，以及每项合同由哪个页面负责，形成一致理解。

同一语言的 tools Skill 与 CLI Skill 中内容相同的 tk 参考文件，源码只保留一份，由构建复制到该语言的每个 Skill。如果四个 Skill 源码目录各保留一份完整副本，每次共享修改都要在同语言的两个 Skill 目录里重复一遍；只改到其中一个目录时，tools Skill 和 CLI Skill 会向 Agent 给出不同的规则。

[Agent 行为规格](../../../../spec/tk-agent.zh.md)规定模式行为要求，[Skill 模式参考](../../../../../projects/tk/skills/tk-cli-zh/references/patterns.md)与 [Skill 指导](../../../../../projects/tk/docs/design/skill.zh.md)说明其用法。

## 分析

[已归档的文档维护决定](../../../archived/2026/08/29-r1-tk-documentation.zh.md)将 `scratchpad` 固定译为“临时记事区”，与“草稿纸”作为模式中文名称冲突。

[早期决定](../../../archived/2026/08/29-r2-tk-documentation.zh.md)要求四个 Skill 目录各自保留完整模式参考。每种语言一份共享源码避免重复修改，继续作为分发选择。[后续版本](../../../archived/2026/08/29-r3-tk-documentation.zh.md)将必要行为和验收唯一归给组件页面，使规格离开这些页面便不完整。因此规格包含完整要求，组件指导、设计和验证保留各自职责。

[直接前驱](../../../archived/2026/08/29-r4-tk-documentation.zh.md#adr-生命周期)要求独立的提案与决定格式。[ADR 机制](../../../decision/2026/08/22-adr-mechanism.zh.md)由任务保存讨论和批准，只保留当前和被替代决定。tk 文档遵循该机制，不改变任务运行时或材料模式。

## 决定

### 使用模式

记录、深度调研、迭代设计和草稿纸组织普通任务材料。任务可以组合采用，也可以都不采用。正式决定遵守项目指定的机制和位置。模式不增加 tk 元数据、schema 字段、`extra` 约定、运行时状态、命令或自动目录生成机制。

### 模式采用

只在信号出现后建议模式，说明增加的材料及维护。用户明确请求即授权采用，无需重复确认。采用不授予任务创建、生命周期、删除、移动或覆盖归属不明材料的权限。普通材料编辑沿用既有权限。

[Agent 行为规格](../../../../spec/tk-agent.zh.md#材料模式)保留各模式的信号、反例、默认值、历史、证据及清理要求，[模式参考](../../../../../projects/tk/skills/tk-cli-zh/references/patterns.md)提供操作指导。项目惯例可覆盖默认路径；只为实际工作创建材料，不预建空目录、不编造历史、不创建未来日期记录、不自动迁移。任务概要、详细材料和 WAL 保留各自职责。

### 合同归属

tools 与 CLI Skill 共用的参考资料，每种语言只保留一份源码。[Skill 设计](../../../../../projects/tk/docs/design/skill.zh.md#安装后的-skill-身份)由组件负责源码及装配布局。同语言共享参考相同，两种语言语义等价。装配拒绝共享文件与 Skill 专属文件的路径冲突，以及目标缺失的载荷 Markdown 链接。

按[自包含决定](../../../decision/2026/08/24-component-self-containment.zh.md)，每个装配后及已安装 Skill 携带本语言全部共享参考，只引用自身文件。源码保留在 tk 组件内部。源码导航可能需要装配，安装后导航必须独立可用。

[Agent 行为规格](../../../../spec/tk-agent.zh.md)包含完整行为与验收，[Skill 指导](../../../../../projects/tk/docs/design/skill.zh.md)独立可用。[术语表](../../../../../projects/tk/docs/design/GLOSSARY.zh.md)、[文档设计](../../../../../projects/tk/docs/design/documentation.zh.md)和[验证](../../../../../projects/tk/docs/design/validation.zh.md)分别负责术语、维护和验证方法。它们、译文及 Skill 参考一同维护。

### 公开文档集合

组件 [README](../../../../../projects/tk/README.zh.md) 介绍 tk，导航完整的双语指南和设计主题，不复制详细合同。仓库入口链接组件入口。审查记录、任务路径、分支状态、实现日志及本地材料不进入公开页面。

### 主题归属

完整 [tk 规格集合](../../../../spec/README.zh.md#tk)负责必要行为和验收。每项详细组件说明有一个主要主题页，由[设计索引](../../../../../projects/tk/docs/design/README.zh.md)导航。用户指导、实现设计、验证方法及术语保留各自职责。

规格完整表达必要命令、参数、字段、默认值、上限、失败语义和兼容性。用户参考独立描述相同合同，设计保存算法和内部机制。组件页面可以链接主要主题说明，但规格不委托要求，也不链接仓库文件。可分发组件文档不依赖仓库规格。

ADR 保存长期决定、替代方案和结果。它们链接当前公开合同，不复制完整命令、字段或测试清单。

### 最终状态写法

公开文档只陈述当前正式合同，就像产品从一开始便按该形式实现。文档不叙述设计修订、审查争论、开发阶段废弃命令、未发布格式兼容或 Agent 工作历史。

正式发布后的真实行为变化可以在用户需要时提供迁移说明。只存在于开发阶段的尝试不会形成兼容历史，也不会列为已移除功能。

### 语言配对

每个 guide 和 design 专题都在一级标题后链接另一语言版本。仓库文件链接使用相对于当前文档的路径。当前目录或子目录中的路径以 `./` 开头，目录外链接使用所需数量的 `../`。

英文和中文页面语义对应。中文使用自然表达，不做逐句机械映射。命令、路径、字段、代码、日志、产品名和标识符保留规定的拼写与大小写。

普通公开 Markdown 页面按照[公开文档决定](../../../decision/2026/08/20-bilingual-docs.zh.md)使用同目录 `name.md` 和 `name.zh.md` 配对，组件 README 也如此。不维护分离的语言目录，也不在被取代的路径保留跳转占位文件；页面移动时修复受影响的入站链接和命令示例。

术语表只包含在 tk 中具有特殊含义、需要固定大小写或必须保持稳定译法的术语。普通技术词留在归属文档中。固定中文形式包括 `受管`、`草稿纸`、`人类可读`、`直接切换`、`支持的子命令`、`活动操作标记`、`表示切换`、`续跑令牌` 和 `续跑状态`。

### 分发文档

公开文档覆盖 tools 与 CLI 模式、通过 `tk install` 选择英文或中文、四个 Skill 身份、多份 Harness 载荷、两份与 Harness 无关的 CLI Skill 载荷、分离的路由合同、互斥的安装目标，以及有限范围的自定义根目录生命周期。

### ADR 生命周期

ADR 使用决定格式。`decision/` 保存当前决定，`archived/` 保存曾经生效、后来被替代的决定。英文和中文文件对保持语义一致。维护者决定是否采用持久选择及归档；设计、实现或验证完成不自动授予这些权限。ADR 文件不包含 `Status` 字段。

任务保存讨论、批准和执行安排，不增加 tk 状态或命令。正式决定独立保留公开理由与契约，包括重要的被否决替代方案。未采纳草稿不是归档决定。需要实现的决定随实现集成，纯文档选择可以独立集成。

### 维护

公开行为变化时，同一变更更新完整的受影响规格、相关设计和参考页、受影响的指南与 CLI 示例、两种语言、受影响 Skill 内容、负责该决定的全部当前 ADR，以及对应验证方法和场景。

仓库现有 Markdown、链接、格式和拼写检查与人工双语审查共同使用。在重复维护或实际偏差证明某项机械不变量值得自动化前，tk 不增加自定义文档结构或翻译检查器。

权威维护细节见[文档设计](../../../../../projects/tk/docs/design/documentation.zh.md)和[术语表](../../../../../projects/tk/docs/design/GLOSSARY.zh.md)。

## 考虑过的替代方案

**在每个 Skill 源码目录保留每个共享参考文件的完整副本。** 每个源码目录都能解析自己的链接，但每次共享修改仍要在同语言的两个目录中重复，tools Skill 与 CLI Skill 之间的偏差只能靠审阅发现。

## 结果

读者可以从规格集合确定完整必要行为，也可以独立使用组件指导。设计和验证分别承担实现及证据职责。这些文档描述相同合同，不使组件用户依赖仓库规格。

共享的 Skill 参考文件和双语公开合同描述同一套模式。共享参考文件每种语言只有一份源码，同语言的 tools Skill 和 CLI Skill 因此不会在这些文件上出现差异。Skill 参考文件、四个 `SKILL.md` 和两种语言仍需一同维护；只更新部分文件可能造成规则不一致，让 Agent 遵循的采用或维护规则与用户读到的规则不同。

浏览 Skill 源码目录的读者或 Agent 沿 `./references/` 链接去找共享文件时找不到，因为该文件只在组装后才出现在那里。没有读过 [Skill 设计](../../../../../projects/tk/docs/design/skill.zh.md)就修改源码树的人可能重新建立本地副本，再次引入重复源码；构建会因路径冲突停止，但那时副本已经写下。

每次产品变更都需要同步维护双语文档。格式检查、链接检查和 Rust 测试无法证明语义一致、写作质量或 Agent 行为，因此仍需要人工审阅；场景验证通过四个 Skill 分别检查四种模式。

最终状态写法使公开文档保持紧凑，但评审历史和实现证据必须保存在任务材料或其他非公开记录中。ADR 保留理由，但不会变成发布说明或进度日志。

## 动机

把 omp-context-pin 扩展作为第一方宿主组件继续维护，让固定文本在压缩后逐字保留，并把它的容量取值留在组件里，而不是留在本决定里。

组件已经存在，它的公开用法记录在组件 README 中，[组件规范](../../../../spec/omp-smart-context/README.zh.md)陈述它的目标、不变量与验收标准。

## 决定

宿主保留 `/pin` 自用，因此组件注册自己的 `/ctx-pin` 命令与 `ctx_pin` 工具。

所有 action 声明最低审批档 `read`。组件不自行增设授权、确认或来源准入，也不写用户配置。

字节上限是组件自身的默认值，不是本决定固定的取值，因此调整取值属于组件变更。

完整用法、记录、编号、重置、上限、持久化与缓存细节见 [Pin 规范](../../../../spec/omp-smart-context/pin.zh.md)，目标、不变量、宿主下限与验收标准见[主规范](../../../../spec/omp-smart-context/README.zh.md)。

## 考虑过的替代方案

无

## 结果

- 固定正文与累计 revision 消耗上下文。字节上限只约束活跃正文，不约束 token、元数据或更早的尾部消息，完整请求仍可能在压缩后溢出。
- 组件 README 是上限唯一的说明来源，调整取值的组件变更与这里记录的内容不冲突。
- 活跃正文超过当前上限的分支仍能列出与读取条目，但在合计降到上限以内前拒绝新的写入；取消固定不受容量约束，因此这样的分支可以自行回到限内。
- 规范记录与它的模型投影是两件事：记录存在而投影缺失时，固定文本会从请求中消失；恢复也可能重复交付，或在快照之后交付更旧的 revision。跨重启、排队和压缩的恢复路径保留在验收范围内。
- 边界选错会丢失已接受的变更，或让已被取代的 revision 重新生效。其他扩展可能在宿主压缩摘要周围插入消息，或由后序处理器丢弃快照，最终 Provider 转换也可能改变钩子中看似正确的顺序，因此验收须检查被测组合的最终请求。
- Provider 原生远端压缩让部分历史保持不透明。组件保持该载荷原样，不声称已经对不透明内容去重。
- 保留的上下文可能被理解为授予权限，会话内整数也可能跨会话冲突或从错误范围恢复。来源标注、说明措辞与会话级高水位是控制手段，Provider 边界的最终 role 以核对结果为准。
- 非主动交付可能把变更推迟到下一次普通 prompt，因此当前请求始终从规范记录推导自身的变更。
- 一次提交靠扩展交给宿主的那段文本识别，与它文字相同的消息在被持有期间认领一次。
- 请求采集可能泄露凭据；采集在写盘前排除敏感传输字段，且不改动实际发给模型的请求。
- 组件检查纳入仓库检查入口，不能代替在真实宿主上的验收。

## 动机

维护 `@ruokee/omp-qol` 及其可独立开关的行为调整。

请求对齐、压缩用量和模型提示词规则属于 smart-context。QoL 保留独立 wait、受限错误恢复、压缩期限实验、原生历史重放、task 参数清理和复制最后回复。

原有四项调整分别是：`wait` 在总期限内持续等待、模型错误后的受限续跑、可选的远端压缩期限延长，以及让恢复进程的首条请求沿用提供方原生历史形式的进程级包装。原生 `wait` 的窗口结束时，它监视的后台工作可能仍在运行，模型必须重新询问，而每次这样的返回都消耗一次轮次。遇到上游错误的轮次即便错误是瞬时的也会保持已结束状态，因为原生重试预算已耗尽，或该错误不在预算覆盖之内。远端压缩请求在固定的请求期限处被中断，压缩转而走回退路径而不是完成。恢复后的进程否则会重新编码它重放的历史，包装让首条请求保持原生重放形式。每项调整选择给定宿主所需的实现。

等待模块原先服务两个内置入口：`hub` 工具和独立 `wait` 工具。按照[宿主内组件按共同的 OMP 下限维护](../../../decision/2026/09/28-host-maintenance.zh.md)，面向 OMP 的组件共用维护下限 OMP 18.5.0，已没有受维护宿主提供 `hub`，因此移除 `hub` 路径。

## 分析

能够处理这些情况的扩展，与它要调整的行为并不在同一处。在 OMP 18.5.0 中，一次原生 [`wait`](https://github.com/can1357/oh-my-pi/blob/v18.5.0/packages/coding-agent/src/tools/wait.ts) 调用在窗口结束时返回，上限为 30 分钟，没有任何设置能触及该窗口。没有设置会在错误之后继续轮次；压缩看门狗是远端压缩与 V2 流式压缩路径内的常量。宿主确实提供了扩展可用的介入点：重新注册原生工具并通过工具上下文委派、session stop 续跑请求、公开的错误分类器，以及压缩生命周期事件。源码核对能确立这些介入点和缺失的配置，但不能确立基于它们的调整在真实会话中行为正确。

进程级压缩补丁还带来一个归属问题：当另一个会话在已安装补丁的进程里启动时，补丁归谁。OMP 会为创建的每个会话绑定已加载的扩展并再次调用它们的工厂函数，可能走模块加载路径，也可能走为新会话重新绑定的 prepared factory，子代理会话因此在运行中的进程里会走到压缩模块的冲突分支。只要进程内已存在 owner 就停用调整的条款，针对的是在「补丁应该做什么」上真正不同的 owner，例如属于其他会话的窗口，或已不再适用的配置快照；而包版本与生效配置快照都一致的第二次激活并不构成这种差异。按该条款执行的实际结果是：第一个子代理会话就让该进程的补丁停止改写，此后设置与状态仍显示实验已开启，进程却一直使用原生的五分钟期限，而配置并未发生任何改动。同一条款也没有为安装方会话结束之后留下确定的状态，后来的会话因此无法区分「已被释放的补丁」与「存在但自己无法驱动的补丁」。

恢复这一情形还涵盖标记覆盖不到的错误。工具调用仍在流式输出时被中断的轮次，宿主记录为 `stopDetails.type: "stream_interrupted_after_content"` 而不是已分类的错误；一次观察到的中继响应以 `1012: websocket closed before terminal event (code 1012)` 结束轮次，被已安装的 `@oh-my-pi/pi-ai` 分类为 `0`。宿主自带的补救分支针对流提前关闭、停滞或重置，都以可重试的 id 为前提，因此该错误同样落在这些分支之外。

该决定定义第一方组件 `omp-qol`、它与宿主保持的职责划分，以及使用者启用各项调整时接受的边界。

## 决定

一个包 `@ruokee/omp-qol` 在[第一方能力边界](../../../decision/2026/08/20-first-party-capabilities.md)与[自包含组件合同](../../../decision/2026/08/24-component-self-containment.md)下承载可独立开关的模块：安装、配置入口与检查各只有一处，而每个模块保留自己的开关、可用状态与故障报告。配置只通过 OMP 插件设置，取值、项目级覆盖与解析都由 OMP 负责。

等待、保守的错误恢复与原生历史重放默认启用，压缩期限实验按需开启。task 参数清理与复制最后回复保留各自合同。单个模块故障不影响其他模块，安装与迁移仍由用户决定。

压缩期限是默认关闭的实验，采用受约束的进程级超时调整。启用它即接受同进程无关工作的匹配超时调用也被延长，因此不提供请求隔离或严格项目隔离。组件 README 兼容性章节按[共同 OMP 下限](../../../decision/2026/09/28-host-maintenance.zh.md)拥有维护下限声明，不设上限。[Smart-context](../../../decision/2026/10/12-smart-cache.zh.md) 拥有迁出的上下文能力。

模块机制、设置键与默认值、范围、状态报告、判定条件、归属与释放规则，以及逐项证据见[组件 README](../../../../../projects/omp-qol/README.zh.md)、[组件规范](../../../../spec/omp-qol.zh.md)与组件自身的 `docs/`。

每项调整都需要自己的真实会话证据。压缩实验的验证要求超过原生期限的远端压缩成功完成，随后仍能正常发起模型请求。宿主升级时，重新阅读引用源码并更新受影响文档；修改声明的维护下限不能替代这些步骤。

保留 wait 委派与总期限、恢复的排除条件与续跑上限、期限模块的进程级匹配及单 owner 窗口、匹配激活复用与 `owner-stopped` 终态，以及 replay 独立归属和按归属还原。对齐可新建协调器的生命周期不用于期限 owner。Replay 即使与缓存相关，也继续留在 QoL。

保留总开关及全部无关设置、默认值、范围、校验规则、状态、失败边界和隐私义务，原生设置仍是唯一权威。未改变的 QoL 功能保留自己的证据要求，不因 smart-context 采用受控集成门槛而降低要求。

[用量](../../../decision/2026/10/13-compaction-usage.zh.md)与[模型规则](../../../decision/2026/09/14-model-prompt-rules.zh.md)后继拥有完整合同。删除它们在 QoL 的实现、登记及停止路径、设置解析与声明、状态段和独占依赖。QoL 不读取旧键，也不转发到其他包。

用户从用户级和项目级 QoL 设置清除 `compactionUsageEnabled` 与 `modelPromptsEnabled`，保留所有其他值。先解析各层级旧有效总开关和模块开关，再把 `enabled && moduleEnabled` 结果迁入 smart-context。迁出键仍按未知键拒绝，可能拒绝整个 QoL 配置。重启前更新扩展入口和设置，不自动迁移真实用户配置。本决定只替代归档中迁出能力的归属及保留设置义务。

## 考虑过的替代方案

- **为每项调整分别发布扩展包。** 收益是独立发布与独立故障；代价是配置、兼容性、迁移与检查分散在每个调整各自的安装中，而各项调整共享同一宿主基线。单个包让这些入口集中。
- **替换原生压缩流程。** 它能直接控制请求选项，但把压缩协议、历史替换、重试与回退路径交给本组件，其中还包括生成会话所依赖摘要的路径。
- **推迟压缩调整，等待 OMP 暴露请求级接口。** 它避免进程级副作用并降低维护量，但保留固定期限；本决定改为保留该受约束的全局机制作为显式、默认关闭的实验，并在宿主提供原生接口时与其比较。
- **owner 退出后由下一次匹配激活安装新补丁。** 这样该进程不必重启就能重新获得该调整，而且新补丁由仍然存活的激活持有。代价是该进程当前是否启用该调整取决于之后是否还有激活出现，状态在 owner 退出后也没有确定的终态可报。

## 结果

- 进程级包装可能与其他扩展的包装相互影响。身份检查和仅按归属还原避免覆盖其他扩展，但可能使本调整停用至进程重启。

- 一个组件让各项调整共享一次发布、一份锁文件和同一个检查入口。破坏其中一个模块的宿主变化也会影响整个组件能否按原样安装，单次依赖升级影响全部调整。
- 调整依赖不带兼容承诺的宿主细节：内置工具描述与空窗结构、`stopReason: "error"` 与公开分类器以及它为被中断轮次写入的 `stopDetails.type` 标记、`AbortSignal.timeout` 的身份，以及压缩生命周期事件的顺序。标记按值比较，无状态条件读取的是字段缺失，因此宿主某次发布若不再写该标记，或开始携带状态，只会静默收窄可接受的集合，而不会直接失败。各模块被写成在识别失败时保持不生效并说明原因，而不是猜测，因此宿主升级可能停用某项调整而不会破坏会话，重新核对之后才再次信任该调整。
- 续跑会重发会话内容并消耗服务额度，重新运行的轮次可能重复失败轮次中的副作用。次数上限、固定排除清单与宿主上限减小了暴露面，但不承诺恰好一次的行为。
- 范围扩大在默认配置下即时生效，因此此前会在无状态中断处停止的会话，现在会为它消耗到续跑次数上限。分类器无法识别的客户端失败在同一条条件下也会被续跑，而每轮都复现的服务端故障会比以前更晚被用户看到，直到次数上限用尽。
- 等待期限到达后仍有工作继续运行，而模型可能已不再关注它们。结果会说明期限已到，模型下一步需要重新检查。
- 压缩实验在窗口打开期间会延长同一进程中无关工作的命中期限，而窗口的开启事件并不指明将被计时的请求。清理无法缩短已经创建的期限，且一个进程只有一个包装。
- 保留补丁的会话不驱动窗口，也不因此获得自己的压缩被延长的保证。状态行与文档是唯一说明这件事的地方，因此状态缺失或缓存的会话会被读成已被完整服务。
- 生效配置快照是已安装补丁与未安装它的会话之间的唯一门槛。若给生效配置新增字段却没有同步更新该比较，复用范围会无声扩大，某个会话可能在它从未选择的配置下被保留。
- 安装方激活退出后，该进程在重启之前不再延长任何压缩期限，状态也一直报告已被释放的补丁。这是选定的终态：释放补丁而不让后续激活重新安装，代价是该进程的剩余生命周期没有该调整。
- 在仍提供内置 `hub` 工具的宿主上，即低于维护下限的宿主，总期限等待不再生效。模块在那里找不到独立 `wait` 入口，保留原生行为并报告有界原因。

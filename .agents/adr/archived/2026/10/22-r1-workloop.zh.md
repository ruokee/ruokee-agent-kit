## 动机

以自包含的双语 Skill 提供 workloop，承载 Agent 的任务工作流。

目标澄清、实现、核验和交付需要一套共同合同，Skill 脱离源码仓库安装后也能读取。操作正文放在 Skill 外会使独立安装不完整；Skill 和宿主 Prompt 都维护完整流程，则会为同一行为建立多份权威正文。

工作流需要不限 Harness 的使用方式，也需要便于调用的 OMP 入口。Markdown 能表达这些指令，无需运行时；组件目录能将完整 Skill 和可选宿主资源放在一起。打包改变指令的发现方式，不改变 Agent 遵守指令的能力。

## 决定

### 组件

在 `projects/workloop/` 维护 workloop，作为第一方纯指令组件。组件包含 Markdown Skill、组件文档及 OMP 资源包，不增加 Extension、运行时代码、构建系统或专用安装器。

英文 `workloop` 和中文 `workloop-zh` 是 `projects/workloop/skills/` 下可独立发现的 Skill 身份。每个 Skill 包含完整公共合同、操作正文及初始化说明。两种语言具有相同的能力与必需指令，同次维护，使用相同组件版本。不在仓库普通 Skill 或语言变体根目录维护另一份副本。

每个安装后的 Skill 只引用自身目录内的文件。`SKILL.md` 提供公共合同和操作索引，操作正文按需加载。宿主 Prompt 只传操作、用户输入及加载指示，不成为另一套流程权威。这遵循现行[组件自包含决定](../../../decision/2026/08/24-component-self-containment.zh.md)。

tk 是任务管理的必需依赖，通过名称和公开接口使用，不导入其实现或引用其文件。其他工具或 Skill 只在操作需要时成为前置条件。安装 workloop 不安装 tk 或协作工具。以 GitHub 或 GitLab Issue、PR 管理任务的方向暂缓，不永久禁止；项目仍可将提交 PR 定义为交付目标。

组件面向新任务，不提供旧入口别名、旧材料名称兼容或存量工作流与任务材料迁移。按 workloop 开始的任务仍支持继续、返工和恢复。

### 操作

提供 `clarify`、`exec`、`verify`、`ship` 和 `supervise` 五个工作流操作。

- `clarify` 澄清目标与完成条件，按需调研或诊断，完成必要设计，并生成或修订执行 Plan。目标清楚时可直接规划。所有进入执行的任务都必须有独立 `plan.md`，简单或单单元任务也不例外。确定推进后自然形成 Plan，不另设例行规划许可门槛，但形成材料不启动实现。只设计、只讨论、暂停、不可行或无需行动的任务不必补齐其他材料。不再继续时保存有用结论，按项目的任务关闭规则处理。
- `exec` 由当前会话实现请求范围并协调检查。未限定更小范围时，从所解析的起点连续完成剩余 Plan。一个会话通常同一时间只处理一个单元，可以串行完成多个。范围内常规实现、修复、自检、独立 Verify 及必要复查不重复索权。执行默认禁止结构化问答工具，必须由用户决定的问题用普通文字提出。`confirm` 表示逐项确认，不取消必需检查，也不启用结构化问答。
- `supervise` 通过独立 Worker 调度所解析的范围，不亲自实现其变更。可将独立单元分派给不同 Worker，整体范围与各 Worker 的分派范围保持区分。它与 `exec` 一样默认连续推进。
- `verify` 根据目标、适用 Skill、项目规范及其他有效要求，独立评估当前材料或单元结果。核验者只读，区分通过、需要修改和无法判断。结论绑定具体范围与候选，不覆盖之后的所有变更。
- `ship` 按项目定义、当次请求及有效许可交付，不统一捆绑合并、清理、安装、部署或发布动作。报告实际达成的项目目标、运行或送审状态、验收结果及生产发布状态，并说明各自证据。达到项目当前交付目标，与生产发布、用户验收及任务关闭分别判断。

Check 是前期隐含检查，不是额外的必需入口。Start 和 End 描述流程位置，不是命令。材料问题和设计缺陷回到 `clarify`，实现偏差回到 `exec`。交付反馈也可以回到 `clarify`，有独立目标或边界时则按适用任务管理规则另建 Task。只重开受影响工作，不因执行或交付结束就关闭任务。

### 材料

材料按职责保存在所属 tk Task。`goal.md` 用自然语言描述预期结果及停止条件，不写实现方法。可选 `design.md` 说明如何达到结果。可选诊断记录问题、现场、有依据或仍不确定的原因，不写修复建议。Research 提供带可追溯来源的汇总，Grill 保存讨论过程。可选活动不要求空文档。

必备的 `plan.md` 定义可执行单元。同一 Plan 可直接展开部分单元，另一些链接到 tk 子任务，保留稳定标识及已完成结果。子任务材料提供对应单元的细节，不要求父任务重复。按完整结果及独立核验的可承受范围划分单元，不按文件数或编辑次数拆分。

分析可在该操作许可内维护普通材料及必要临时文件，不因此取得实现、配置、Git 或托管元数据修改许可。材料完成不邀请或启动下一操作。Verification 逐轮追加候选、范围、证据及结论，不改写过去的评估。

### 检查

Plan 形成后默认自检材料，发现决定不同步、遗漏及可预见的执行卡点。这不是环境预检。未决需求与重要取舍回到讨论。前期材料的独立 Verify 仅按请求启动；除非用户限定审阅范围，该请求涵盖作者的范围内修订及同一只读核验者的必要复查，直到当前材料通过或遇到实际阻塞。

前期材料自检与实现后的快速自检都只读，由作者修订。按任务情况在三至五轮中选择默认检查上限，适用外部指引可覆盖。通过即提前结束。前期材料与各实现单元分别计数，首次检查及复查均计入；修订或独立 Verify 反馈不重置计数。达到上限后停止追加自检，完成可处理修订，说明未解决和未复查的变更，不虚构通过。

每个实现单元都需要自检及独立 Verify。独立 Verify 不受自检轮次上限约束，前期材料也不因自检达到上限而自动需要独立 Verify。

实际检查改变的行为，记录目标、条件、输入、观察结果、证据、覆盖范围及限制。区分文件与加载路径检查、实际 Harness 发现和模型行为。候选变化使受影响证据失效，过去的通过不覆盖变化后的候选。

### 协作

各角色分别按当次明确指定、继续有效选择或适用外部默认解析。不从执行者推断 Verify 的模型，不静默替换不可用选择。Senior 仅在明确分配时参与，设置其默认模型不启用角色。

按所选工具协作。推荐 Herdr，但不将其设为必需依赖；其他终端协作方式仍须保持角色隔离、适当会话复用、普通消息派工及最终结果等待。复用合适的 Verify 和已分配 Senior 会话，与实现保持隔离。每次分派重新解析当前 Task、单元、候选、范围及回复对象。正常启动会话，不用系统提示词注入任务。审阅期间冻结候选。

默认等待最终结果。显式 `nowait` 改变跨会话等待，不改变原生自检的最终结果等待、执行范围或验收。最终回信不等待接收者。已保存结果未送达时，先恢复同一结果，再考虑重派。路由及待完成分派属于运行状态，不写入稳定 Task 内容。

执行许可不包含集成、推送、发布、本机安装、费用或任务关闭等受保护许可。保留明确限制，复用已有授权；已授权的临时目录文件检查仍属于其检查范围。已验证但未合入的前序候选可提供后续单元的开发依赖，不产生集成许可；分支不能代替确实需要的外部部署或服务状态。开发遵循项目的工作约定。

### 恢复

在可用的持久上下文或能跨压缩保留的会话状态中，保存操作、Task、当前单元与候选、依据、有效范围、许可、明确禁令、检查次数及下一动作。保留限制的含义，包括禁止结构化问答工具，不只保存 `noask` 这样的控制词。

完整指令退出上下文后，先重读公共合同及当前操作，再继续。记得路径或历史上读过文件，不代表正文仍然可见。不依赖宿主专用 Pin API。重载提供指令，不强制保证遵守。

### 初始化

`SKILL.md` 通过简短的条件引用提供初始化及重新配置说明的发现路径，不将其作为普通使用的前置条件。初始化可将角色默认模型、两类自检上限、协作方式、项目工作约定及 Ship 定义保存到适用的 `AGENTS.md` 一类外部指引。不内置本机模型，不建立通用的用户级与项目级配置层次。

直接按请求执行当前操作，不增加工具、环境或文件可用性的主动检查。实际加载或执行报错后，只获取处理该错误所需的信息，按需读取准备或诊断说明。这不取消必要质量检查，也不授权无法执行的操作。

### 分发

通过目标 Harness 已有的发现与加载机制，说明完整所选语言 Skill 的安装、更新、移除及重新加载条件。支持完整目录复制，以及宿主支持时的链接方式。不设置封闭 Harness 名单，不猜测未知宿主路径，不要求不同宿主采用相同维护步骤。仓库普通 Skill 安装器不管理本组件。

OMP 额外提供原生资源包，包含两种完整 Skill，以及 `/wl-clarify`、`/wl-exec`、`/wl-verify`、`/wl-ship` 和 `/wl-supervise` 的薄入口。入口遵循明确选择的语言 Skill，未指定时使用英文。包资源使用同一组件版本。原生包的维护说明与独立 Skill 安装分开，依据宿主实际接口及资源冲突处理行为编写。不增加宿主运行时代码，也不为其他 Harness 建立专用集成。

其他 Harness 使用完整 Skill，以自然语言选择操作，不新增专用工作流命令或运行时集成层，也不要求采用 OMP 的命令语法。

### 规格

[组件 Spec](../../../../spec/workloop.zh.md) 定义目标、边界及可观察结果，Skill 与[组件文档](../../../../../projects/workloop/README.zh.md)维护操作和使用细节。规格随交付能力同步维护。

[Skill 布局决定](../08/20-r2-skill-variants.zh.md#变更)将项目组件包含的 Skill 保留在组件内部，普通同名语言变体规则保持不变。依赖仍按名称声明。仓库检查对已登记组件 Markdown 执行格式检查，不增加运行时检查；包清单和未登记输入保留完整检查回退。

## 考虑过的替代方案

将完整 Skill 放在普通根 Skill 及语言变体目录，可以复用该布局，但 OMP Prompt 和包资源会由另一处承载。独立项目布局将这些资源集中维护，同时保留独立安装 Skill 的能力。它接受普通 Skill 安装器之外的分发路径，不在两种布局中重复维护正文。

## 结果

纯指令组件无法强制执行操作或许可边界。Agent 没有加载当前正文，或无视仍可见的规则时，仍可能跳过必需检查或执行未授权动作。自包含加载与恢复指引减少正文缺失的失败路径，但打包和重读不能取消独立核验，也不能证明模型行为可靠。

两种可独立安装的语言 Skill 各自承载完整权威合同。只修改一种语言的正文，会使另一语言的用户收到不同许可或检查要求，即使两份文件都能成功加载。同次维护两种语言并核对语义等价，是独立语言分发的持续成本；版本号一致不能单独证明内容等价。

## 变更

### 2026-10-23 规格完整性

组件规格完整表达必要操作行为、权限、边界和验收，不含实现描述或仓库文件链接。Skill 提供 Agent 执行指令，组件文档提供同一合同下独立可用的指导。非规格索引承载语言、主题和决定导航。这保留了必要结果与操作、使用方法之间的职责划分。

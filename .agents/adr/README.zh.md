# 架构决策记录

[English](./README.md) | 中文 | [术语表](./glossary.zh.md)

**ADR** 记录一项长期仓库决定的理由和合同。ADR 不是进度日志、发布记录、临时计划或日常变更总结。

## 什么时候使用 ADR

规划需求前，先搜索现有提案和当前决定。判断需求是增加无关能力、无冲突地扩展当前决定，还是与当前决定冲突。

一项选择存在真实替代方案，并改变架构、职责归属、公开或宿主合同、持久化格式、兼容规则或仓库级开发与发布流程等长期边界时，创建或更新 ADR。

局部缺陷修复、机械重构、普通文档更新、状态报告和临时计划不需要 ADR，除非它们改变了上述边界。

## 位置与文档类型

本仓库使用 `.agents/adr` 作为 ADR 根目录：

```text
.agents/adr/proposal/yyyy-mm-dd-topic-title.md
.agents/adr/decision/yyyy-mm-dd-topic-title.md
.agents/adr/rejected/yyyy-mm-dd-topic-title.md
.agents/adr/archived/yyyy-mm-dd-topic-title.md
```

`proposal` 和 `decision` 是两类文档。`proposal/` 保存活跃提案，`rejected/` 保存被拒绝的提案；`decision/` 保存当前决定，`archived/` 保存已归档的决定。目录同时表达类型和状态，因此 ADR 文件不包含 `Status` 字段。

英文使用 `Create decision`、`Update decision` 和 `Reverse decision` 作为动作短语。`Reverse decision` 是动词短语，不是名词标签。新决定使用 `Reverses` 链接归档决定，归档决定使用 `Reversed by` 链回新决定。

文件名日期记录首次提出时间，文件对移动时不改变。slug 使用简短英文。包括日期、语言后缀和扩展名在内的完整文件名不得超过 60 个字符。

四个生命周期目录始终使用 `.gitkeep` 保存在 Git 中，即使目录内已有 ADR 文件。

术语表的每项简明定义都注明另一种语言中的对应术语。

## 双语文件

每项 ADR 由同目录文件对表示：

```text
yyyy-mm-dd-topic-title.md
yyyy-mm-dd-topic-title.zh.md
```

无后缀文件使用英文，是默认公开链接；`.zh.md` 是中文审计副本。两种语言在语义上具有同等权威，并且必须一起移动。

作者可以从任一语言开始，但两份文件必须在同一变更中补齐。语义冲突会阻止合入，直到维护者解决该冲突。路径、命令、API 名称、元数据字段名和代码标识符保留仓库原有拼写。

在完整元数据块后紧接着放置双向语言链接。文件对中的负责人字段与起草者字段必须一致：提案为 `Draft owner` 和 `Draft writer`，决定为 `Decision owner` 和 `Decision writer`。负责人字段记录负责维护者，起草者字段记录最初起草者，后续维护时不改变。`Reverses`、`Archived` 和 `Reversed by` 等关系与生命周期字段位于起草者字段之后、语言链接之前。

## 提案格式

先说明活跃格式，再说明被拒绝格式。

### 活跃提案

英文文件头：

```markdown
# ADR proposal: <title>

Draft owner: <name>
Draft writer: <writer>

English | [中文](./<filename>.zh.md)
```

中文文件头：

```markdown
# ADR 提案：<标题>

Draft owner: <name>
Draft writer: <writer>

[English](./<filename>.md) | 中文
```

正文包含以下必需章节：

```markdown
## Motivation
## Proposal
## Alternatives considered
## Acceptance criteria
## Risks
```

中文正文使用 `## 动机`、`## 提议`、`## 考虑过的替代方案`、`## 验收标准` 和 `## 风险`。英文文件可在动机章节后紧接可选的 `## Analysis` 章节，中文文件对应使用可选的 `## 分析` 章节。

实现开始前，将获准的提案作为独立变更合入 `main`。实现从包含该提案的新 `main` 创建短期分支。一个提案可以创建多项决定、反转多项决定，或同时执行两种操作。

实现完成后，在实现变更中创建新决定、更新没有冲突的决定、反转冲突决定，并删除已落实的提案。Git 历史保留独立合入的提案及其理由。

### 被拒绝的提案

将双语提案文件移动到 `rejected/`，增加 `## Rejection reason` 或 `## 拒绝原因`，修复事实链接后冻结。只有当拒绝理由仍能防止现实中重犯同类错误时，才保留该提案。

## 决定格式

先说明当前格式，再说明归档格式。

### 当前决定

英文文件头：

```markdown
# ADR decision: <title>

Decision owner: <name>
Decision writer: <writer>

English | [中文](./<filename>.zh.md)
```

中文文件头：

```markdown
# ADR 决定：<标题>

Decision owner: <name>
Decision writer: <writer>

[English](./<filename>.md) | 中文
```

正文包含以下必需章节：

```markdown
## Motivation
## Decision
## Alternatives considered
## Consequences
```

中文正文使用 `## 动机`、`## 决定`、`## 考虑过的替代方案` 和 `## 结果`。英文文件可在动机章节后紧接可选的 `## Analysis` 章节，中文文件对应使用可选的 `## 分析` 章节。

### 更新决定

新增内容与当前决定没有冲突时，将它追加到最后的 `## Changes` 或 `## 变更` 章节。每次更新使用带日期的三级标题。新增内容值得单独成为 ADR 时，链接新的决定。纯表达维护没有形成新选择，不需要反转。

### 反转决定

不得通过重写当前决定表达冲突的新选择。先创建提案，列出需要反转的每项决定，并指出有效条款、新选择，以及二者为何不能同时成立。代码量、增加功能、增加宿主依赖或文件改名，本身都不足以证明需要反转。

实现完成后，将旧决定仍然有效的规则和获得接受的提案整合成一项完整的新决定。后继决定保留该决定范围内仍有效的规则，不复制组件的实现规格。

在新决定的文件头元数据块中增加 `Reverses`，在每项归档决定的文件头元数据块中增加 `Reversed by`。同一变更将旧决定的双语文件移动到 `archived/`。

### 归档决定

归档决定保留决定格式，在文件头元数据块中增加 `Archived: YYYY-MM-DD`，并将它放在可选的 `Reversed by` 之前。修复关系链接和事实链接后冻结。当前文档不得将它引用为当前权威。

## 编写规则

### 开头

两类文档都以 `## Motivation` 或 `## 动机` 开头，并准确说明考虑或采用这项选择的具体理由。其首句必须说明对象及具体问题、拟作出的变更或目标，不依赖标题、链接或后文才能理解。新增能力不必被包装成缺陷。反转提案开头说明拟作出的改变，后继决定则说明它记录的完整选择。

英文文件可在动机章节后紧接可选的 `## Analysis` 章节，中文文件对应使用可选的 `## 分析` 章节，位于 `## Proposal`/`## 提议` 或 `## Decision`/`## 决定` 之前；没有实质分析时省略。分析只包含影响选择的观察、证据、约束、推导和不确定性，不能成为实施计划或调研笔记的副本，也不与动机或替代方案章节相互重复。

### 必要契约与实现材料

ADR 记录一项完整且连贯的长期选择、理由、必要边界与归属、重要公开承诺，以及重大的兼容、安全、成本和失败后果。仅当省略某项技术细节会妨碍读者理解选择或重要取舍，或丢失必须保留的契约时，才将它写入 ADR，并只写必要片段。配置权威、身份不可变性或进程级副作用，即使需要具体标识符说明，也可能是必需内容。

完整的 API 与配置表、schema、命令参考和持续维护的清单，归所属公开文档。内部函数名、算法步骤、逐文件修改、执行计划、测试命令与验证日志，归实现文档、代码、测试或任务材料。验收标准描述外部可观察的结果，不列测试操作步骤。ADR 链接可访问的公开契约，不把忽略的任务材料作为公开依据。

移走一条有约束力的条款，不等于取消它，必须保留其含义和可访问的引用；历史记录应保留足以解释当时选择的原有细节，指向持续变化的当前文档不能替代历史契约。

### 封闭约束与防御规则

区分有意封闭的协议、归属规则或安全边界，与示例和可增长的清单。优先链接清单的所属页面，而不固定数量或穷举文件树；确实需要封闭集合或禁止事项时，说明受保护的边界和理由。

当前范围限制或首个版本不需要的选项，不自动成为永久禁令，应在起草决定时说明区别。不能事后把既有禁令降格以绕开它，也不能仅为让文案可扩展而预建抽象或配置。

防御规则应针对实际操作及其危害。普通校验、损坏修复、生命周期变化和重复激活可能需要不同前提；保留身份、权限和副作用保护，不用与保护边界无关的全面限制取代它们。

### 审查替代方案与风险

审查 `## 考虑过的替代方案` 和 `## 风险` 时，确认 ADR 说明了每个替代方案在哪次需求讨论或分析中成为实际备选方案，且每条风险都写明了不良后果。直接删除没有依据或归类错误的条目，不要把它们润色成看似合理的方案或风险。

必需章节需要内部结构时，使用描述性的三级标题。不能替换必需的二级标题，也不能用子章节记录进度历史或复制实现清单。

### 考虑过的替代方案

必需的 `## 考虑过的替代方案` 章节记录检查真实替代方案后的结果。它不要求作者在没有替代方案时强行凑出选项。

不要为了让 ADR 显得完整而编造替代方案。只记录编写 ADR 时已经存在的选项，或在讨论和分析需求过程中真正考虑过的方案。一个仅仅可以想象、从未进入实际选择的选项，不是考虑过的替代方案。

每个条目必须是针对同一项决定的另一种做法。当前仓库的事实、要求或约束、验收标准、实现细节，以及对当前提议的换一种说法，都不是替代方案。

没有条目满足这些规则时，英文版只写 `None`，中文版只写 `无`。这表示检查结果为空，不是内容缺失。

### 风险

必需的 `## 风险` 章节记录提议可能造成不良后果的可信方式。它不要求作者在没有已知风险时强行凑出风险。

不要为了让 ADR 显得完整而编造风险。风险必须描述采用这项提议可能造成的不良后果，或者没有处理、没有考虑某项相关内容可能造成的不良后果。必须写明不良后果。事实、要求、约束、不变量、验收标准或待办本身都不是风险。

例如，“必须让行为保持一致”表达的是约束，不是风险。风险需要有可信的失败路径，例如两个实现各自演化后产生不一致行为。具体失败路径取决于当前 ADR。

没有条目满足这些规则时，英文版只写 `None`，中文版只写 `无`。

## 维护规则

维护者负责批准或拒绝提案，以及归档决定。Agent 可以在授权变更中起草和实现 ADR，但未经明确授权不能作出这些生命周期决定。

两种语言文件必须一起移动，并在同一变更中修复入站链接。事实路径、名称或验证入口变化时，更新当前决定。不得借事实维护反转决定。

归档决定在修复关系链接和事实链接后冻结，被拒绝的提案在修复事实链接后冻结。[ADR 机制决定](./decision/2026-09-23-clarify-adr-content-boundaries.zh.md)记录了对该次清理开始时已有的中英文 ADR 配对的一次性例外，允许在不改变已记录的选择、理由、约束、不确定性、历史能力范围、作者、日期和反转关系的前提下调整结构与措辞。该例外不解除任何记录的冻结，也不是持续修改冻结材料的许可。

第一版依靠评审、仓库搜索和 Git 历史，不增加专用 Skill、分类体系、归档 manifest 或自定义检查器。只有重复维护或实际错误证明某项机械约束确有必要时，才增加最小检查。

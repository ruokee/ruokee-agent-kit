# ADR 提案：状态栏 token 指标只统计对话自身用量

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-02-scope-token-metrics-to-conversation.md) | 中文

## 动机

状态栏的 token 读数和缓存命中率改为只统计对话自身的用量，而不是 OMP 返回的整个会话用量统计。

OMP 把它记录的每次模型调用汇总进一个会话总量。状态栏读的是这个总量，于是对话从未发起的调用也进入读数，仿佛由对话付费。Find 工具的判定级联就是这样一个调用方：它以 `purpose: "find"` 把自己的模型调用记进会话账本，而这些记录不携带任何 cache 读数。判定路径只报告输入数、输出数与计费成本，无论服务端是否复用了缓存前缀，它都把 cache read 与 cache write 写为零，因此这些记录说明不了缓存前缀是否被复用。

影响足以让读数反过来。在本变更记录的验证轮里，一次针对大型仓库的 Find 调用计费 16 次判定请求、68K 输入 token：对话自身用量是 10K 输入、7.7K cache read，命中率 43.5%，而会话总量读到 78K 输入、8.9%。判定记录的条数随 Find 调用读取的文件数增长，因此偏离随搜索规模增长。

这五项 token 读数用于显示一次对话花 token 的效率、以及它的 prompt cache 复用得如何，它们和描述对话自身的读数并排：已回答请求次数和上下文估计。对话没有发起的流量让它们偏离这一用途。

## 分析

报告的数值在算术上没有问题，问题在于它描述的是会话而不是对话。OMP 的会话总量没有按用途拆分，也没有逐条明细，因此该 API 的任何调用方都无法把对话的用量与其余部分分开。直接读取账本是唯一能做出区分的途径，而扩展已经持有的会话分支带着每条条目的父子链。

扩展已经为已回答请求次数读取这个分支，回退与分支行为也因此在那个位置定义。把 token 口径移到同一来源，两项读数就保持一致：`/tree` 回退或新建分支会像重置次数一样重置 token，会话切换读取当时在前的分支。

一条判定记录只抬高 `I`、对 `C` 毫无贡献，因此每次级联请求既抬高输入读数，也压低 `C / (I + C)`，偏离程度取决于判定记录的条数，而不取决于服务端缓存了多少。在上面的验证轮里，这些记录增加 68K 输入且不含任何 cache read，读数因此从 43.5% 变为 8.9%，而对话自身的请求从缓存读取了 7.7K。

`task` 工具调用是相反的情况。它的子代理处理的是对话提出的请求，OMP 把这份用量作为工具结果的用量报告出来，因此这些 token 属于对话，保持计入。

## 提议

五项 token 读数保留 [Package 使用文档](../../../projects/omp-status-bar/docs/usage.zh.md) 持有的公式，只改变汇总的记录。`I` 是对话的 input 加 cache write，`C` 是它的 cache read，`O` 是它的 output，`T` 是 `I + C + O`，命中率是 `C / (I + C)`。

计数的只有两种形态：会话所持分支上 assistant 消息的用量，以及 `task` 工具结果报告的用量。其余条目不贡献任何用量：携带任何用途的独立 `model_usage` 记录都不计入，其他类型的条目或其他角色的消息不计入，没有 usage 的消息也不计入。在计入的 usage 内部，只累加有限数值，因此非法的计数桶被排除，其余有效的计数桶仍然计入。

该行其余部分不变。不增加也不删除任何 Provider ID、option、颜色或形式，Package 仍不提供 cost 读数，OMP 自身的 statusline 与成本报告保持原有含义。

本提案反转[随 OMP 宿主升级维护状态栏](../decision/2026-09-28-maintain-omp-status-bar.md)中把共享 token 口径写为“来自会话用量统计”的条款，以及其中文对应条款。该口径不可能既来自那个总量、又排除带外记录，两者不能同时成立。后继决定保留该决定的其余全部规则，包括 Widget、Provider 契约、内置清单、投机估计及其限制、已回答请求次数，以及发布前执行的真实 TUI 检查。

两份语言的使用文档说明该口径、列出被排除的内容，并继续持有公式。

## 考虑过的替代方案

**从会话总量中减去带外记录。** 这会把文档记载的数据源保留为基数。该总量不提供按用途拆分，减法只能遍历本提案读取的同一分支、分类同一批记录，再从已经包含它们的总量中减去。结果因此依赖必须持续一致的两侧：总量决定基数，分类决定修正值；宿主任何一侧发生变化都会留下 Package 无法解释的残差。直接求和只有一个来源，也没有残差。

**保留会话总量，另加一项带外流量读数。** 这保留所有现有数字，并在旁边报告被排除的量。它让使用者用来对照对话自身成本的读数继续失真，并要求使用者用一项读数减去另一项，才能还原对话的用量。

**把修正后的口径挂在一次上游变更上。** OMP 可以让判定调用报告真实的 cache 字段，或者提供按用途拆分。这两者都不在 Package 控制范围内，也没有承诺，Package 等待期间读数会持续失真。

## 验收标准

- 在运行过 Find 判定级联的会话中，token 读数与缓存命中率与对话自身用量逐 token 一致，没有任何带外记录进入读数。
- 读数跟随会话所持有的分支，`/tree` 回退或分支切换会像重置已回答请求次数那样重置它们。
- 每条文档化公式保持原义，文档化的 Provider 清单不变，也不出现兼容别名。
- 中英两份使用文档描述该口径与被排除内容，当前决定记录该口径，同时被反转的条款移入归档。
- 每次发布在打标签前记录一次含带外流量的会话的真实 TUI 检查，遵循当前决定已经设定的证据规则。

## 风险

**使用者把该行与 OMP 自身的会话级报告对比，把差异当作缺陷。** 原生 statusline 的 token 段和任何成本报告仍包含带外流量，两组数字按设计不同。使用文档在公式旁写明口径与被排除的记录，使这一差异成为已记录的后果，而不是待查的问题。

**宿主改变记录形态后，读数会静默少报。** 如果 OMP 不再把 `task` 用量报告在工具结果上，或者开始用 Package 不读取的形态记录对话用量，该行仍会渲染不再符合对话的数字。读取规则集中在一个模块里，其测试固定了当下读取的两种形态，因此适配新形态是一处小改动；但没有任何测试能自行发现这一变化。宿主改变记账形态时，最先表现为读数不再符合对话，随后通过使用者报告，或通过当前决定已经要求的真实账本与真实 TUI 发布检查到达 Package。

**每次采样都遍历分支。** 遍历开销随会话条目数增长，并按采样节奏运行，长会话每 tick 都要付出与长度成正比的代价。遍历只读取需要的字段，并且每 tick 对五项读数至多执行一次，而不是每项读数各执行一次。

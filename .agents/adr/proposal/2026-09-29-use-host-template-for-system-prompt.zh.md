# ADR 提案：用宿主模板渲染 OMP 系统提示词策略

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-09-29-use-host-template-for-system-prompt.md) | 中文

## 动机

为系统提示词扩展确定双路径契约：用户选择组件提供的模板时走宿主模板入口，输入仍是宿主默认块时走既有转换。

`@ruokee/omp-system-prompt` 扩展用自有维护文本替换 OMP 默认指令块的固定策略文字，并追加按模型匹配的规则文档。它依据渲染后的结构识别默认块，再用自有模板重建它。本次升级目标范围内的宿主版本重写了该块，于是已识别的结构不再匹配，扩展在这些宿主上保持宿主提示词不变。自有的固定策略、Delivery 设置与 footer 修正在这些宿主上因此全部停止生效，而在扩展仍能识别指令块的宿主上继续生效。

宿主为同一件事提供了受支持的入口：用 Handlebars 模板渲染指令块，并获得与内置模板相同的实时数据和已注册 helper。契约说明扩展在每条路径上各自负责什么。

## 分析

在模板入口下，宿主用被选中的来源渲染指令块，并保留自己生成的 footer 块，该块仍以 `<project-context>` 开始，承载上下文文件、工作区数据和 append 文本。Anthropic 的缓存断点落在第一个 `<project-context>` 块之前的最后一个块上，因此该标记、块顺序以及静态前缀与工作目录派生块之间的划分属于宿主的缓存布局，而不是表现形式（见[定制文档](https://github.com/can1357/oh-my-pi/blob/v18.4.3/docs/system-prompt-customization.md)）。

模板会拿到会话的实时数据，包括可见 Skills、规则、always-apply 规则、工具清单、Internal URLs、设备列表、工具引用与任务设置，但拿不到插件设置。因此组件偏好无法写在模板内部，渲染结果里也没有任何信息能证明是哪一个作者选择了它。

footer 仍由宿主按自己的来源生成，并以文本形式出现在扩展收到的块数组里，与今天一致。

## 提议

### 两种已识别的指令块

扩展改为识别两种指令块形态。

1. 宿主默认块，即今天识别的那一种，在 turn 输入仍携带它时使用。这仍是旧路径：既有结构校验、自有重建与既有 footer 转换保持原有行为。
2. 组件自有模板的渲染结果，在会话选择了它时使用。这是新路径。扩展依据组件自有的模板标识加已校验的骨架来识别它，而不是依据宿主是否具备模板机制。

其它任何形态——其他作者的模板、扩展无法完整校验的宿主默认块、只部分匹配的骨架——都保留输入不变，并报告一个有界原因。扩展不猜测结构，也不声称策略已经生效。

### 选择组件模板

组件以受维护产物的形式提供自己的模板，由自有策略文本派生，并带有扩展可校验的稳定标识。用户通过宿主已有的模板选择机制使用它。组件不写用户配置、不写已安装的宿主文件，也不复制宿主自带模板。

模板加载失败归属读取它的那条宿主路由。严格模板参数缺失、不可读、为空或格式错误时，该会话在扩展运行前就启动失败，扩展没有可保留的输入，也没有原因可报告。宿主按自己的优先级顺序处理发现式模板：空文件的候选被跳过，宿主继续查找更低优先级的纯文本或模板，没有候选时才回退到自带提示词，因此空候选不会给 handler 留下可归因于该文件的输入。已选中的发现式模板格式错误是另一种结果：宿主给出警告并渲染自带提示词。扩展只分类最终进入 handler 的那个块，不问它由谁产生：该块能校验为组件模板时就报告新路径生效，包括宿主在跳过空候选之后选中的正是较低优先级组件模板的情形；其它块按其实际形态走旧路径或无法识别回退；无法校验的块报告为无法识别，而不报告为模板失败。

### 新路径上扩展负责的部分

- **Delivery。** 每个受覆盖 turn 继续通过公开设置 API 读取有效的 `renderDelivery` 值，据此决定是否把自有 Delivery 章节紧接在已识别的模板块之后插入。该章节的正文、默认值、fail-open 取值与逐轮刷新保持原义。
- **footer。** 扩展修正外层加载指引并删除固定外层 critical 尾部，同时让 `<project-context>`、上下文正文、列出的路径、workstation 数据、工作区数据、活动仓库文本与 append 文本逐字节保留。无法唯一确定的边界保留整个 footer 不变，并报告本次修正未生效。
- **模型规则。** 第二个 handler 继续把匹配的规则文档追加到该轮已有的数组上，匹配方式、顺序与逐字正文保持不变。
- **Skill 文本。** 模板绑定宿主传入的可见 Skill 数据。该路径上扩展不再从命令元数据重新推导描述，不恢复被宿主缩短的描述，也不向可见集合补充任何 Skill。描述单行化保留在旧路径。

上述各项各自报告自己的有界结果。某一步失败不会压制其它步骤，任何一步的成功也不能代表其他步骤。

### 重复 turn 与设置变化

新路径是幂等的。输入中已经带有组件模板块、处于预期位置的自有 Delivery 章节和已修正的 footer 时，扩展识别该形态，在无内容变化时不返回替换。`renderDelivery` 在轮次之间变化时，只增删该章节。

### 兼容边界

兼容对象是扩展，不是宿主。组件不要求宿主保留旧默认块，不把模板入口回移到没有它的宿主，不内置宿主自带的模板文本，也不提高任何维护下界。旧宿主保留既有转换及其行为。

### 与现行决定的关系

[添加 OMP 系统提示词扩展](../decision/2026-09-09-add-omp-system-prompt.zh.md)中有若干条款无法与本契约同时成立。

- 「识别恰好一个受支持的默认主块和一个结构有效的 PROJECT 块」与「使用自有模板重建主块」：在新路径上，指令块是组件自有模板的渲染结果，由宿主在钩子运行前生成。把它作为第二种已识别形态，意味着扩展不再要求宿主默认块，并在该路径上不再重建指令块。
- 把 `renderDelivery` 章节作为被重建主块的一部分：在新路径上该章节是独立的自有块，放在模板渲染结果之后，因为模板读不到插件设置。
- 「使用有界诊断安全回退」中把自定义提示词和边界有歧义的情况一律保留输入不变：宿主渲染的组件模板两者都不是。若不把模板渲染结果列为受支持输入，扩展只能把这条受支持的新路径当作失败处理。

因此，提案获准后需要一份完整的后继决定，记录这份双路径契约，并保留现行决定中仍然有效的规则：用结构识别而不读版本，资格、激活、转换、诊断与回退都不读取宿主版本；逐轮读取设置；对无法识别的输入 fail-open 并给出有界诊断；模型规则契约及其顺序；覆盖范围与证据边界；以及禁止写用户文件和内置宿主内容的约束。

[为系统提示词扩展添加按模型生效的提示词规则](../decision/2026-09-14-add-model-prompt-rules.zh.md)不冲突。其追加步骤读取该轮实际携带的数组，在新路径上也是如此。

## 考虑过的替代方案

**扩建既有转换器以识别升级目标的默认块。** 在决定如何在新宿主上保住策略时考虑过。它只保留一条路径，也不需要用户配置，但组件要继续维护一套解析宿主散文的解析器，宿主每次重写该块都会重复同一次失败。

**改用纯文本自定义提示词入口，而不是模板。** 在比较受支持入口时考虑过。纯文本安装更简单，但该入口用宿主的纯文本自定义模板渲染会话数据，而不是用组件自有文本，因此自有的工具、设备、Internal URLs 与运行时各段无法保留。

**把 Delivery 章节写进模板。** 在决定该章节放在哪里时考虑过。它不需要逐轮插入，但模板读不到插件设置，已记录的开关及其逐轮变化会因此丢失。

## 验收标准

1. 仍携带宿主默认块的轮次保持今天的行为：已识别的块被重建，既有 footer 转换生效，无法识别的结构保留输入不变并给出有界诊断。
2. 选择了组件模板的会话，其 Provider 输入在指令块中带有自有策略与宿主渲染的工具清单、设备文档、Internal URLs、Skills 和规则，并带有 `<project-context>` 标记仍然完整的宿主 footer 块。
3. `renderDelivery` 未配置或为 true 时包含自有 Delivery 章节，为 false 时省略；该章节位于模板块之后、footer 块之前，轮次之间的变化只影响该章节。
4. footer 修正删除外层加载指引与固定外层 critical 尾部，并逐字节保留上下文正文、列出的路径、工作区数据与 append 文本；边界无法唯一确定时不改动任何内容，并报告本次修正未生效。
5. 被宿主拒绝的严格模板参数使该会话在扩展运行前就失败；空的发现式候选被跳过，不决定扩展收到什么；已选中的发现式模板格式错误时给出警告并渲染宿主自带提示词。三者的任何一种本身都不被报告为新路径。扩展只分类最终进入 handler 的那个块，因此空候选被跳过之后，较低优先级的组件模板仍可被合法报告为新路径。扩展无法校验的块，包括其他作者的模板、形似的正文、缺失的标识与损坏的渲染骨架，都不被改写，报告为无法识别，也不是报告为已适配。
6. 匹配的规则文档在两条路径上保持相同的匹配键、顺序、逐轮读取与逐字正文；替换失败时追加步骤仍能扩展收到的数组。
7. 实机会话中，Provider 请求携带组件策略、Delivery 设置的实际效果与匹配规则正文；仅有 handler 返回值不构成该证据。
8. 组件文档在两条路径上继续区分会运行该钩子的会话与不会运行该钩子的会话。
9. 实现时创建后继决定、在当前提示词决定上记录关系，并在同一变更中调整组件版本与中英文文档。

## 风险

- 同一项行为的两套实现容易漂移。改动只落在旧转换或只落在模板上时，两个受维护宿主会得到不同的策略文本，且没有任何报错。
- 接受宿主对 Skill 描述的预览与摘要，意味着扩展此前能保留的激活限制可能从提示词中消失，而且不会有诊断，因为宿主侧的缩短属于预期行为。

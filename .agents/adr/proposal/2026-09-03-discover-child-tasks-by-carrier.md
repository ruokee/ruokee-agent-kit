# ADR proposal: Discover child Tasks by carrier

Decision owner: Ruokee
Draft writer: OMP GPT-5.6 Sol

English | [中文](./2026-09-03-discover-child-tasks-by-carrier.zh.md)

## Motivation

The [tk Task data model decision](../decision/2026-08-28-define-tk-task-data-model.md) uses `subtasks_dir` for both child Task creation and discovery. A child is visible only when every level follows the configured directory and `NN--slug` topology.

That coupling lets a placement preference hide valid Task data. Changing `subtasks_dir`, importing an existing child Task, or organizing a child below an ordinary material directory can make the Task unreachable even when its carrier and schema are valid.

Creation needs one predictable destination and numbering rule. Discovery needs to recognize valid Task carriers already present below a parent without treating every Markdown directory as a Task.

## Proposal

### Separate creation placement from discovery

Keep `subtasks_dir` as the default destination for newly created child Tasks. An empty value creates them directly below the parent. A non-empty value creates them below that relative directory. New child directories continue to use `NN--slug` names.

Allocate the next sequence from discovered direct children whose leaf directory has a valid two-digit `NN--slug` prefix. Do not fill gaps, and keep `99` as the maximum generated sequence. The configured destination selects where the new directory is written; it does not define which existing Tasks are siblings.

Changing `subtasks_dir` affects later creation only. It does not move existing Tasks and cannot make an existing valid child disappear from discovery.

### Discover by carrier markers

Keep the canonical `YYYY/MM/DD-NN--slug` requirement for top-level Tasks. After finding a valid top-level Task, recursively inspect real descendant directories below each valid parent Task.

A directory becomes a structural candidate only when it carries an intentional marker for the project's metadata mode:

- In `split` mode, `tk.toml` is the marker. A valid Task also requires its matching `TASK.md`.
- In `embed` mode, `TASK.md` must begin with recognizable tk frontmatter. An unrelated file named `TASK.md` is ordinary material.

A candidate becomes a discovered Task only after the runtime validates its complete carrier, schema, identity, and safe project path. Duplicate identities and invalid relationships are project-graph diagnostics; they do not make a marked directory ordinary material. Malformed marked candidates remain invalid managed content for `check` to report and are not returned as Tasks by normal discovery.

Do not follow symbolic links or special files. Exclude WAL directories, tk temporary content, cleanup data, and other runtime-owned paths from descendant traversal. Traverse ordinary material directories because a valid child Task may be nested below them.

The parent of a discovered Task is its nearest enclosing valid Task. Discovery continues below a valid child so nested carriers form descendants of that child. Direct children are therefore determined by valid ancestry, not by physical distance from the parent or the configured creation directory.

### Apply one discovery graph

Use the same carrier-based Task graph for search, exact path resolution, descendant checks, relationship validation, `check`, schema migration, metadata mode switching, and sequence allocation. An absolute path to a discovered Task directory or its managed carrier is an exact Task reference even when the directory was not generated by tk.

For a child Task outside the generated `NN--slug` layout, `rename` updates the managed `name` without moving its directory. For a generated child directory, `rename` preserves the sequence and updates its slug in place. Top-level rename keeps the existing canonical path behavior.

This proposal conflicts with the current data model decision's requirement that child candidates follow `subtasks_dir` and exact `NN--slug` topology. If accepted and implemented, it will reverse [Define the tk Task data model](../decision/2026-08-28-define-tk-task-data-model.md). The replacement decision must preserve all still-effective identity, lifecycle, relationship, persistence, migration, Git, and maintenance rules while replacing child discovery and affected rename rules.

## Alternatives considered

**Keep discovery under `subtasks_dir`.** This is the current decision and runtime behavior. It makes scanning narrow and keeps every discovered path generated by tk, but a placement configuration remains part of Task identity in practice. Existing valid child carriers become unreachable when they are imported elsewhere below the parent or when the configured creation directory changes.

## Acceptance criteria

1. `subtasks_dir` controls only the default creation destination. Changing it does not hide or move existing valid child Tasks.
2. Top-level discovery retains the canonical date and sequence topology. Descendant discovery traverses real directories below valid Tasks without requiring `subtasks_dir` or a generated leaf name.
3. `split` discovery uses `tk.toml` as the intentional marker and requires a valid paired `TASK.md`. `embed` discovery requires recognizable, valid tk frontmatter. Unrelated `TASK.md` files remain ordinary materials.
4. The nearest enclosing valid Task determines parenthood. Nested valid carriers form descendants even when ordinary directories occur between Tasks.
5. Symbolic links, special files, WAL, temporary content, cleanup data, out-of-project paths, and malformed carriers cannot become discovered Tasks. `check` reports marked invalid content, duplicate identities, and invalid relationships through stable diagnostics instead of silently treating them as ordinary materials.
6. Search, exact path resolution, lifecycle descendant checks, relationship validation, `check`, migration, metadata mode switching, and sequence allocation use the same discovered Task graph.
7. Creation keeps two-digit `NN--slug` names, does not fill sequence gaps, and fails before writing when generated direct-child sequence `99` is already in use.
8. Rename preserves non-generated child directories, updates generated child slugs in place, and retains canonical top-level rename behavior.
9. Runtime tests cover children in the configured directory, directly below the parent, below ordinary material directories, after a `subtasks_dir` change, and in invalid or excluded paths. English and Chinese design and Skill documentation describe the same rules.
10. Implementation archives the current tk Task data model decision and creates a complete replacement decision with reciprocal relationship metadata.

## Risks

A material directory that contains an intentional marker and fully valid Task metadata can become a Task even if its author meant it as an example. That can change descendant closure checks and relation scope. Requiring a mode-specific marker and full schema validation makes accidental promotion unlikely, but repositories must avoid copying valid managed carriers into ordinary materials.

Recursive descendant scanning can read more directories than the current configured-path scan. Large material trees or unreadable directories can slow project-wide commands or make a required scan fail. Traversal must remain within the Task root, skip runtime-owned and linked paths, use deterministic bounded resource handling, and preserve explicit incomplete-scan errors.

Moving a valid carrier below another valid Task changes its derived parent without changing metadata. An accidental file move can therefore alter close blockers and direct-child numbering. `check` and rename results must expose the resolved parent and path clearly enough to diagnose that change.

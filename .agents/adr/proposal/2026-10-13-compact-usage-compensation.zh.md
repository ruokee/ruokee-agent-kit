# ADR 提案：在 QoL 中补记压缩请求用量

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-13-compact-usage-compensation.md) | 中文

## 动机

在 [omp-qol](../../../projects/omp-qol/README.md) 中增加一个可独立开关的调整项，记录宿主压缩请求的 token 用量与成本，直到 OMP 自己记录这些请求为止。

会话压缩时，OMP 会自己发起摘要请求：`soft` 方法的摘要、短摘要与回合前缀调用，以及 `handoff` 方法的请求。provider 对每一次这样的请求都上报了用量，但该值止步于摘要调用。会话的 `model_usage` 条目以及读取它们的会话统计完全没有覆盖压缩请求，于是会话文件少算了这次会话的真实开销，任何基于这些统计的报告、预算或额度视图都会偏差，偏差量等于该会话执行过的压缩次数。

上游以 [issue #15031](https://github.com/can1357/oh-my-pi/issues/15031) 跟踪该缺口，并在 [pull request #15034](https://github.com/can1357/oh-my-pi/pull/15034) 中修复。2026-10-13 该 pull request 仍处于 open 状态、未合入，最新发布的 `@oh-my-pi/pi-coding-agent` 18.10.3 也不包含该修复。

## 分析

宿主通过 telemetry 通道暴露该用量，而默认安装下这条通道是关闭的。

已在宿主源码 `18.5.0`（组件声明的下限）核对，并在本机已安装的 `18.8.3` 上复核：所有本地压缩与 handoff 请求都经过 `@oh-my-pi/pi-agent-core` 中同一个带监控的补全封装，该封装会开启一个 chat span、在 span 上写入该请求的 oneshot kind，并发出携带用量快照与响应结束原因（finish reasons）的 chat 用量事件。coding agent 中的各压缩调用点与 handoff 调用点在每次调用前从 agent 解析 telemetry 配置；除非用户配置了 telemetry，该配置为 `undefined`，因此默认安装既不产生 span 也不产生事件。session manager 已经拥有一种条目的类型，专门表示不属于对话记录的模型调用；当这样的条目写在活动分支上、且位于压缩条目之前时，宿主自身的会话统计会把它计入。

在真实的 `18.8.3` CLI 上用一个上报唯一 token 数的桩 provider 验证过：一次 soft 压缩与一次 handoff 各自产生了带预期 kind 的用量事件，能从快照还原 provider 的 prompt、cached 与 completion token，能拿到 provider 的逐项成本；由这些事件写入的条目被宿主自身的会话统计计入，统计增量与条目相等。

有三点约束决定了该调整项的形状。被取消或失败的尝试同样会发出事件，其快照全为 0、结束原因（finish reason）为错误，因此没有过滤的写入会记下零用量噪声。只要存在 telemetry 配置，宿主就会为每一个模型步骤创建 span，因此注入的配置必须保持惰性。此外没有任何路线能触达请求本身：没有事件或 hook 携带用量，请求函数是构造期按值捕获的私有实例字段，模块级的补全符号无法改写，所以封装内部被重试丢弃的尝试无法找回。

## 提议

### 一个调整项

组件新增一个调整项 `compactionUsageEnabled`，默认开启，在现有的总开关之下可独立开关，并按现有设置规则被拒绝或上报。其效果：已完成的压缩与 handoff 请求会出现在会话的用量条目中，也会出现在宿主由这些条目得出的统计中。

### 挂载位置

调整项在宿主读取 agent telemetry 配置的位置安装一份 telemetry 配置，并保留已有的那份：已有的导出配置继续使用自己的 tracer、自己的 hook 与自己的输出，调整项不向导出中增加任何内容。原本没有配置时，调整项提供一份惰性配置。为了识别请求，调整项观察宿主写在请求自身 span 上的 oneshot kind；它不读取该 span 的其他内容，也绝不触碰请求、模型、缓存键、历史或会话文件。

### 记录内容

对每一次已完成的压缩或 handoff 请求，调整项通过 session manager 已有的用量条目接口写入一条用量条目，包含该 kind 对应的 purpose、实际执行的 api、provider 与 model、provider 的 token 计数、provider 的逐项成本，以及使该条目属于请求所属会话的分支位置。压缩与 handoff 的 kind 采用显式白名单；宿主标注的其他 oneshot kind，例如评估补全、技能描述与图像提问，不在范围内。

没有产生任何 token、以错误结束或被取消的尝试不写入。宿主已经原生记录的请求不写入。不延迟、不重试、不改道、不重写任何请求，也不读取或保存任何模型内容。

### 退场

该调整项是一段有明确终点的补偿。它检测宿主对这些请求的原生记录能力，在具备该能力的宿主上保持停用并给出原因；组件文档包含一节上游复核（upstream re-check），与模型提示规则那一节同类，写明被检查的宿主接口。当某个已发布的 OMP 版本自行记录压缩与 handoff 用量后，删除该调整项的代码、设置、文档与测试，组件规格去掉该能力，并用一个决定记录这次移除。

### 文档、规格与版本

实现变更把该调整项加入[调整项文档](../../../projects/omp-qol/docs/adjustments.md)、README 的调整项与设置表格、`/qol` 状态报告与 `package.json` 的设置清单，并更新[组件规格](../../spec/omp-qol.md)的目标、公开接口、不变量与验收标准。组件的 `Z` 版本随该变更递增。

## 考虑过的替代方案

无

## 验收标准

1. 在受支持的宿主上开启该调整项后，真实的 OMP CLI 会话经 `soft` 方法压缩一次、以及执行一次 handoff，都会为每一次已完成的摘要请求产生一条用量条目，条目携带 provider 的 token 计数与逐项成本，宿主自身的会话统计包含这些条目且增量等于写入值。
2. 被取消、失败或上报零 token 的尝试不产生用量条目，因此摘要请求全部失败的会话不会新增条目。
3. 关闭该调整项时不安装 telemetry 配置、不写入用量条目，也不产生额外的 span。
4. 已有的 telemetry 配置保留其 tracer、hook 与导出输出，调整项不新增自己导出的 span 或事件。
5. `/qol` 报告该调整项的有效状态，停用时给出有界的原因；其他所有键的设置校验保持不变，未知键、类型错误或超出取值范围的取值行为与今天一致。
6. 行为检查覆盖范围内的请求 kind、被忽略的 kind、全零与错误尝试、宿主接口缺失，以及已有 telemetry 配置的保留。该调整项在真实 CLI 上的证据记录在调整项文档对应的版本与验证一节，未跑的场景标注为未验证。
7. README 表格、设置清单、调整项文档与组件规格对该调整项的键、默认值、范围、限制与退场条件保持一致，规格保留现有宿主下限。
8. 上游复核一节写明使该调整项退场的宿主接口，以及下一次检查要看什么。
9. 组件目录内 `bun run typecheck` 与 `bun test` 通过，提案从 `proposal/` 中移除并生成对应的决定，所有入链可解析。

## 风险

- 挂载 telemetry 配置会改变宿主行为：只要存在配置，宿主就会为原本被跳过的模型步骤创建 chat span 并运行 hook 路径，给每个请求增加开销，并把这些 span 携带的内容属性送入用户已有配置的导出。调整项提供自己的惰性配置，不向已有导出增加内容，且只保留自己需要的请求 oneshot kind。
- 用量可能被记到错误的请求或错误的分支上。如果事件的 span 不是读取 kind 的那个 span，写下的 token 与成本描述的是另一个请求；如果条目没有落在请求所属的分支上，它对想要修正的统计不可见。两种情况下会话总额仍然错误，而调整项仍报告为启用；因此 kind 从事件自带的 span 读取，span 无法识别时不写，分支位置在写入时读取。
- 宿主开始自行记录这些请求之后，仍然开启的调整项会记录第二遍，抬高 token 计数与成本。退场检测与 `/qol` 报告的状态是代码删除之前的护栏。
- 临时补偿可能活过自己的条件：跨宿主版本长期保留时，它会附着在已经移动的接口上、静默失效，并在用户以为会话账目已补齐时报告停用状态。版本说明、`/qol` 中有界的原因，以及上游复核一节让这种重叠保持可见。

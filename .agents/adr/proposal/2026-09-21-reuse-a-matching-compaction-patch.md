# ADR proposal: Reuse a matching compaction patch across activations

Draft owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

English | [中文](./2026-09-21-reuse-a-matching-compaction-patch.zh.md)

## Motivation

The compaction deadline experiment installs one process-wide patch and stops rewriting when another activation already owns that patch. OMP `18.2.4` binds the loaded extensions for every session it creates and calls their factory again; some paths reuse a prepared factory instead of evaluating the module again, but the factory runs either way (`packages/coding-agent/src/sdk.ts:505-518`, `packages/coding-agent/src/extensibility/extensions/loader.ts:479-508`). A subagent session therefore reaches this module's conflict path in a running process.

The patch the first activation installed stops rewriting, the second activation installs nothing, and the process keeps the native five-minute deadline for the rest of its life. Settings say the experiment is on while `/qol` reports `incompatible` with `runtime-conflict`, so the user loses the adjustment without changing any configuration. Live OMP `18.2.4` sessions with `compactionTimeoutEnabled: true` show the stopped patch and the second activation in the same millisecond, which is what a subagent activation looks like in the log.

That conflict path implements the "Ambiguous ownership" clause of [Add configurable OMP quality-of-life adjustments](../decision/2026-09-20-add-omp-qol.md): an owner already registered in the process stops the adjustment for that process instead of sharing or overriding it. The clause was written for owners that differ in what the patch should do, such as a window from another session or a settings snapshot that no longer applies.

Two activations that carry the same package version and the same effective settings do not become one object, though. The window the patch rewrites in is opened by the events of the activation that installed it, and that window is process-wide: the wrapper rewrites a deadline by whether the call happens inside the window and whether its number matches the range, and it does not identify the session a call belongs to. Keeping the patch says the installed policy still applies to the process; it says nothing about which activation can drive the window on its own, and it cannot transfer the installing activation's lifecycle to a later one. The proposal therefore changes both the re-activation rule and what a re-activation reports.

## Proposal

Narrow the clause for the re-activation case described above: a second activation keeps the installed patch instead of stopping it when all of the following hold.

- The activation itself asks for the experiment: the master switch is on and this module's switch and keys are usable, so nothing is installed or enabled on a default value.
- Its package version equals the version recorded by the installed patch.
- Its effective compaction settings snapshot equals the snapshot the installed patch was built from: enabled, `timeoutMs`, `floorMs`, `guardMs`, and `notify`.
- The patch is still this module's own: not already disabled by an earlier conflict, and the current `AbortSignal.timeout` is still the wrapper of the installed patch.

Such an activation installs no second wrapper and does not stop the patch. It registers no window events and opens no window, because the window belongs to the installing activation, so it does not report `enabled`. It reports `incompatible` with the reason `patch-owned-elsewhere`: the process patch exists, another activation owns it, and this activation cannot drive the window on its own. That reason says the window is not opened by this activation; it does not say this session's compaction is never rewritten. While the installing activation's window is closed, this session's compaction runs on the native deadline; while the window is open, every call in the process whose number matches the range, this session's compaction included, is extended. The recorded activation cwd stays diagnostic and takes no part in the comparison, because a subagent may run in another directory under the same settings.

`/qol` resolves the compaction line from the process registry when the command runs instead of repeating one activation's result. While this module's wrapper is installed by another activation, the line reports ownership; once that activation stops the patch (a conflict, an overlapping window, the experiment switched off) the line reports that reason; if another extension replaced `AbortSignal.timeout`, the line reports `patch-overwritten`. A session never keeps showing `enabled` for a patch it cannot drive.

When the installing activation ends its session, the process does not leave the patch to a later activation. `session_shutdown` closes the window it opened and restores the native function only while `AbortSignal.timeout` is still the wrapper this module installed; the registry keeps a bounded `owner-stopped` terminal state recording that the process patch was released by its owner. `/qol` reports that state from then on instead of `enabled`, and no exited activation is treated as a live owner. The process installs no new patch, takes over nothing, and re-contends for nothing: a later matching activation reports the terminal state instead of installing a patch, and getting the adjustment back in that process requires restarting OMP, so no session is extended between the owner's exit and the restart. `session_switch` is the same activation serving a new session: it closes the current window and is not an activation exit.

Everything else stays as it is: one wrapper per process, owned by the activation that installed it; that activation's events open the windows the wrapper rewrites in; a second activation with another snapshot or another version, a master switch that keeps it off, invalid keys, settings that could not be read, a registry slot this version cannot read, or a wrapper that another extension replaced still stops the patch where the current rule stops it and reports the same reasons. Disabling the experiment on the installing activation still restores the native function. No conflict is reported for a keeping activation: another activation owning the patch is the declared single-owner scope, not a failure.

The component documents the rule in `projects/omp-qol/README.md` and `projects/omp-qol/docs/adjustments.md`, in English and Chinese, and the automated checks cover those outcomes.

## Alternatives considered

- **Keep the rule and document the consequence.** This was considered when deciding whether to change the component. It leaves every live process without the adjustment once a subagent starts, so the experiment would only ever apply to sessions that never delegate.
- **Change the host so a session does not re-activate process-global extensions.** This was considered when weighing where the fix belongs. Per-session binding is deliberate: each `Extension` closes over its own session's cwd, event bus, and runtime, and restricted children are the only path that loads no extensions. Changing that model affects every extension, not this adjustment, and this component cannot verify the result without rebuilding the host.
- **Let the newest activation take over the wrapper.** This was considered while choosing the conflict behavior. It would let a session whose settings differ from the installed snapshot replace the patch in place, which is the overriding the current decision rejects.
- **Share the patch and let every activation register the window hooks.** This was considered while deciding how far a re-activation may reach into the installed patch. Several sessions would then open and close one window, and the existing rules treat a window from another session as ambiguous ownership and stop the experiment on it.
- **Report `enabled` for a keeping activation and leave the limit to the documentation.** This was considered while deciding what a re-activation may claim. A session would then read as fully served although the patch answers to another activation's events, which is the reporting defect this proposal removes.
- **Let the next matching activation install a patch after the owner exits.** This was considered while choosing the recovery path. The process would regain the adjustment without a restart, and the new patch would be owned by an activation that is still alive, matching the first-install rules. It would also make whether the process currently has the adjustment depend on whether another activation shows up later, and `/qol` would have no settled state to report after the owner exits; the proposal takes the settled state and the restart instead.
- **Identify the request and let a window apply only to the session that owns it.** This was considered while judging whether the window's side effect can be removed. The wrapper's call site receives no session or request identity, so deciding per session would change the types and host interfaces of the compaction call chain, beyond this component's reach; the current decision already accepts the side effect that unrelated timeouts inside the window are extended.

## Acceptance criteria

1. Automated checks in `projects/omp-qol` cover the keeping path: a second activation with the same version and snapshot keeps the installed patch, installs no second wrapper, reports `incompatible` with `patch-owned-elsewhere`, and leaves the installing activation's window rewriting deadlines; a second activation with another snapshot, another package version, this module's switch off, the master switch off, or invalid keys stops the patch with `runtime-conflict`; an activation whose settings could not be read still stops a recognised patch; a stopped patch stays stopped for a later matching activation; and the reported status follows the registry when the patch is stopped after the keeping activation ran.
2. Automated checks cover the interleaving of a process-wide window: a non-owner call outside the owner's window keeps the native deadline and is extended inside the window; a non-owner `session_shutdown` does not close the owner's window, and that window keeps rewriting deadlines from its own events.
3. Automated checks cover the owner's exit: `session_shutdown` closes the window and restores the native function while the current function is still its own wrapper, without restoring over another extension's replacement, and leaves the `owner-stopped` terminal state; `/qol` in later sessions of that process reports that state instead of `enabled`; a later matching activation reports the same state and installs no new patch; and `session_switch` only closes the current window, with the same activation serving the new session.
4. A real OMP CLI run in one process demonstrates that starting and ending a subagent session no longer stops the patch, that `/qol` keeps reporting `compaction: enabled` for the session that installed it and reports `compaction: incompatible (patch-owned-elsewhere)` for a session that shares the process without owning the patch, and that `/qol` reports the terminal state after the owner session exits. The run records the OMP version, the model, and the component version, and it is reported separately from the automated checks.
5. `projects/omp-qol/README.md`, `projects/omp-qol/README.zh.md`, `projects/omp-qol/docs/adjustments.md`, and `projects/omp-qol/docs/adjustments.zh.md` state the new rule and its boundaries in both languages, and the component version is incremented.
6. The component's own texts stop describing a matching second activation as a conflict, and stop promising that a session which merely shares the process gets extended deadlines or is never rewritten: the registry documentation, the inline comments, and the `/qol` sample output.
7. The decision that carries this change reverses [Add configurable OMP quality-of-life adjustments](../decision/2026-09-20-add-omp-qol.md) and keeps every rule of that decision that remains in force.

## Risks

- The settings snapshot comparison becomes the only gate between an installed patch and a session that did not install it. A settings field added to the effective configuration without being added to that comparison would widen reuse silently, and a session could then be kept under a configuration it never chose. The comparison and the snapshot type must change together.
- A keeping activation does not drive the window and gains no guarantee of an extension: with the window closed its compaction runs on the native deadline, and with the window open it is rewritten like every other matching call in the process. The state line and the documentation are the only places that say so; without them, a subagent session would look like a fully served session that is never affected.
- Status resolution depends on reading the registry when the command runs. A status cached at activation time recreates the defect this proposal removes, so the check and the resolution must be tested together.
- After the installing activation exits, the process extends no compaction deadline until it restarts, and `/qol` keeps reporting `owner-stopped`. That is the chosen terminal state: releasing the patch without letting a later activation install one costs the adjustment for the rest of that process's life.
- A process-wide window means unrelated timeouts inside the window are extended too. The current decision already accepts that side effect, this proposal keeps it, states it in the contract, the status, and the documentation, and does not introduce request identity or multi-owner coordination for it.
- A relaxed ownership rule can drift towards shared or overridden patches in later changes. Without an explicit boundary in the component documentation and the decision, the next second-activation change can weaken the remaining refusal reasons.

## Changes

- The request-isolation wording is gone: a keeping activation registers no window events and is not guaranteed an extension of its own compaction. The window is process-wide, so a non-owner runs on the native deadline while the window is closed and is rewritten like other matching calls while it is open.
- Owner-exit rules are added: `session_shutdown` closes the window, restores the native function while it is still this module's wrapper, and leaves a bounded `owner-stopped` terminal state; later activations install no new patch, recovery requires restarting OMP, and `session_switch` only closes the window.
- The acceptance criteria are split into the keeping path, the interleaving of a process-wide window, and the owner's exit and recovery boundary, with a real-CLI check of the terminal state.
- The reported state of a keeping activation is `incompatible` with the reason `patch-owned-elsewhere`, because the patch belongs to another activation and does not serve this session's compaction.
- `/qol` resolves the compaction line from the process registry at query time instead of repeating the activation result, so a later stop shows up in every session of the process.
- The motivation no longer claims that every session evaluates the entry module again; it states that the factory runs for every session, on the module path or on a reused prepared factory.
- The ownership wording separates three things that were implied to be one: another activation of this extension, the activation that owns the process patch, and the activation whose events own the current window.

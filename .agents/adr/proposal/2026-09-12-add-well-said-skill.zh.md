# ADR 提案：增加 well-said 写作 Skill

Decision owner: Ruokee
Draft writer: OMP GPT-6 Astra

[English](./2026-09-12-add-well-said-skill.md) | 中文

## 动机

Agent 写作即使事实正确，也可能显得机械。套话、过度格式化和重复限定会掩盖作者的意思。纠正还可能在成品里留下痕迹，例如描述已舍弃想法的标签、反复证明服从要求、无法访问的草稿引用，以及被写成长期要求的临时指令。

目标是让文字像一个人在表达经过思考的意思，语气适合用途，信息足以服务读者。清除编写会话残留是优先事项。文风清理和减少无用自证共同服务于这一目标，同时保留事实、不确定性、有用解释和作者声音。

这些问题需要一个可统一维护的 Skill，并共用语义保护规则。完整写作指南集中在一个文件中，使日常起草无需先识别问题，再获取解释该问题的规则。文风、会话残留和自证可能同时出现，需要综合处理。

## 提议

### 能力与范围

增加名为 `well-said` 的第一方 Skill。名称采用常见词，适合“使用 well-said 检查这段文字”等日常请求。

Agent 撰写、编辑或审阅用户可见自然语言时均适用，包括回复、报告、文档和代码注释。支持用户明确调用，也支持 Agent 根据上述范围激活。起草时即应用规则，不只在写完后做清理。

可执行代码和配置不属于编辑范围。混合文件中的注释与可执行内容分别处理。引文、命令、标识符、原始日志、录制输出及其他字面材料，在其用途或用户请求要求逐字保留时保持原样。

Skill 不增加文件修改权限。审阅请求在未获编辑授权时保持只读。处理范围遵循用户指定的文件、文本和结构。

### 组件布局与内容归属

英文组件位于 `skills/well-said/`，完整中文变体位于 `variants/zh/skills/well-said/`。每个组件用一份 `SKILL.md` 提供全部写作规则、保护边界和必要示例，并通过清晰章节组织。

保持所需内容完整，包括保留的 unslop 材料。不预建专项参考文件。只有实际内容及加载测量表明有必要时，才考虑移出篇幅可观的低频补充材料；日常写作仍须由 `SKILL.md` 中的完整规则支持。

遵循[组件自包含决定](../decision/2026-08-24-keep-components-self-contained.zh.md)。每个语言组件提供完整规则和示例，内部引用解析到自身目录。两种语言中的安装路径示例均使用 `skills/well-said/`。组件使用不依赖其他 Skill、个人指令、私有研究或源仓库。

应用[第一方能力决定](../decision/2026-08-20-establish-first-party-capability-kit.zh.md)时，以开发和维护的能力主体判断归属。第一方能力可以引用、摘录或改编第三方内容。是否属于 fork，取决于是否以第三方能力本身为主体，不能仅根据是否使用或使用了多少第三方内容判断。

`well-said` 是独立设计和维护的能力主体，拥有自己的目标、组织、激活规则和语义保护边界。unslop 为其中的文风章节提供外部材料。在 `SKILL.md` 中大幅保留来源原文、例子和有效组织，仅作必要衔接与补充。复用材料保留其原作者归属。

unslop 的来源链包括 [Cursor plugins 的 unslop](https://github.com/cursor/plugins/blob/main/pstack/skills/unslop/SKILL.md)。纳入并分发复制内容前，确定具体来源版本及本地补充内容，核实适用许可，保留所需署名和通知。能力主体归属与来源使用义务分别判断，来源核查尚待完成。

[architect Skill](../decision/2026-09-18-make-architect-model-invoked.zh.md#参考资料与改写) 已有相同实践：它使用外部架构仓库作为主题地图和内容来源，同时保持独立编写的 Skill 主体。改写来源材料是 architect 的具体选择，不是取得第一方身份的通用前提。

在 [AGENTS.md](../../../AGENTS.md) 和第一方能力决定的 `Changes` 下明确这一通用归属原则。澄清内容边界措辞，避免把第一方能力中的第三方材料引用或复用等同于引入第三方能力、fork 或镜像。保留对这些第三方能力的禁止，以及来源署名与许可义务。为 well-said 的能力契约建立独立决定，并从该更新建立链接。

泄露清理章节以维护者已有的编写会话清理规则为基础，形成可独立使用的指南。其他案例可以补充语义保护边界，不引入其宿主或仓库操作流程。证明姿态章节按下文定义的具体行为新写。合并公共规则，保持各章节一致。

### 核心规则

在 `SKILL.md` 中突出适用范围、共同保护规则、关键禁令和简短复核要求，并在同一文件提供完整的主题规则及示例：

- 面向只拥有成品及其可访问来源的读者写作。遵循当前有效要求，清除已舍弃的概念、纠错标签和只有编写会话中才能理解的引用。
- 让事实、观察、判断和有用行动成为正文主线。必要理由与来源放在其支持的主张旁边。
- 清除空泛服从证明、泛化自保、重复核验旁白、冗词、黑话和机械表达。保留作者真实的语气、观察与判断。
- 保留事实、数字、条件、否定、义务、不确定性、来源和因果强度。不为让文字更像人或更具体而编造经历、立场、测量结果或行为主体。
- 已经清楚的文字可以不改。按请求交付文章、回答、诊断或编辑结果，不附送无关清理报告。保留有用的完成信息、真实阻塞和用户要求的解释。

unslop 的明确禁令保持强制性。直接列出关键标点要求：不用破折号，不以括号、短破折号或连字符替代同类插入表达，弯引号换成直引号。详细规则和例子放在同一文件中。字面材料保护继续适用。

### 主题规则

文风章节保留 unslop 来源中的 32 类规则，覆盖夸大内容、公式化语言、标点与格式、聊天机器人套话、冗余、黑话和平实表达。术语列表用于提示判断，不授权盲目替换专业术语或删除真实不确定性。

泄露清理章节处理可见的编写会话残留，包括纠错标签、已舍弃或被替换的要求、被提升为政策的临时指令、不可访问的草稿或审查引用、无用过程复述，以及围绕编辑过程而非读者主题组织的表述。这里的“泄露”指可见文本中的问题，不要求取得模型隐藏推理。保留混合句中的有效事实、有用历史、迁移义务、真实软件版本和运行期新旧状态区别。

证明姿态章节处理围绕证明作者有资格作出判断而组织的文本，包括反复自证、来源评级或核验旁白挤占主题、空泛免责声明和多余的中间解释。必要时重排段落、合并重复限定，并在相关位置保留具体依据与边界。教程、正式证明、研究方法、复现说明、审计和重要决策仍需符合用途的推理与风险信息。

### 加载与应用

将 Skill 应用于输出前，取得完整 `SKILL.md`。描述、摘要或截断片段不能代替完整指南；宿主未提供的内容需要补齐。当前上下文已有完整正文时复用，不为每次回复重复读取。上下文丢失导致所需内容不可用时，恢复该内容。

起草和编辑时综合应用相关章节。纠正、撤销和替换要求时检查当前有效需求及会话残留；润色请求关注文风；反复自证时检查证明姿态。这些信号用于在已有正文中确定关注点，不触发额外文件读取。普通输出同样遵循完整的适用规则，已经清晰的文字可以不改。

加载失败时，使用已有规则与保护边界，必要时说明受影响的检查范围，不宣称已经应用缺失内容。分别验证宿主发现、完整加载与规则遵循；仅有完整加载不能证明写作质量。

### 编辑与交付

允许在授权范围内调整结构，包括重排段落、合并重复、重写开头和结尾。调整非常广泛时，Agent 可以询问是否整篇重写；已有授权即可执行，不设置人为改动比例门槛。保留固定结构与逐字要求。

对照原始信息和当前请求复核结果。尤其不能把未测试环境写成不支持环境、把义务写成已经完成的行为、把假设设计写成已有能力。保留具体未知，查证有实际影响的矛盾，不以流畅改写掩盖问题。

实现时将 Skill 加入中英文能力索引。两个语言组件按仓库版本规则同步维护版本号。组件由 Skill 指南与示例组成，无需检测器、评分服务、编辑脚本或 Plugin 包装。

## 考虑过的替代方案

- 由现有 unslop Skill 继续处理一般文风，另建泄露清理 Skill。能力边界选择时考虑过这一方案。它分开了需要共同保护语义的规则，无法提供选定的统一写作行为。
- 短核心加三份按需加载的专项指南。文件布局比较中考虑过这一方案。低频专项材料较多时可能节省上下文，但增加了信号识别、文件读取和多指南综合处理。完整单文件省去日常写作中的这些依赖；实际上下文节省和行为差异尚未测量。
- 入口只保留导航，每次输出用户可见文本都读取完整 unslop 指南。确定强制禁令的可见位置时考虑过这一方案。它增加读取步骤，入口自身也无法完整提供统一写作规则。
- 将 unslop 的明确禁令放宽为默认建议，并允许文风例外。规则强度选择时考虑过这一方案。选定的文风偏好保留禁令，同时保护字面材料与含义。
- 仅作局部措辞修改，结构调整前一律询问。编辑范围选择时考虑过这一方案。证明姿态清理可能需要重组文本，该方案会为已有授权的结构调整增加确认。

## 验收标准

1. 两个语言组件完整且语义一致。各自的 `SKILL.md` 提供全部写作规则、保护边界和必要示例，不依赖专项参考文件。内部引用均在组件内解析，公开索引描述相同的范围与激活行为。
2. 来源规则类别、可见会话残留清理、证明姿态、关键禁令和保护边界均在同一文件中有规则及示例覆盖。复制内容分发前完成来源版本、复用许可、署名和通知核查。
3. 实机 Harness 测试分别覆盖 luna 和 ds-flash，并实际使用两个语言组件。记录候选版本、实际模型与 Harness 版本、相关指令、输入、输出和加载证据。提案或仓库自动检查不能代替行为验证。
4. 测试覆盖普通起草、已有文本清理、只读审阅、授权文件编辑、长文结构、作者声音、字面保护、有用解释与历史，以及多轮新增、纠正、撤销、替换和临时要求。同时检查漏清理与有害误改。
5. 测试完整入口加载、已有内容复用、上下文丢失后的恢复、内容不完整或不可用、明确调用和普通宿主发现。覆盖普通输出及文风、泄露、证明姿态混合场景，不要求读取专项文件。区分加载失败与加载后未遵循规则。
6. 宿主支持时，以相同输入比较有无候选的结果。记录现有写作规则的干扰，区分独立行为与共存行为。宿主无法提供独立条件时，明确报告限制，不宣称已验证独立效果。
7. 使用人工语义判断，允许多种合格改写。文风改善不能抵消事实误改、义务或限定丢失、虚构经历及越权编辑。各模型与语言分别判断。
8. 保存失败输出，调整相关规则，复测失败和邻近保护场景，验收前在两个模型上运行完整适用集。冻结候选后测试新输入；用于调整规则的输入转入回归集。重复高风险和曾失败场景，报告波动，不挑选最好输出作为结论。
9. 执行仓库要求的自动检查。分别报告实机结果与剩余限制，不向未测试的模型、文本或环境推导效果。
10. 仓库指引和第一方能力决定明确区分能力主体归属与第三方来源使用。该原则普遍适用，包括 architect 与 well-said，不能仅凭使用第三方内容认定 fork。复用材料保留来源归属，并满足适用许可与署名要求。

## 风险

过度清理可能删除限定、迁移义务、证据、有用历史或作者声音，产生流畅但误导的文字。共同保护规则以及应该保留和应该修改的配对案例需要约束所有章节。

完整加载可能让当前回复不需要的细节占用上下文，较长文件也可能使关键规则更容易被忽略。测量实际内容和加载行为，保持结构清楚，同时检查漏清理与有害误改。

Agent 可能未发现 Skill、只取得部分正文、在上下文中丢失内容，或没有遵守已经读取的规则。单文件省去专项读取步骤，但不保证完整加载与遵循；需要同时检查加载证据与实际输出来定位失败。

Skill 内部规则与现有写作指令可能重叠或冲突，导致修改不一致。现有规则还可能掩盖候选的缺陷，造成效果被高估。

针对熟悉样例调整规则，可能只改善这些样例，对新文字无效。需要新输入测试与回归检查暴露这一问题。

未核实来源和许可就复制文本，可能遗漏必要署名或未经许可分发材料。新组件的归属不能解决这些义务。

# 把 Pin 容量取值交给组件

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-15-keep-pin-capacity-in-component.md) | 中文

## 动机

把 Pin 的容量取值从决定中移出，交给组件持有。

[添加 omp-context-pin 扩展](../decision/2026-09-15-add-omp-context-pin.zh.md)在容量条款里固定了两个取值：单条正文的容量上限，以及同一分支活跃条目的合计上限。这两个值都是随组件用法而定的默认值。Pin 承载的是接口约定、文件结构说明与必须按原文执行的命令，这类关键信息通常不多，一个较小的分支合计已经够用。上限约束的是最坏情况下的上下文占用，而不是容纳大段材料。这样的默认值会随使用经验移动，而把它写进决定，会让之后的每次调整都变成一次 ADR 反转。

## 提议

反转[添加 omp-context-pin 扩展](../decision/2026-09-15-add-omp-context-pin.zh.md)的容量条款，并由后继决定记录该选择。

后继决定保留机制、不保留取值：两个入口在任何状态变更之前按 UTF-8 字节校验单条正文与分支活跃正文合计；超过任一上限的操作被拒绝，不改变任何状态，并报告上限与当前用量。当前取值是组件自身的默认值，由组件 README 说明，调整取值属于组件变更。

两种表述不能并存：固定了取值的决定会被该取值的任何一次调整否定，因此取值与机制不能同时留在决定里。

## 考虑过的替代方案

- 保留决定里的取值，每次调整取值时反转决定。在判断取值该放在哪里时考虑过。每次调整都要带一份提案、一份后继决定和一次归档，比一个随用法而定的默认值所需的记录更多。
- 用 `## 变更` 追加一条记录来移除取值。作为更轻的机制考虑过。追加内容只在不与决定冲突时允许，而撤回现有条款约束力的记录与之冲突，因此这条路不成立。
- 把取值写进规范层。在核对哪一层持有取值时考虑过。组件规范陈述目标、不变量与验收标准，并把体积上限指向组件 README。在那里重复可调取值会多出一处需要同步的地方。

## 验收标准

- 后继决定陈述容量机制，且不出现任何一个取值。
- 被反转的决定已归档，两份记录通过 `Reverses` 与 `Reversed by` 互相链接。
- 组件 README 仍是当前取值的说明来源，组件、文档与检查对取值保持一致。

## 风险

- 后继决定若漏掉被反转决定中仍然有效的规则，那条规则就失去记录在案的约束力。后继决定必须在决定范围内保留每一条仍然适用的规则。
- 决定不再写出取值之后，调整取值的组件变更可能被误认为与该决定冲突，取值也可能在 README 之外悄悄漂移。后继决定须说明取值归组件所有，README 须保持为唯一的说明来源。

# 移除 omp-system-prompt 扩展

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-15-remove-omp-system-prompt.md) | 中文

## 动机

从仓库移除 `@ruokee/omp-system-prompt`，并归档保留它的决定。

该扩展通过用户选择的模板把自有英文策略文本渲染进 OMP 的系统提示词，插入 Delivery 章节，并修正 `<project-context>` 页脚。[保留即将弃用扩展的模板功能](../decision/2026-10-07-retain-system-prompt-template.zh.md)在把组件标记为即将弃用的同时保留了模板、Delivery 章节、页脚与当前维护。

后续某次 OMP 版本大幅简化了默认系统提示词，并原生支持模板。这个扩展所做的自定义因此不再必要，精简后的默认提示词也不再臃肿。曾经位于本组件中的模型提示词规则已转移到 QoL，所以移除该组件不会移除那项能力。

## 分析

该扩展自身的价值是 Delivery 章节与页脚修正。模板渲染不需要扩展运行，因此只要模板文件的副本仍然存在且宿主仍选中它，策略文本就会保留：把这样一份副本安装为 `SYSTEM_TEMPLATE.md`，或用 `--system-prompt-template` 传入该副本的用户，仍得到该文本，且不会有诊断。只有在扩展不运行时，也就是它已被停用或卸载、当前进程不再执行其 handler 时，才会失去 Delivery 章节与页脚修正；仅删除仓库不会让宿主仍加载、且其输入仍被 handler 识别的完整插件副本停止工作。若传入的是仓库中 `host-template.hbs` 的路径，则在该目录消失后启动会失败，因为显式模板参数按严格方式加载，宿主不会回退到自己的提示词。

该组件没有发布渠道。安装实例都来自本仓库，或复制进本机插件目录，或链接到该目录。复制安装仍可运行，但已不再匹配其 patch 所针对的宿主版本；链接安装在目录消失后失效。两者都是本机的安装，因此没有需要迁移路径的发布物。

移除该组件还会改动仓库的记录：承载组件清单与 QoL 共存表述的 spec 层，以及两条陈述该组件当前角色的现行决定。

## 提议

### 要反转的决定

以下生效条款与本选择不能并存：

| 现行决定 | 生效条款 | 提议的选择与冲突 |
| --- | --- | --- |
| [保留即将弃用扩展的模板功能](../decision/2026-10-07-retain-system-prompt-template.zh.md) | 组件作为即将弃用的扩展保留，其模板、Delivery 章节、页脚、诊断、可选安装与当前维护继续存在 | 组件及其仓库内容被删除。保留组件的决定与删除组件的决定不能并存，因此该保留条款不能留在决定里。 |
| [由 QoL 提供默认关闭的模型提示词规则](../decision/2026-10-07-use-qol-model-prompts.zh.md) | 模板、Delivery 章节与页脚归系统提示词组件，由它继续维护；两个组件共存时实际加载顺序必须是系统提示词组件在前、QoL 在后 | 该组件已不存在。把上述行为归给一个已删除组件的边界不能成立，两个组件之间的加载顺序要求在其中一个消失后也没有对象。 |

本次反转只改动表中的条款。保留决定中的其余内容以组件为范围，例外是「模型提示词规则已转移到 QoL」这一陈述，它由 QoL 决定作为自身选择记录。QoL 决定中关于规则匹配、组合、设置、诊断以及主会话与子会话的规则不受影响，其后续决定保留这些规则。

删除 `projects/omp-system-prompt`，并让仓库的现行记录与本次移除一致：列出该组件的文档、变更路径检查配置、spec 层，以及上文两条现行决定。

新增一条记录本次移除的决定，归档保留决定，并用一份保留其仍生效规则的后续决定取代 QoL 决定。被归档的保留决定保留其既有的 `Reverses`，并新增 `Archived` 与 `Reversed by`；新决定记录 `Reverses`，使决定链条保持可读。

[宿主内组件按共同的 OMP 下限维护](../decision/2026-10-04-raise-omp-host-floor.zh.md)在其面向 OMP 组件清单里列有该组件。去掉这个名字不改变该决定的选择，即剩余组件共用一个下限，因此该清单按事实性维护处理，而不是反转。

本次移除不提供兼容层、迁移指引或替代组件。不发布、不标记弃用、也不下架任何包，因为没有发布渠道。已归档的决定与 Git 历史保留对它的提及。

本机对该插件的安装在同一变更中移除，否则链接安装会指向一个已删除的目录。

## 考虑过的替代方案

**保留组件但停止维护。** 在决定如何退役该组件时考虑过。仓库组件清单不变，但仓库会继续承载一个已无用途的组件，其「即将弃用」状态会在没有删除日期的情况下无限期悬置。

**归档保留决定但保留组件。** 在确定记录该如何描述一个已无用途的组件时考虑过。这样记录了状态变化而不动组件，但归档的决定与保留的组件描述的是仓库的不同状态，且同样的维护成本仍在。

**把 Delivery 章节与页脚修正迁到其他组件。** 在判断这两项遗留行为是否需要去处时考虑过。这样可以保留它们，但移除该扩展的理由正是这类自定义已不再必要，维护面会为不再需要的行为继续存在。

**保留两条现行决定中关于该组件的条款，不做任何改动。** 在核对本次移除对记录的波及范围时考虑过。这样两条决定会继续陈述一个已删除组件的当前角色，而本提议在其他位置要消除的正是这种结果。

## 验收标准

- `projects/omp-system-prompt` 不存在，除已归档决定、其他历史记录与 Git 历史外，仓库中没有任何文件引用该目录或该包。
- spec 层不再列出该组件：其 spec 文件对已删除，spec 列表中没有对应条目，宿主兼容清单与链接不再提及它，QoL spec 不再声明与它共存。
- 检查配置与其夹具不再引用该组件后，仓库检查通过。
- 移除决定与 QoL 的后续决定记录 `Reverses`；保留决定与 QoL 决定位于 `archived/` 并带有 `Archived` 与 `Reversed by`，且保留决定保留其既有的 `Reverses`。
- 宿主下限决定的组件清单不再列出该组件。
- 本机插件安装中不再包含该插件，指向仓库的链接已移除。

## 风险

- 漏改的引用会让仓库继续描述一个不存在的组件。QoL 的共存表述与宿主兼容清单是最容易漏掉的位置。
- 已安装的副本会继续在一个其 patch 并非针对的宿主版本上运行，patch 可能在无诊断的情况下失效，用户因此可能以为策略文本仍然生效。
- 移除本机安装会改动仓库之外的状态。没有此前插件清单的记录时，恢复它需要重新执行链接或安装命令。
- QoL 的后续决定漏掉仍生效的规则，或关系字段缺失，会让决定链条不完整，并让仍在生效的规则从当前记录中消失。

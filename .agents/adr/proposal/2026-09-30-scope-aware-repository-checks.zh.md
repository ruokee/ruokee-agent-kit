# ADR 提案：按范围执行开发检查并保留完整合并门禁

Draft owner: Ruokee
Draft writer: OMP GPT-6.1 Sol

[English](./2026-09-30-scope-aware-repository-checks.md) | 中文

## 动机

审查前使用受影响检查，合并前使用完整检查，并为串行文档任务设置有条件的主工作目录例外。

[仓库检查决定](../decision/2026-09-12-unify-repository-checks.md)要求在请求审查前完成全部自动化检查。根 [package.json](../../../package.json) 检查 Markdown、Rust、全部打包 OMP 组件、tk 原生适配器和 Skill 生命周期。因此，文档和单组件工作在审查前也需要准备并检查无关环境，审查修改还可能要求重新运行整个序列。

工作目录隔离、依赖准备和验证范围解决不同问题。独立 worktree 保护并行工作，但不意味着必须安装无关组件依赖。如果现有主工作目录干净且能够确认独占，串行文档任务可以避免创建另一个工作目录。

文件以 Markdown 结尾，并不意味着只需要格式检查。运行时提示词模板是组件输入，tk 打包其 Skill 和适配器树，Skill 生命周期测试会读取安装文档。受影响检查必须包含这些已知消费者，同时保留每个合并结果的完整检查。

## 提议

### 审查与合并门禁

新增 `pnpm check:changed`，作为开发和审查前的受影响自动化检查。请求审查前，提交任务改动，保持任务工作树干净，并通过覆盖分支受影响范围的检查。

保留 `pnpm check` 作为唯一完整自动化入口。所有审查修改完成后、合并前，仍必须运行该入口。保留全部现有覆盖、明确组件目标、相对执行顺序、命令输出和首次失败传递。完整检查还覆盖受影响检查的选择逻辑。

完整检查成功只适用于确定的最终任务状态和目标 `main`。验证前，候选内容必须包含目标 `main` 状态，合并内容必须等于已验证内容。新增受跟踪变更、候选变化或目标 `main` 前进，都使原结果失效，需要对新的最终状态重新完整验证。受影响检查成功本身不能授权合并。

自动化成功不替代已有的真实模型、交互界面或实机验证义务。保留[分支工作流决定](../decision/2026-08-20-use-trunk-based-squash-workflow.md)规定的短期分支、干净审查状态、squash 集成，以及独立的合并和推送授权边界。

### 受影响范围与保守回退

相对于分支与 `main` 的 merge base 选择变更，并允许明确指定其他基线。范围包含已提交、已暂存、未暂存和非忽略的未跟踪变更。删除路径和重命名的两端都参与分类，避免移动文件后静默丢失原消费者的检查。

由仓库显式维护路径到现有检查的映射。已知范围选择必需检查的并集，不重复执行。普通说明性 Markdown 对仍存在的变更文件执行格式检查。已知构建或测试输入，包括 Markdown，还选择其消费者检查。共享检查基础设施和未知范围选择完整检查。

基线缺失或不可靠、历史不足或分类失败时，必须回退 `pnpm check`，不能报告缩小范围后的成功。任一选中检查失败，或缺少必需可执行文件、本地依赖，都使入口失败。报告识别范围、选中命令、完整回退原因和失败位置，保留子命令输出，并在首次失败时停止。

保持选择机制小而直接，使用现有仓库工具链。本次变更不把组件迁入 workspace，也不引入任务图依赖。

### 工作目录隔离

只有主工作目录干净、没有并行工作且能够确认独占时，串行文档或 ADR 任务才可以复用该目录。编辑前创建并切换到短期任务分支。任何任务都不得直接在 `main` 上编辑或提交。

该例外覆盖说明性 Markdown，不包括源文件、脚本、清单、锁文件、工具配置或生成规则。运行时模板不会因为扩展名是 `.md` 就变成说明文档。被测试读取的文档，如果本身仍是说明性内容，依然可以适用文档例外，但必须运行其消费者检查。

代码及其他非文档工作、并行任务，或无法确认目录干净和独占的任务，使用独立 worktree。主目录任务范围扩展到例外之外或失去独占条件时，先停止在该目录编辑，并在继续前把已有工作保存在独立 worktree 中。

### 环境归属与准备

开发阶段只准备选中检查所需的依赖，最终验证或完整回退时再准备完整环境。使用锁定依赖版本，保留各组件独立的依赖树。

在同一信任边界内复用包管理器内容缓存，但不同分支不共享可写依赖目录或构建输出。检查不能安装依赖、格式化源码或升级工具。pre-commit 格式化钩子保持既有职责。

工作目录选择与检查范围保持独立。运行消费者检查，本身不会使说明文档任务变成代码任务，也不要求安装无关组件依赖。

### 与现有决定的关系

反转[统一仓库检查决定](../decision/2026-09-12-unify-repository-checks.md)中请求审查前必须运行完整入口的条款。本提案改为该门禁使用受影响检查，最终合并候选使用完整检查。两种时点规则不能同时作为仓库的最低审查门禁。

后继决定必须保留原决定仍然有效的完整覆盖、明确目标与执行顺序、基础入口、独立依赖准备、非修改性检查行为、可见的失败传递、pre-commit 职责、文档要求和组件特定场景义务。增加受影响选择和工作目录政策，不改变组件布局、分发契约或产品行为。

公开开发规则和双语仓库文档应一致描述这些门禁、有条件的工作目录例外、按范围准备环境和完整结果失效规则。

## 考虑过的替代方案

**保留审查前完整验证，只把受影响检查用于开发。**这保留现行门禁，但审查迭代仍可能重复无关环境准备和检查。目标门禁将完整自动化推迟到最终状态，并未从任何合并结果移除完整检查。

**所有任务继续使用 worktree，按范围准备依赖。**这保留最简单的隔离规则，也仍是无法确认独占时的回退方案。但串行说明文档工作依然需要创建目录并准备根工具链。

**迁移 workspace 或引入任务图工具。**这些工具提供包图和受影响任务能力，但会改变独立锁文件、组件准备方式和仓库结构，超出当前需要。显式范围复用现有布局和检查。

**所有 Markdown 只检查格式，不追加消费者检查。**这简化选择，但运行时模板、打包内容和受测试约束的安装步骤可能直到最终验证才暴露回归。受影响检查应包含已知消费者。

## 验收标准

1. 开发与审查具有受影响检查入口，覆盖分支和工作状态变更，包括删除与重命名两端，并报告实际范围与失败。
2. 已知范围选择检查并集且不重复执行。Markdown 构建或测试输入包含消费者检查；未知或共享范围，以及不可靠的分类，选择完整验证。
3. 缺少必需工具、本地依赖、选中检查失败或未完整执行，都不能产生成功的受影响结果。
4. 每个合并结果保留完整自动化覆盖。成功只对未变化的最终候选与目标 `main` 有效，原有组件特定场景义务保留。
5. 只有目录干净、串行且独占的说明文档或 ADR 任务可以在主工作目录的短期分支上执行。其他工作使用独立 worktree，任何任务都不直接编辑 `main`。
6. 开发只准备选中环境，使用锁定版本和独立可写依赖树。最终或回退验证需要完整环境，检查内部不自动安装或格式化。
7. 后继检查决定保留原决定仍有效的规则，公开中英文规则描述相同门禁和边界。

## 风险

遗漏消费者关系可能使开发或审查阶段的受影响验证漏掉回归。显式映射、选择逻辑回归测试、保守完整回退和最终强制完整检查降低此风险，但不能推断全部语义依赖。

错误的独占确认可能让其他会话在文档任务执行期间修改共享工作目录或分支。例外要求明确确认；无法确认时，回退独立 worktree。

任务状态或目标 `main` 改变后，如果没有使结果失效，就可能把完整成功结果用于未经验证的合并内容。合并门禁必须核对两种状态与内容一致性；本提案不增加自动合并服务来代替这项责任。

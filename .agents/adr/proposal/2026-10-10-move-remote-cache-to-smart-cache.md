# ADR proposal: Move remote cache alignment into smart-cache

Draft owner: Ruokee
Draft writer: OMP

English | [中文](./2026-10-10-move-remote-cache-to-smart-cache.zh.md)

## Motivation

Move remote compaction cache alignment from QoL into the independent `@ruokee/omp-smart-cache` extension, serving main sessions, native child sessions, and same-process navigation.

The [current QoL decision](../decision/2026-10-07-maintain-qol-model-prompts.md) assigns remote alignment to one main-session owner. A child activation cannot drive that owner's repair, and navigation releases eligibility without a same-process recovery path. Ordinary requests also finish transformations after context handlers return, while native V2 prepares its retained history separately. Comparing an intermediate context or requiring every request option to match can reject valid common-content repair.

Cache capabilities need an independent home without changing QoL's wait, recovery, deadline, replay, or model-rule behavior. Remote and Handoff repair have different protocols and evidence. Moving remote does not approve Handoff integration or replace an installed Handoff prototype.

## Analysis

A final sent result and its source range establish different facts. Seeing the final payload proves what was sent; it does not prove that part of a cross-range result can be reused after native trimming. If an ordinary request sent only an indivisible result `Y = F(U, T, s)` and V2 changes `T` to `T'`, there may be no independently sent result for `U`. Reusing all of `Y` retains a dependency on removed content; computing `F(U, T', s)` creates a new result and may repeat handler side effects. More provenance does not create an absent independently sent result.

The proposed boundary therefore supports complete retained ranges and independently reusable local results. It leaves indivisible dependency changes native and counts them as unaligned. It does not restrict handlers to one-to-one transformations, change native trimming, require a new handler protocol, or equate an unknown proof with proven impossibility. Client alignment, native usability, and Provider cache benefit remain separate claims.

## Proposal

### Component and public configuration

Maintain the self-contained package `@ruokee/omp-smart-cache` at `projects/omp-smart-cache`, with its own native `omp.extensions` entry, settings, checks, and English and Chinese documentation. Follow the [first-party boundary](../decision/2026-08-20-establish-first-party-capability-kit.md) and [self-contained component contract](../decision/2026-08-24-keep-components-self-contained.md). Do not import runtime code, settings readers, or documents from QoL or a local prototype.

The remote public contract has native OMP settings `compactionCacheEnabled` defaulting to `false`, `compactionCacheProvider` defaulting to `""`, and `compactionCacheMode` defaulting to `"hooks"`. The mode accepts only `standard` and `hooks`; it does not enable the repair. A user explicitly selects one exact configured Provider name. No Provider list, extra mode, Handoff placeholder setting, or second configuration source is added.

The mode set is closed for this remote contract because the two modes preserve distinct preparation and reuse promises; extending it requires a new contract decision. Multi-Provider selection and Handoff interfaces are outside this change, not permanent prohibitions on separately specified capabilities. Native settings remain the sole source to preserve host-owned precedence and restart semantics.

OMP owns user values, project overrides, and parsing under the [native settings contract](../decision/2026-09-10-use-codex-web-plugin-settings.md#native-settings-and-scopes). Read and validate the effective settings as one activation snapshot. Repeated activation events do not duplicate registration. Changes require restarting OMP; creating or navigating a session does not refresh an existing snapshot. Children use their own actual model, API, tools, prompt, and identities, not the parent's model or a freshly hot-read configuration. Invalid settings or unavailable interfaces affect the corresponding capability or registration, never unrelated live sessions. Diagnostics name a key and fixed rule without echoing its value.

`/smart-cache` reports remote state without starting a model turn. Its states distinguish `disabled`, `unavailable`, `awaiting-reference`, `already-aligned`, `rewritten`, and `rejected`. Keep online confirmation, operation binding, candidate validation, and sending causes separately, so a later missing-reference result does not erase the original proof failure. Report logical operations separately from physical sends and retries; a rewrite, native result adoption, and a Provider cache hit are different outcomes. Diagnostics use bounded counters, local session and operation identifiers, and fixed reasons, with no request body, opaque content, credentials, raw endpoint, private path, or dynamic private key. Ship no body-sampling log, trial environment variable, sampling command, or special rate-limit abort policy.

### Target requests and modes

Cover the selected Provider's non-Codex `openai-responses` native V2 requests in main sessions and native `task` and Eval children. Preserve first, subsequent, and process-restored compaction and the manual, automatic, in-turn, and speculative entry points the host supplies to each session class. An absent host entry point does not require a new extension entry point. Non-target Providers, models, APIs, Codex, V1, and unrecognized shapes remain native.

Both modes perform common alignment without context handlers and require final transport confirmation and complete candidate validation. `standard` retains recognized native repairs and does not acquire generic handler projection through the new observation path. `hooks` additionally reuses proved completed context handling, including insertion, reordering, restoration, and cross-range merging. Neither mode reruns handlers, recognizes a companion extension's text format, inspects its private state, or maintains a replacement Provider serializer.

Only an actual ordinary main-loop dispatch supplies a reference. Its source history, completed preparation, existing payload callbacks' final result, and actual transport must refer to the same dispatch and reach sending unchanged. Title, advisor, cache-warming, Handoff, and other side requests cannot become ordinary references. A new online candidate suspends future operation binding until it is confirmed; operations already bound keep their immutable old reference, including an explicitly missing reference. Observation failures stay local and do not swallow native callback, resolver, or transport exceptions. Ordinary and non-target requests remain byte-exact.

### Reuse units and atomic safety

A reuse unit is an independently extractable result already sent by that same ordinary request, with proved source correspondence, assembly boundaries, and all source dependencies retained unchanged in the native V2 range. The operation's captured reference and relevant processing conditions must remain valid. Matching output, array length, index, provenance alone, or apparent message independence is insufficient proof.

A complete retained source range can be one unit containing all its sent results, even when a lawful handler changes message count or order. Prefer that complete-range proof before local matching; lawful duplicate source messages or ambiguous local matches do not invalidate a proved complete range. When only part of the source remains, reuse units whose independence follows from native item-wise semantics or existing independent-result evidence that survives every subsequent transformation. Preserve native rewritten items instead of replacing them with their old originals.

If an indivisible unit's dependencies were trimmed or changed and no independent sent part exists, leave the entire target request native and report `projection-dependency-changed`. Unknown source, dependencies, or result boundaries leave the entire request native with `projection-unconfirmed`, a proof gap rather than a claim that the transformation is inherently unprojectable. These refusals pass only their safety boundary, not alignment. Known complete-range and independent local positive cases remain required; neither trimming nor black-box handling permits blanket rejection.

Validate the complete candidate before one atomic replacement. Preserve system content, date and cwd reminders, tool schema and descriptions, recognized reasoning/replay and default semantics, new ordinary/tool/image history, native tool-output trimming, call/result pairing, compaction-only tails, trigger, and opaque replacement history in their proper order. Do not expand or reconstruct opaque data, restore removed dependencies, recompute handler output, or trim based on transformed output instead of native source history.

Classify fields by their native meaning instead of requiring all online and V2 options to be equal. Keep V2's own `max_output_tokens` value or omission; never copy the online limit into V2. Its known legitimate difference must not block unrelated common-content alignment. An implicit native `tool_choice: auto` can be normalized only when its default origin and the absence of an explicit online choice are proved. Preserve explicit tool choice, model policy, authentication, routing, cache keys, Provider responses, and stored history; reject when their differences invalidate the reference. Every unclassified difference preserves the entire original request. An identical candidate is `already-aligned`, not a rewrite or a reason to reserialize it.

### Ownership, isolation, and recovery

Use one process-wide set of transport and native signal-composition wrappers, one thin resolver wrapper per actual model registry, and independent registrations for each actual session. A compatible repeat registration is idempotent; a second session is not an ownership conflict. Distinguish persistent session identity from Provider session identity, and bind session, model, dispatch, native root, epoch, and coordinator generation explicitly. Model equality, endpoint, cache key, timing, or similar text cannot establish ownership. Native endpoint and V2 shape checks remain independently required.

Retain signal-parent relationships and resolve ownership when the signal is used, including derivation before resolver binding and multiple ordinary dispatches sharing a root. Distinct, unambiguously owned operations may coexist. Every native operation keeps its initially captured immutable reference across newer online work, handler-state advances, authentication refresh, and transport retries. A retry cannot acquire a newer reference. Unknown or conflicting identity, cancellation, invalidated epochs, old coordinator generations, or ambiguous reuse leaves that request native, without disabling other valid sessions.

Before switch, branch, or tree navigation, revoke that session's old epoch and references. During navigation it cannot confirm new references. After success, cancellation, or failure, verify that native transition state has settled and the current identities are valid; a new ordinary send restores eligibility without restarting the process. Do not depend exclusively on a success event or a timer, and never revive old operations. A child's finish, shutdown, cancellation, or replacement releases only its own registration; a revived child must obtain a new valid reference.

Restore only still-owned functions and their original property shapes. A lost session wrapper affects that registration; lost shared transport or signal ownership affects registrations that depend on it. Mixed versions, unreadable registries, and external overwrites are reported conflicts, not permission to seize or reinstall another party's wrappers. Release shared resources when the last registration ends; a later fresh registration may create a new coordinator generation while old operations stay invalid. Retain only the latest per-session reference and snapshots reachable through native operations, using shared immutable data rather than large copies on each retry. Keep no growing completed-operation history, and do not parse bodies when no active target registration needs them.

### Native responsibility and compatibility

OMP retains preparation, triggering, speculative startup and waiting, cancellation, authentication and transport retries, model and method fallback, result validation and adoption, history commits, and continuation. Forward native arguments, receivers, credential results, promises, exceptions, signals, and cancellation reasons unchanged. Do not read credential material, add authentication or reference requests, wrap the public manual compaction method, or treat one credential resolution or transport settlement as operation completion. A non-V2 fallback remains native and is not reported as V2 success.

Do not register `session_before_compact`, keep it as a fallback, hide another handler, bypass a veto, or change another extension's settings. QoL's separately enabled deadline module and other extensions may still veto speculation under their own contracts. Remote alignment preserves the native speculative result's direct adoption, without a replacement request, but does not promise speculation is globally enabled.

Apply the [shared OMP maintenance floor](../decision/2026-10-04-raise-omp-host-floor.md), currently `18.5.0`. The component README pair owns its declaration, with no upper bound or version whitelist. Lock host development dependencies to the shared floor; do not narrow host peers or add an installation or activation version gate. Choose maintained behavior by capability and structure. Replace these adaptations when a maintained native interface provides equivalent results, configuration semantics, isolation, and failure behavior across the required paths, after behavioral verification rather than merely an upstream PR merge.

### Decision reversal and preserved contracts

Implementation would reverse [Maintain QoL model prompts and existing quality-of-life adjustments](../decision/2026-10-07-maintain-qol-model-prompts.md). The conflicts and replacement choices are:

| Effective clause in that decision | Replacement choice and conflict |
| --- | --- |
| Component and scope: six modules in QoL, including remote alignment | Remote belongs to smart-cache; QoL retains wait, recovery, deadline, replay, and model rules. Both cannot own the same remote feature after cutover. |
| Component configuration, opt-in model-rule preservation, and standalone-wait setting preservation: keep every pre-existing key, including cache keys | Remove the three remote keys from QoL in the cutover and declare them only in smart-cache. Preserve every unrelated key, default, range, and validation rule. Old cache keys cannot remain accepted compatibility paths. |
| Remote scope: only the owning main session | Main, native task, and Eval sessions each use their own reference. The main-session-only exclusion is withdrawn. |
| Remote equivalence and generic-context Changes: whole-request equality as a gate despite legitimate operation-option differences | Preserve complete atomic safety, but validate known fields by native semantics, retain V2 output options, and use proved complete or independent local sent units. Unknown differences still reject the whole candidate. |
| Remote owner-bound registry and matching later activations that cannot drive the repair | Shared process dispatch and per-registry wrapping serve independent session registrations. Matching children are eligible, not non-owner observers. |
| Remote conflicting or unusable activation stops module rewriting | Invalid or disabled session settings stop only that registration or capability; actual shared wrapper conflicts affect their dependent registrations. |
| Remote shutdown/navigation terminal state and no new owner in the process | Release one registration locally, restore after settled navigation with a new send, and permit a new coordinator generation after final release. Old epochs and operations never regain eligibility. |
| Remote status and effective mode belong to `/qol` | `/smart-cache` owns remote state, modes, stage reasons, and counts; `/qol` retains only its remaining adjustments. |

All non-conflicting rules remain binding. The complete QoL successor must preserve standalone wait delegation and deadlines, recovery safety exclusions and bounded continuations, the experimental compaction-deadline module's single-owner windows and `owner-stopped` terminal state, replay's separate process-wide ownership and release rules, [model prompt rules](../decision/2026-10-07-use-qol-model-prompts.md), native settings authority, module isolation, privacy, documentation evidence, and host-maintenance obligations. In particular, this proposal's remote recovery does not relax the deadline module's terminal owner rule or migrate replay merely because it is cache-related.

The remote successor records the still-effective online confirmation, immutable root snapshots, native lifecycle, explicit-policy preservation, bounded retention, ownership-conditional restoration, no-veto, two-mode, privacy, and native-interface replacement contracts together with the changes above. Repair inbound references when the old pair is archived. Other current decisions are not reversed; adding smart-cache to the shared floor is a non-conflicting extension of that contract.

### Direct cutover and public documentation

Deliver remote directly in smart-cache, without a QoL multi-session interim release. Remove QoL's remote implementation, settings consumption, types, tests for obsolete behavior, aliases, re-exports, and public status entry. Keep no shim or runtime cross-component dependency. Preserve valid consumer-visible assertions and every unrelated QoL behavior.

Public migration guidance belongs in the repository README pair. It must cover user and project layers, not just the merged effective object: preserve the old effective Provider and mode, and enable the new repair only when the old effective QoL master `enabled` and `compactionCacheEnabled` were both valid and enabled. Defaults or invalid settings must not turn a previously inactive repair on. Users explicitly set the new package's values and remove all three old remote keys from every applicable QoL layer while retaining other settings. Old keys become unknown QoL keys and can reject the whole component, so deletion, new installation, and restart must be coordinated before the changed source is loaded. Runtime code neither reads QoL settings as a fallback nor edits user configuration or installation.

Switch by restarting affected processes, not by hot-transferring in-flight owners or references. Accidental coexistence with old QoL remote reports a conservative conflict and does not seize its wrapper. Handoff protocol, support, status, benefit evidence, and installation remain separate; this proposal does not replace its prototype, reuse remote V2 rules for Handoff, or add placeholder Handoff interfaces.

Component documentation owns detailed settings and commands, applicability, side effects, native-off behavior, fixed source baselines, versions actually exercised, and native replacement conditions in both languages. Source inspection, real CLI coverage, client alignment, native adoption, and Provider measurements are labeled separately. Change the QoL project Spec and add the smart-cache Spec, their index entry, component documentation, and check registration in the same implementation change as the changed targets. Keep current Specs and decisions unchanged while this is a proposal. Implement only after the maintainer approves and separately merges the proposal under the [ADR lifecycle](../README.md#active-proposal).

## Alternatives considered

- **Expand QoL first, then migrate.** Considered while choosing the delivery location. It reduces the first installation change but adds an interim multi-session contract, release, configuration, and migration validation. Direct smart-cache delivery avoids that intermediate maintained path.
- **Keep the unrestricted alignment promise and stop at the limitation.** Considered while choosing the reuse contract. When an indivisible result's dependency is removed, more observation cannot produce a missing sent sub-result without changing another requirement. It preserves the old promise but prevents a complete deliverable.
- **Introduce a frozen pure-projection cooperation protocol.** Considered for trimmed cross-range transformations. It can compute a new result after one stateful preparation, but requires cooperating handlers and proof of no side effects, changes the sent-result reuse contract, and gives no guarantee that the new result reuses old Provider cache. This proposal adds no such protocol.
- **Rerun ordinary preparation or issue a new reference request.** Considered during final-context design. It repeats stateful handler effects, can read state newer than the operation snapshot, and may spend another request. Reusing already sent results preserves the selected boundary.
- **Wait for an equivalent native interface or use Handoff instead.** Considered while assessing wrapper maintenance. Waiting leaves current remote differences unresolved; Handoff changes the selected compaction protocol and has separate evidence. An equivalent native interface remains the replacement condition.

## Acceptance criteria

1. The new package is self-contained, loads once through native OMP plugin discovery, and declares its actual version and maintained-host baseline. It starts disabled with an empty Provider and default `hooks`; both explicit modes, native user/project overrides, invalid values, activation snapshots, and restart behavior are observable. No hidden QoL reader or hot configuration refresh exists.
2. Ordinary and non-target requests are unchanged. Both modes align their common native cases; `hooks` also aligns complete insertion, reordering, restoration, merging, images, and already-used later transformations without repeating handlers. A proved complete range containing lawful duplicate messages succeeds despite ambiguous local matches.
3. Native item-wise and independently proved local results align through partial history retention and tool-output rewriting. New ordinary, tool, and image tails, tool pairing, opaque replacement history, and trigger retain their native content and order. Indivisible changed dependencies and unknown proof gaps preserve the whole request with their distinct reasons; successful refusal is not a positive alignment result.
4. System content, reminders, tool schemas, replay/default semantics, no-tool requests, and legitimate V2 output-limit differences retain their intended behavior. Explicit tool choices, unknown fields, model or tool mismatch, and unproved transformations do not cause partial or unsafe replacement.
5. Main, native task, and Eval sessions each complete applicable target compaction with their own references. Parallel siblings, parent/child interleaving, same-model different histories, different models, non-target children, cancellation, finish, and revive neither mix context nor stop valid neighbors.
6. First, subsequent, and separately process-restored compaction preserve native commits and usable continuation. Applicable manual, automatic, in-turn, and speculative paths keep native scheduling, preparation, waiting, result adoption, and fallback. New online work and authentication or transport retries retain the old operation snapshot; valid speculative results are adopted without a substitute request. Cancellation revokes old eligibility and a later independent operation can recover.
7. Switch, branch, and tree navigation recover after success, cancellation, and failure using a fresh ordinary send after transition settlement. Old in-flight operations stay invalid, other registrations stay valid, and no process restart or timer is required for normal recovery.
8. Missing references, identity ambiguity, mixed versions, foreign overwrites, old generations, and unavailable interfaces leave affected requests native with locatable reasons. Last-registration cleanup restores only still-owned functions and property shapes; later registrations cannot revive old operations. Live retention is bounded to current references and reachable operations, not completed history.
9. The actual `/smart-cache` and `/qol` TUI commands do not start model turns. Remote status exposes stage-specific causes and bounded counts without sensitive content. Already-aligned, rewritten, native adopted, and Provider-cached outcomes are not conflated.
10. Native configuration migration removes old user and project QoL remote keys, preserves the effective opt-in state and all unrelated settings, and gives each request one owner. Old QoL coexistence fails conservatively. QoL's remaining modules and other installed extensions retain their behavior; Handoff's independent prototype and request boundary are not replaced by remote delivery.
11. Automated checks and real maintained-host CLI/TUI evidence cover the changed public contracts, actual outgoing requests, native results, and the shared `18.5.0` floor. Required full and affected check registration, selector mapping, selector regressions, paired documentation, project Specs, and complete successor decisions agree at implementation cutover. Source inspection and synthetic usage are not real Provider evidence.
12. Separately authorized comparable real-Provider runs repeatedly show reduced uncached input while preserving client correctness and native usability. Report overall target, aligned, and unaligned groups, including all dependency-change refusals, proof gaps, and other refusals, by session class and applicable compaction lifecycle. Separate logical operations and physical requests. For each group report requests, valid usage samples, total/cached/uncached input, zero-hit fraction, and token-weighted hit rate. Failures, cancellation, 429, fallback, and missing usage stay explicit rather than becoming zero hits or disappearing from denominators. Claim no fixed hit rate, cache residency, or savings amount; remote benefit does not prove Handoff benefit.

## Risks

- Wrong source correspondence, lost unit boundaries, or concurrent attribution can insert another session's content, restore removed history, or break tool pairing. Complete and local proofs, explicit identities, immutable snapshots, and atomic refusal are required before replacement; conservative refusal alone still leaves required positive coverage incomplete.
- Host changes or competing process wrappers can make the adjustment unavailable; incorrect restoration can overwrite another extension. Capability checks, conditional restoration, and maintained-host behavioral evidence reduce that exposure without promising universal compatibility.
- Multiple live sessions and long-lived native operations can retain large payloads. Sharing immutable references and releasing unreachable operation state avoids retry copies and completed-history growth, but does not bound the host's number or lifetime of live operations.
- A user who updates linked QoL source before removing old keys can lose every QoL module through unknown-key rejection. Coordinated user/project migration and restart guidance must preserve unrelated settings and avoid silently enabling an inactive repair.
- A correctly aligned request can still miss Provider cache, and indivisible dependency changes remain unaligned. The added maintenance may therefore produce insufficient overall benefit; real comparable repeated measurements with complete denominators are the release criterion, not a synthetic success count.

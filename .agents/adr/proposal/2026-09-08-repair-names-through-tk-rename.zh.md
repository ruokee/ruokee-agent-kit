# ADR 提案：恢复 rename 修复功能

Decision owner: Ruokee
Draft writer: pro-20x/gpt-6-astra

[English](./2026-09-08-repair-names-through-tk-rename.md) | 中文

## 动机

`rename` 在最初设计中除了正常重命名，还额外承担修复既有 Task 名称及其生成式目录后缀的职责。这是原始需求的一部分，不是本提案新增的能力。后续实现和契约整理偏离了这一预期，把“旧 Task 已通过完整校验”变成了 rename 的前置条件，反而拦住了本应由它修复的对象。

对 tk 而言，UUID 是身份，名称是可修改的描述，路径是定位方式。名称需要修复，不等于 Task 身份失效。要求用户先手改受管数据再执行 rename，既破坏了运行时管理元数据的职责，也使 split 和 embed 的恢复能力不一致。

本提案恢复原有修复职责，并纠正将功能失效写成使用限制的契约。旧名称不必先合法；修复结果和修复范围之外的约束仍须合法。

## 提议

### 恢复原有修复职责

`tk rename <task_ref> <name>` 同时承担正常重命名及名称修复，不增加 `--repair`、`--force` 或独立修复命令。新名称仍按当前规则规范化并完整校验。

对能安全定位、按当前表示解析的唯一 Task，以下问题属于名称修复范围：

- `name` 是字符串，但未规范化、为空、规范化后为空或超过当前显示宽度限制。
- 生成式目录结构可识别，但非空后缀与元数据名称不一致。
- 上述问题同时存在。

缺失名称、错误字段类型、不可解析载体、缺失受管标记、不支持的 schema、损坏身份和不安全路径不在范围内。rename 不推断缺失元数据，不迁移 schema，也不修复损坏的日期、序号或无法识别的生成式目录结构。

### 保持统一入口

split 和 embed 提供相同修复能力。完整 UUID、精确 Task 目录和精确载体路径均可定位符合范围的修复对象，不要求其先成为普通发现中的有效 Task。

身份必须唯一；名称损坏的副本不能被忽略以消除 UUID 歧义。修复不得改变父子归属，无法确定结构时明确拒绝。不增加名称模糊匹配、普通材料路径回退或跨项目查找。

CLI 和既有 `tk_exec rename` 使用相同对外行为，不新增参数、持久字段、元数据 schema 或第二套结果格式。

### 保留修复边界

- 只修改名称、适用的生成式目录，并正常追加 WAL。身份、生命周期、创建时间、关系、extra、正文和已有 WAL 保持不变；embed 正文按字节保留。
- 顶层及生成式子 Task 保留日期、序号和父级位置，仅调整名称后缀；非生成式子 Task 不移动目录。
- 修复范围内的旧名称错误不阻塞操作；新名称、其他元数据、关系及最终路径必须通过校验。其他命令的普通校验规则不放宽。
- 关闭状态只读、Git 策略、活动操作、目标冲突和路径安全保护继续有效。名称修复不是权限绕过。
- `--dry-run` 不进行持久写入，报告原始旧名称、规范化新名称、原路径、目标路径、父级及引用。只需修复路径时也应报告变更。
- 保留断链保护及 `--ignore-brokenlinks` 的既有含义，rename 不自动改写普通 Markdown。
- 保留部分提交报告和从当前状态重新规划的语义，不增加自动回滚保证。

### 纠正现行契约

本提案与[数据模型决定](../decision/2026-09-03-define-tk-task-data-model.zh.md)中“rename 依赖有效发现结果”的约束冲突，需要按 ADR 规则反转该约束；普通发现、身份及其他维护规则继续有效。反转的是后续偏离原意的限制，不是最初的修复设计。

[运行时及 CLI 决定](../decision/2026-08-28-define-tk-runtime-and-cli.zh.md)的公开入口及断链规则不变，需补充原有修复职责的恢复。当前决定在提案阶段仍保持原状。

## 考虑过的替代方案

保留严格旧名称加载，要求用户先人工修复受管名称，再执行 rename。现有维护指导采用这一路径处理部分历史 split 名称。未采用，因为它延续了对原始设计的偏离，把 rename 本来承担的修复交给外部编辑，embed 又没有等价入口。人工绕过不能代替恢复原有功能。

## 验收标准

1. 符合修复范围的 Task 能通过现有 rename 入口预演并完成修复，不因旧名称或后缀错误被拦截；split、embed 及各精确引用方式行为一致。
2. 修复后目标可被普通发现和读取接受，名称及生成式路径符合当前规则，身份、正文和父子归属保持不变。
3. 名称错误与其他缺陷同时存在时，其他校验仍有效；新名称非法、身份歧义、不安全路径及已有写入保护不能被修复能力绕过。
4. dry-run、引用门禁、冲突处理和部分提交报告遵循原有公开契约；无变更、成功及失败结果准确反映实际状态。
5. 普通有效 Task 的 rename 行为不回退，其他命令不获得宽松权限。公开契约不再要求用户手工修复 rename 职责范围内的旧名称。

## 风险

- 若将名称修复扩展为普遍容忍损坏元数据，身份或关系错误可能进入正常写入流程，导致修改错误 Task。
- 若名称损坏的候选未参与身份及结构判断，可能漏掉重复 UUID 或改变子 Task 归属。
- 生成式路径修复仍可能使旧引用失效，也可能出现目录已移动但元数据未提交的部分完成状态；恢复修复能力不消除这些既有风险。

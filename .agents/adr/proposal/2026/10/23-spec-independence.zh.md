# 规格独立性

Draft writer: OMP GPT-6 Astra

[English](./23-spec-independence.md) | 中文

## 动机

让规格完整表达所需行为，并独立于具体实现。

规格应说明功能为什么需要存在、要做什么，以及区分符合要求与偏离目标的可观察结果。删除原实现及其说明资料后，读者仍应能据此重建功能基本一致的新实现，内部选择可以不同。

[规格决定](../../../decision/2026/10/04-specifications.zh.md)却将详细合同交给其他页面，并允许规格链接这些页面。[已归档的 Pin 决定](../../../archived/2026/09/15-r2-omp-context-pin.zh.md)曾把 README 定为上限唯一的说明来源。[tk 规格](../../../../spec/tk.zh.md)把详细行为与验收交给设计页面，还包含实现选择。仅删除链接会留下需求缺口，复制被链接页面则会把实现细节带入目标。

## 提议

### 完整目标

规格说明对象的目标、范围、必要条件、可观察行为、失败结果和验收标准。它包含重建基本一致功能所需的全部已确认要求，不依赖原实现或其说明文档。

精确命令、输入输出格式、取值、默认值、上限和兼容承诺，在属于已确认外部要求时进入规格。按条款约束的对象判断归属，不按是否出现技术标识符判断。存储格式可以是外部兼容合同，内部记录字段不会因为实现使用它就自动成为要求。

内部函数、模块组织、算法、构建安排、实现步骤、测试命令和验证日志不进入规格。一段文字混合可观察要求和实现选择时，独立保留要求，不能整段删除，也不能把机制保留为要求。

已有实现帮助发现遗漏，但不批准目标。编写者可以调查相关代码、设计材料、当前决定及其带日期变更、已确认要求，包括现有规格未链接的来源。读者不应再靠这些来源补全目标。必要行为的原始要求与现行决定冲突时，由维护者裁决，不能直接复制代码现状来解决。

### 导航

规格正文不链接仓库文件，包括组件文档、源码、ADR、规则、语言对应页和其他规格。裸路径、要求查阅其他文档的指示，以及“按当前实现”等措辞也不能代替需求正文。

保留同目录英文和中文配对，两种语言各自完整、语义等价。语言、主题和相关决定导航放到[规格索引](../../../../spec/README.zh.md)，该页仍是承载项目补充的非规格页面，不能成为缺失功能要求的第二存放处。规格正文移除“相关 ADR”章节；其他既有章节按适用性保留，不强迫无关主题出现宿主或接口章节。

一个主题可以由多份规格组成，前提是各自范围和合起来的需求边界清楚。外部索引标明完整文件集合及语言配对，整组规格应能脱离实现资料成立，不要求按内部模块结构拆分。ADR、规则、索引和普通组件文档继续遵循各自适用的链接与语言导航规则。

### 文档职责

规格持有完整目标。组件文档按该目标说明安装和使用，并继续独立服务使用者。因此，必要要求可以同时出现在规格和用户参考中，不能为了避免重复文字而省略规格要求，也不能另立相反的目标权威。规格写入必要约束，不整份复制用户文档；安装说明、使用指引和参考材料继续承担组件文档职责。实现设计归设计材料和代码，证据归维护记录。ADR 保留持久选择、理由和必要历史合同，即使这些合同包含不应进入规格的实现细节。

内部 `maintain-spec` Skill 继续持有主要维护方法。其检查必须拒绝把必要要求委托给组件文档，也必须拒绝把实现说明改名后当作规格。检查需求含义和完整性，不只检查标题、格式或链接能否解析。

修正时保留已确认行为、数值、默认值、条件、例外、失败语义和兼容承诺。同一变更更新维护方法、项目补充、受影响规格、文档规则、词典说明、根 README 文件对，以及受影响的组件职责声明。导航和入站引用仍应可用。本次改变文档职责，不改变组件行为、配置值、持久化格式或宿主维护下限。

可分发组件继续自包含，使用、构建和分发不依赖仓库规格。内部维护 Skill 可以读取所维护的项目文档。规格仍是说明性 Markdown，本选择不增加生成器、专用检查器或运行时读取方。

### 冲突决定

下列八份决定定义受影响的文档职责。只反转仍与完整、独立规格冲突的条款，保留已经符合该分工的当前记录。每份完整继任保留其范围内所有其他有效条款和带日期变更。保存真实历史选择，不追改成它们从来都要求规格独立。按既有 ADR 机制同时维护所需语言版本和直接前后继关系。

1. [规格](../../../decision/2026/10/04-specifications.zh.md)的“维护归属”和“引用方向”等条款，将详细命令、参数、设置、格式和维护声明委托给其他页面，要求规格包含语言互链和相关 ADR，并允许引用仓库文件。以完整目标和外部导航替代这一分工。保留规格位置与清单、当前目标就地维护、已确认需求权威、ADR 冲突处理、内部 Skill 的归属和加载触发、任务 Goal 边界及组件自包含要求。
2. [tk 文档](../../../decision/2026/08/29-tk-documentation.zh.md)的“合同归属”和“主题归属”将行为和可观察验收交给设计页，并要求其他页面链接规范细节而不重复。替换这种独占归属：规格持有必要的 Agent 与产品行为和验收，Skill 设计说明其设计与实现，验证文档持有验证方法和证据。规范性的外部参数和字段必须在规格中完整表达，组件参考仍可独立使用，算法和内部定义留在实现设计中。保留四种使用模式及其采用权限、权威 Skill 源码与共享参考组装、安装后自包含、组件文档组织、规格正文以外的语言规则、分发覆盖，以及其他全部 tk 合同。
3. [双语文档](../../../decision/2026/08/20-bilingual-docs.zh.md)的“语言范围”要求双向语言链接。增加规格正文例外，将对应语言导航放到外部索引。保留同目录配对、完整性、同变更语义一致、标识符拼写、普通文档链接、Skill 打包，以及 ADR 元数据和生命周期要求。
4. [仓库规则](../../../decision/2026/10/12-repository-rules.zh.md)的“迁出内容”要求仓库规格链接迁出程序细节的所属页。取消这项要求。工作程序仍归规则，仓库规格完整表达交付物性质和验收。保留规则层、维护归属、Agent 入口职责、项目边界，以及带日期的内部维护方法补充。
5. [OMP QoL](../../../decision/2026/09/20-omp-qol.zh.md) 的“决定”把模块机制和逐项证据分配给包含规格在内的页面。规格保留必要行为、默认值、上限、状态和失败结果，内部机制与已记录证据留在规格之外。保留组件模块与配置边界、开关和默认值、进程级限制、归属与释放行为、兼容合同和真实会话验证义务。README 的维护声明按下文继续有效的宿主维护合同保留，规格完整表达同一项已确认下限及其含义。
6. [Task 参数清理](../../../decision/2026/10/17-task-argument-cleanup.zh.md)的“与组件的契合”同样将机制和逐项证据交给 README 与规格。只替换这项归属，保留 `taskArgsEnabled`、按 schema 判断的激活、seance 与非 seance 行为、改写边界、激活和状态规则、已接受的推测执行成本、宿主兼容，以及上游修复后的退出条件。决定中的实现合同不会因为留在规格之外而被删除。
7. [已归档的 omp-context-pin 决定](../../../archived/2026/09/15-r2-omp-context-pin.zh.md)曾把 README 定为上限唯一的说明来源。其[当前继任](../../../decision/2026/09/15-omp-context-pin.zh.md)已将完整用法、记录、编号、重置、上限、持久化和缓存要求交给 Pin 规格。保留该分工，规格完整表达必要公开行为和容量约束，README 保留独立可用的操作说明和参考。保留 `/ctx-pin`、`ctx_pin`、`read` 审批档位、不增设组件自身的授权、确认或来源准入检查，以及不写用户配置。上限仍是组件可调整的默认值，不是 ADR 固定常量；调整取值时同步更新规格和用户文档。上限只约束活跃正文，不约束 token、元数据或更早的尾部消息，完整请求仍可能在压缩后溢出。保留超限条目可读、拒绝新写入、取消固定不受容量检查、逐字保留、来源与身份规则、恢复、持久化、缓存和验证合同。
8. [Context Pin 工具契约](../../../decision/2026/10/17-context-pin-tool-contract.zh.md)的“决定”末段已将动作和可观察行为交给 Pin 规格，共同目标与不变式交给主规格，用户操作交给 Pin 指南。保留该分工。保留六种动作、无需 revision 的当前条目写入、重试身份与冲突语义、完整只读 `show`、不改动状态的容量拒绝反馈、已确认编辑作用于当前条目、旧草稿覆盖后果、既有 journal 兼容、`read` 审批档位，以及组件可调上限。

### 继续有效的决定

[宿主维护决定](../../../decision/2026/09/28-host-maintenance.zh.md#维护声明)继续把各组件 README 的兼容性小节作为面向组件使用者的已确认下限权威声明，这不表示要求只能在该处陈述。规格必须完整写出同一下限及其维护含义，不要求 README 补全缺口。两份文档都不得另定不同下限，调整下限仍遵守既有批准要求，并同时更新两处陈述。保留[状态栏](../../../decision/2026/09/04-omp-status-bar.zh.md)、[模型提示词规则](../../../decision/2026/09/14-model-prompt-rules.zh.md)、[smart-context](../../../decision/2026/10/12-smart-cache.zh.md) 和 OMP QoL 重复陈述的这项声明归属，不引入维护上限、安装门槛、新版本保证，也不声称所有受维护版本都经过测试。这些声明条款无需反转。

[workloop 决定](../../../decision/2026/10/22-workloop.zh.md#规格)已经把目标、边界和可观察结果交给规格。通过非冲突的带日期补充，明确全部必要操作行为在规格中表达，Skill 与组件文档继续承担操作方法和用法。[词典决定](../../../decision/2026/10/17-repository-dictionary.zh.md#仓库接入)要求仓库规格说明词典和术语规则，没有要求链接，保留该选择，不做反转。其他未改变的决定继续有效。

## 考虑过的替代方案

无

## 验收标准

- 每个当前规格主题的完整规格集合，都能独立表达重建基本一致功能所需的功能范围、必要条件、可观察成功和失败行为，以及验收要求，允许采用不同的内部实现。
- 每项已确认要求都有对应的保留陈述。原来仅存在于实现材料中的必要要求，经核实后进入规格；实现选择不默认成为需求。
- 规格正文既没有仓库文件链接，也没有通过路径或现有材料间接委托要求，不包含实际实现描述。外部索引能找到完整主题集合和语言配对，不承载缺失要求。
- 维护方法能拒绝细节委托和把实现说明当成规格，同时保留容量值等已确认外部约束。
- 八份决定表达所需文档职责。必要的继任只改变点名的职责，保留其他全部有效合同。非冲突决定、规则、术语和受影响文档表达一致职责，档案保留历史选择和直接关系。
- 中英文表达等价且完整的要求。组件仍可独立安装和使用，产品行为、配置值、存储合同和维护下限不因本次文档修正而改变。

## 风险

规格和用户参考可能同时陈述同一外部上限或默认值。只更新其中一处，会让实现者和使用者依据不同的行为要求。同变更维护和语义比较不可省略，格式正确和链接有效无法发现这种冲突。

一段文字可能同时包含实现机制和必要的失败结果。整段移除会无声丢失要求。修正必须区分两种含义，逐项确认行为得到保留，不能把删除技术文字当作完成。

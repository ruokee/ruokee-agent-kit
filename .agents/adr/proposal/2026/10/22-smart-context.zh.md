## 动机

将已有上下文能力整合到自包含的 `@ruokee/omp-smart-context` 扩展。

各能力有不同的状态归属和失败边界，但安装及维护归属应当统一。包级合同需要支持独立维护的能力，不能把当前成员清单变成永久架构约束。

## 提议

延续 [smart-cache](../../../decision/2026/10/12-smart-cache.zh.md) 的决定身份。包和目录改为 `@ruokee/omp-smart-context` 与 `projects/omp-smart-context`，保留一个原生扩展入口、OMP 原生设置来源、组件内依赖和检查以及双语公共文档。删除旧包，不保留适配器或跨组件 import。

后继保留 `decision/2026/10/12-smart-cache.md` 及语言配对，被替代文件归档为 `archived/2026/10/12-r1-smart-cache` 配对。包改名不重置该身份。

冲突条款是旧包身份、`/smart-cache`、每项能力都需用户显式启用，以及所有能力共享对齐协调器。使用 `/smart-context` 提供只读状态，保留每项能力规定的默认值，将共享协调器限定于[请求对齐](./22-request-alignment.zh.md)。Pin journal、用量记账及模型规则状态保留各自归属。

后继只持有共同不变量：自包含、宿主负责用户与项目设置覆盖、单次激活快照、模块局部失败隔离、只读状态入口，以及 `18.5.0` 的共同 OMP 维护下限。不增加包级总开关。未知键或无效设置根拒绝组件配置，无效模块键只停用对应模块。诊断使用固定原因，不暴露正文、opaque 内容、凭据、原始端点、私有路径或动态私有键。保留不限制版本的 host peers，不增加版本门禁。

各能力在自己的决定中维护行为、开关、状态和验收。README 和组件 Spec 维护已交付能力清单及详细参考。增删能力若不改变共同不变量，就不反转包级决定。不提供占位设置，不引入模块框架。

整合扩展通过仓库检查和本地受控运行验收。区分客户端对齐、原生行为和 Provider 收益测量。真实模型调用、缓存收益测量及完整 CLI/TUI 矩阵不作为整合门槛。历史证据保留实际候选及条件。

用户级和项目级配置显式迁到新包，运行时不回读旧命名空间，不自动编辑用户设置。通过重启切换，保留有效启用意图及无关设置。

## 考虑过的替代方案

无

## 验收标准

- 每项迁入能力只有一个自包含包作为所有者，开关及失败边界独立，没有旧运行时别名。
- 状态入口分别报告已交付能力，不启动模型轮次，不暴露内容。
- 普通能力增删不改变无关决定，共享所有权规则只约束实际使用该机制的能力。
- 后继保留仍有效的自包含及宿主维护义务，双语引用完整，证据覆盖明确。

## 风险

共享发布和入口可能让多个能力的回归一同交付。独立状态和失败边界减少干扰，组合行为仍需受控验证。

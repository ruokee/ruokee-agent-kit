# tk 名称排版

Draft owner: Ruokee
Draft writer: OMP GPT-6.1 Sol

[English](./19-tk-name-formatting.md) | 中文

## 动机

允许保存的任务名称与生成式目录后缀在普通空格、连字符和下划线的使用或省略上不同。

格式化器可能在 embed 任务的 `name` 中为中英文本插入空格，例如把 `AI学习` 改为 `AI 学习`，但不改目录。保存名称的规范化校验和名称与后缀的逐字匹配校验都不接受这种状态，调用方修复之前无法继续普通操作。

[tk 数据决定](../../../decision/2026/08/28-tk-data.zh.md)以 UUIDv7 作为身份，名称用于描述，路径用于定位。名称仍合法且对应同一生成式后缀时，排版差异不应要求名称修复或目录移动。实际显示宽度、无关数据的严格校验、显式改名目标和部分失败报告必须保留。

## 提议

在 [tk 数据决定](../../../decision/2026/08/28-tk-data.zh.md)的带日期 `变更` 条目中记录名称排版兼容。身份、生命周期、严格发现、rename 窄修复、正文保留、引用保护和不自动回滚的规则继续有效。这会扩展严格校验接受的合法名称，不会让普通操作使用 rename 的修复加载器。不反转现有决定。[tk 运行时决定](../../../decision/2026/08/28-tk-runtime.zh.md)继续负责共用运行时和结果合同。

### 保存名称

名称和生成式目录后缀分别仅移除普通空格 `U+0020`、连字符 `-` 和下划线 `_` 后，剩余文字相同即可对应。不折叠大小写、不替换其他文字，不放宽原有 NFKC、非空和其他字符约束。因此，`AI学习`、`AI 学习`、`AI-学习` 和 `AI_学习` 可以对应同一后缀，但不因此成为同一任务。

保存名称和生成式后缀分别按各自实际字符串校验 32 个终端显示列上限。全部空格、连字符和下划线都计入，不使用剥离后的比较键或改写后的字符串代替测宽。日期和序号前缀不属于名称后缀。格式化使名称从 32 列变为 33 列时，仍属无效名称，返回 `task_name_too_wide`。

生成式目录名称继续不含空格，默认使用连字符。普通发现、读取、检查和更新不规范化保存名称，也不移动目录。这些规则针对 tk 生成的目录部分，不约束无关项目路径。非生成式子任务目录不新增名称与路径匹配要求。

元数据解码、发现、读取、原本允许的更新、受管写入及 split/embed 转换共用同一合法性规则。普通写入和转换保留允许的名称写法及正文原始字节。所有公开接口共用 Rust 运行时中的规则，适配器不另作解释。详细合同由[数据模型](../../../../../projects/tk/docs/design/data-model.zh.md)负责。

### 创建重试

保留创建和 rename 请求的规范化方式，包括无空格的生成式目录。已有子任务名称增加合法排版空格后，以相同原始创建请求重试，其余匹配字段不变时必须复用该子任务。

不能用忽略分隔符的目录比较作为创建身份或去重键。`AI学习` 与 `AI-学习` 等规范化创建名称原本不同的请求，必须保留这种区分。排版比较不产生搜索别名、全局名称唯一规则或任务合并行为。

### 显式改名

保留 rename 的具体规范化目标。只有保存名称和适用路径都精确达到目标时才返回无变化，不能仅比较排版键。

例如，合法名称为 `AI 学习`、目录后缀为 `AI学习` 时，显式 rename 为 `AI 学习`，目标名称和后缀仍为 `AI-学习`。名称为 `AI-学习`、后缀为 `AI_学习` 时，同名请求也可能需要移动路径。rename 继续报告真实计划及引用，拒绝已存在的目标，并对真实移动应用引用保护。仅元数据修复不属于路径移动，不自动改写引用。

保留用于修复旧字符串名称和可识别生成式后缀的窄加载入口，包括空名称或超宽名称。closed 任务保持 closed，新目标必须通过完整校验。新增普通后缀校验不能使这些可修复旧状态无法访问。

保留提交前对名称、路径、元数据和引用的精确复检。外部编辑即使保持排版等价，仍可能使 rename 计划失效。目录移动成功而元数据写入失败时，报告原始部分提交错误及已完成、未完成项。兼容规则可能使结果状态可读，但这不表示该次 rename 已完成。重试必须继续达到具体目标，不能按排版等价返回无变化。不增加回滚或持久恢复状态。

正文继续作为普通内容维护，不要求标题存在或与受管名称匹配，名称宽度限制不约束标题，rename 不同步标题。初始正文生成方式保持不变。

## 考虑过的替代方案

- 在比较排版兼容与严格名称存储时，考察过保持严格写法并优化修复提示。可以维持规范存储，但格式化仍会反复阻断普通使用，要求执行可能移动路径的修复。
- 在分析如何协调保存名称与目录后缀时，考察过在读取或检查中自动规范化元数据或目录。通过隐式写入或移动消除不匹配，会改变诊断行为，并可能破坏引用。接受兼容写法可以避免这种迁移。
- 在分析创建重试及 rename 与排版对应规则的交互时，考察过将同一排版比较用于去重和完成判断，以减少独立匹配规则。会混淆原先不同的创建请求，吞掉显式分隔符调整或未完成的元数据写入。
- 在讨论格式化插入空格导致名称超过 32 列的处理时，考察过先去掉普通空格再应用 32 列上限，使原有名称仍能通过。会允许实际展示超过上限，改变宽度约束的含义，不能解决名称与路径对应的问题。

## 验收标准

- split 和 embed 中，顶层任务及生成式子任务仅发生合法名称排版变化后，仍可发现，并继续用于 read、search、check、原本允许的更新、受管写入和表示切换。这些操作按既有职责保留允许的写法、身份、路径、归属和正文，不为合法状态提示修复。
- 实际名称为 32 列时通过宽度校验，33 列时返回 `task_name_too_wide`，包括仅插入一个排版空格的情况。生成式后缀独立校验宽度且不含空格。真实文字不同、字段损坏和其他无效数据仍报错。既有合法任务无需迁移。
- 子任务格式化后仍可用原创建请求重试，不产生重复，原先不同的规范化创建名称仍保持区分。搜索语义和 UUID 身份不变。
- 显式分隔符调整和同显示名请求达到具体规范化名称及路径目标。dry-run 报告真实计划。目标冲突、移动引用保护、仅元数据修复及非生成式子任务位置保持原行为。
- 窄修复仍可访问符合范围的损坏旧名称和后缀，包括 closed 任务，并完整校验新目标。rename 保留正文原始字节及状态。
- 目录移动成功、元数据写入失败时，即使 read 或 check 成功，操作仍为部分失败。重试完成精确目标。精确的过期计划检查仍拒绝变化后的输入。
- 实现同步更新双语数据合同和受影响参考，不新增 schema 字段、CLI 参数、结果字段、适配器名称规则或标题校验。这些行为的证据继续由[验证合同](../../../../../projects/tk/docs/design/validation.zh.md)规定。

## 风险

合法保存名称的集合扩大。即使 schema 不变，旧运行时也可能拒绝新运行时接受的写法；schema 不变不承诺旧版本能读取新增写法。

排版对应关系比创建请求匹配更宽。将它用于名称与路径校验以外的职责，可能静默合并不同请求，或隐藏一次明确的 rename，因此这些操作保留各自的匹配规则。

对合法任务按其显示名称显式 rename，仍可能移动目录。具体目标和既有引用检查使这一结果可观察，无需增加第二种 rename 模式。

格式化器可能使名称超过实际宽度上限。这仍是真实校验错误，需要显式提供合法名称，不豁免宽度。

部分完成的 rename 可能留下合法且可读的任务。调用方必须依据操作失败及已完成、未完成项判断完成状态，不能把成功读取当作恢复完成的证据。

## 动机

采用两个内部 Skill，维护仓库的长期规格和 ADR。

仓库的 [Spec 指南](../../../../spec/README.zh.md)和 [ADR 指南](../../../README.zh.md)已经形成维护契约。普通功能工作改变目标或持久选择时，Agent 需要应用这些契约。Skill 可以按需提供维护方法，其描述和项目入口说明何时需要加载。

Skill 应持有主要维护内容。如果指南也保留完整规则，就会留下两处需要同步维护的权威来源。项目补充仍需承载语言政策、Git 流程和维护者权限。

## 提议

### 内部范围

在 `.agents/skills/` 下采用 `maintain-spec` 和 `maintain-adr`，各目录包含英文 `SKILL.md` 入口。每个 Skill 持有对应文档的结构、维护规则、生命周期和操作。内部参考文件按读取需要拆分，不限定文件数量，不增加公共框架。

以项目现有机制为基线。Spec 和 ADR 的 README 文件对保留项目覆盖、补充和导航，不再保存另一套完整规则。内部 Skill 是项目维护材料，不是公开分发组件。其项目文件引用不放宽对外分发 Skill、扩展、插件和包的自包含契约。

公开分发、适配其他项目或宿主、为没有既有机制的项目初始化，需另行确定范围。本试点不增加公开安装源、语言分发副本、维护 CLI、翻译 sidecar、归档 manifest 或按年龄归档的政策。

### 触发

Agent 在创建、修改或审查对应文档前加载适用 Skill，也覆盖功能工作影响长期目标或持久决定的情况。项目入口在 Skill 加载前说明这些触发条件。普通阅读、提及文档类型、维护任务 Goal，本身不要求加载任一 Skill。

采用宿主原生的项目 Skill 发现与调用机制。加载一个 Skill 不要求始终加载另一个，维护跨越双方职责时才同时加载。加载提供操作说明，不授予编辑、批准、拒绝、归档、合并或管理任务生命周期的权限。

### 维护依据

读取适用的项目说明与补充、相关规格、包含带日期 `Changes` 的当前决定、活跃提案和必要组件文档。核对先前拒绝时读取被拒绝提案；身份、作者、关系或历史理由需要时，读取归档或 Git 历史。提案或已有实现本身不批准目标变化。

编辑前识别受影响要求和完整文档范围，包括所需语言版本、生命周期关系、当前权威与历史引用、入站链接和标题片段。保留未受影响的要求、数量、条件、例外、权限和历史契约。只读分析与审查返回问题，不修改被审查文档。

项目补充决定语言政策和 Git 流程。本项目保留双语要求与现行集成规则。项目允许 Agent 无需单独批准即可集成提案时，两个 Skill 不额外增加审批门禁。所需语言版本保持语义一致，遇到未解决冲突时报告问题，不默选其中一版。

### 规格维护

`maintain-spec` 维护组件或仓库领域的当前目标，覆盖新增、调整、移除和边界澄清。它读取有效决定及其变更，保留未变要求，区分目标变化、正文遗漏、实现偏差和纯表达修复。与持久决定冲突时，需要遵循适用的 ADR 流程，不能靠修改 Spec 掩盖冲突。

规格仍是在原文上维护的当前文档。目标、范围边界、公开接口、不变量、适用的宿主维护下限、验收标准及相关 ADR 保留现有含义。详细命令和规范性参考内容留在所属页面。任务 Goal 可以提供已确认需求，其创建、访谈、修订和保存不属于本 Skill。历史任务文件名为 `spec.md`，不因此成为长期项目规格。

### ADR 维护

`maintain-adr` 按既有机制处理创建、事实修复、无冲突更新、反转、拒绝和归档。它先搜索再分类，不为没有持久选择变化的普通修改创建 ADR。

保留原作者、首次提案身份日期、稳定当前路径、每项决定连续的归档修订序列、真实事件日期、直接前驱和后继关系，以及当前权威与特定历史版本的区别。后继包含其范围内所有仍有效条款。归档契约保留足以解释当时选择的细节，不能用指向持续变化的 Skill 的链接代替。

Skill 持有现有内容规则，包括有依据的替代方案、重要后果、可信风险和合法的空章节。项目补充保留由维护者负责的批准、拒绝和归档。操作已有有效授权时直接复用；Skill 不授予缺失权限，也不引入统一的 Git 审批顺序。

### 决定后继

三项当前决定包含与上述归属和范围不兼容的条款：

- [ADR 机制](../../../decision/2026/08/22-adr-mechanism.zh.md#维护)选择评审、搜索和 Git 历史而不增加专用 ADR Skill，并将详细格式和操作归给 ADR 指南。采用 Skill，将这些主要内容迁入其中。完整后继保留其余术语、身份、序列、编写、双语、生命周期、权限、历史和同步契约。评审、搜索和 Git 历史仍是维护的一部分。不增加分类体系、翻译 sidecar、归档 manifest、索引和常驻维护脚本的约束继续有效。机械检查仍需由重复维护或实际错误确定具体约束后才增加。
- [规格](../../../decision/2026/10/04-specifications.zh.md#位置)将主要编写和职责分工契约归给 Spec README，并在 `spec 格式`、`分工`、`引用方向` 章节进一步规定归属。将主要维护内容迁给 `maintain-spec`，README 保留项目清单和补充。完整后继保留当前目标含义、包含 `Changes` 的当前决定权威、双语文档、对外分发组件的引用方向及同变更同步要求。
- [组件自包含](../../../decision/2026/08/24-component-self-containment.zh.md#决定)把每个 Skill 都称为可分发组件，同时又将引用限制施加于可分发组件。以公开组件和内部项目 Skill 的区别替换宽泛分类。完整后继保留全部公开文件引用限制、显式前置条件、独立语言组件和组件内维护声明。这是纠正适用范围，不是给公开自包含增加豁免。

[仓库规则决定](../../../decision/2026/10/12-repository-rules.zh.md#归属)保留单一归属原则。修复受影响的归属引用，在 `Changes` 中追加 Skill 与项目补充分工的无冲突说明，不因链接修复反转该决定。

批准并实现后，保留每项被反转决定的身份和下一个未用归档修订号，形成完整双语后继，按引用含义修复直接关系和链接，删除已消费提案。未变化的决定和历史契约不因采用 Skill 而重写。

## 考虑过的替代方案

将完整维护规则留在项目 README，Skill 只提供通用步骤。这保留现有归属，但 Agent 在每次维护时都必须把操作步骤与另一处完整规则拼成方法。让各 Skill 持有主要规则和操作，可以一并提供完整方法，代价是迁移归属时必须保留每条有效契约和历史引用。

## 验收标准

1. 两个内部 Skill 提供完整维护方法，包含可发现的触发说明、可访问的内部参考、项目补充和权限边界。适用维护任务不要求用户逐次点名 Skill。
2. Skill 规则与项目补充的每条规范只有一个主要归属。迁移保留有效条件、例外、身份、作者、生命周期、语言和历史契约，不留下重复的完整指南。
3. 项目文档一致区分内部 Skill 和对外分发组件。公开安装源和自包含要求保持不变，内部 Skill Markdown 属于已知文档检查范围，未知输入和共享检查输入仍保留完整验证。
4. 长期规格、当前决定、Skill 说明、项目入口及两种语言的职责一致。三项冲突决定具有完整后继、正确归档和直接关系；仓库规则决定保留原有无冲突选择。
5. 实际项目维护会话显示，Agent 无需逐次提示即在相关操作前加载适用 Skill，读取有效来源，并按已确认要求正确维护受影响文档。证据覆盖各 Skill 的适用行为，标明使用的文件和对应文档结果。仅可发现、手动加载、文件迁移或格式通过不足以成立。
6. 维护尊重只读请求、项目语言政策和有效生命周期权限。普通修改不制造 ADR，任务 Goal 维护不属于这两个 Skill。

## 风险

完整方法迁入按需加载的 Skill 后，正确维护依赖 Agent 加载它们。如果触发说明不完整，或 Agent 跳过 Skill，缩减后的项目指南不能再提供被略过的规则，规格更新就可能丢失要求，ADR 变更也可能破坏历史关系。项目入口的触发说明和实际维护证据用于处理这项依赖，仅发现文件不足以说明正确使用。

# ADR 提案：为系统提示词扩展增加模型级提示词规则

Decision owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

[English](./2026-09-14-add-model-prompt-rules.md) | 中文

## 动机

不同模型对指令的遵循方式不同。维护者可能希望某个模型在动手前先说明假设，另一个模型保持简短回答，而不必修改扩展源码、宿主文件或发行版。

OMP 18.1.16 没有模型级指令机制。上游 [issue #6739](https://github.com/can1357/oh-my-pi/issues/6739) 请求以模型级 `modelInstructions` 的形式提供。公开的 `before_agent_start` 事件给出渲染后的 `systemPrompt: string[]`，并接受本轮替换数组（[事件](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/extensibility/extensions/types.ts#L752-L768)、[返回值](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/extensibility/extensions/types.ts#L1149-L1153)），`ctx.model` 提供当前 `Model`，包含 Provider 与 id（[上下文](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/extensibility/extensions/types.ts#L476-L480)）。因此 OMP 扩展可以按模型选择提示词文本，不必修改 OMP。

`@ruokee/omp-system-prompt` 已经在转换同一个数组，用于替换固定策略。再加一个组件会给同一条轮次输入引入第二次转换，可见结果会取决于安装顺序（[链式调用](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/extensibility/extensions/runner.ts#L1715-L1725)）。改由一个组件按固定内部顺序一并处理更合适。

规则以用户编写的 Markdown 提供。frontmatter 承载匹配元数据，不参与注入；正文就是被注入的文本。

## 提议

### 组件与版本

扩展现有的 `projects/omp-system-prompt`，不新增包。保留包名、原生 `omp.extensions` 入口、现有 `renderDelivery` 设置与 peer 依赖契约。组件继续满足[自包含组件决定](../decision/2026-08-24-keep-components-self-contained.zh.md)。它只从用户目录与项目目录读取规则文件，不读取仓库其他组件的文件。

版本从 `0.1.2` 升到 `0.2.0`。没有规则文件时每轮行为与之前一致，因此对已安装用户是增量变更。不新增启用开关。规则文件是否存在决定该能力是否生效。

按此顺序注册两个 `before_agent_start` 处理器：先执行现有的替换处理器，再执行规则追加处理器。追加处理器读取替换产生的数组，因此不会重新分类替换刚写入的块。两个步骤的失败互不影响。替换失败时把传入的宿主数组留给追加步骤扩展，追加失败时替换结果继续生效。两者都通过组件现有的有界、按会话去重的诊断通道上报。

### 规则文档与匹配

在钩子运行的每个轮次读取两个固定目录：

- 用户目录 `getAgentDir()/model-prompts`，通过 `@oh-my-pi/pi-utils` 提供的宿主函数 `getAgentDir()` 解析；
- 项目目录 `getProjectAgentDir(ctx.cwd)/model-prompts`，通过同一个包中的 `getProjectAgentDir()` 解析。

目录只读取其直接子项中扩展名为小写 `.md` 的普通文件。不递归，不跟随文件符号链接，不读取隐藏文件。按文件名的 JavaScript 字符串比较排序，因此 `10-`、`20-` 之类前缀可以控制顺序，异步读取的完成顺序不能改变它。用户目录的正文排在项目目录之前。不跨目录去重，不让项目文件遮蔽用户文件，也不合并内容相同的文件。目录不存在视为空集合，一个目录读取失败不影响另一个目录贡献内容。

规则文档以恰好为 `---` 的行围出的 frontmatter 开头，文件开头允许一个 UTF-8 BOM。frontmatter 只有一个必填键 `match`，其值是非空数组。每个数组项是恰好含下列一个键的对象，值为非空字符串：

| 键 | 匹配对象 |
| --- | --- |
| `exact` | 与 `${model.provider}/${model.id}` 相等 |
| `model` | 与 `model.id` 相等 |
| `contains` | `${model.provider}/${model.id}` 的字面子串 |
| `regex` | `new RegExp(value).test()` 作用于 `${model.provider}/${model.id}`，不带 flags |

数组项之间是“或”的关系。任一项命中即应用该文件，同一文件命中多项时，由追加步骤只追加一次。匹配区分大小写、按文本比较，不解析别名、角色、模型族、展示名、传输名（wire name）或选择思考等级的后缀，也不提供通配符或模型列表。含 `/` 的模型 id 按完整 id 比较。

追加步骤取结束分隔行之后的正文，按字节原样追加，包括空行、CRLF、缩进、HTML 注释、类模板文本与结尾换行。它移除开头的 BOM。

未知键、同一项包含多个键、`match` 为空数组、值不是字符串、YAML 无效、分隔行缺失或格式错误、正则无法编译，都会使该文件无效。组件跳过无效文件，并给出一条指出来源文件名与固定原因码的诊断。被跳过的文件不会被部分应用，组件也不会删除或替换其他文件的文本。追加步骤在钩子运行的每个轮次重新读取规则文件，因此新增、编辑与删除在下一轮生效，无需重启会话。

### 注入契约

至少有一条规则命中时，返回传入数组原样，其后按上述顺序追加每个命中文件的一个块。没有命中时不返回内容，轮次输入保持不变。

只使用系统提示词通道。宿主每轮从基础提示词构建本轮提示词（[基础提示词](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-tools.ts#L1488-L1524)），不把某轮的 override 复用为下一轮输入，因此普通连续轮次不会累积追加块。验收标准 6 覆盖这一行为。

追加步骤不读取 `ctx.getSystemPrompt()`，不修改传入块，不添加包装标签或标题，也不重新渲染宿主内容。

### 诊断

无效规则、目录不可读，以及校验之外抛出的错误，都通过组件现有通道上报：交互会话用 `ctx.ui.notify`，其他情况用宿主 logger，并按会话与来源去重。诊断包含固定原因码与可定位来源，例如 `project/20-reasoning.md`；不得包含规则正文、绝对路径、原始解析错误、正则源码或会话内容。

正则按 JavaScript 正则执行，不设超时，也不设沙箱。

### 上游复核

组件文档记录当宿主自行提供模型级指令时需要复核什么，触发依据是上游 issue #6739 或等价能力：

- 宿主覆盖哪些匹配维度，例如精确 `provider/model`、裸模型 id、子串与正则；
- 宿主文本与替换后或自定义系统提示词的组合方式：替换还是追加，以及它在块序列中的位置；
- 宿主文本的刷新时机：每轮、每次 Provider 请求、切换模型、临时切换与回退；
- 宿主如何发现规则：目录、用户级与项目级优先级、文件顺序。

复核结果决定本地能力保留、只覆盖宿主未覆盖的部分，还是删除，并伴随相应的版本变更。

### 实现后的收尾

实现时为本能力创建一个新决定，并在[添加 OMP 系统提示词扩展](../decision/2026-09-09-add-omp-system-prompt.zh.md)的 `## Changes` 下追加带日期的条目，记录该组件同时追加模型级文本。不反转任何现行决定。替换契约保持已决定的内容。

## 考虑过的替代方案

### 分发独立扩展并记录顺序契约

该方案在确定能力归属时成为备选。两个组件转换同一个数组，使可见结果取决于安装顺序，因为处理器按扩展顺序执行且没有优先级参数；替换步骤还必须识别或保留由另一个组件拥有的文本。合并同时消除了这两处依赖。

### 给追加块加可识别前缀

该方案在加固独立扩展设计时成为备选。组件自有标记会让替换步骤的块分类失败，而不是误判。它会把组件簿记文本写进本来按原样注入的提示词内容，因此随独立扩展设计一起放弃。

### 作为首条对话消息注入

该方案在确定注入位置时成为备选。`message` 通道把 `role: "custom"` 消息插入本轮的 messages（[消费处](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/agent-session.ts#L6496-L6525)），会话会把这些消息记录为 `custom_message` 条目（[持久化](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/agent-session.ts#L2806-L2820)、[记录类型](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L2488-L2499)），因此每轮都会再向历史追加一份指令。中途切换模型后，历史里仍保留为上一个模型选择的指令，并且该文本的层级低于系统提示词。最终选择的是每轮重建的系统提示词。

### 按 OMP 角色别名匹配

该方案在确定匹配维度时成为备选。由于宿主不记录启动角色，角色条件只能表达该角色当前解析到的模型，那是另一个问题。该选项被放弃，保留了上述四个键。

### 修改 Provider 请求负载

该方案在权衡刷新时机（按 Provider 请求刷新还是按轮次刷新）时成为备选。它需要针对每个 Provider 构造请求负载的知识，而可用扩展点里没有覆盖 Provider 请求负载的公开契约。所要求的行为也不需要按请求刷新，因此该选项留作未来的变更，不属于本提案。

## 验收标准

1. 仓库检查通过，包括组件的类型检查与测试。
2. 组件测试覆盖四个匹配键的正反用例、同一文件内的“或”语义、含 `/` 的 id、大小写敏感，以及 `exact` 与 `model` 的差异。
3. 组件测试覆盖规则校验：分隔行缺失、伪分隔行、YAML 无效、未知键、同一项多个键、`match` 为空数组、空白正文、正则无法编译与 BOM 处理。组件跳过每个无效文件，并给出一条指出来源文件的有界诊断，同一轮的其他文件仍然生效。
4. 组件测试覆盖正文保真（LF、CRLF、缩进、HTML 注释、结尾换行）、与读取完成顺序无关的两目录排序，以及用户目录与项目目录缺失的情况。
5. 组件测试覆盖与替换步骤的组合：替换结果保留且追加正文排在其后，替换失败时仍可追加，追加失败时替换仍然生效。
6. 组件测试覆盖连续轮次：每轮给定宿主基础提示词时不累积追加块；删除、修复或使规则文件无效后，下一轮输出变化且不重用过期文本。
7. 实机运行确认面向 Provider 的最终内容，而不是处理器返回值：每个匹配键在请求中出现预期标记文本，frontmatter 从不出现，会话内切换模型后按新模型重新匹配，只配置规则、只配置模板与两者都配置时提示词结构符合预期。记录 OMP 版本、所用模型与观察到的请求内容。
8. 实机运行确认宿主块与动态内容保留，且连续轮次或轮中重建后追加文本不重复。
9. 实机运行确认替换能力已记录的覆盖边界：常规子代理轮次因沿用父级扩展而继承规则，受限与 plan-mode 子代理不运行该钩子。当前模型配置无法触发的场景（例如自动回退）记为未验证，不做推断。
10. 组件双语文档描述两个规则目录、文件格式、匹配键、文件顺序、追加文本相对替换后提示词的位置，以及上面的上游复核。

## 风险

项目目录中的规则文件把仓库内容变成系统提示词文本。OMP 不做项目信任门控。项目级设置与扩展对当前目录无条件加载。因此，克隆下来的仓库只要带有 `.omp/model-prompts/*.md`，就能给在其中打开的任何会话加入指令。文档会说明该目录与注入行为，维护者自有规则放在用户目录。

如果宿主将来把上一轮的 override 作为输入回传，追加文本会不断累积。追加步骤依赖宿主每轮从基础提示词构建本轮提示词。宿主若改变该行为，每轮都会再加一份命中正文。验收标准 6 与 8 覆盖连续轮次与轮中重建，上游复核条目覆盖迁移到宿主自有机制的情况。

规则正文会增大每个命中轮次的系统提示词。没有大小限制或预算检查，因此一个大规则文件会把全文加入该会话后续所有轮次，并可能挤占其他提示词内容。文档说明，只要文件命中，追加步骤就按原样加入正文。

文本匹配无法区分有意命中与偶然命中。`contains` 或 `regex` 规则可能作用于比作者预期更多的模型，而正则无法编译时只丢弃该规则，并给出一条诊断；该诊断不说明作者想覆盖哪些模型。文档说明匹配对象、大小写敏感与诊断通道；是否命中当前模型由作者自行判断。

追加步骤在钩子运行的每个轮次都读取两个规则目录，因此目录读取缓慢或位于远端时，这段延迟会计入每一轮的提示词装配，没有缓存来分摊。目录按设计保持精简，读取只限直接子项；目录不可读时通过诊断通道报告，而不是阻塞轮次。

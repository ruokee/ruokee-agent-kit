# ADR proposal: Add the omp-context-pin extension

Decision owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

English | [中文](./2026-09-15-add-omp-context-pin.zh.md)

## Motivation

Sessions that run long enough to compact need a small set of details kept word for word: an agreed interface, a file map, a command whose exact form matters. Compaction summarizes history, and a summary can shorten or reword that material. Asking the model to reproduce text after the fact is unreliable in the same way.

OMP's experimental `context_notes` keeps one note body per branch and restores it along the current path. It provides whole-note replacement rather than per-entry operations, and context building injects the newest note at the start of the message array. Editing that block changes an early part of the request and shortens its reusable prefix. Entry-level Pin operations need a different placement strategy.

The repository already distributes first-party OMP extension packages. This proposal uses that component format and targets public extension APIs. The host behavior described here was inspected in [OMP 18.1.16 at a fixed source revision](https://github.com/can1357/oh-my-pi/tree/61b1b8aef634334eaf1412afd003a763e1d1b9c1), including [context notes](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/tools/context-notes.ts) and [session context construction](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-context.ts). Source inspection establishes the host behavior described below; it does not establish real-machine acceptance.

## Proposal

### Component and scope

Add the first-party package `projects/omp-context-pin/`, named `@ruokee/omp-context-pin`, under the [first-party capability boundary](../decision/2026-08-20-establish-first-party-capability-kit.md) and the [self-contained component contract](../decision/2026-08-24-keep-components-self-contained.md). The package declares its extension entry through `omp.extensions` metadata in `package.json`, keeps its runtime, checks, and bilingual `README.md` and `README.zh.md` inside the component directory, and uses only public OMP extension APIs. It does not import private host modules, patch upstream source or installed binaries, or require files from another repository component.

The package registers exactly one slash command, `/ctx-pin`, and exactly one native tool, `ctx_pin`. `/pin` is a reserved built-in command name used for session pinning in the resume list, and OMP filters extension commands that reuse a reserved name while logging a conflict warning, so this extension uses a distinct name.

`/ctx-pin` without arguments opens the entry list for the current branch with create, view, edit, and delete, with the create item first, the entries next in creation order, and a close item last; each row shows the entry's integer id and a summary derived from its body, so no stored label is needed. `/ctx-pin add <body>` submits a create directly. An unknown subcommand or a missing body reports brief usage and sends no message; everything after `add` and one separating space is the body, with no shell-style splitting, quoting, unescaping, or whitespace normalization. Inline view, edit, and delete are out of scope for the first version. Both creation entry points share one submission function so the host chooses the ordinary send path when the session is idle and steering while a turn is running, instead of reading an idle flag before an await. The host trims and pre-processes the whole composer input before the command sees it, so verbatim retention starts from the body the extension actually receives; a body that needs exact leading or trailing whitespace uses the multi-line editor.

Multi-line bodies use the host's editor dialog. `ctx_pin` dispatches on an `action` parameter:

| action | purpose | main input |
| --- | --- | --- |
| `list` | list current entries with id, source, revision, and size | none |
| `get` | return one complete body and its id, source, revision, and size | `id` |
| `create` | pin a new text body | `content` |
| `update` | replace an existing body | `id`, `content`, `expectedRevision` |
| `delete` | unpin an entry | `id`, `expectedRevision` |

The schema is stable and never enumerates current entries. The tool uses `loadMode: "essential"` so an enabled `ctx_pin` remains in the top-level tool list. Pin operations do not change its definition. `update` and `delete` require an existing `id` and the revision observed by the caller. An unknown id or revision mismatch fails without writing. No action performs an implicit upsert or a create by rename. An empty body is rejected; accepted bodies retain their whitespace and characters without trimming or normalization.

Entry ids and operation numbers are positive integers scoped to one session. An entry id is assigned at its first successful creation and never reused in that session; operation numbers are assigned per user submission or per new Agent write call, are reused when that submission or call is retried, and may leave gaps. The host tool-call id stays an internal idempotency key that the model neither generates, fills in, nor interprets. The list, receipts, and tool results all show the same integers. The tool's `id` parameter takes that integer directly and accepts no digit string.

The tool declares the lowest approval class, `read`, for every action. With no explicit per-tool policy, `always-ask`, `write`, and `yolo` therefore do not prompt for a Pin operation; an explicit user policy that marks `ctx_pin` as `prompt` or `deny` still applies, the extension writes no user configuration, and it adds no authorization, confirmation, or source admission of its own. Type, existence, revision, capacity, and record-integrity checks remain: they keep an operation acting on the data it targeted rather than restricting who may call it.

Pin means the entry body stays present, verbatim, in every ordinary model request on the current session branch until it is updated, unpinned, or the branch's context is reset. Compaction does not end a pin; the body is restored from the extension's own records after each committed compaction.

An accepted operation changes the effective set at once; for `/ctx-pin` that moment is when the host consumes the message the user confirmed, not when the dialog closes. Published older bodies can remain in earlier history until compaction folds them into a new base snapshot. Entry ids, revisions, and delete records express which contents remain effective. The next snapshot contains only the latest active bodies and excludes deleted entries.

The first version pins text bodies supplied by the user or the Agent. It does not read files, fetch URLs, watch pinned content for changes, or pin anything whose body changes without an operation.

### Interaction and acceptance

`/ctx-pin` is the user's entry point for browsing and editing: it opens the entry list for the current branch, shows bodies and revisions, and offers create, edit, and delete. `/ctx-pin add <body>` writes without opening a dialog, because sending that command is the confirmation. Listing, reading a body, and editing a draft are read only operations: they send no message, change no Pin state, and do not interrupt a running turn, and an abandoned draft leaves nothing behind.

A confirmed write becomes an ordinary user message whose body comes first and whose short management marker is appended at the end. The extension submits the body through the public message API and keeps it verbatim, so the text that gets pinned is the text the user wrote. Only the last marker appended by the submit function is recognized, so a similar tag inside the body, inside a code fence, or at the end of the user's own text stays prose. The marker carries the integer operation number and a short scope token that distinguishes one session and reset period from another; the token is not a credential, and identity is never inferred from body equality, timestamps, array position, or `input.source`. A delete has no body to pin, so it reads as a short management sentence with the same marker. The host runs the message as an ordinary prompt when the session is idle and as steering while a turn is running, and that message is both the request and the visible record of what the user sent. An explicit task in the body is carried out as usual, background material is answered or clarified, and a Pin failure does not by itself cancel an independent request in the same message.

The operation becomes effective when the host consumes that message and the extension accepts it. Before consumption the entry point reports the operation as pending, and the accepted set changes only after the checks described under Canonical state pass: the current process still holds that submission, the carrier matches the text it recorded, the observed session, branch, and reset period are still current, the entry exists, and the revision still matches the one the draft was opened at. Because integer operation numbers are predictable, acceptance compares the whole recorded submission, including action, target, observed revision, and body, instead of trusting the number alone; a message the host never consumes, a cancelled draft, and a conflict that leaves the current body in place all change nothing. Text that merely resembles the marker stays ordinary prose.

After the host consumes the message and the checks run, the entry point reports the outcome to the user: accepted, no change, or not applied with its reason. The request that consumes the operation carries the same outcome tied to that numbered operation, so the model sees whether the operation was accepted, changed nothing, or was refused, and it does not have to write the same operation again to make an accepted command take effect. That statement is scoped to the Pin operation and does not forbid the other tool work the same request may need. The outcome keeps the result separate from the body, repeats no body text, starts no turn of its own, and adds no persistence guarantee. An outcome carrier holds no Pin state, and replay ignores it.

The Agent manages Pins through the `ctx_pin` tool inside a turn it is already running, and the tool result is its receipt. A user can also ask for a Pin operation in an ordinary message, for example "pin the interface we just agreed on". The Agent is then expected to call `ctx_pin`, the same way it is expected to call any other tool the request needs. The extension does not parse natural language into Pin operations, and neither path guarantees that a model picks the right tool, arguments, or moment; the operation is whatever the tool call actually did. An operation the Agent performs this way records `source: agent`, because the entry point, not the intent behind the request, decides the source.

### Canonical state

Canonical state is an append-only operation log in the session journal, written with `appendEntry` under the custom type `omp-context-pin`. Each accepted write appends one record:

| field | meaning |
| --- | --- |
| `schemaVersion` | payload version of the record; the current version is `2` |
| `operationId` | positive integer for one user submission or Agent write call, retained across its retries and used to match its projection |
| `action` | `create`, `update`, or `delete` |
| `entryId` | positive integer assigned at creation and never reused in that session |
| `revision` | starts at 1; each accepted update or deletion advances it by 1 |
| `body` | complete new text for `create` and `update` |
| `source` | `user` or `agent`, recording which entry point authored the operation |

The effective set is computed by replaying the current branch chronologically after its latest `reset_boundary`, using `getBranch()`. The creation record determines the source reported for an entry; later operation authors do not change it. `list`, `get`, an `update` whose body is unchanged, a rejected operation, and a failed capacity check append nothing. Identity and revision validation precede the no-op check. Numbering reads the whole session through public `getEntries()` to restore the high-water marks of both sequences, including numbers reserved by submissions this process has not consumed yet and by the carriers and outcomes the host already holds; that scan only assigns numbers and never applies another branch's bodies, receipts, or operations to the current branch. A session or extension reload rebuilds the allocation state, and an ordinary `/tree` or `/clear` does not lower the counters. Effective state still comes only from `getBranch()`.

One confirmed user submission or one Agent write call keeps one `operationId`. A message the host consumes once appends one operation, and a resubmission carrying the same identity is a retry of it rather than a second entry. Retrying an accepted invocation returns its receipt without appending a second operation, and an Agent retry finds its accepted operation number in the persisted record through the internal tool-call id after checking that the call content matches, instead of allocating a fresh number first. A fresh `create` invocation creates a distinct entry even if its body matches another entry, and a fresh user submission receives a fresh number. Delivery retries reuse the accepted operation's identity.

A number that leaves the safe integer range, or an allocation state that cannot be established reliably, is reported as an explicit error instead of wrapping around or silently restarting from 1. A session written by an earlier candidate holds string identities; the current version reports those records as an unsupported format inside its active range rather than mixing them with integers, and a clean switch applies: the old records are not migrated, the user starts a new session or resets the range, and the old string identities take no part in the new numbering. A damaged range keeps the behavior described under Capacity and reset.

An accepted operation is present in the host's in-memory branch journal. Public `appendEntry` returns no result and does not acknowledge persistence. Branch replay remains authoritative across requests, session changes, and recovery; tool results are receipts, not state storage. A receipt must not claim disk durability that the host has not confirmed. Non-persistent sessions retain Pins only for their in-process lifetime and must expose that limit to both entry points.

### Session persistence and responsibility

Canonical records live in the session journal the host maintains. Creating a session file, writing it, saving it on exit, restoring it, and copying its messages are host responsibilities. Pin reads the branch the host provides and replays the records in it. It does not create, repair, move, or write that file itself, and it does not promise outcomes the host never reports.

Neither entry point receives a write confirmation from the host: public `appendEntry` returns no result, and the public message API returns no delivery receipt. A receipt therefore states what the extension has submitted or accepted, and never that the host has saved it. The public session interface exposes no persistence operation either, so an extension cannot confirm a save; in the inspected source the session file is created by host-side paths ([ReadonlySessionManager](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L376-L400)).

The extension does not work around that boundary: it creates no second session behind the user's back, writes no journal file directly, calls no private method, and starts no extra model turn to force a save. A session the host does not save, a file lost or truncated outside the extension, and a restore that never reaches the branch all leave Pin with nothing to replay. Those are host outcomes rather than Pin defects, and the evidence for such a failure has to show which side produced it.

Non-persistent sessions keep Pins for the lifetime of the process. Both entry points state that limit instead of implying durable storage.

### Tail changes

Ordinary changes reach the model as session-journal custom messages with a dedicated custom type and `details.operationId`. A `create` or `update` message contains the entry id, revision, and complete new body; a `delete` message records which entry was unpinned. The host retains their appended positions and rebuilds their custom type and details, so the extension can recognize its projections without matching body text or array position. A write the user confirmed is already carried by the message the user sent, and the extension adds no second copy of that body; the projection above carries Agent writes and re-expresses a change whose carrier is missing from the request. Their survival across process exit follows the host's session save and restore. Their metadata also carries the originating session identity, so a queued carrier from another session cannot match by integer alone; the extension filters carriers by the current branch and reset period, and the host identity stays in internal metadata rather than in entry numbers or receipt text.

A projection and a restored body keep the quoted text separate from the management note and label its entry id, revision, and source. A restored body is retained session context: its facts and the user requirements that still apply stay valid, pinning grants the text no authority it did not already have, and pinning does not mean repeating work that is already done. A body written by the Agent gains no user or system instruction authority from being pinned. The note neither claims that every pinned body is not an instruction nor repeats the management envelope inside the quoted text. OMP converts ordinary custom messages through a shared converter that can produce developer-role messages, so the final role at the provider boundary is verified rather than assumed.

An Agent write must not start a model turn. The call is made inside a turn the Agent already runs, and the projection is delivered through the public non-initiating mode: `pi.sendMessage(message, { deliverAs: "nextTurn", triggerTurn: false })`. During streaming the host places that message in its hidden follow-up queue without scheduling a continuation, and when the session is idle it appends the message without opening a turn. `triggerTurn: false` alone is not enough, because the default delivery path is steering and drains a queue. A result that the extension hands to the host uses the same non-initiating mode. A write the user confirms takes the ordinary user path instead, so the host starts a turn when the session is idle and steers the running turn otherwise; that turn is the user's request and it carries the operation. Because the host may append such a message only when the next ordinary prompt arrives, the call return is not treated as delivery: the current request still derives its changes from canonical records, so a change accepted during that turn has to reach it through those records. Positions stay stable: an outcome binds to the user message it belongs to, an Agent change binds to the completion position of its tool call, and a copy the host later appends with the same identity is deduplicated by the extension instead of being placed at the new tail. When a carrier disappears because of host compaction or pruning, the snapshot and the log order decide its position, never an array index. Acceptance checks consecutive tool steps within one run, because re-appending the same missing projection on every request build would move the prefix each time ordinary history grows.

### Compaction boundary

At request preparation, the extension finds the latest compaction entry actually committed after the current branch's active reset boundary. It reconstructs the pin set through that committed entry as the period's base snapshot. It places the snapshot immediately after the corresponding host compaction summary and filters only its own projections covered by that snapshot. Changes accepted after the boundary stay in the tail.

Boundary selection uses the committed branch entry. It does not use the pre-compaction notification or depend on the post-compaction callback having run. Operations accepted before the commit are folded into the snapshot; operations accepted after it stay in the tail. Discarded, failed, and cancelled speculative compactions do not advance the boundary. Provider-native remote compaction keeps its opaque payload unmodified; the extension's snapshot must follow the corresponding replay in the effective provider input. A context-hook insertion alone does not prove the final placement: conversion, normalization, and later handlers must be checked on actual requests.

Without a committed compaction boundary the extension creates no base snapshot, and the tail messages alone express the current set.

The snapshot carries the boundary identity and the pin contents, and no current time, request counter, random value, or per-request estimate, so unchanged state produces a byte-identical projection. Because the projection is recomputed from the branch on each request, a lost callback, a detached notification, or a restart after the compaction does not lose the base.

### Cache behavior

- Reads and unchanged updates leave canonical Pin state and published Pin projections untouched. Their ordinary tool calls and results can still extend host history.
- Accepted writes appear in the tail: an Agent write as the extension's projection, a user write as the message the user submitted. Messages that were already published keep their positions, and earlier instructions are not rewritten.
- The base snapshot changes only at a committed compaction boundary, where the host has already rebuilt the history.
- Tool definitions, the tool list, and their schema are independent of the current pin set.
- Outside the specified compaction folding and stale-queue filtering, the extension rewrites no earlier system, tool, or history content.

Verification compares provider-facing effective context, including the preceding requests when the host sends chained deltas. Attribute host-originated changes separately and check whether Pin introduces an avoidable prefix rewrite.

### Capacity and reset

- An operation written through either `/ctx-pin` form has `source: user`; one written through `ctx_pin` has `source: agent`. `list` and `get` report the source recorded at creation. An operation the Agent performs in response to an ordinary user message is `source: agent`: the entry point decides the source, not the intent behind the request.
- Capacity is measured in UTF-8 bytes and enforced by both entry points before any state change: 16,384 bytes per entry body, and 65,536 bytes across the active entries of a branch. An operation that would exceed either limit is rejected, changes nothing, and reports the limit and the current usage. Both limits are declared constants documented in the component README.
- A successful `/clear` appends a host `reset_boundary` and ends the active Pin set. State replay, compaction selection, and queued-message filtering all use the period after that boundary. `/new` starts a separate session with its own empty set. `/fresh` resets provider stream state without clearing local history, so it does not clear Pins. Navigating back to another branch reconstructs that branch's own period.
- Validation and append use one shared synchronous path. The tool checks before it accepts an operation; `/ctx-pin` checks when the host consumes the confirmed message. Both entry points compare the observed session, branch, reset period, and entry revision with current state. The draft keeps the revision shown when editing began and compares it at consumption; the tool supplies `expectedRevision`. Re-check after any await and reject a stale operation rather than overwriting an intervening edit. A draft that is edited, abandoned, or cancelled before consumption writes nothing; cancellation after acceptance does not roll back the operation or produce a second write. Both command forms submit through the same function and the same synchronous validation path, and a draft is compared against the revision it was opened at.
- An unknown `schemaVersion`, damaged record, or invalid operation sequence in the active replay range makes the effective state unavailable. Disable writes and new snapshot or recovery projections for that range, preserve existing journal records and published messages, and emit a bounded diagnostic. Reads report the unavailable state rather than a complete-looking partial or empty set. Do not skip a damaged update or deletion and present an older revision as current. Re-evaluate the condition when the active branch or reset period changes. The string identities written by an earlier candidate are reported as an unsupported format rather than read as integers, as described under Canonical state.

## Alternatives considered

- Keep the host's `context_notes` as the mechanism. Considered when choosing whether a new component is needed. It gives one whole-note body per branch with branch-aware restore, but it has no entry-level operations, each write replaces the whole note, and the newest note is injected at the start of the message array, which moves previously stable bytes on every edit. Enabling the experimental mode also changes automatic context maintenance.
- Republish the complete pin set at the front of the request after each change. Considered when choosing where a change goes. It is the simplest way to keep the full text visible and was kept as a comparison baseline, but each edit then shortens the reusable prefix of the request.
- Append tail messages only, without a base snapshot. Considered when choosing how pinned text survives compaction. Tail appends alone leave the pinned text at the mercy of compaction, and only the log would still hold bodies that the model can no longer see.
- Adopt a broader context-management extension. Considered while comparing retrieval, archive search, history folding, and full context planning with entry-level Pin requirements. Those additional responsibilities exceed this component's scope. Importing an existing third-party capability into this repository would also conflict with its first-party ownership boundary.
- Replace the host's compaction. Considered when deciding how much control the extension needs over summaries. It would let the extension compose the summary, but native remote, snapcompact, handoff, soft, and shake paths each have their own semantics, and the extension reads the committed boundary instead.
- Let a confirmation in the `/ctx-pin` dialog write state directly. Considered while choosing when a user operation becomes effective, and used in an early candidate. The receipt is immediate, but the operation takes effect before the message reaches the host, so a queued, edited, or withdrawn message can leave a change the user never sent, and the running turn never receives it as steering.
- Parse a natural language request into Pin operations inside the extension. Considered when asking how an ordinary message could manage Pins without depending on the model. It would need a command syntax, a precedence rule against ordinary prose, and its own error path, while the tool already gives the Agent the operation, so the request is left to the model.
- Start a model turn to make the host save the session. Considered while working around the session file boundary for an initial fresh session. It spends a turn the user did not ask for on a host responsibility, and it still returns no confirmation that the write happened.

- Keep the generated UUID strings as entry and operation identities. Considered while revisiting the identity format. No observed model failure was caused by a UUID, so the reason to change is readability and context cost: an integer is easier to read, easier to pick from a list, and shorter in every message that carries it.
- Remove the identity marker completely and recover the operation from something else. Considered while simplifying the message shape. The public user-message API exposes no `details` and returns no consumption identity, so equality of body text, timestamps, array position, and `input.source` would decide which message is an operation; switching the carrier to a custom message would leave the ordinary user-message path unverified. A short appended marker is kept instead.
- Keep the stored `title` as the list label. Considered while changing how entries are presented. A title can drift from the body it labels, while an integer id plus a summary derived from the body already distinguishes entries, so the field is removed and no de-duplication rule for repeated titles is needed.
- Declare the mutating actions as write-class operations. Considered while defining the tool's approval class. It makes the host prompt for a create in `always-ask` even though the operation touches no file, process, or network resource, and host policy already governs the tool, so the single lowest class is declared for every action.
- Keep delivering Agent changes through the default send path with `triggerTurn: false`. Considered while defining the delivery path. The host routes such a message into steering and drains the queue, which can add a turn or cancel work in the same batch; the explicit non-initiating delivery mode is used instead.

## Acceptance criteria

1. The package installs, activates, and uninstalls through native OMP mechanisms on an unmodified supported runtime, and declares its peer version range in package metadata. Runtime checks use public host version and capability information before registration; peer metadata alone is neither a runtime compatibility check nor evidence that every version in the range is supported. An unsupported runtime registers no tools or commands, emits a bounded diagnostic, and does not terminate the session. Acceptance attributes each failure to its cause: a Pin defect, a host fault, or model behavior. An external failure that leaves no evidence about Pin is recorded as undetermined with its reason, not as a Pin failure.
2. With the extension and tool enabled, its only provider-facing Agent entry point is `ctx_pin`, with a schema independent of Pin state. The list order and the entry labels match the presentation rule under Component and scope. `/ctx-pin` is discoverable, built-in `/pin` still performs session pinning, and no command conflict warning is logged. It has two forms: no arguments opens the list, and `add <body>` submits a create without a dialog, keeps everything after one separating space as the body, and reports usage without sending anything for an unknown subcommand or a missing body. Either form is the only direct extension path that turns a user message into an operation; an ordinary message may instead lead the Agent to call `ctx_pin`, and the extension never parses prose into one. With no explicit per-tool policy, no Pin action prompts for approval in `always-ask`, `write`, or `yolo`, while an explicit user policy that marks `ctx_pin` as `prompt` or `deny` is still honored.
3. State: each accepted logical operation appears once in the current branch journal; reads and unchanged updates add nothing. A confirmed user write changes state only when the host consumes its message; an edited, abandoned, or cancelled draft leaves no record, and a message the host withdraws before consuming it leaves none either. Branch switching, `/tree`, restore, and reload reproduce the expected entries, sources, and revisions. `/clear`, `/new`, and `/fresh` follow their distinct contracts. Unknown ids, stale revisions, submissions cancelled before acceptance, and rejected writes leave state unchanged. Retrying an accepted invocation does not append another operation. Entry ids are positive integers that a session never reuses, and operation numbers identify one submission or write call, are reused only by its retries, and may leave gaps. Numbering survives an extension reload, does not decrease on `/tree` or `/clear`, and reports an explicit error when the allocation state cannot be established. Records use `schemaVersion: 2`; a session that holds the earlier string identities is reported as an unsupported format in the active range instead of being mixed with integer numbering.
4. Delivery: the base snapshot and uncovered tail jointly express the effective set without duplicate application or revival of superseded revisions. A snapshot-covered operation does not require an individual tail projection. Already published historical revisions may remain until compaction; they must not become effective again. An Agent write goes out through the explicit non-initiating delivery mode and starts no model request: during streaming the host queues it without scheduling a continuation, and an idle session appends it without opening a turn. The next safe request boundary carries it, and because the host may append it only at the next ordinary prompt, the current request still derives the change from canonical records. Published positions stay stable: a copy the host later appends with the same identity is deduplicated instead of moving to the new tail, and consecutive tool steps inside one run keep the prefix they had. A user write is an ordinary user message, so it opens a turn when the session is idle, and the request it opens carries that write once. Restore between a recoverable canonical write and its projection preserves the operation; stale queued projections stay out of the active request. When the host saves a session and restores it, verify that Pin replays the restored records correctly, covering a session that began empty, ran ordinary turns, and resumed, and an explicit `/new` session. The request that consumes a command operation carries its outcome tied to the operation identity, and the entry point shows the user the same outcome. A host that does not save, or a file lost outside the extension, is recorded as a host outcome rather than a Pin failure.
5. Cache: unchanged published Pin content retains its bytes and position across ordinary history growth. Creates, updates, and deletions preserve the preceding system, tool, and history content until a host compaction or reset changes that period. Compare consecutive effective requests within matched runs with the extension, without it, and with a front-rewrite baseline. Record each first differing message and field and its cause. Reconstruct effective input across `previous_response_id` deltas; Pin must not add a full replay beyond the host's own context change.
6. Exercise and report each maintenance subcase on real requests: repeated manual compaction, automatic threshold and mid-turn compaction, overflow recovery, adopted, discarded, failed, and cancelled speculative compaction, handoff, snapcompact, provider remote compaction, shake and tool-result pruning, `/tree` to an earlier boundary, and a request before the post-compaction callback completes. Cover changes accepted during compaction and delayed queue delivery. Effective pinned bodies remain verbatim and ordered, their revisions resolve correctly, and opaque remote payloads remain unmodified. Run core maintenance paths through both user-created and Agent-created entries.
7. Capacity and failure: byte limits are enforced before state changes; rejection changes neither the log nor projection and reports its reason to the user and to the consuming request. Test multi-byte limits, unknown schema versions, damaged records, interrupted receipts, concurrent edits, non-persistent sessions, and a dialog left open across session, branch, or revision changes. Test cross-entry management in both directions, including source preservation after a UI edit. A damaged deletion must not revive an older entry as valid state. Check the approval boundary in all three default modes and with an explicit per-tool `prompt` and `deny`. Rebuild numbering from a session that already holds entries, deleted ids, and unconsumed submissions, and check that a retry reuses its recorded operation number instead of allocating a new one.
8. Evidence: use the real interactive OMP CLI with dedicated test configuration, sessions, and synthetic workspace. User cases operate the actual command, editor, and list. Record the exact host version, candidate hash, effective configuration, resolved models, driver version, and process/session/branch/input associations. Verify driver readiness and completion handling before functional cases; use bounded, paginated observation without blind input retries. For every relevant request, including failures and retries, correlate inputs, calls, canonical records, context-hook output, and final provider-facing payload. Verify the observation point covers serialization and chained requests. Remove credentials, Cookie headers, and private connection details before capture reaches disk, without changing the sent payload. Preserve the captured evidence and exact exports without formatting; do not supply test answers or history exports to the subject as business material. Cases whose purpose is not a length boundary use varied business bodies: at least one that requires immediate work stated in the body, one that only supplies background material, one long-lived requirement, and one whose answer needs a tool call. Two further directions belong here: a body that quotes or resembles the management marker, and a message that carries both a Pin failure and an independent business task. Repeated filler text is reserved for the byte-limit boundary cases. A background-only body, an empty body, and an over-limit body do not by themselves show that the model ignored an executable task, and none of them supports that conclusion. Missing key evidence blocks a pass.
9. Autonomy: pre-register three independent trajectories on the final candidate. Each starts from a fresh test session and covers autonomous selection and creation, update, removal of expired information, use after real compaction, and avoiding unnecessary writes. Judge each stage of each trajectory. The Agent chooses actions and ids from business context and normal tool guidance, without manual calls, copied successful state, step-by-step instructions, or re-supplied answers. Every failed stage is recorded with its evidence and attributed: a defect in the Pin implementation, the tool definition, or its description requires a component fix and a rerun of all three trajectories on a new candidate, while a pure model deviation is recorded as a behavior observation and does not by itself change the Pin functional verdict. Where no run reached a Pin-required path, the matching functional check is undetermined rather than passed. Separately test recovery from real tool errors. A user request for a Pin operation in an ordinary message is observed the same way: a model that does not call the tool, or that calls it with wrong arguments, is a behavior observation, unless the tool definition or its description caused the misuse.
10. All required cases and their parameterized subcases pass with evidence for the final candidate. Preserve failures and associate fixes with new candidate and run records; keep candidate, configuration, driver, and criteria fixed during each run. Repeat affected cases and core user, Agent, prefix, compaction, and restore paths after fixes. Unavailable triggers, missing observation, and unexecuted mandatory paths block acceptance; only the maintainer may approve a scope exception. Distinguish driver completion, evidence completeness, and functional success. Validate reload and coexistence with the actual context-extension combination as well as the fixed test configuration. Attribute each failure: a Pin defect, a host fault, or model behavior; when the evidence cannot separate them, record the case as undetermined with its reason instead of a Pin failure. An attributed model deviation is preserved as a behavior observation and requires no component fix, and it does not count as a Pin functional pass.
11. `pnpm check` passes, with the component's checks included in the root aggregate. The component README documents command and tool usage, invocation and revision rules, record format, limits, reset rules, the responsibility boundary, how state follows the host session, the inline command form, integer identity and the summary rule used by the list, and the host versions actually exercised. Automated checks do not substitute for real-machine acceptance.

## Risks

A canonical record can exist without its model projection, causing pinned text to disappear from the request. Recovery can also deliver it twice or deliver an older revision after a snapshot. The extension must reconcile operation identities and snapshot coverage across restart, queueing, and compaction; the restore cases must exercise those failure paths.

Selecting the wrong compaction boundary publishes a snapshot for a compaction that never took effect, or skips one that did, so changes are dropped or an older version reappears. The boundary comes from the committed branch entry, and speculative results that were discarded must not advance it.

Other extensions can insert messages around the host's compaction summary or drop the snapshot in a later handler. Final provider conversion can also change the apparent hook-level order. These failures can omit pinned text or apply changes in the wrong order, so acceptance must inspect the final request for the tested extension combination.

Provider-native remote compaction keeps part of history opaque. Pinned text may remain inside that payload as well as in an explicit snapshot. Editing the opaque payload could corrupt replay; incorrectly ordering the explicit snapshot and tail could reinstate superseded constraints. Verify preservation and effective ordering on actual requests without claiming to deduplicate opaque contents.

Pinned bodies and accumulated revisions consume context. Limits on active body bytes do not bound token use, metadata, or older tail messages, so the full request can still overflow after compaction. Acceptance must measure full-request size and verify native overflow recovery without truncating active Pin bodies or repeatedly triggering recovery without progress.

Retained context can be read as granting authority. A body the Agent pinned could be taken as a user requirement, and a restored note that stops separating facts from requirements could make an expired instruction look current. State the source, keep the note from claiming authority the text never had, and verify the final role and the treatment of text that resembles a delimiter at the provider boundary.

Session-scoped integers can collide across sessions or be restored from the wrong range. If allocation ignores numbers already reserved by unconsumed submissions, or reads a different branch, an idempotency check accepts a message that belongs to another operation, or rejects a legitimate retry, and a change is applied twice or lost. Allocation has to restore session-wide high-water marks, and a queued carrier has to keep the originating session identity.

Non-initiating delivery can postpone a change to the next ordinary prompt. If the current request stops deriving changes from canonical records at the same time, the model works a turn without the change that was just accepted. The derived-request path stays a release gate, and consecutive tool steps are checked on real requests rather than assumed from a queued call.

Request captures can leak credentials or unrelated private content. The inspected host's [request debug writer](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/ai/src/utils/request-debug.ts#L56-L78) includes request headers; synthetic prompts and repository exclusion alone do not make those files safe. Use capture that excludes sensitive transport fields before writing and does not mutate the request sent to the model.

A user confirms an edit against the revision the dialog showed. If the message is consumed after the Agent changed that entry, or after a session, branch, or reset change, applying the stored revision would overwrite the newer body. Validation has to run at consumption against current state, and a conflict has to leave the existing body in place.

The extension reports what it has submitted or accepted, and the host decides what reaches disk, so a user who confirms an operation while its message is still queued, or whose session the host never saves, must not be told the Pin is stored. Accepted state has to come from the journal rather than from the submission, and evidence has to separate a missing record caused by the host from a record that Pin failed to replay. The remaining delivery and placement checks stay release gates.

# ADR 提案：重构 smart-cache 合同层并纳入 Handoff 缓存对齐

Draft owner: Ruokee
Draft writer: OMP

[English](./2026-10-12-restructure-smart-cache-contract.md) | 中文

## 动机

反转 `@ruokee/omp-smart-cache` 的 remote 决定，把顶层决定改为记录拓展本身，remote 对齐与 Handoff 缓存对齐各一份单独决定，并让项目规格采用同一框架。

本包力求避免 OMP 请求出现意料之外的缓存未命中，同时保持普通请求与原生请求路径不变，[组件 README](../../../projects/omp-smart-cache/README.zh.md) 也是这样描述的。合同层描述的范围更窄：[remote 决定](../decision/2026-10-10-use-smart-cache-remote.zh.md)以 remote 对齐为主题，[项目规格](../../spec/omp-smart-cache.zh.md)在四处声明 Handoff 不属于本合同。

Handoff 从当前对话生成压缩摘要或交接文档。它把这件工作作为侧请求发出，重复会话的 system 提示与工具定义，而普通主循环 dispatch 已经发送过同样的内容。Provider 按请求前缀命中缓存，因此侧请求若以不同形式重建 system 提示、丢掉在线 reasoning 设置或替换在线 tool choice，就会为对话已经付过费的内容支付全额输入。一个本地试用扩展对齐了这些侧请求，在一组真实请求观测中把生成调用的未缓存输入从 14,388 降到 470 token，命中率从 34.42% 升到 97.94%。该扩展是仓库外的单会话试验：每个进程只保留一个参照，没有设置，也没有逐会话隔离。

承载这项能力使本包成为一个具有两项优化、各自开关与各自状态的拓展，现有合同文本无法记录这一点：它们的主题是单项能力，而 ADR 规则不允许改写现行决定来表达冲突选择。本提案反转该决定，起草取代它的三份决定，并说明随之进行的项目规格回正。

## 分析

### 冲突条款

[remote 决定](../decision/2026-10-10-use-smart-cache-remote.zh.md)的标题与首句把范围限定为 remote 对齐。它的动机段记录该次迁移既不批准 Handoff 集成，也不替换已安装的 Handoff 原型；结尾段把 Handoff 的协议、支持、状态、收益证据与安装放在分别处理的工作里。

[项目规格](../../spec/omp-smart-cache.zh.md)在四处重复这一排除：目标段声明 Handoff 不属于本合同，非目标段排除集成 Handoff，公共接口段把 Handoff 占位排除在本合同范围外，不变量 12 声明本包独立于 Handoff 原型。

这些表述写的是当次变更的范围，而不是永久禁止，remote 决定本身也这样记录。承载第二项能力本身并不与它们冲突。冲突在顶层问题上：现行决定的主题是 remote 对齐，组件级条款无处安放，而与其并列的 Handoff 决定会让项目规格的框架、目标段与不变量 12 继续描述一个比其当前行为更窄的组件。

### 为什么必须反转而非追加变更段

`## Changes` 段落记录与现行决定不冲突的内容。它无法改变该决定的主题，也无法退役把 Handoff 放在别处的条款，因为读者在现行决定里仍会看到主题是 remote 对齐、Handoff 由分别处理的工作承担。ADR 规则要求提案写明要反转的决定、生效条款、取代选择以及两者不能同时成立的原因。本提案即为此，归档决定的仍有效条款迁入三份现行决定，而不是消失。

### 被移动文件的入链

remote 决定的语言对以原文件名移入 `archived/`，其入链须在同一变更中修复：[归档的模型提示词决定](../archived/2026-10-07-maintain-qol-model-prompts.zh.md)在 `Reversed by` 字段里指向它，[共同宿主下限决定](../decision/2026-10-04-raise-omp-host-floor.zh.md)以它说明 smart-cache 的行为与协议边界，[OMP 体验决定](../decision/2026-10-10-maintain-omp-experience-extension.zh.md)以它说明 remote 切换，[宿主兼容规格](../../spec/host-compatibility.zh.md)把它列在相关决定中。每处链接与关系字段指向现在拥有被引用合同的现行决定，因为现行文档不得把归档决定当作现行权威引用。

### 决定 Handoff 能力的两个宿主事实

handoff 侧请求由宿主用会话自身历史与基础 system 提示构建。没有公开接口把某个请求标识为 handoff 请求、指出应作为其参照的普通 dispatch，或在发送前暴露已准备好的侧请求。扩展只能观察会话的请求准备与发送接缝，并从这些接缝携带的信号推断哪次调用属于哪个操作。

remote 能力已经包装会话的流式入口并带有归属检查，以便只还原仍由自己持有的函数。在同一方法上再装一层独立包装会让前一层包装的归属检查失败，remote 对齐随之停止并报告固定原因，而不是没有信号地结束。因此 Handoff 对齐不能作为第二层包装或独立扩展与 remote 并存。两项能力对每个原生方法共用一个包装，并按能力分派。

### 试用证据边界

试用在真实请求上验证了三处接缝与识别集。在 HTTP 响应为本地模拟的探针运行中，它还验证了状态性上下文投影与用户主动切换 thinking 时拒绝改写而不是覆盖，模型没有收到这些请求。它没有验证自动与投机压缩、取消与重试、模型与工具切换、多模态输入及子代理。它的收益数字来自一组请求，服务端共享缓存也无法分离各还原字段的贡献。对齐正确的请求仍可能不命中 Provider 缓存。

## 提议

### 拓展决定

记录 `@ruokee/omp-smart-cache` 是一个力求避免 OMP 请求出现意料之外的缓存未命中、同时保持普通请求与原生请求路径不变的拓展，使用同一个 `omp.extensions` 入口与同一处原生设置来源。该决定承载仍然有效的组件级条款：不导入其他组件的运行时或设置读取器，只容纳第一方能力，OMP 维护下限只通过面向全部 OMP 组件的共同决定调整，`/smart-cache` 是本包的状态命令。

它也记录能力模型：每项优化各有自己的决定、开关与状态；各能力共用包、进程协调器与每个原生方法的唯一包装；按能力分派，不共用规则、载荷形状、原因码或收益证据；一项能力被拒绝或接口缺失不影响另一项。

拓展决定为 `2026-10-12-maintain-smart-cache-extension`，并携带指向归档决定的 `Reverses`。

### remote 决定

remote 决定承载归档决定的仍有效条款：smart-cache 拥有 remote 对齐，包含其 Responses V2 协议规则、Provider 要求、各项边界、公共承诺、替代方案与结果。含义与可观察承诺不变。该决定记录选择本身，不复制组件实现规格；设置与命令参考留在组件文档。

归档决定还反转了[模型提示词决定](../archived/2026-10-07-maintain-qol-model-prompts.zh.md)，该关系随其所属条款一起迁移：新的 remote 决定携带指向归档模型提示词决定的 `Reverses`，后者的 `Reversed by` 字段反向指向它。

该决定为 `2026-10-12-provide-remote-alignment`。

### Handoff 决定

Handoff 缓存对齐成为同一个包的第二项能力，使用同一个 `omp.extensions` 入口与同一处原生设置来源，不需要单独安装、单独包或第二个设置读取器。

公共开关是一个原生设置 `handoffCacheEnabled`，boolean，默认 `false`。它只启用这项能力；remote 保持 `compactionCacheEnabled`、`compactionCacheProvider` 与 `compactionCacheMode` 不变。开关关闭或缺失时每个请求保持原生。不新增 Provider 白名单、模式或第二种配置来源；该开关与 remote 设置在同一激活快照中读取，需要重启生效。

适用性按会话 api 判定，而不是按 Provider 列表：会话模型 api 为 `openai-completions` 时是 Handoff 候选，api 为 `openai-responses` 时仍归 remote，其他 api 两者都不适用。同一请求最多由一项能力接管。

能力把 handoff 侧请求与已经发送的普通请求对齐：在线 system 段、在线 `reasoning_effort`，以及参照没有显式选择时的在线 `tool_choice`。只有当侧请求延长参照的非 system 历史、侧 system 是参照 system 的前缀，且参照仍属于同一会话、模型、api、提示、thinking 状态与工具集时才进行。在该边界内，它在宿主自身 payload hook 之后一次性替换请求体，保持侧指令、新增历史、缓存键、取消信号及其他所有选项不变。某一投影无法还原时只跳过该投影并计数，不放弃整条请求。

只有普通主循环 dispatch 提供参照，且仅在其 HTTP 响应确认发送之后。本能力自己对齐的调用永不成为参照，参照对其所属操作保持不可变，因此较新的在线工作、认证刷新或传输重试都不能移动它。每个会话保留自己的参照，导航、压缩提交与会话释放清空该参照并使该会话的 epoch 失效。

在边界之外，请求原样发送并带固定原因：操作已失效、参照未确认、参照的会话、模型、api、提示、thinking 状态或工具集发生变化，或 system 前缀与历史投影发生变化。`rejected` 表示本能力没有改写该请求，绝不表示请求被阻断、延迟或丢弃。

该能力与 remote 共用包、协调器、逐会话登记与每个原生方法的包装，其他一律不共用。`/smart-cache` 保持单一命令并分段报告两项能力，各自显示状态、分阶段原因与计数；remote 段保持现有文案与字段。本地试用扩展只保留到本能力通过自身验收并获得安装授权为止，该授权随后替换并停用试用扩展；试用扩展仍在自动发现目录时，本包保守报告包装冲突，不抢占任何包装，切换通过重启完成。

该决定为 `2026-10-12-provide-handoff-alignment`。

### 归档决定与入链

remote 决定的语言对以原文件名移入 `archived/`，并加上指向拓展决定的 `Archived` 与 `Reversed by`。同一次变更修复该移动触及的每处链接：仓库其他位置的入链与关系字段、被移动语言对自身指向现行决定的链接（改为 `../decision/…`），以及本提案每语言两处指向被移动决定的链接（改指其归档路径）。语言对互链、指向项目规格的链接与 `archived/` 下的链接保持原形式。

### 项目规格回正

[项目规格](../../spec/omp-smart-cache.zh.md)的语言对采用同一框架：目标段与组件 README 一致，四处 Handoff 排除表述消失，remote 条款保留，规格自身的不变量 1 与不变量 11 保留，相关 ADR 列表指向三份现行决定，自包含含义保留：本包不导入其他组件的运行时或设置读取器。仅移除不变量 12 中的 Handoff 排除句。

在实现变更交付能力之前，规格不声明任何 Handoff 行为。该实现变更回正规格、创建 Handoff 决定、更新组件双语文档，并把组件版本递增一个 patch 位。

### 落地顺序

提案单独合入 `main`。其后进行的合同变更创建拓展与 remote 决定、把现行决定语言对移入 `archived/`、修复该移动触及的链接与关系字段（含本提案自身）；它不链接尚未创建的决定，也不触碰项目规格与组件。交付能力的实现变更创建 Handoff 决定、回正项目规格、更新文档，并移除被消费的本提案。Git 历史保留本提案作为已独立合入的理据。

## 考虑过的替代方案

- **作为独立包或第二个扩展交付 Handoff 对齐。** 在选择归属时考虑。它保持 remote 包不被触碰，但宿主每个接缝只暴露一个方法，而 remote 能力的归属检查会拒绝外来包装，因此独立包装会让 remote 对齐停止并报告包装冲突。它还会重复本包已有的登记、生命周期处理与诊断。
- **只保留本地试用扩展。** 作为现状考虑。它在本机已能对齐手动 handoff，但留在仓库之外，没有设置、没有逐会话隔离、没有未覆盖路径的验收证据，也没有发布流程。
- **以 `## Changes` 段追加 handoff 决定并让 remote 决定保持现行。** 在选择合同形式时考虑。增加该能力不与生效的 remote 规则冲突，因此这种形式可用。它被否决，是因为现行决定仍以 remote 对齐为主题，仍保留把 Handoff 放在别处的条款，不会产生归档关系，而项目规格的框架、目标段与不变量 12 会继续描述一个比其当前行为更窄的组件。
- **把 Handoff 对齐并入 remote 的 V2 复用规则。** 在选择能力边界时考虑。Handoff 与 remote 对齐的是不同形状的请求，遵循不同的协议规则，现行 remote 决定也已经排除把其 V2 规则用于 Handoff。合并成一套规则要么丢掉 remote 的 Provider 专属检查，要么把这些检查用于并非为其而写的请求。
- **以整条请求相等作为改写闸门。** 在选择本能力拒绝什么时考虑。要求侧请求在每个字段都与参照相同，是试用后期版本的做法，会因任一无关字段差异放弃整条改写，并掩盖是哪一投影失败。所选形式保留安全与归属检查，按轴还原，并计数无法投影的差异。
- **像 remote 一样要求精确 Provider 名称。** 在定义开关时考虑。remote 需要 Provider 名称，是因为 V2 的 opaque 数据、裁剪与路由语义随 Provider 变化。handoff 只依赖 chat-completions 形状，并把参照绑定到同一会话、模型、提示与工具集，因此 Provider 键只会增加配置面与第二份 Provider 清单，不增加保护。改为由组件文档声明验证矩阵与缺口。

## 验收标准

1. 存在三份现行双语决定：`2026-10-12-maintain-smart-cache-extension` 与 `2026-10-12-provide-remote-alignment` 在合同变更后存在，`2026-10-12-provide-handoff-alignment` 在实现变更后加入。每对符合决定格式，拓展决定携带指向归档 remote 决定的 `Reverses`，合同变更的两份决定都不链接当时尚未创建的决定。（两次变更）
2. 归档的 remote 决定语言对保持原文件名，并携带指向拓展决定的 `Archived` 与 `Reversed by`。新的 remote 决定携带指向归档模型提示词决定的 `Reverses`，后者的 `Reversed by` 字段把原先指向被归档语言对的条目改指新 remote 决定并保留其余条目，因此移动前记录的每次反转仍由现行决定记录。（合同变更）
3. 归档决定的每项仍有效条款都出现在拓展决定、remote 决定或 Handoff 决定中，含义与可观察承诺不变；Handoff 面向的条款（不把 remote V2 规则用于 Handoff、试用扩展的替换条件）随 Handoff 决定在实现变更落地；合同变更的两份决定可以复述这些条款，但其落点必须是 Handoff 决定。没有条款丢失，也没有条款被复制为实现规格。（两次变更）
4. 没有受版本控制的仓库文件链接指向被移动路径，且被移动语言对自身的链接在其新目录中可解析。`.tk/` 下被忽略的任务材料保留其自身引用，由各自任务维护。这包含本提案自身指向被移动决定的链接，同一变更把它们改指归档路径。归档的模型提示词决定的 `Reversed by` 字段、宿主下限与 OMP 体验文档指向现在拥有被引用合同的现行决定；宿主兼容规格的相关决定列表指向拓展决定并保留其余条目。（合同变更）
5. 项目规格的语言对采用该框架：目标段与组件 README 一致，四处排除表述消失，remote 条款保留，规格自身的不变量 1 与不变量 11 保留，仅移除不变量 12 的 Handoff 排除句，相关 ADR 列表指向三份现行决定并保留模型提示词、共享下限与自包含条目，宿主兼容规格的相关 ADR 列表同样指向三份现行决定，且规格只声明同一次变更实际交付的 Handoff 行为。（实现变更）
6. remote 的规则、可观察承诺、状态输出与收益证据不因本次重构改变。（合同变更）
7. Handoff 决定记录该能力的归属、`handoffCacheEnabled` 开关及其 `false` 默认值、相对 remote 的独立性、不把 remote V2 规则用于 Handoff，以及试用扩展的替换条件。（实现变更）
8. 该能力自身的验收保持 handoff 对齐所要求的内容：开关关闭时每个出站请求与原生请求相同；实际出站 handoff 请求的 wire body 携带三项还原后的投影；无关字段差异不放弃改写；边界之外的请求原样发送并带固定原因；不阻断、延迟或丢弃任何请求；同一会话连续两次 handoff 不复用上一次侧请求体；`/smart-cache` 报告该能力自身的状态；另行授权的可比真实 Provider 运行重复观察到未缓存输入下降，同时生成的文档与压缩后续接保持正确；试用扩展被移除，受维护能力在重启后加载。（实现变更）
9. 提案在实现开始前单独合入。拓展与 remote 决定及归档移动落在合同变更；Handoff 决定、项目规格回正、组件文档与被消费提案的移除落在实现变更。（流程）
10. 最终候选干净、已提交、包含目标 `main`，并通过仓库完整检查。（合入候选）

## 风险

- 条款在决定之间迁移时可能丢失含义，使仍然有效的边界或承诺读起来更弱，或使关系字段指向一份不再承载该反转选择的决定。逐条对照归档文本复核与验收标准 3 是防护手段。
- 被忽略的入链会继续把归档决定呈现为现行权威，使读者或 Agent 依据已被取代的范围行动。仓库检索、链接检查与验收标准 4 是防护手段。
- 把合同变更与实现变更分开使提前回正规格成为可能：规格在组件尚未承载该能力时把它声明为组件的一部分，即描述了并不存在的行为。落地顺序与验收标准 5 把该项回正留在实现变更。
- 试用扩展与受维护能力可能包装同一批会话方法。若在移除试用扩展前启用开关，一层包装可能丢掉另一层，对齐随之停止并报告包装冲突，或形成包装循环重复同一次改写。保守冲突报告与基于重启的切换能限制这一点，但用户仍可能同时安装两者。
- 宿主按自身快照构建 handoff 侧请求。宿主改动该路径会使参照不再匹配，本能力随后要么拒绝、按固定原因报告并失去收益，要么在边界检查过松时还原宿主对该请求已不再意图的 system 提示或 tool choice，产出错误或截断的交接文档。实现前探测宿主路径并保持严格前缀与归属检查是防护手段。
- 对齐请求不保证命中 Provider 缓存，且观测到的收益只来自一组请求。本能力可能增加维护却不复现收益，因此发布判据是它自身获授权的测量，而不是试用数字。
- 同一协调器内的两项能力可能互相干扰。为 handoff 做的改动可能改变共享包装、逐会话生命周期或 remote 的诊断，使 remote 退化随 handoff 改进一起发布。原样搬移 remote 规则并在发布前重跑 remote 验收是防护手段。
- 把在线 system 提示与 tool choice 还原进宿主为生成文档而构建的请求，可能使模型调用工具而不产出文本，宿主随后提取文档失败。本能力不执行工具也不增加重试，该失败会表现为宿主自身的空文档错误。

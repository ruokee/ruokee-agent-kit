# 移除 omp-codex-web-access 扩展

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-15-remove-omp-codex-web-access.md) | 中文

## 动机

从仓库移除 `@ruokee/omp-codex-web-access`，并归档保留它的决定。

该扩展注册 `codex_web_search` 与 `codex_web_fetch`，通过 OMP 的 `openai-responses` API 访问转发 Provider 的模型，并用 OMP 原生插件设置中的五个键配置它们。[Codex 网页访问使用原生插件设置](../decision/2026-09-10-use-codex-web-plugin-settings.zh.md)维护该包、它的两个工具、设置合同、激活行为与模型执行。

组件自 2026-10-08 起在其 README 与仓库 README 中标记为即将弃用。维护者报告近期 OMP 版本可用托管网页搜索访问转发 Provider 的模型，而这正是 `codex_web_search` 覆盖的路径；在该路径可用时，该工具与宿主能力重复。页面提取没有原生等价物，当时的弃用标记也不是删除它的计划。

维护者现在移除该组件，并接受两个工具随之消失。页面提取不迁移到其他组件、OMP 设置或宿主配置，也不计划替代物。

移除该组件还会改动仓库的记录：spec 层、两份根 README、`docs/installation`、改动路径检查配置，以及三条陈述该组件当前角色或引用其设置条款的现行决定。

## 分析

该组件没有发布渠道。安装实例都来自本仓库，或复制进 OMP 插件目录，或链接到该目录。复制安装在仓库不再承载该组件后仍可运行，链接安装会在其指向的目录消失后失效。两者都不是已发布的发行物，因此本次移除不需要自己的迁移路径。

两条现行决定与一份现行 spec 把该已归档决定当作现行权威引用。[维护提高 OMP 使用体验的拓展](../decision/2026-10-10-maintain-omp-experience-extension.zh.md)与[在 smart-cache 中提供 remote 对齐](../decision/2026-10-12-provide-remote-alignment.zh.md)把它的 `### Native settings` 段当作「组件如何读取 OMP 插件设置」的现行权威；它们依赖的条款说明 OMP 拥有设置文件、用户与项目作用域的合并以及 getter，并非该组件特有。QoL spec 把它列入该 spec 背后的决定。现行文档不得把已归档的决定当作现行权威引用，因此该条款需要一个在归档之后仍然存在的去处，该 spec 的列表也需要一个现行的条目。

已归档决定的其余内容都限定在该组件范围内：两个工具、设置键、激活、迁移规则与模型执行描述的都是移除之后不再存在的行为。

## 提议

### 要取代的决定

以下生效条款不能与本选择并存：

| 现行决定 | 生效条款 | 提议选择与冲突 |
| --- | --- | --- |
| [Codex 网页访问使用原生插件设置](../decision/2026-09-10-use-codex-web-plugin-settings.zh.md) | 仓库在 `projects/omp-codex-web-access` 维护 `@ruokee/omp-codex-web-access` 包，含两个工具、原生设置键、激活行为、迁移规则与模型执行 | 组件及其仓库内容被删除，两个工具都不被替代。维护组件的决定与删除组件的决定不能并存，因此该维护条款不能留在决定里。 |

本次取代只改动表中的条款。该决定的其余内容都限定在组件范围内。

删除 `projects/omp-codex-web-access`，并让仓库的现行记录与移除一致：列出该组件的文档、改动路径检查配置，以及 spec 层（含 QoL spec 相关决定列表中的设置决定条目）。

把移除记录进一条带 `Reverses` 的决定，并归档上面的决定，加 `Archived` 与 `Reversed by`；它现有的指向[添加 OMP Codex 网页访问组件](../archived/2026-09-06-add-omp-codex-web-access.zh.md)的 `Reverses` 保留。后续决定只记录移除，不重述组件的设置合同。引用已归档决定的两条决定在自己的正文里陈述它们所依赖的内容，并保留各自已有的选择；这些改动属于编辑性维护，不新增 `## Changes` 条目。

设置决定的两份语言文件一起移动会让所有指向其原路径的相对链接失效。同一变更一并修正它们：添加决定里的 `Reversed by`、以及已归档的 QoL 与 smart-cache 决定里的历史出处都只改路径、保留内容，因为归档记录在其链接修好之后即冻结。

[宿主内组件按共同的 OMP 下限维护](../decision/2026-10-04-raise-omp-host-floor.zh.md)在面向 OMP 组件清单中列出该组件，并在陈述其下限处链接设置决定。该组件从清单中去掉，该链接随之去掉。这些改动不影响该决定的选择，也就是其余组件共用一个下限，因此是事实性维护而不是一次取代，变更按该决定已有的做法，追加一条带日期的 `## Changes` 条目（与 smart-cache 时相同）。

本次移除不提供兼容层、迁移指引或替代组件。不发布、不标记弃用、也不下架任何包，因为没有发布渠道。已归档的决定与 Git 历史保留对它的提及。

## 考虑过的替代方案

**保留组件目录但停止维护。** 在需求澄清阶段决定如何退役该组件时考虑过。组件清单与所有引用点保持不变，但仓库会继续为一个已无用途的组件保留条目，「即将弃用」状态也会在没有删除日期的情况下继续悬置。

**保留组件以维持页面提取，只移除搜索工具。** 在需求澄清阶段判断页面提取是否需要去处时考虑过。这样可以保住宿主不提供的那个工具，但仓库会为一个工具继续维护该组件、它的检查与文档。

**把页面提取能力迁到其他组件或 OMP 配置。** 在判断剩余行为是否需要去处时考虑过。这样可以保留下该能力，但本次移除是有意放弃页面提取，迁移会为一个维护者选择不保留的能力带来新的维护面。

**不走 ADR 提案流程，把移除当作普通改动实施。** 在判断移除是否需要走 ADR 流程时考虑过。这样省掉提案与归档，但一条现行决定会继续维护一个已不存在的组件，决定链条也会失去它被移除的原因记录。

**保留本机安装，只移除仓库内容。** 在需求澄清阶段决定移除范围时考虑过。这样只删除仓库副本，但链接安装会指向一个已删除的目录。

**把设置条款写成后续决定里的通用段落，适用范围隐含。** 在决定该条款归档之后的去处时考虑过。这样插件设置合同保留一处出处，但查找「组件如何读取设置」的读者会在一条移除决定里找到该规则，还得自行推断它覆盖哪些组件。

**把设置条款写成后续决定里的通用段落，并写明适用范围。** 作为保留单一出处的另一种做法考虑过。这样既保留出处又明确了适用范围，但移除决定会带上一条与移除无关的条款。

**为原生插件设置合同另立一条决定。** 作为该条款的第三种去处考虑过。这样每条决定只讲自己的主题，但会扩大本次变更超出移除的范围，而新决定的唯一主题是使用该合同的组件已经自行陈述的内容。

## 验收标准

- `projects/omp-codex-web-access` 不存在，除已归档决定、其他历史记录与 Git 历史之外，仓库中不再有文件引用该目录或该包。
- spec 层不列出该组件：其 spec 对已删除，spec 列表没有它的条目，宿主兼容清单与链接不再列出它，QoL spec 的相关决定列表也不再列出该设置决定。
- 除移除决定必需的 `Reverses` 链接之外，没有现行决定或 spec 把已归档的设置决定当作现行权威引用，QoL spec 的相关决定列表指向陈述该设置合同的扩展决定。
- 指向该设置决定的相对链接全部可达：添加决定的 `Reversed by` 与已归档 QoL、smart-cache 决定中的历史出处指向归档后的路径，且内容不变。
- 两份根 README、`docs/installation` 及其中文副本、改动路径检查配置不再列出该组件，其余清单条目编号保持连续，仓库检查通过。
- 移除决定带有 `Reverses`；设置决定位于 `archived/`，带 `Archived` 与 `Reversed by`，并保留它已有的 `Reverses`；引用它的两条决定不再引用它，并保留各自已有的选择。
- 宿主下限决定不再列出该组件，也不再链接设置决定，且一条带日期的 `## Changes` 条目记录了这次更新。

## 风险

- 漏改一处引用会让仓库继续描述一个不存在的组件，或指向一个已经移动的决定。spec 列表、宿主兼容清单、根 README 的清单编号与归档链接是最容易漏掉的地方。
- 把设置条款写在两条决定里，两份副本会分叉，读者会照着一个与另一份不再一致的规则行事。
- 复制安装在仓库不再承载该组件后仍会运行，后续某次宿主变更可能让它无声失效，而用户仍以为两个工具在维护中。

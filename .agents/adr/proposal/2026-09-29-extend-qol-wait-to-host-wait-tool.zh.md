# ADR 提案：将 omp-qol 等待调整扩展到宿主的现行 wait 工具

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-09-29-extend-qol-wait-to-host-wait-tool.md) | 中文

## 动机

请求维护者批准把 omp-qol 的等待调整绑定到宿主内建 `wait` 工具的契约。

[projects/omp-qol](../../../projects/omp-qol/README.zh.md) 的等待调整给一次等待调用一个可配置的总期限，并在原生窗口没有带来新信息时把这次调用继续下去。它挂载在内建 `hub` 工具上。本次升级目标范围内的宿主版本不再提供这个工具，于是该调整在这些宿主上保持停用，用户同时失去可配置期限与空窗口合并；同一个扩展在仍有 `hub` 的宿主上则继续提供这两项能力。

目标宿主确实提供了等待工具，但把调整绑定到它需要单独说明契约：该工具不接受参数、不提供组件设置所描述的路由，也不暴露配置入口。契约说明包装器绑定哪一个入口、新增的一个参数表示什么，以及哪些配置行为在那里适用、哪些不适用。

## 分析

目标宿主的等待工具不接受参数，一次调用的上限是固定的；调用在被监视的任务完成、收到对等方消息、用户 steer 或中断，或达到上限时结束（见[等待工具源码](https://github.com/can1357/oh-my-pi/blob/v18.4.3/packages/coding-agent/src/tools/wait.ts)）。会话自有运行中任务的快照把任务放在非空的 `details.jobs` 集合里，因此仍在监视这类任务的调用可以与其他结果区分开。

其余结果共用同一种形状。空 `jobs` 集合加上同一个标记，既覆盖「没有可等待对象」，也覆盖消息窗口耗尽；服务完成与达到上限也使用同一个空集合，只在正文上不同。因此任务快照是可用的继续判据，消息或服务帧不是；要区分后者就必须匹配宿主正文，而本组件不做这种匹配。

目标宿主通过 Internal URLs 暴露进程控制，包括状态、stdin、mode 与 kill，但没有命名进程等待操作（见 [proc 协议](https://github.com/can1357/oh-my-pi/blob/v18.4.3/packages/coding-agent/src/internal-urls/proc-protocol.ts)）。配置的命名进程期限在该宿主上没有入口。

## 提议

### 按能力选择入口

模块继续以该工具自己的名字重新注册宿主的等待工具，并通过扩展 API 委托每一次调用。它依据会话实际暴露的入口选择，而不是依据宿主版本：会话暴露内建 `hub` 时走既有路径且行为不变，没有 `hub` 但暴露内建 `wait` 时走新路径。两者都不存在，或候选入口已被其它扩展替换，或其参数结构不符合已核对契约时，模块保留宿主原有行为，通过既有诊断通道报告一个有界原因，且不声称该调整已生效。

### 新路径上新增的一个参数

新路径上工具保留原名，并新增一个可选数字参数 `timeout`，单位为秒，表示这一次调用的总期限。取值范围与组件已经为其期限设置说明的范围一致：大于 0 且不超过 3600 的有限数值。不新增操作、选择器或不存在的参数。委托调用只携带原生 schema 声明的参数；外层参数不会被转发。

### 期限来源与配置适用性

`waitJobsSeconds` 在两条路径上都是任务等待或混合等待的缺省期限，显式 `timeout` 覆盖它。`waitMessagesSeconds` 与 `waitProcessSeconds` 在 `hub` 路径上保持原义，在新路径上没有等价物，因为该入口既不提供消息路由选择器，也不提供命名进程等待。`waitEnabled` 与 `waitContinueEmptyWindows` 在两条路径上保持原义；关闭调整时两条路径都回到宿主自身行为。

组件在 `/qol` 与自身文档中按入口说明这些差异，而不是显示一个没有被读取的配置值。

### 继续一次调用与结束一次调用

只有返回帧确定没有新信息时才继续：帧中的自有任务全部仍在运行，且没有结果、消息、错误、取消或中断。这类快照不算结果：在总期限还允许时它进入下一个原生窗口，宿主自身上限结束的窗口也一样。

宿主自己交付的内容保持宿主语义。真实结果、已投递消息、错误、用户中断与调用方取消都按其自身原因返回，取消不会被报告为组件的期限。

只有组件自己的总期限归组件报告。它到达时包装器中止仍在执行的原生窗口，并返回自有的有界期限结果：见过确定的空窗口时带上该窗口，再加一段说明，指出已流逝的期限与当前宿主上确实存在的入口；没有见过时只带这段说明。被中止的窗口若仍然交付了结果，该结果原样返回，期限不会替换宿主已经产出的信息。到达期限只结束这一次调用：后台任务与进程继续运行。

### 新路径不提供的能力

在一次调用内合并纯消息空窗口、按路由使用 `waitMessagesSeconds`、为命名进程等待填入 `waitProcessSeconds`，以及跨原生上限合并只等待 service 的窗口，在新路径上保持暂不支持。它们各自报告为暂不支持，而不是报告为已启用或未启用；也不通过状态轮询循环或宿主正文分类来模拟。

### 兼容边界

兼容对象是扩展，不是宿主。组件不要求宿主增加可配置的上限或路由选择器，不把新工具及其参数回移到没有它的宿主，也不提高任何维护下界。旧宿主保留既有实现与完整配置。

### 与现行决定的关系

[在 OMP 宿主升级中维护 OMP 生活质量调整](../decision/2026-09-28-maintain-omp-qol.zh.md)没有任何条款与本契约冲突。该决定规定等待模块重新注册原生工具、委托每一次调用、只在结果确定没有新信息时继续调用、不新增操作、转发宿主的审批等级与可中断性，并且不声称拥有它未收到的结果。这些在本提案中都没有改变：参数不是操作，承载该调整的入口由会话决定，而不是由决定固定。该决定中提到旧入口的文字只是描述性的，出现在动机与范围段落的模块名称里；具有约束力的条款与具体入口无关。

因此，提案获准后按该决定的 `## Changes` 章节追加新内容记录，并同步组件的 README、其调整文档、状态输出与检查。[让第一方宿主组件适配宿主升级](../decision/2026-09-28-adapt-components-to-host-upgrades.zh.md)是本次适配的规则依据，本身不需要改动。

## 考虑过的替代方案

**把上限留给宿主。** 在决定是否要越过宿主单次调用上限去实现总期限时考虑过。只做委托而不设外层期限，或退役该调整、让模型在原生上限后重新调用，都不需要新增参数与继续判据，但该宿主上没有可配置期限与空窗口合并，而且每次达到上限都要多一次模型调用。

**复制或重建宿主的等待工具，或直接接入其任务与消息通道。** 在判断组件可以让渡多少等待控制权时考虑过。这样可以覆盖消息与 service 路由，但会把任务、消息与结果的所有权转移给组件，而现行决定把这些留在宿主。

**用宿主写入的通用空帧标记判断是否继续。** 在寻找继续判据时考虑过。该标记同样覆盖消息窗口、没有可等待对象以及部分中断，使用它的包装器会把协作提示或已完成的 service 等待吞掉，而不是交回调用方。

**按宿主版本比较来选择入口。** 在决定如何选择入口时考虑过。版本比较会拒绝掉实际具备所需能力的宿主，并且每次发行都需要维护；现行升级决定已经把版本范围排除在资格判断之外。

## 验收标准

1. 暴露内建 `hub` 入口的会话行为与今天一致：同样的设置、同样的路由、同样的继续行为、同样的期限结果。
2. 暴露内建 `wait` 入口且没有 `hub` 的会话由扩展注册等待工具，其模型可见定义携带可选的秒数参数 `timeout`，委托调用只携带原生 schema 声明的参数。
3. 不带 `timeout` 的调用使用 `waitJobsSeconds` 缺省值，带范围内 `timeout` 的调用使用该值，超出范围的值是参数错误而不是静默截断。
4. 真实结果、已投递消息、错误、用户中断与调用方取消都保持宿主自身的原因，不会被报告为组件的期限；全部仍在运行的任务快照在总期限还允许时进入下一个原生窗口，宿主自身上限结束的窗口也一样。
5. 到达总期限时返回包装器自有的有界期限结果：见过确定的空窗口时携带该窗口，否则只带期限说明，并指出已流逝的期限与当前宿主上存在的入口；它只结束这一次调用，被中止的窗口若仍交付结果则该结果原样返回。
6. `/qol` 与组件文档说明实际采用的入口，以及在该入口上不适用的配置键；暂不支持的细分能力读起来是暂不支持，而不是已启用。
7. 入口依据会话实际暴露的内容选择。不读取宿主版本来决定资格、启用、行为或诊断；陌生或无法识别的入口保留宿主原有行为，并给出一个有界原因。
8. 实机会话中，最终下发的工具定义携带新增参数，超出单次原生调用时限的任务通过一次外层调用拿到结果，取消与到达期限可以区分，期限前后由宿主交付的结果原样返回。
9. 组件版本、中英文文档与检查随本次批准的改动同步变化。

## 风险

- 继续判据比宿主实际报告的范围窄。宿主版本一旦改变任务详情结构，或报告本组件无法识别的情形，调用就会提前结束：用户继续看到本该被配置期限合并掉的等待调用，而工具仍在注册，调整仍显示为已启用。
- 一个模块保留两条入口容易产生漂移。后续针对继续判据、期限结果或审批转发的改动只落在其中一条路径上时，两个受维护的宿主会出现不同行为，且没有任何报错。

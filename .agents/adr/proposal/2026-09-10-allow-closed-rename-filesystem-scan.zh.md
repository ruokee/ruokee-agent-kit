# ADR 提案：允许 closed Task 重命名并按文件系统扫描引用

Decision owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

[English](./2026-09-10-allow-closed-rename-filesystem-scan.md) | 中文

## 动机

[现行数据模型决定](../decision/2026-09-08-repair-names-through-tk-rename.zh.md)让 rename 负责修复损坏名称和生成式目录后缀，同时让 closed Task 保持只读。两条规则组合后没有出路：rename 拒绝 closed Task；重新打开又走不通，因为严格加载在处理生命周期分支之前就以旧名称损坏为由拒绝。名称损坏的 closed Task 没有任何公开恢复路径，`check` 也只能继续报告损坏而不修复。

同一决定让 `track` 引用扫描从索引枚举 Git 跟踪的 Markdown。已存在于工作树但尚未加入索引的文件永远不会被扫描；索引仍有记录、文件已不在工作树的条目又会让整个扫描在 dry-run 或执行开始前失败。引用报告应当描述用户实际保留的文件，而不是工作树的暂存状态。

重新打开是需要原因和授权的生命周期变更。恢复名称属于维护操作：UUID 是身份，名称只是可变描述。closed Task 应当与其他 Task 一样获得名称维护，无需改变生命周期状态。

## 提议

### 允许 closed Task 重命名

`tk rename` 与 `tk_exec rename` 用与其他 Task 相同的精确引用形式接受 closed Task。普通改名、已有字符串名称的修复，以及可识别生成式目录后缀的修复都被允许，操作后 Task 保持 closed。不新增参数或确认标志，也不要求临时重新打开。

修复范围保持不变：字符串名称不规范、为空、规范化后为空，或超过当前显示宽度限制，以及后缀与元数据不一致的可识别生成式目录。范围之外保持严格：名称缺失、字段类型错误、载体不可解析、标记缺失、schema 不受支持、身份损坏、不安全路径和无法识别的生成式结构仍然报错。新名称和最终路径保留完整校验。目标冲突、Git 策略、活动操作标记和写入前的当前状态复核等既有写保护保持原行为。

`update` 与重新打开保持严格的名称加载。rename 是恢复路径；恢复规范名称后，需要继续编辑的 closed Task 可以重新走普通 reopen 流程。

### 保持引用扫描与断链保护一致

每次 rename 都会构建计划并扫描、报告 Markdown 引用，包括只改元数据、不移动路径的请求，以及最终无任何变化的请求。dry-run 和执行结果都包含引用列表，rename 从不改写引用。

断链保护保持现有条件：会移动 Task 路径的执行在发现旧路径引用且未收到 `--ignore-brokenlinks` 时，在首次写入前以 `broken_reference_conflict` 停止。不移动路径的 rename 不会触发该拒绝。`--ignore-brokenlinks` 仍然允许移动且不改动引用文件，错误详情与成功结果仍列出每个引用。

### 按文件系统枚举引用候选

引用候选通过遍历实际文件系统获得：

- `git_policy=track` 扫描项目范围内的普通 Markdown。
- `ignore` 或 `none` 扫描 Task 根目录下的普通 Markdown。

遍历沿用当前遍历顺序和安全规则：排除符号链接、tk 自有运行时路径（WAL 目录和 `.tk-tmp`）和 Git 管理目录；遇到固定资源上限时显式失败，不返回部分列表。扫描开始时已不存在的文件不会是候选，索引残留不会让请求失败。现存的 Markdown 文件无论是否被跟踪都会参与，暂存和提交状态不改变结果。

遍历或读取过程中的必要 I/O 失败仍然是显式错误。dry-run 和 `--ignore-brokenlinks` 不得在扫描无法完成时报告扫描成功。

Git 策略保持当前范围和时机：只在持久写入前运行，检查项目根目录整体（`track` 要求受管 Task 文件不被忽略，`ignore` 要求 Task 根目录被忽略，`none` 不调用 Git 命令），不按目录或文件筛选引用候选。读取与 dry-run 不做策略检查。

### 修正现行合同

本提案与[现行数据模型决定](../decision/2026-09-08-repair-names-through-tk-rename.zh.md)中的两条规则冲突：closed 只读规则，以及 `track` 扫描的索引来源。两者通过 ADR 流程反转。该决定的其余规则继续有效：修复范围、精确引用形式、保留字段与 WAL 追加、目标与策略检查、dry-run 语义，以及报告引用而不改写。

替换决定必须承接现行决定仍然有效的规则，包括其更新条目。提案阶段现行决定保持不变。

## 考虑过的替代方案

**要求先重新打开再 rename。** 这样能保住 closed 只读规则，但无法作为恢复路径：reopen 要求损坏的旧名称通过严格加载，而这正是待修复的缺陷。它还会把名称维护变成需要原因和授权的生命周期变更，却不改变任何生命周期事实。

**把 closed rename 限制在损坏名称修复。** 这会继续拒绝 closed Task 的普通名称更正。区分修复与普通改名会给同一请求增加第二套分类，同时仍然阻塞合法更正；规范名称的维护价值不取决于旧名称因何出错。

**保留 Git 索引枚举并容忍缺失文件。** 跳过文件已消失的条目可以消除失败，但扫描仍会漏掉现存的未跟踪 Markdown，仍依赖暂存状态。按目录或按路径查询 Git 只是把同一依赖扩散到每个候选。

## 验收标准

1. 通过 CLI 与 `tk_exec rename`，split 与 embed 中的 closed Task 均可重命名。普通改名与损坏名称或生成式后缀的修复都成功，Task 保持 closed，UUID、状态、正文、关系、`extra`、创建时间、现有 WAL、日期、序号和父级位置不变。dry-run 不写入。
2. closed Task 的生成式目录后缀修复会按修复后的 slug 移动目录，身份与父子归属不变，移动的断链行为与其他任何 Task 一致。
3. 每次 rename 请求都扫描并报告引用，包括仅元数据变更和 no-op 请求。no-op 返回 `changed: false`、报告扫描到的引用并且不写入。
4. 引用候选跟随文件系统。`track` 报告项目范围内现存 Markdown 的引用；`ignore` 与 `none` 报告 Task 根目录内的引用。扫描前已删除的文件不会导致失败，现存的未跟踪 Markdown 会参与，暂存或提交状态不改变结果。
5. 断链保护不变：有引用且未传 `--ignore-brokenlinks` 的路径移动执行会在首次写入前以 `broken_reference_conflict` 停止；dry-run 报告计划且不写入；`--ignore-brokenlinks` 完成移动并保持引用文件字节不变。
6. 扫描期间的必要 I/O 失败（权限、编码或扫描中途消失的文件）会显式报告。dry-run 与 `--ignore-brokenlinks` 绝不会把不完整的扫描报告为成功。
7. 既有安全校验仍然拒绝不安全的 rename：重复 UUID、字段类型错误、关系损坏、不安全路径、目标冲突和 Git 策略失败保持当前行为。
8. `update` 与重新打开保持严格名称校验，CLI 与 exec 保持当前参数、结果形状和合同版本。

## 风险

closed Task 的重命名会移动已完成的工作。扫描范围之外的引用，例如其他项目、导出文档或非 Markdown 文件，不会被报告，外部链接可能悄悄失效，而 Task 表面仍然稳定。

更宽的文件系统遍历可能纳入生成内容或无关 Markdown。恰好包含旧路径字符串的构建产物可能让合法移动触发 `broken_reference_conflict`，把调用方推向 `--ignore-brokenlinks`，从而削弱该参数所绕过的保护。

带有大型第三方或生成 Markdown 目录树的项目会扫描比索引枚举更多的内容。触及固定资源上限会让请求失败，rename 在此类项目中可能暂时不可用。

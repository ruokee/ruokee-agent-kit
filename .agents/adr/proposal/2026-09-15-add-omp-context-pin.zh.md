# ADR 提案：添加 omp-context-pin 扩展

Decision owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

[English](./2026-09-15-add-omp-context-pin.md) | 中文

## 动机

运行到触发压缩的长会话，需要把少量细节逐字保留下来：约定好的接口、文件结构说明、必须按原文执行的命令。压缩会摘要历史，而摘要可能缩短或改写这些内容。事后要求模型自行复现原文同样不可靠。

OMP 实验性的 `context_notes` 为每个分支保存一整本笔记，并按当前路径恢复。它提供整本替换而非条目级操作，上下文构建会把最新笔记插在消息数组开头。编辑这个块会改动请求的靠前部分，缩短可复用前缀。条目级 Pin 操作需要不同的放置策略。

仓库已经分发第一方 OMP 扩展包。本提案采用相同的组件形式，以公开扩展 API 为目标。文中宿主行为的源码核对基线为 [OMP 18.1.16 的固定提交](https://github.com/can1357/oh-my-pi/tree/61b1b8aef634334eaf1412afd003a763e1d1b9c1)，包括 [context notes](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/tools/context-notes.ts) 和[会话上下文构建](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-context.ts)。源码核对确认了下文的持久化障碍，不代表实机验收通过。

## 提议

### 组件与范围

按[第一方能力边界](../decision/2026-08-20-establish-first-party-capability-kit.zh.md)和[组件自包含契约](../decision/2026-08-24-keep-components-self-contained.zh.md)，在 `projects/omp-context-pin/` 添加第一方包 `@ruokee/omp-context-pin`。该包通过 `package.json` 的 `omp.extensions` 元数据声明扩展入口，运行时、检查以及双语 `README.md` 和 `README.zh.md` 都位于组件目录内，并且只使用公开的 OMP 扩展 API。它不导入宿主私有模块，不修改上游源码或已安装的二进制，也不依赖其他仓库组件中的文件。

该包只注册一个斜杠命令 `/ctx-pin` 和一个原生工具 `ctx_pin`。`/pin` 是内置保留命令名，用于切换会话在恢复列表中的置顶状态，OMP 会过滤重用保留名的扩展命令并记录冲突警告，因此本扩展使用不同名称。

`/ctx-pin` 打开当前分支的条目列表，提供创建、查看、编辑和删除。多行正文使用宿主的编辑对话框。`ctx_pin` 通过 `action` 参数分发：

| action | 作用 | 主要输入 |
| --- | --- | --- |
| `list` | 列出当前条目及其 id、标题、来源、revision 和体积 | 无 |
| `get` | 返回完整正文及其 id、来源、revision 和体积 | `id` |
| `create` | 固定一段新的文本正文 | `content`，可选 `title` |
| `update` | 替换已有正文 | `id`、`content`、`expectedRevision` |
| `delete` | 取消固定条目 | `id`、`expectedRevision` |

schema 保持稳定，不枚举当前条目。工具使用 `loadMode: "essential"`，使已启用的 `ctx_pin` 保持在顶层工具清单中。Pin 操作不改变工具定义。`update` 和 `delete` 要求已有的 `id` 以及调用者观察到的 revision。未知 id 或 revision 不匹配时拒绝写入。任何 action 都不执行隐式 upsert 或改名式的创建。空正文被拒绝；已接受的正文保留空白和字符，不做 trim 或规范化。

Pin 的含义是：条目的正文以原文形式持续出现在当前会话分支的后续普通模型请求中，直到该条目被更新、取消固定，或分支上下文被重置。压缩不结束 Pin；每次提交后的压缩都会从扩展自身的记录中恢复正文。

更新与删除立即改变有效集合。已经发布的旧正文可以继续留在历史中，直到压缩将其归并到新的基准快照。条目 id、revision 和删除记录表达哪些内容仍然有效。下一份快照只包含最新的活跃正文，不包含已删除条目。

首版固定由用户或 Agent 提供的文本正文。它不读取文件、不抓取 URL、不监听内容变化，也不固定任何在没有操作的情况下就会变化的正文。

### 规范状态

规范状态是会话日志中的追加式操作日志，通过 `appendEntry` 以自定义类型 `omp-context-pin` 写入。每个被接受的写操作追加一条记录：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 记录的载荷版本 |
| `operationId` | 一次调用的稳定身份，重试时保留，也用于匹配投影 |
| `action` | `create`、`update` 或 `delete` |
| `entryId` | 条目身份，创建时分配且不再复用 |
| `revision` | 从 1 开始，每次被接受的更新或删除递增 1 |
| `body` | `create` 和 `update` 的完整新正文 |
| `source` | `user` 或 `agent`，记录由哪个入口写入 |
| `title` | 创建时可选的列表标签，正文更新时保留 |

有效集合通过 `getBranch()` 读取当前分支，按时间顺序重放其最近一次 `reset_boundary` 之后的记录计算得出。创建记录确定条目展示的来源，后续操作的作者不会改变它。`list`、`get`、正文未变化的 `update`、被拒绝的操作以及容量检查失败都不追加记录。先校验身份和 revision，再判断 no-op。

一次 UI 提交或一次宿主工具调用身份对应一个固定的 `operationId`。重试已接受的调用时返回其回执，不追加第二次操作。新的 `create` 调用创建独立条目，即使正文与其他条目相同。交付重试复用已接受操作的身份。

操作被接受意味着它已出现在宿主的内存分支日志中。公开的 `appendEntry` 没有返回值，也不确认持久化。跨请求、会话切换和恢复时均以分支重放为准；工具结果是回执，不是状态存储。回执不得宣称宿主尚未确认的落盘保证。非持久会话中的 Pin 只在当前进程内存续，两个入口都须明确展示该限制。

### 宿主持久化前提

核对的 OMP 源码中，初始 fresh 会话还没有 assistant 消息时，仅追加操作记录和普通自定义消息不会创建会话文件。正常退出只关闭已有写入，不会创建缺失文件。显式 `/new` 属于另一条路径，会在返回前创建文件。依据是[延迟持久化条件](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L965-L987)、[新会话创建](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L1480-L1489)、[退出处理](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/agent-session.ts#L2399-L2408)及[会话关闭](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L1869-L1884)。

内置 [context-notes 写入路径](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/tools/context-notes.ts#L120-L142)调用 `ensureOnDisk()` 和 `flush()`。公开的 [ReadonlySessionManager](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L376-L400) 没有暴露这两个方法。因此，该源码版本没有提供建立初始 fresh 会话空闲保存恢复能力所需的公开持久化操作。

要求仍是空闲保存后正常退出并恢复，且不额外启动模型轮次。支持该场景需要经验证的公开宿主机制，用来创建会话文件并确认写入。缺少该能力时，此宿主基线上的实现验收被阻塞。扩展不得通过悄悄新建另一个会话、直接写宿主日志文件、调用私有方法或启动模型轮次绕过限制。初始 fresh、显式 `/new`、已有持久会话和非持久会话必须分别检查。

### 尾部变更

普通变更以会话日志中的自定义消息送达模型，使用专门的自定义类型和 `details.operationId`。`create` 或 `update` 消息包含条目 id、revision 和完整新正文；`delete` 消息记录被取消固定的条目。宿主保留其追加位置，并重建自定义类型和 details，因此扩展可以识别自己的投影，不需要靠正文相等或数组下标猜测。它们能否跨进程退出保留，取决于宿主持久化前提。

投影把引用的正文与管理说明分开组织，正文以引用数据的形式呈现，并附条目 id 和 revision。OMP 通过共享转换器处理普通自定义消息，可能生成 developer role 的消息，因此最终 role 以 Provider 边界处的核对结果为准，不做假定。

记录变更不得启动模型轮次。核对的源码中，普通空闲 `sendMessage` 在 `triggerTurn: false` 时只追加消息，不启动轮次。由于 `sendMessage` 不返回交付确认，扩展必须核对规范记录与自身可见投影。在下一个安全请求边界，尚未覆盖且缺少投影的操作按日志顺序交付。基准快照已经表达的操作无需再单独交付尾部消息。不属于当前分支或重置周期、或已被快照覆盖的排队投影不得进入请求。恢复与去重由扩展负责，必须通过真实请求验证。

### 压缩边界

请求准备时，扩展找到当前分支生效重置边界之后、最近一次实际提交的压缩条目。重放截至该提交条目的 Pin 集合，形成该周期的基准快照。快照紧跟对应的宿主压缩摘要插入，只过滤本扩展已被该快照覆盖的投影。边界之后接受的变更留在尾部。

边界取自分支上已提交的条目，不取压缩前通知，也不依赖压缩后回调是否已经执行。提交前接受的操作并入快照，提交后接受的操作留在尾部。被弃用、失败及取消的推测压缩不推进边界。Provider 原生远端压缩的不透明载荷保持原样；扩展快照必须在 Provider 有效输入中位于对应重放之后。仅在 context 钩子中插入不能证明最终位置，还须在实际请求中核对转换、规范化及后续处理器的影响。

没有已提交的压缩边界时，扩展不生成基准快照，由尾部消息单独表达当前集合。

快照携带边界身份和 Pin 内容，不含当前时间、请求计数、随机值或按请求产生的估计值，因此状态不变时投影逐字节一致。由于投影在每次请求时从分支重新计算，回调丢失、通知脱离或压缩后重启都不会丢失基准。

### 缓存行为

- 读操作和正文未变化的更新不改变规范 Pin 状态与已发布投影。普通工具调用及结果仍可增加宿主历史。
- `create`、`update` 和 `delete` 追加到尾部；已发布的消息保持原位置，更早的指令不被改写。
- 基准快照只在已提交的压缩边界变化，而此时宿主已经重建了历史。
- 工具定义、工具清单及其 schema 与当前 Pin 集合无关。
- 除约定的压缩归并和过期队列过滤外，扩展不改写更早的系统、工具和历史内容。

验证比较 Provider 可见的有效上下文；宿主发送链式增量时，还要纳入前序请求。单独归因宿主自身的变化，检查 Pin 是否引入可避免的前缀改写。

### 容量与重置

- 通过 `/ctx-pin` 写入的操作 `source` 为 `user`；通过 `ctx_pin` 写入的操作 `source` 为 `agent`。`list` 和 `get` 报告创建时记录的来源。
- 容量按 UTF-8 字节计算，由两个入口在任何状态变更之前执行：单条正文上限 16,384 字节，同一分支活跃条目合计上限 65,536 字节。超过任一上限的操作被拒绝，不改变任何状态，并报告上限和当前用量。两个上限都是组件 README 中说明的常量。
- 成功执行 `/clear` 后，宿主追加 `reset_boundary`，当前 Pin 集合随之结束。状态重放、压缩边界选择和排队消息过滤均以该边界之后的周期为准。`/new` 新建独立会话，使用自己的空集合。`/fresh` 只重置 Provider 流状态、不清空本地历史，因此不清空 Pin。跳转到另一分支时重建该分支自己的周期。
- 校验与追加通过同一条同步路径完成。写入前，两个入口都将观察到的会话、分支、重置周期和条目 revision 与当前状态比较。UI 保留开始编辑时显示的 revision，工具传入 `expectedRevision`。出现 await 后重新核对；旧操作必须被拒绝，不能覆盖期间发生的编辑。接受前取消不写入；接受后取消不回滚操作，也不产生第二次写入。
- 生效重放范围内出现未知 `schemaVersion`、损坏记录或非法操作序列时，有效状态不可用。关闭该范围的写操作、新快照及恢复投影，保留已有日志记录和已发布消息，并输出受限诊断。读取报告状态不可用，不能返回看似完整的部分集合或空集合。不得跳过损坏的更新或删除后，将旧 revision 当成当前状态。当前分支或重置周期变化后重新判断。

## 考虑过的替代方案

- 继续使用宿主自带的 `context_notes` 作为机制。在判断是否需要新组件时考虑过。它按分支保存一整本笔记并沿当前路径恢复，但没有条目级操作，每次写入都替换整本笔记，而且最新笔记被插在消息数组开头，每次编辑都会移动此前稳定的字节。启用实验模式还会改变自动上下文维护方式。
- 每次变更后在前部重新发布完整 Pin 集合。在决定变更放置位置时考虑过。它是最简单的完整可见做法，并作为对照基线保留，但每次编辑都会缩短请求中可复用的前缀。
- 只追加尾部消息，不生成基准快照。在决定固定文本如何跨压缩存续时考虑过。仅靠尾部追加会让固定文本完全受压缩影响，只有日志还留有模型已经看不到的正文。
- 采用更广泛的上下文管理扩展。在比较检索、归档查询、历史折叠、完整上下文规划与条目级 Pin 需求时考虑过。这些额外职责超出本组件范围。将现有第三方能力引入本仓库，也会违反第一方所有权边界。
- 接管宿主的压缩流程。在决定扩展需要对摘要掌握多少控制时考虑过。这样做可以自行撰写摘要，但原生 remote、snapcompact、handoff、soft 和 shake 各有自己的语义，扩展改为读取已提交的边界。

## 验收标准

1. 该包在未修改且受支持的运行时上，通过原生 OMP 机制完成安装、激活和卸载，并声明实测验证的 peer 版本范围。注册前通过公开的宿主版本及能力信息执行运行时检查；peer 元数据本身不算运行时兼容检查。不支持的运行时不注册工具或命令，输出受限诊断，且不终止会话。兼容运行时必须满足宿主持久化前提。
2. 扩展及工具启用后，本扩展唯一的 Provider 可见 Agent 入口为 `ctx_pin`，schema 不随 Pin 状态变化。`/ctx-pin` 可被发现，内置 `/pin` 仍执行会话置顶，且没有命令冲突警告。
3. 状态：每个被接受的逻辑操作在当前分支日志中出现一次，读取与无变化更新不追加记录。分支切换、`/tree`、恢复和重载均重建预期条目、来源及 revision。`/clear`、`/new` 和 `/fresh` 分别符合各自契约。未知 id、过期 revision、接受前取消的提交及被拒绝的写入不改变状态。重试已接受调用不追加第二次操作。
4. 交付：基准快照与未覆盖的尾部共同表达有效集合，不重复应用，也不让已被取代的 revision 重新生效。已被快照覆盖的操作无需单独的尾部投影。已经发布的历史 revision 可以留到压缩归并，但不能再次生效。空闲写入不启动模型请求，并在下一个安全请求边界体现。可恢复的规范记录已写入、投影尚未交付时发生恢复，操作仍保留；过期排队投影不得进入当前请求。分别验证尚无 assistant 输出的初始 fresh 会话，以及显式 `/new` 会话中的空闲保存、正常退出和恢复。一条路径通过不能替代另一条。
5. 缓存：普通历史增长时，未变化的已发布 Pin 内容保持字节和位置一致。创建、更新和删除保留此前的系统、工具及历史内容，直到宿主压缩或重置改变该周期。在条件相同的启用扩展、不启用扩展、前部重写基线中，分别比较连续的有效请求。记录每处首个差异所在的消息、字段及原因。跨 `previous_response_id` 增量恢复有效输入；Pin 不得在宿主自身上下文变化之外再引入完整重放。
6. 在真实请求中分别执行并报告维护子场景：多次手动压缩、自动阈值与轮中压缩、overflow 恢复、被采用、被弃用、失败及取消的推测压缩、handoff、snapcompact、Provider 远端压缩、shake 与工具结果 pruning、通过 `/tree` 回到较早边界，以及压缩后回调完成前的请求。覆盖压缩期间接受的变更与延迟队列交付。有效固定正文保持原文和正确顺序，revision 覆盖关系正确，远端不透明载荷不被改写。核心维护路径分别通过用户创建和 Agent 创建的条目执行。
7. 容量与失败：字节上限在状态变化前执行，拒绝操作不改变日志和投影。测试多字节容量边界、未知 schema、损坏记录、中断回执、并发编辑、非持久会话，以及跨会话、分支或 revision 变化保持打开的对话框。双向测试跨入口管理，包括 UI 编辑后来源不变。损坏的删除记录不得让旧条目作为有效状态复活。
8. 证据：使用真实的交互式 OMP CLI，配合独立测试配置、会话和合成工作区。用户用例操作实际命令、编辑器及列表。记录确切的宿主版本、候选哈希、有效配置、解析后的模型、驱动版本，以及进程、会话、分支与输入的对应关系。功能用例前验证驱动就绪和完成判据；使用有上限且能分页的观察，不盲目重试输入。每个相关请求都关联输入、调用、规范记录、context 钩子输出和最终 Provider 载荷，包括失败及重试。确认观察点覆盖序列化和链式请求。采集内容写盘前排除凭据、Cookie 头和私人接入信息，不改变实际发送的载荷。采集证据和逐字导出保持原样，不运行格式化；测试答案和历史导出不得作为业务材料提供给被测 Agent。缺少关键证据时不能判通过。
9. 自主行为：在最终候选上预先登记 3 条独立轨迹。每条从新的测试会话开始，覆盖自主选择并创建、更新、删除失效信息、真实压缩后使用，以及避免不必要写入。各轨迹的每个阶段分别判定。Agent 从业务上下文和正常工具说明中选择 action 与 id，不使用手工调用、复制的成功状态、逐步指令或重新提供的答案。任何行为失败都使该候选的轨迹组失败，额外成功运行不能消除失败。修复后在新候选上重跑完整的 3 条轨迹。另行测试真实工具错误后的恢复。
10. 所有必需用例及参数化子场景均有最终候选的通过证据。保留失败，将修复关联到新的候选与运行记录；每次运行中固定候选、配置、驱动及判据。修复后复测受影响用例，以及用户、Agent、前缀、压缩和恢复核心路径。无法触发、缺少观测或未执行的必需路径均阻塞验收；只有维护者能批准范围例外。分别判断驱动完成、证据完整和功能通过。在固定测试配置之外，还要验证实际上下文扩展组合中的重载与共存。
11. `pnpm check` 通过，组件检查纳入根聚合命令。组件 README 说明命令和工具用法、调用与 revision 规则、记录格式、上限、重置规则、持久化条件及经验证的宿主版本。自动检查不能代替实机验收。

## 风险

规范记录存在而模型投影缺失时，固定文本会从请求中消失。恢复还可能重复交付，或在快照之后交付更旧的 revision。扩展必须跨重启、排队和压缩核对操作身份与快照覆盖范围，恢复类用例必须实际触发这些失败路径。

选错压缩边界会为一次并未生效的压缩发布快照，或漏掉真正生效的压缩，使变更丢失或旧版本重新出现。边界取自分支上已提交的条目，被弃用的推测结果不得推进它。

其他扩展可能在宿主压缩摘要周围插入消息，或由后序处理器丢弃快照。最终 Provider 转换也可能改变钩子中看似正确的顺序。这些失败会遗漏固定正文或按错误顺序应用变更，因此验收必须检查被测扩展组合的最终请求。

Provider 原生远端压缩会让部分历史保持不透明。固定文本可能同时留在该载荷和显式快照中。修改不透明载荷可能破坏重放；显式快照与尾部顺序错误可能使已失效约束重新生效。需要在实际请求上验证保持与有效顺序，不能声称已经对不透明内容去重。

固定正文与累计 revision 都消耗上下文。活跃正文的字节上限不能约束 token 用量、元数据或旧尾部消息，因此完整请求仍可能在压缩后溢出。验收必须测量完整请求体积，核对原生 overflow 恢复，不能截断活跃 Pin 正文，也不能在没有进展时反复触发恢复。

固定文本可能被解释为指令，尤其当宿主指定的 role 为 developer 时。正文应按引用数据分隔、管理说明独立组织，并核对转义及最终 role，包括看似结束分隔符的正文。

请求采集可能泄露凭据或无关的隐私内容。核对的宿主[请求调试写入器](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/ai/src/utils/request-debug.ts#L56-L78)会保存请求头，仅使用合成提示词和排除仓库提交并不能保证文件安全。采集方式必须在写盘前排除敏感传输字段，且不改动实际发给模型的请求。

核对的宿主无法通过上述公开扩展接口满足初始 fresh 会话的持久化要求。忽略这一缺口发布，可能让用户空闲保存的内容在正常退出后丢失。持久化前提、最终请求的恢复和放置检查均是发布门槛，尚未完成验证。

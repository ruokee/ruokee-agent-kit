# ADR 提案：添加 omp-context-pin 扩展

Decision owner: Ruokee
Draft writer: deepseek/deepseek-v4.1-flash

[English](./2026-09-15-add-omp-context-pin.md) | 中文

## 动机

运行到触发压缩的长会话，需要把少量细节逐字保留下来：约定好的接口、文件结构说明、必须按原文执行的命令。压缩会摘要历史，而摘要可能缩短或改写这些内容。事后要求模型自行复现原文同样不可靠。

OMP 实验性的 `context_notes` 为每个分支保存一整本笔记，并按当前路径恢复。它提供整本替换而非条目级操作，上下文构建会把最新笔记插在消息数组开头。编辑这个块会改动请求的靠前部分，缩短可复用前缀。条目级 Pin 操作需要不同的放置策略。

仓库已经分发第一方 OMP 扩展包。本提案采用相同的组件形式，以公开扩展 API 为目标。文中宿主行为的源码核对基线为 [OMP 18.1.16 的固定提交](https://github.com/can1357/oh-my-pi/tree/61b1b8aef634334eaf1412afd003a763e1d1b9c1)，包括 [context notes](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/tools/context-notes.ts) 和[会话上下文构建](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-context.ts)。源码核对用于确认下文所述的宿主行为，不代表实机验收通过。

## 提议

### 组件与范围

按[第一方能力边界](../decision/2026-08-20-establish-first-party-capability-kit.zh.md)和[组件自包含契约](../decision/2026-08-24-keep-components-self-contained.zh.md)，在 `projects/omp-context-pin/` 添加第一方包 `@ruokee/omp-context-pin`。该包通过 `package.json` 的 `omp.extensions` 元数据声明扩展入口，运行时、检查以及双语 `README.md` 和 `README.zh.md` 都位于组件目录内，并且只使用公开的 OMP 扩展 API。它不导入宿主私有模块，不修改上游源码或已安装的二进制，也不依赖其他仓库组件中的文件。

该包只注册一个斜杠命令 `/ctx-pin` 和一个原生工具 `ctx_pin`。`/pin` 是内置保留命令名，用于切换会话在恢复列表中的置顶状态，OMP 会过滤重用保留名的扩展命令并记录冲突警告，因此本扩展使用不同名称。

不带参数的 `/ctx-pin` 打开当前分支的条目列表，提供创建、查看、编辑和删除，创建项固定在第一项，随后按创建顺序排列条目，最后是关闭项；每行显示条目的整数 id 与由正文派生的摘要，因此不需要保存标签。`/ctx-pin add <正文>` 直接提交创建。未知子命令或缺少正文时只显示简短用法、不发送消息；`add` 之后的一个分隔空格起，其余内容就是正文，不做 shell 式分词、引号去除、转义处理或空白规范化。内联的查看、编辑和删除不在首版范围内。两个创建入口复用同一个提交函数，因此由宿主在空闲时选择普通发送、运行中作为 steering 进入，而不是在异步等待前先读一次空闲状态。宿主会先处理整段输入（包括外侧 trim），逐字保持以扩展实际收到的正文为边界；需要精确首尾空白的正文使用多行编辑器。

多行正文使用宿主的编辑对话框。`ctx_pin` 通过 `action` 参数分发：

| action | 作用 | 主要输入 |
| --- | --- | --- |
| `list` | 列出当前条目及其 id、来源、revision 和体积 | 无 |
| `get` | 返回完整正文及其 id、来源、revision 和体积 | `id` |
| `create` | 固定一段新的文本正文 | `content` |
| `update` | 替换已有正文 | `id`、`content`、`expectedRevision` |
| `delete` | 取消固定条目 | `id`、`expectedRevision` |

schema 保持稳定，不枚举当前条目。工具使用 `loadMode: "essential"`，使已启用的 `ctx_pin` 保持在顶层工具清单中。Pin 操作不改变工具定义。`update` 和 `delete` 要求已有的 `id` 以及调用者观察到的 revision。未知 id 或 revision 不匹配时拒绝写入。任何 action 都不执行隐式 upsert 或改名式的创建。空正文被拒绝；已接受的正文保留空白和字符，不做 trim 或规范化。

条目 id 和操作号都是会话内的正整数。条目 id 在首次成功创建时分配，同一会话内不复用；操作号在每次用户提交或每次新的 Agent 写调用时分配，该提交或调用重试时复用，允许出现空号。宿主 tool call id 仍只是内部幂等键，模型不生成、不填写也不解释它。列表、回执和工具结果展示的都是同一组整数。工具的 `id` 参数直接使用该整数，不接受数字字符串。

工具对所有 action 声明最低审批档 `read`。在没有显式 per-tool 策略时，`always-ask`、`write` 和 `yolo` 都不会因 Pin 操作发起询问；用户显式把 `ctx_pin` 标记为 `prompt` 或 `deny` 时仍按其配置执行，扩展不写用户配置，也不自行增设授权、确认或来源准入。类型、条目存在性、revision、容量和记录完整性校验保留：它们让操作作用于正确的数据，而不是限制谁能调用。

Pin 的含义是：条目的正文以原文形式持续出现在当前会话分支的后续普通模型请求中，直到该条目被更新、取消固定，或分支上下文被重置。压缩不结束 Pin；每次提交后的压缩都会从扩展自身的记录中恢复正文。

被接受的操作会立即改变有效集合；对 `/ctx-pin` 而言，这一时刻是宿主消费用户确认的消息时，而不是对话框关闭时。已经发布的旧正文可以继续留在历史中，直到压缩将其归并到新的基准快照。条目 id、revision 和删除记录表达哪些内容仍然有效。下一份快照只包含最新的活跃正文，不包含已删除条目。

首版固定由用户或 Agent 提供的文本正文。它不读取文件、不抓取 URL、不监听内容变化，也不固定任何在没有操作的情况下就会变化的正文。

### 交互与接受

`/ctx-pin` 是用户浏览和编辑的入口：打开当前分支的条目列表，展示正文与 revision，并提供创建、编辑和删除。`/ctx-pin add <正文>` 不打开对话框直接写入，因为发出这条命令本身就是确认。列表、正文查看和草稿编辑都是只读操作：不发送消息、不改变 Pin 状态，也不中断正在执行的轮次；放弃编辑不留任何痕迹。

确认的写入会变成一条普通用户消息，正文在前，末尾附加一段简短的管理标记。扩展通过公开的消息接口提交正文并逐字保留，因此被固定的正是用户写下的那段文本。只识别提交函数最后追加的那一个标记，因此正文内部、代码围栏里或用户自己文本末尾的同形标签都仍是普通文本。标记携带整数操作号和一段短作用域标记，用于区分会话与重置周期；该标记不是凭据，身份也从不靠正文相等、时间戳、数组位置或 `input.source` 推断。删除没有待固定正文，因此是一条简短的管理语句加同样的标记。会话空闲时宿主按普通 prompt 执行这条消息，运行中则作为 steering 进入；这条消息既是请求，也是用户发出内容的可见记录。正文中的明确任务照常执行，背景材料正常回应或澄清，Pin 失败不会因此取消同一条消息里彼此独立的请求。

操作在宿主消费这条消息、并由扩展通过校验之后生效。消费之前，入口报告该操作处于待处理状态；只有规范状态一节所述的校验（当前进程仍持有该提交、载体与登记文本相符、观察到的会话、分支和重置周期仍然有效、条目存在、revision 仍与打开草稿时一致）通过后，被接受的集合才发生变化。由于整数操作号可以预测，接受时必须比较整条登记提交，包括 action、目标、观察到的 revision 和正文，而不是只凭编号。宿主始终未消费的消息、被取消的草稿，以及保留现有正文的冲突，都不改变任何内容。正文里恰好长得像标记的内容仍然只是普通文本。

宿主消费这条消息并执行校验后，入口向用户报告结果：已接受、无变化，或未应用及原因。消费该操作的请求携带与这个编号关联的同一结果，因此模型能看到操作是被接受、没有产生变化还是被拒绝，也不需要为同一操作再写一次才能让已接受的命令生效。这句话只针对该 Pin 操作，不禁止同一请求需要的其他工具工作。结果与正文分开表达，不重复正文，不自行启动轮次，也不增加持久化保证。承载结果的记录不携带 Pin 状态，重放时忽略。

Agent 在它已经执行的轮次中通过 `ctx_pin` 工具管理 Pin，工具结果就是它的回执。用户也可以在普通消息里要求执行 Pin 操作，例如“把刚才约定的接口固定下来”；此时预期 Agent 像调用该请求所需的其他工具一样调用 `ctx_pin`。扩展不会把自然语言解析成 Pin 操作，两条路径也都不保证模型选出正确的工具、参数或时机，操作以工具调用实际产生的结果为准。Agent 通过这种方式执行的操作记录为 `source: agent`，因为决定来源的是入口，而不是请求背后的意图。

### 规范状态

规范状态是会话日志中的追加式操作日志，通过 `appendEntry` 以自定义类型 `omp-context-pin` 写入。每个被接受的写操作追加一条记录：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 记录的载荷版本，当前版本为 `2` |
| `operationId` | 一次用户提交或一次 Agent 写调用的正整数，重试时保留，也用于匹配投影 |
| `action` | `create`、`update` 或 `delete` |
| `entryId` | 创建时分配的正整数，同一会话内不复用 |
| `revision` | 从 1 开始，每次被接受的更新或删除递增 1 |
| `body` | `create` 和 `update` 的完整新正文 |
| `source` | `user` 或 `agent`，记录由哪个入口写入 |

有效集合通过 `getBranch()` 读取当前分支，按时间顺序重放其最近一次 `reset_boundary` 之后的记录计算得出。创建记录确定条目展示的来源，后续操作的作者不会改变它。`list`、`get`、正文未变化的 `update`、被拒绝的操作以及容量检查失败都不追加记录。先校验身份和 revision，再判断 no-op。 编号分配通过公开的 `getEntries()` 读取整个会话，恢复两个序列的高水位，其中包含本进程尚未消费的提交所预留的编号，以及宿主已持有的载体和结果占用的编号；这次扫描只分配编号，不把其他分支的正文、回执或操作应用到当前分支。会话或扩展重载会重建分配状态，普通 `/tree` 与 `/clear` 不会降低计数。有效集合仍只通过 `getBranch()` 重放得出。

一次确认的用户提交或一次 Agent 写调用对应一个固定的 `operationId`。一条消息被宿主消费一次就追加一次操作；携带同一身份重新提交属于该操作的重试，而不是写入第二条。重试已接受的调用时返回其回执，不追加第二次操作；Agent 重试通过内部 tool call id 在持久化记录中找回已被接受的整数操作号，并核对调用内容一致，而不是先分配新号。新的 `create` 调用创建独立条目，即使正文与其他条目相同；新的用户提交获得新的编号。交付重试复用已接受操作的身份。

编号超出安全整数范围，或无法可靠建立分配状态时，给出明确错误，不回绕，也不悄悄从 1 重新开始。早期候选写入的会话使用字符串身份；当前版本在其有效范围内把这些记录报告为不支持的格式，不与整数混用，并采取干净切换：旧记录不做迁移，用户新建会话或重置范围后开始新的编号，旧字符串身份不参与新格式的整数计数。损坏范围的处理见容量与重置一节。

操作被接受意味着它已出现在宿主的内存分支日志中。公开的 `appendEntry` 没有返回值，也不确认持久化。跨请求、会话切换和恢复时均以分支重放为准；工具结果是回执，不是状态存储。回执不得宣称宿主尚未确认的落盘保证。非持久会话中的 Pin 只在当前进程内存续，两个入口都须明确展示该限制。

### 会话持久化与责任边界

规范记录位于宿主维护的会话日志中。创建会话文件、写入、退出时保存、恢复以及复制其中的消息都属于宿主职责。Pin 读取宿主提供的分支，并重放其中的记录；它不自行创建、修复、迁移或写入该文件，也不承诺宿主没有报告的结果。

两个入口都拿不到宿主的写入确认：公开的 `appendEntry` 没有返回值，公开的消息接口也不返回交付回执。因此回执说明的是扩展已经提交或已经接受了什么，而不会宣称宿主已经保存。公开的会话接口同样没有暴露持久化操作，扩展无法确认落盘；在核对的源码中，会话文件由宿主侧路径创建（[ReadonlySessionManager](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L376-L400)）。

扩展不绕过这条边界：不暗中新建另一个会话，不直接写日志文件，不调用私有方法，也不额外启动模型轮次来促成保存。宿主没有保存的会话、在扩展之外丢失或截断的文件，以及始终没有到达该分支的恢复，都会让 Pin 无记录可重放。这些属于宿主结果而非 Pin 缺陷，这类失败的证据必须说明是哪一侧造成的。

非持久会话的 Pin 只在进程存活期间有效。两个入口都说明这一限制，而不暗示持久存储。

### 尾部变更

普通变更以会话日志中的自定义消息送达模型，使用专门的自定义类型和 `details.operationId`。`create` 或 `update` 消息包含条目 id、revision 和完整新正文；`delete` 消息记录被取消固定的条目。宿主保留其追加位置，并重建自定义类型和 details，因此扩展可以识别自己的投影，不需要靠正文相等或数组下标猜测。用户确认的写入已经由用户发出的那条消息承载，扩展不会为它再追加一份相同正文；上面的投影用于承载 Agent 的写入，并重新表达请求中缺少载体的变更。它们能否跨进程退出保留，取决于宿主的会话保存与恢复。 其 metadata 同时携带原始会话身份，因此来自其他会话的排队载体无法仅凭整数编号匹配；扩展按当前分支与重置周期过滤载体，并把宿主的原始身份留在内部 metadata 中，不放进面向模型的条目号或回执正文。

投影与恢复出的正文都把引用文本与管理说明分开组织，并标注条目 id、revision 和来源。恢复出的正文是保留的会话上下文：其中的事实和仍然适用的用户要求继续有效，固定不会让这段文本获得它原本没有的权限，也不代表重新执行已经完成的任务。Agent 写入的正文不会因为被固定而获得用户或系统指令权限。说明既不宣称所有固定正文都不是指令，也不在引用文本里重复管理封套。OMP 通过共享转换器处理普通自定义消息，可能生成 developer role 的消息，因此最终 role 以 Provider 边界处的核对结果为准。

Agent 的写入不得启动模型轮次。调用发生在 Agent 已经在执行的轮次中，投影通过公开的非主动交付模式发出：`pi.sendMessage(message, { deliverAs: "nextTurn", triggerTurn: false })`。运行中宿主把这条消息放入隐藏的后续输入队列，不调度续跑；会话空闲时直接追加，也不开启轮次。只设 `triggerTurn: false` 并不够，因为默认交付路径会进入 steering 并排空队列。扩展交给宿主的结果使用同一非主动交付模式。用户确认的写入改为走普通用户路径，会话空闲时由宿主启动轮次，运行中则作为 steering 进入；那一轮就是用户的请求，并承载该操作。由于宿主可能要到下一次普通 prompt 才把这类消息追加进历史，调用返回不视为已交付：当前请求仍从规范记录推导自己的变更，因此这一轮中接受的变更必须通过这些记录到达该请求。位置保持稳定：结果绑定对应用户消息，Agent 变更绑定对应工具调用的完成位置，宿主随后追加的同身份副本由扩展去重，而不是放到新历史尾部。载体因宿主压缩或 pruning 消失时，按快照与日志顺序恢复位置，不按数组下标猜测。验收必须检查同一次运行中的连续工具步，因为每次构建请求都把同一条缺失投影重新追加到新尾部，会让普通历史一增长前缀就发生移动。

### 压缩边界

请求准备时，扩展找到当前分支生效重置边界之后、最近一次实际提交的压缩条目。重放截至该提交条目的 Pin 集合，形成该周期的基准快照。快照紧跟对应的宿主压缩摘要插入，只过滤本扩展已被该快照覆盖的投影。边界之后接受的变更留在尾部。

边界取自分支上已提交的条目，不取压缩前通知，也不依赖压缩后回调是否已经执行。提交前接受的操作并入快照，提交后接受的操作留在尾部。被弃用、失败及取消的推测压缩不推进边界。Provider 原生远端压缩的不透明载荷保持原样；扩展快照必须在 Provider 有效输入中位于对应重放之后。仅在 context 钩子中插入不能证明最终位置，还须在实际请求中核对转换、规范化及后续处理器的影响。

没有已提交的压缩边界时，扩展不生成基准快照，由尾部消息单独表达当前集合。

快照携带边界身份和 Pin 内容，不含当前时间、请求计数、随机值或按请求产生的估计值，因此状态不变时投影逐字节一致。由于投影在每次请求时从分支重新计算，回调丢失、通知脱离或压缩后重启都不会丢失基准。

### 缓存行为

- 读操作和正文未变化的更新不改变规范 Pin 状态与已发布投影。普通工具调用及结果仍可增加宿主历史。
- 被接受的写入出现在尾部：Agent 的写入以扩展投影的形式出现，用户的写入以用户提交的那条消息出现。已发布的消息保持原位置，更早的指令不被改写。
- 基准快照只在已提交的压缩边界变化，而此时宿主已经重建了历史。
- 工具定义、工具清单及其 schema 与当前 Pin 集合无关。
- 除约定的压缩归并和过期队列过滤外，扩展不改写更早的系统、工具和历史内容。

验证比较 Provider 可见的有效上下文；宿主发送链式增量时，还要纳入前序请求。单独归因宿主自身的变化，检查 Pin 是否引入可避免的前缀改写。

### 容量与重置

- 通过 `/ctx-pin` 任一形式写入的操作 `source` 为 `user`；通过 `ctx_pin` 写入的操作 `source` 为 `agent`。`list` 和 `get` 报告创建时记录的来源。Agent 在普通用户消息要求下执行的操作 `source` 为 `agent`：决定来源的是入口，而不是请求背后的意图。
- 容量按 UTF-8 字节计算，由两个入口在任何状态变更之前执行：单条正文上限 16,384 字节，同一分支活跃条目合计上限 65,536 字节。超过任一上限的操作被拒绝，不改变任何状态，并报告上限和当前用量。两个上限都是组件 README 中说明的常量。
- 成功执行 `/clear` 后，宿主追加 `reset_boundary`，当前 Pin 集合随之结束。状态重放、压缩边界选择和排队消息过滤均以该边界之后的周期为准。`/new` 新建独立会话，使用自己的空集合。`/fresh` 只重置 Provider 流状态、不清空本地历史，因此不清空 Pin。跳转到另一分支时重建该分支自己的周期。
- 校验与追加通过同一条同步路径完成。工具路径在真正接受之前校验；`/ctx-pin` 在宿主消费确认消息时校验。两个入口都将观察到的会话、分支、重置周期和条目 revision 与当前状态比较。草稿保留开始编辑时显示的 revision，并在消费时比较；工具传入 `expectedRevision`。任何 await 之后都重新核对，revision 过期时拒绝操作，而不是覆盖期间发生的编辑。消费之前被编辑、放弃或取消的草稿不写入任何内容；接受之后取消不回滚操作，也不产生第二次写入。 两个命令形式都通过同一个提交函数和同一条同步校验路径，草稿与打开时的 revision 比较。
- 生效重放范围内出现未知 `schemaVersion`、损坏记录或非法操作序列时，有效状态不可用。关闭该范围的写操作、新快照及恢复投影，保留已有日志记录和已发布消息，并输出受限诊断。读取报告状态不可用，不能返回看似完整的部分集合或空集合。不得跳过损坏的更新或删除后，将旧 revision 当成当前状态。当前分支或重置周期变化后重新判断。 早期候选写入的字符串身份按不支持的格式报告，不当作整数读取，见规范状态一节。

## 考虑过的替代方案

- 继续使用宿主自带的 `context_notes` 作为机制。在判断是否需要新组件时考虑过。它按分支保存一整本笔记并沿当前路径恢复，但没有条目级操作，每次写入都替换整本笔记，而且最新笔记被插在消息数组开头，每次编辑都会移动此前稳定的字节。启用实验模式还会改变自动上下文维护方式。
- 每次变更后在前部重新发布完整 Pin 集合。在决定变更放置位置时考虑过。它是最简单的完整可见做法，并作为对照基线保留，但每次编辑都会缩短请求中可复用的前缀。
- 只追加尾部消息，不生成基准快照。在决定固定文本如何跨压缩存续时考虑过。仅靠尾部追加会让固定文本完全受压缩影响，只有日志还留有模型已经看不到的正文。
- 采用更广泛的上下文管理扩展。在比较检索、归档查询、历史折叠、完整上下文规划与条目级 Pin 需求时考虑过。这些额外职责超出本组件范围。将现有第三方能力引入本仓库，也会违反第一方所有权边界。
- 接管宿主的压缩流程。在决定扩展需要对摘要掌握多少控制时考虑过。这样做可以自行撰写摘要，但原生 remote、snapcompact、handoff、soft 和 shake 各有自己的语义，扩展改为读取已提交的边界。
- 在 `/ctx-pin` 对话框确认时直接写入状态。在决定用户操作何时生效时考虑过，早期候选也采用过。它的回执即时返回，但操作在消息到达宿主之前就已生效，因此排队、被编辑或撤回的消息可能留下用户从未发送的变更，运行中的轮次也不会把它作为 steering 收到。
- 由扩展解析自然语言请求并执行管理操作。在考虑普通消息如何在不依赖模型的情况下管理 Pin 时考虑过。它需要命令语法、与普通叙述的优先级规则和自己的错误路径，而工具已经为 Agent 提供了该操作，因此请求交给模型处理。
- 启动模型轮次以促使宿主保存会话。在绕过初始 fresh 会话的文件边界时考虑过。它会花掉用户没有要求的轮次来处理宿主职责，而且仍然不会返回写入已发生的确认。

- 保留生成的 UUID 字符串作为条目与操作身份。在重新审视身份格式时考虑过。已有观察中没有出现由 UUID 引起的模型异常，因此改用整数的理由是易读与上下文占用：整数更易读、在列表里更容易挑选，也在每条携带它的消息里更短。
- 完全去掉身份标记，改用其他方式识别操作。在简化消息结构时考虑过。公开的用户消息接口不暴露 `details`，也不返回消费身份，因此只能靠正文相等、时间戳、数组位置或 `input.source` 判断哪条消息是操作；改走自定义消息载体又会让普通用户消息路径失去验证。因此保留末尾的简短标记。
- 保留持久化的 `title` 作为列表标签。在调整条目呈现方式时考虑过。标题会与它所标注的正文脱节，而整数 id 加正文派生的摘要已经足以区分条目，因此删除该字段，也不再需要重复标题的去重规则。
- 把写操作声明为 write 档。在确定工具审批分类时考虑过。这会让 `always-ask` 下对一次不涉及文件、进程或网络资源的创建发起询问，而宿主策略本已管辖该工具，因此所有 action 统一声明最低档。
- 继续用默认发送路径加 `triggerTurn: false` 交付 Agent 变更。在确定交付路径时考虑过。宿主会把这类消息归入 steering 并排空队列，可能增加轮次或取消同批工作；因此改用显式的非主动交付模式。

## 验收标准

1. 该包在未修改且受支持的运行时上，通过原生 OMP 机制完成安装、激活和卸载，并在包元数据中声明 peer 版本范围。注册前通过公开的宿主版本及能力信息执行运行时检查；peer 元数据既不算运行时兼容检查，也不代表范围内每个版本都被支持。不支持的运行时不注册工具或命令，输出受限诊断，且不终止会话。验收按原因归属：Pin 缺陷、宿主故障和模型行为分别记录。外部故障导致无法判断 Pin 是否正确时，记录为未判定并保留原因，而不是判作 Pin 功能失败。
2. 扩展及工具启用后，本扩展唯一的 Provider 可见 Agent 入口为 `ctx_pin`，schema 不随 Pin 状态变化。列表顺序与条目标签遵循组件与范围一节的呈现规则。`/ctx-pin` 可被发现，内置 `/pin` 仍执行会话置顶，且没有命令冲突警告。它有两种形式：不带参数打开列表，`add <正文>` 不打开对话框直接提交创建，保留一个分隔空格之后的全部内容作为正文，未知子命令或缺少正文时只显示用法且不发送任何消息。任一形式都是把用户消息直接转成操作的唯一入口；普通消息只能通过促使 Agent 调用 `ctx_pin` 来管理 Pin，扩展不会把自然语言解析成操作。在没有显式 per-tool 策略时，`always-ask`、`write` 和 `yolo` 三档都不会因 Pin 操作发起审批；用户显式把 `ctx_pin` 标记为 `prompt` 或 `deny` 时仍按其配置执行。
3. 状态：每个被接受的逻辑操作在当前分支日志中出现一次，读取与无变化更新不追加记录。用户确认的写入只在宿主消费其消息时改变状态；被编辑、放弃或取消的草稿不产生记录，宿主在消费前撤回的消息同样不产生记录。分支切换、`/tree`、恢复和重载均重建预期条目、来源及 revision。`/clear`、`/new` 和 `/fresh` 分别遵循各自契约。未知 id、过期 revision、接受前被取消的提交以及被拒绝的写入都不改变状态。重试已接受的调用不追加第二次操作。条目 id 是会话内不复用的正整数；操作号对应一次提交或一次写调用，只在该提交重试时复用，可以出现空号。编号在扩展重载后仍然有效，`/tree` 与 `/clear` 不会降低计数，无法可靠建立分配状态时给出明确错误。记录使用 `schemaVersion: 2`；持有早期字符串身份的会话在其有效范围内按不支持的格式报告，不与整数编号混用。
4. 交付：基准快照与未覆盖的尾部共同表达有效集合，不重复应用，也不让已被取代的 revision 重新生效。已被快照覆盖的操作无需单独的尾部投影。已经发布的历史 revision 可以留到压缩归并，但不能再次生效。Agent 的写入通过显式的非主动交付模式发出，不启动模型请求：运行中宿主把它排入隐藏队列、不调度续跑，空闲时直接追加、不开启轮次。下一个安全请求边界会体现该变更；由于宿主可能要到下一次普通 prompt 才追加，当前请求仍从规范记录推导变更。已发布位置保持稳定：宿主随后追加的同身份副本会被去重，而不是移动到新的尾部，同一次运行中的连续工具步保持原有前缀。用户的写入本身就是一条普通用户消息，会话空闲时由它开启轮次，该请求只携带这次写入一次。可恢复的规范记录已写入、投影尚未交付时发生恢复，操作仍保留；过期排队投影不得进入当前请求。当宿主保存并恢复会话时，验证 Pin 正确重放恢复出的记录，覆盖从空白会话开始、执行普通轮次后恢复的会话，以及显式 `/new` 会话。消费命令操作的请求携带与操作身份关联的结果，入口向用户展示同一结果。宿主没有保存、或在扩展之外丢失文件的情况记录为宿主结果，而不是 Pin 失败。
5. 缓存：普通历史增长时，未变化的已发布 Pin 内容保持字节和位置一致。创建、更新和删除保留此前的系统、工具及历史内容，直到宿主压缩或重置改变该周期。在条件相同的启用扩展、不启用扩展、前部重写基线中，分别比较连续的有效请求。记录每处首个差异所在的消息、字段及原因。跨 `previous_response_id` 增量恢复有效输入；Pin 不得在宿主自身上下文变化之外再引入完整重放。
6. 在真实请求中分别执行并报告维护子场景：多次手动压缩、自动阈值与轮中压缩、overflow 恢复、被采用、被弃用、失败及取消的推测压缩、handoff、snapcompact、Provider 远端压缩、shake 与工具结果 pruning、通过 `/tree` 回到较早边界，以及压缩后回调完成前的请求。覆盖压缩期间接受的变更与延迟队列交付。有效固定正文保持原文和正确顺序，revision 覆盖关系正确，远端不透明载荷不被改写。核心维护路径分别通过用户创建和 Agent 创建的条目执行。
7. 容量与失败：字节上限在状态变化前执行，拒绝操作不改变日志和投影，并向用户与消费该操作的请求报告原因。测试多字节容量边界、未知 schema、损坏记录、中断回执、并发编辑、非持久会话，以及跨会话、分支或 revision 变化保持打开的对话框。双向测试跨入口管理，包括 UI 编辑后来源不变。损坏的删除记录不得让旧条目作为有效状态复活。在三种默认模式下以及显式 per-tool `prompt` 与 `deny` 下核对审批边界。在已有条目、已删除 id 与尚未消费提交的会话上重建编号，并核对重试复用已记录的操作号而不是分配新号。
8. 证据：使用真实的交互式 OMP CLI，配合独立测试配置、会话和合成工作区。用户用例操作实际命令、编辑器及列表。记录确切的宿主版本、候选哈希、有效配置、解析后的模型、驱动版本，以及进程、会话、分支与输入的对应关系。功能用例前验证驱动就绪和完成判据；使用有上限且能分页的观察，不盲目重试输入。每个相关请求都关联输入、调用、规范记录、context 钩子输出和最终 Provider 载荷，包括失败及重试。确认观察点覆盖序列化和链式请求。采集内容写盘前排除凭据、Cookie 头和私人接入信息，不改变实际发送的载荷。采集证据和逐字导出保持原样，不运行格式化；测试答案和历史导出不得作为业务材料提供给被测 Agent。除专门用于长度边界的用例外，用例正文使用多样化的业务文本：至少一条要求直接执行正文所述任务、一条只提供背景材料、一条长期要求，以及一条回答需要工具调用。此外还要覆盖两个方向：正文引用或形似管理标记的用例，以及同一条消息里同时存在 Pin 失败与独立业务任务的用例。重复填充串只保留给字节上限边界用例。只有背景材料的正文、空正文和超限正文本身都不能证明模型忽略了可执行任务，也不能据此得出该结论。缺少关键证据时不能判通过。
9. 自主行为：在最终候选上预先登记 3 条独立轨迹。每条从新的测试会话开始，覆盖自主选择并创建、更新、删除失效信息、真实压缩后使用，以及避免不必要写入。各轨迹的每个阶段分别判定。Agent 从业务上下文和正常工具说明中选择 action 与 id，不使用手工调用、复制的成功状态、逐步指令或重新提供的答案。每个失败阶段都记录证据并归因：Pin 实现、工具定义或其说明存在缺陷时，需要修复组件并在新候选上重跑完整的 3 条轨迹；纯模型偏差记录为行为观察，本身不改变 Pin 功能判定。运行没有触达 Pin 必需路径时，对应的功能检查记为未判定，而不是通过。另行测试真实工具错误后的恢复。用户在普通消息中要求 Pin 操作时同样观察：模型没有调用工具，或参数错误，属于行为观察；只有当工具定义或说明导致误用时，才继续检查本组件的问题。
10. 所有必需用例及参数化子场景均有最终候选的通过证据。保留失败，将修复关联到新的候选与运行记录；每次运行中固定候选、配置、驱动及判据。修复后复测受影响用例，以及用户、Agent、前缀、压缩和恢复核心路径。无法触发、缺少观测或未执行的必需路径均阻塞验收；只有维护者能批准范围例外。分别判断驱动完成、证据完整和功能通过。在固定测试配置之外，还要验证实际上下文扩展组合中的重载与共存。逐项归因失败：Pin 缺陷、宿主故障或模型行为；证据无法区分时，记录为未判定并保留原因，而不是判作 Pin 失败。归因于模型行为的偏差作为行为观察保留，不需要修复组件，也不计入 Pin 功能通过。
11. `pnpm check` 通过，组件检查纳入根聚合命令。组件 README 说明命令和工具用法、调用与 revision 规则、记录格式、上限、重置规则、责任边界、状态如何跟随宿主会话，内联命令形式、整数身份与列表使用的摘要规则，以及实际执行过的宿主版本。自动检查不能代替实机验收。

## 风险

规范记录存在而模型投影缺失时，固定文本会从请求中消失。恢复还可能重复交付，或在快照之后交付更旧的 revision。扩展必须跨重启、排队和压缩核对操作身份与快照覆盖范围，恢复类用例必须实际触发这些失败路径。

选错压缩边界会为一次并未生效的压缩发布快照，或漏掉真正生效的压缩，使变更丢失或旧版本重新出现。边界取自分支上已提交的条目，被弃用的推测结果不得推进它。

其他扩展可能在宿主压缩摘要周围插入消息，或由后序处理器丢弃快照。最终 Provider 转换也可能改变钩子中看似正确的顺序。这些失败会遗漏固定正文或按错误顺序应用变更，因此验收必须检查被测扩展组合的最终请求。

Provider 原生远端压缩会让部分历史保持不透明。固定文本可能同时留在该载荷和显式快照中。修改不透明载荷可能破坏重放；显式快照与尾部顺序错误可能使已失效约束重新生效。需要在实际请求上验证保持与有效顺序，不能声称已经对不透明内容去重。

固定正文与累计 revision 都消耗上下文。活跃正文的字节上限不能约束 token 用量、元数据或旧尾部消息，因此完整请求仍可能在压缩后溢出。验收必须测量完整请求体积，核对原生 overflow 恢复，不能截断活跃 Pin 正文，也不能在没有进展时反复触发恢复。

保留的上下文可能被理解为授予权限。Agent 固定的正文可能被当作用户要求，恢复出的说明如果不再区分事实与要求，可能让过期指令看起来仍然有效。说明必须标注来源，不宣称这段文本拥有它原本没有的权限，并在 Provider 边界核对最终 role 以及形似分隔符文本的处理。

会话内整数可能跨会话冲突，也可能从错误范围恢复。如果分配忽略了尚未消费提交已预留的编号，或读到了其他分支，幂等检查就会接受属于另一操作的消息，或拒绝一次合法重试，导致变更被应用两次或丢失。分配必须恢复会话级高水位，排队载体必须携带原始会话身份。

非主动交付可能把变更推迟到下一次普通 prompt。如果当前请求同时不再从规范记录推导变更，模型会在缺少刚被接受变更的情况下工作整轮。从规范记录推导请求的路径仍是放行条件，连续工具步要在真实请求上核对，而不是从一次排队的调用推测。

请求采集可能泄露凭据或无关的隐私内容。核对的宿主[请求调试写入器](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/ai/src/utils/request-debug.ts#L56-L78)会保存请求头，仅使用合成提示词和排除仓库提交并不能保证文件安全。采集方式必须在写盘前排除敏感传输字段，且不改动实际发给模型的请求。

用户在对话框中基于当时显示的 revision 确认修改。如果消息在 Agent 改动该条目之后，或在会话、分支、重置变化之后才被消费，按草稿保存的 revision 执行会覆盖更新的正文。校验必须在消费时针对当前状态执行，冲突时保留现有正文。

扩展报告的是自己已经提交或已经接受了什么，落盘由宿主决定；用户在消息仍在排队时确认操作，或宿主始终没有保存该会话时，都不应被告知内容已经保存。被接受的状态必须来自日志而不是提交动作，证据也要区分记录缺失是宿主造成的，还是 Pin 重放失败。其余交付与放置检查仍是发布门槛。

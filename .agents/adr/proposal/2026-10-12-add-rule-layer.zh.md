# ADR 提案：新增规则层

Draft owner: Ruokee
Draft writer: OMP DeepSeek V4.1 Flash

[English](./2026-10-12-add-rule-layer.md) | 中文

## 动机

为仓库工作规则新开一层，位于 `.agents/rule/`，与 `.agents/spec/`、`.agents/adr/` 并列，并把工作程序类正文从根 `AGENTS.md` 和仓库规格中迁出。

仓库有说明各组件与领域当前目标的文档类型，也有记录持久选择理由的文档类型，两者的职责都不包含「在这个仓库里工作要怎么做」。提交、分支、worktree、验证和文档的规则现在放在[根入口文件](../../../AGENTS.md)里，与该文件的仓库定位和导航混在一起；[仓库规格](../../spec/repository.md) 的 Invariants 也把动作约束与交付物性质混在一起。[规格规则](../../spec/README.md) 自己点出了这个缺口：其中的分工把「告诉贡献者怎么做」交给仓库说明与 README，却没有页面拥有这些内容。[ADR 规则](../README.md) 也放不下它，因为一条规则没有替代方案和结果需要记录。读者想知道「提交时该怎么做」时没有页面可读，而同一条约束写在两层里，改动只更新其中一处，另一处随之失效。

## 分析

本仓库的规范性陈述分为五类，其中两类的边界决定这一层。只看交付物即可验证的陈述是规格 invariant：仓库文件链接相对当前文档、普通公开页面成对提供两种语言、Prettier 格式化全部受跟踪 Markdown。约束动作、步骤、顺序、授权或禁止的陈述是规则：提交、合并、推送和删分支是四个独立授权，开发期检查在请求审查前运行，完整检查在最终候选上运行。记录选择、替代方案和结果的陈述是决定。组件安装与使用的说明是组件文档。入口、指向其他层的指针，以及无法从文件与工具配置推断的速记，归根入口文件。

同一条约束常以两种形式出现，这不构成重复：规格说 commit message 是英文 Conventional Commits 且 scope 来自固定集合，规则说在什么时机运行格式化钩子、哪些文件属于当前任务，以及每个 Git 动作需要哪一项授权。只有两层都在陈述同一件事才是重复，而这一层消除的正是这种重复。

[仓库规格](../../spec/repository.md) 有多条 Invariants 混了这两类：它把提交、合并、推送和删分支列为四个独立授权边界，写明开发期检查的运行时机，要求完整检查在干净且已提交的最终候选上运行并记录候选提交与树，要求聚合、选择器映射和回归测试同步改动，并把版本变更写成从 `Z` 到 `X` 的规模。[根入口文件](../../../AGENTS.md) 把规则与它的导航和第一方边界放在一起。[新增规格层](../decision/2026-10-04-add-spec-layer.md) 记录了规格、ADR 与组件文档的分工，并把「告诉贡献者怎么做」留给仓库说明与 README。本提案把那一部分内容放进独立的一层，为这套分工增加第四种文档类型，而不反转其中任何一部分：规格继续陈述目标与可观察结果，决定继续记录选择与理由，新层承接对动作的约束。ADR 机制和规格层都没有为自己的内容引入检查器、分类系统或清单，规则层沿用同一立场。

## 提议

### 分层与归属

`.agents/rule/` 承载仓库的工作规则：贡献者或 Agent 必须做什么、按什么顺序、持哪项授权，以及什么被禁止。一条规范性陈述只有一个归属层。规格说明对象应当是什么、哪个可观察结果显示它成立；决定记录持久选择、理由与结果；规则陈述约束动作的约束；组件文档告诉用户如何安装和使用组件；根入口文件与 README 提供导航和非平凡速记。规则不承载长篇理由：读者需要理由时，规则链接拥有它的决定，或拥有它所执行性质的规格。

### 目录与文件

规则层位于 `.agents/rule/`，与 `.agents/spec/`、`.agents/adr/` 并列，目录名与 `spec` 一样取单数。规则扁平放在同一目录，按活动一文件一份，采用同目录 `name.md` 与 `name.zh.md` 配对，标题下方互链；层自身的规则是 `README.md` 与 `README.zh.md`。规则文件不带日期、不带状态、不设子目录：`.agents/adr/` 用子目录表达记录的生命周期状态，而规则是就地编辑的当前约束，不保留历史。首批交付覆盖仓库边界、规划、任务、Git、验证、文档、协作和维护；文件集合跟随活动变化，出现真实的活动需求时新增页面。

### 单条规则的写法

一条规则陈述一个约束，用祈使句写，可以补一句简短说明。规则不编号，引用一条规则使用文件路径加小节标题，因为编号会立刻变成需要维护的清单，而这一层不引入清单文件。规则尽量追溯到一条规格 invariant、一条现行决定，或维护者的明确决定；没有这样的出处时，只要它是当前确实执行的做法即可，但不得与规格或现行决定冲突。规则保留原有的条件、例外、强度和权限，用「尽可能」表述的规则保持该强度，禁止性规则保留它的例外。

### 编辑与变更

规则新增、删除或改变它所承载的持久选择时，例如授权边界、流程要求或发布策略，先走 ADR 流程再改规则；不改变持久选择的编辑性澄清不需要决定层流程。规则就地编辑，不保留历史，也不记状态、评审意见、任务或会话信息。

### 引用方向

引用单向。规则可以链接组件文件、组件文档、规格和决定。可分发组件内部的文件不得链接、命名或依赖 `.agents/rule/`，组件的运行、构建和分发不依赖规则层。规则是说明性文档：Markdown 检查和变更路径选择器把它当作普通 Markdown，不为它引入检查器、分类系统或清单文件。

### 迁出内容

[根入口文件](../../../AGENTS.md) 让出工作规则正文，保留仓库定位、按活动的导航、读者已经引用的标题，以及 ADR 规则、规格规则和规则规则的入口。[仓库规格](../../spec/repository.md) 让出工作程序类条目，保留交付物性质、结果验收，以及本次迁移未触及的全部要求，并链接拥有迁出细节的页面。[根 README](../../../README.md) 让出重复陈述根入口文件的程序段落，保留面向贡献者的概览、布局小节和各层入口链接。规则层不单独建规格：规则层的目标、边界与验收由仓库规格承接，因为本层描述的领域就是仓库本身。只在一台机器上成立、或写出本地模型、供应商、端点或路径的规则不进入这一层。组件内部的规则留在组件内：`SKILL.md` 的指令是交付给宿主的产品，不是仓库规则。首批交付还覆盖当前适用于仓库工作、却还没有归属文档的规则，因此来源是仓库的可公开工作规则，而不是一份文件清单。迁移保留实机测试的工具选择合同：实机测试必须启动 OMP CLI，不使用 RPC。

### 版本变更权限

迁移把版本规则表述为一条：功能变更连同变更一起更新组件的 `X.Y.Z` 版本，默认只递增 `Z`，调整 `X` 或 `Y` 是维护者的明确决定，Agent 不按变更规模自行选择级别。现行 invariant 写作「`Z` for small compatible changes, `Y` for larger behavior or capability changes, and `X` for a rewrite」，可以被读成允许 Agent 自选级别，规则在不改变默认值的前提下替换这种读法。

### 落地顺序

本提案单独合入 `main`。其后的实现变更从合入后的 `main` 开始，在新的短期分支上建立规则层 README 配对与各活动页面，更新[根入口文件](../../../AGENTS.md)、[根 README](../../../README.md) 配对、[规格规则](../../spec/README.md) 配对和[仓库规格](../../spec/repository.md) 配对，形成规则层当前决定配对，并移除本提案。旧规格层决定内容不变，因为新层扩展了分工而不是反转它，且不链接任何尚未存在的决定。

## 考虑过的替代方案

**把层名定为 `standard` 而不是 `rule`。** 选择层名时考虑过。标准化体系和若干文档分类法把与 ADR 并列的第三层称作 standards，该词读起来像面向团队外部读者的出版物集合，同时 `standard` 与仓库已有的 standard 入口用法相撞。`rule` 命名的是这一层实际承载的条款级约束，与 `spec`、`adr` 的裸名词形式一致，也保留了中文词「规则」。

**把规则写成根目录的单文件 `RULES.md`。** 选择层的位置时考虑过。单文件容易找到，但无法按主题承载语言配对，且每个活动都要通过同一个文件编辑，与仓库现有的文档布局不符。

**把规则并入 `.agents/spec/`。** 划分层边界时考虑过。这样不新增目录，但读者无法判断某条是目标状态还是动作约束，同一条陈述会有两个可能的归属。

**按活动分子目录组织规则。** 选择文件布局时考虑过。`.agents/adr/` 使用子目录，但那里编码的是生命周期状态，规则没有状态，子目录只会增加路径深度和链接层级，不承载含义。

**把工作规则继续留在根 `AGENTS.md`，不新增层。** 作为现状考虑过。它不需要新的文档类型，但入口文件把导航、定位和规则放在一起，仓库规格又以另一种形式重复了其中若干条，且没有任何页面以规则本身为主题。

**给规则编号并维护清单。** 选择引用方式时考虑过。编号和清单让规则容易被检查表引用，但仓库没有为 ADR 或规格维护这样的列表，且每次增删规则都要维护编号。

**在 `.agents/spec/` 下为规则层新建一份规格。** 选择规则层目标写在哪里时考虑过。专门的规格能把目标与验收放在其他领域声明自己的位置，但本层描述的领域就是仓库本身，而仓库规格已经存在，无需拆分任何文档就能承接规则层的目标。

## 验收标准

1. `.agents/rule/` 含层 README 配对和每个活动一份页面配对，每对文件标题下方互链，两种语言陈述同一组规则。
2. 层 README 配对说明规则层的定义、与规格和决定及组件文档的分工、文件组织与命名、单条规则的写法、编辑与变更、引用方向，以及规则层背后的决定。
3. 从[根入口文件](../../../AGENTS.md)、[根 README](../../../README.md) 或[仓库规格](../../spec/repository.md) 迁出的每条工作规则，以及当前还没有归属文档的每条仓库工作规则，都有记录归属：迁入规则页、保留并链接拥有它的页面，或保留在仓库之外；每条迁出的规则保留原有的条件、例外、强度和权限。规格中不再保留动作类陈述，实机测试必须启动 OMP CLI、不使用 RPC 的合同得到保留。
4. [根入口文件](../../../AGENTS.md) 声明规则层的位置，按 ADR、规格入口已有的形式链接规则入口，保留按活动的导航和既有标题锚点，并以「尽可能」的强度说明验证与评估工作读取适用规则。
5. [根 README](../../../README.md) 配对说明规则层及其用途，[规格规则](../../spec/README.md) 配对在分工中写明规则层的职责，并让其规格清单与各规格实际拥有的内容一致。
6. [仓库规格](../../spec/repository.md) 配对陈述规则层的目标、边界与验收，仍陈述自身的 Goals、Non-goals、Public surface、Invariants、Acceptance criteria 和 Related ADRs，保留本次迁移未触及的全部要求，并链接规则页面与规则层当前决定。
7. 存在规则层当前决定配对，本提案配对已从 `proposal/` 移除，所有入链可达。
8. 只改 `.agents/rule/` 下 Markdown 的变更被分类为 documentation，不触发完整检查；改动选择器脚本或其测试仍然选择完整检查，选择器回归测试覆盖新路径。根 README 的受影响检查映射把规则层列入说明性 Markdown。
9. 规则层不含长篇理由、规则编号、清单文件或组件内部规则。
10. 最终候选干净、已提交、包含目标 `main`，并通过完整仓库检查。

## 风险

- 迁出根入口文件后，规则不再随宿主在会话开始时注入的说明一起到达，Agent 可能在未读到约束其工作的规则时动手，跳过完整门、在越界分支上提交，或在未获授权时合并。导航条目、规则层 README 的按活动索引和入口文件要求读取适用规则能缩小这个范围，但读取仍是按需行为，没有机制强制。
- 规则在迁移中可能丢掉条件、例外或权限，留下的文本便允许或禁止了错误的事情，例如丢掉「review 请求不授权修改被审文件」这一条，或把「尽可能」弱化为强制要求。归属记录和对照来源正文的复核是防护手段。
- 版本规则可能保留或被读成允许 Agent 按变更规模自选 `X` 或 `Y`，发布版本因此在没有维护者决定的情况下变动。规则把默认值与权限写在一起，验收标准 3 同时保留两者。
- 两层仍可能陈述同一条约束，后续改动只更新其中一处，另一处就留下过时规则。归属规则缩小重叠范围但无法消除，也没有机制机械核对两份文本。
- 仓库规格可能在移除工作程序类条目时丢掉不属于工作程序的要求，例如 commit scope 集合、双语配对规则或某条验收标准。归属记录和验收标准 6 让未受影响的条目可追溯。
- 选择器可能把只含规则页的变更分类错误，或放宽后的正则不再把共享输入和未知路径回退到完整检查，导致某分支实际改了共享输入却被记为仅文档变更。回归测试和验收标准 8 是防护手段。
- 英文规则与其中文配对可能漂移，两份权威文本对同一条约束给出不同说法，各语言的读者遵循不同的规则。两份文件在同一次改动内更新并由复核比较语义，因为格式检查看不出语义差异。

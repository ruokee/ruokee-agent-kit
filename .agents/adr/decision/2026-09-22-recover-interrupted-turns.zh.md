## 动机

第一方 `omp-qol` 扩展提供可独立配置的调整，用于减少反复空等待、受限地恢复符合条件的失败轮次，以及可选地延长压缩期限。hub `wait` 在它监视的后台工作仍在运行时返回空窗口，模型必须重新询问，而每次空返回都消耗一次轮次。遇到上游错误的轮次即便错误是瞬时的也会保持已结束状态，因为原生重试预算已耗尽，或该错误不在预算覆盖之内。远端压缩请求在固定的请求期限处被中断，压缩转而走回退路径而不是完成。

## 分析

能够处理这些情况的扩展，与它要调整的行为并不在同一处。在 OMP 18.2.4 提交 [`1c0303b1f2ec515cbf4b44a9a49d68a029531aac`](https://github.com/can1357/oh-my-pi/tree/1c0303b1f2ec515cbf4b44a9a49d68a029531aac) 中，等待窗口取自[任务管理器](https://github.com/can1357/oh-my-pi/blob/1c0303b1f2ec515cbf4b44a9a49d68a029531aac/packages/coding-agent/src/async/job-manager.ts#L51)里的编译期阶梯，没有任何设置能触及它；没有设置会在错误之后继续轮次；压缩看门狗是[远端压缩](https://github.com/can1357/oh-my-pi/blob/1c0303b1f2ec515cbf4b44a9a49d68a029531aac/packages/agent/src/compaction/openai.ts#L239)与 [V2 流式压缩](https://github.com/can1357/oh-my-pi/blob/1c0303b1f2ec515cbf4b44a9a49d68a029531aac/packages/agent/src/compaction/compaction-v2-streaming.ts#L252)路径内的常量。宿主确实提供了扩展可用的介入点：重新注册原生工具并通过工具上下文委派、session stop 续跑请求、公开的错误分类器，以及压缩生命周期事件。源码核对能确立这些介入点和缺失的配置，但不能确立基于它们的调整在真实会话中行为正确。

进程级压缩补丁还带来一个归属问题：当另一个会话在已安装补丁的进程里启动时，补丁归谁。OMP 会为创建的每个会话绑定已加载的扩展并再次调用它们的工厂函数，可能走模块加载路径，也可能走为新会话重新绑定的 prepared factory（[会话 SDK](https://github.com/can1357/oh-my-pi/blob/1c0303b1f2ec515cbf4b44a9a49d68a029531aac/packages/coding-agent/src/sdk.ts#L505-L518)、[扩展加载器](https://github.com/can1357/oh-my-pi/blob/1c0303b1f2ec515cbf4b44a9a49d68a029531aac/packages/coding-agent/src/extensibility/extensions/loader.ts#L479-L508)），子代理会话因此在运行中的进程里会走到压缩模块的冲突分支。只要进程内已存在 owner 就停用调整的条款，针对的是在「补丁应该做什么」上真正不同的 owner，例如属于其他会话的窗口，或已不再适用的配置快照；而包版本与生效配置快照都一致的第二次激活并不构成这种差异。按该条款执行的实际结果是：第一个子代理会话就让该进程的补丁停止改写，此后设置与状态仍显示实验已开启，进程却一直使用原生的五分钟期限，而配置并未发生任何改动。同一条款也没有为安装方会话结束之后留下确定的状态，后来的会话因此无法区分「已被释放的补丁」与「存在但自己无法驱动的补丁」。

恢复这一情形还涵盖标记覆盖不到的错误。工具调用仍在流式输出时被中断的轮次，宿主记录为 `stopDetails.type: "stream_interrupted_after_content"` 而不是已分类的错误；2026-09-22 观察到的一次中继响应以 `1012: websocket closed before terminal event (code 1012)` 结束轮次，已安装的 `@oh-my-pi/pi-ai` 18.2.4 将其分类为 `0`。宿主自带的补救分支针对流提前关闭、停滞或重置，都以可重试的 id 为前提，因此该错误同样落在这些分支之外。

该决定定义第一方组件 `omp-qol`、它与宿主保持的职责划分，以及使用者启用各项调整时接受的边界。

## 决定

### 组件与范围

在 [第一方能力边界](./2026-08-20-establish-first-party-capability-kit.md)与[自包含组件合同](./2026-08-24-keep-components-self-contained.md)下新增 `projects/omp-qol/`，包名 `@ruokee/omp-qol`。一个包包含三个可独立开关的模块：持续等待 hub、可续跑模型错误后的续跑，以及实验性的压缩期限延长。安装、配置入口与检查各只有一处，而每个模块保留自己的开关、可用状态与故障报告。

组件只通过 OMP 插件设置配置，遵循[原生设置决定](./2026-09-10-use-codex-web-plugin-settings.md)，取值、项目级覆盖与解析都由 OMP 负责。等待与保守的错误恢复默认启用，压缩延长明确为选择启用。模块报告自己的有效状态与不生效的原因，单个模块的故障不会停用其他模块。被拒绝的设置只写键与规则，不回显取值。

组件只限于这些行为调整。外部工具守卫（包括 Herdr 守卫）与无关的宿主行为不在其中。安装与迁移仍由用户决定：组件不改动已有扩展、用户配置或宿主安装文件。

### 宿主职责

任务与进程归属、消息消费、结果送达、审批等级、会话历史以及压缩协议都由 OMP 掌握。

等待模块重新注册原生工具，把每次调用委派给它，并且只在返回结果确定不含新信息时重复调用。期限只结束等待：后台任务与进程继续运行，已送达的消息或已结束的任务结果原样返回，用户取消保留自身原因。模块不为工具新增操作，转发原生审批等级与原生工具声明的可中断性，也不主张拥有它没有收到的结果。

恢复模块使用原生 session stop 续跑请求。固定安全排除项优先于配置，任何设置都不能把它们变成续跑。排除项覆盖取消、拒绝、认证与配额结果、上下文溢出和确定性失败。续跑同时受模块与宿主上限约束，每次续跑报告次数与等待时间，模块不声称重新运行是幂等的，也不声称已完成的工具调用不会重复。续跑正文是固定文本，不携带服务端错误内容。

### 中断与无状态错误

把默认恢复范围扩展到不带分类结论的中断，且不匹配服务端文本。在 `knownTransient` 中，固定排除项与终止性客户端状态规则之后，满足以下任一条件即接受该错误：

- 中断标记：最后的 assistant 错误带 `stopDetails.type: "stream_interrupted_after_content"`，这是宿主为「内容或工具参数已经开始流式输出后流被切断」留下的标记。标记按值比较而非导入，该情形报告为 `stream-interrupted`。
- 无状态且无结论：错误不带 HTTP 状态，即 `errorStatus` 缺失且分类器无法从消息中解析出状态，同时分类器返回 `0` 或位于类别掩码之外的值。该情形报告为 `statusless-unclassified`。

排除项与终止性客户端状态规则保持优先级，因此被排除的类型、以及没有瞬时措辞的 4xx，即使同时带中断标记也保持原生行为。`unclassified` 仍接受所有未分类的错误，不论是否带状态，且不会因中断标记而改变。模块继续只读取宿主结构与宿主判定，不匹配错误文本，分类使用副本，不会改动宿主消息。

这不新增任何设置：`recoveryEnabled`、`recoveryMode`、次数与退避键、固定续跑正文与链规则保持原义，模块与宿主各自保留自己的上限。组件版本随新增的判定条件递增。

### 压缩实验及其替换条件

压缩期限延长作为默认关闭的实验提供：一个受约束的进程级超时调整，通过全局注册表安装，保留原生压缩协议、历史替换、重试与回退。

启用它即接受其边界。在压缩窗口内，同一进程中无关工作发出的命中超时调用同样会被延长，因此该机制既不提供请求隔离，也不提供严格的项目隔离。它只能延长期限，不能缩短。关闭时若当前值仍是本组件的函数则还原原生函数，否则报告该情况。

一个进程只保留一个包装，归安装它的激活所有，改写所在的窗口由该激活自己的事件打开。两次激活在「补丁应该做什么」上不一致时，第二次激活仍在现行规则停止它的地方停止补丁，并报告同样的原因：生效配置快照不同、包版本不同、总开关使该激活保持关闭、键不可用、设置无法读取、注册表槽位本版本无法读取、窗口重叠、事件顺序无法解释，或包装已被其他扩展替换。覆盖与共享仍被拒绝。

包版本与生效压缩配置快照一致、补丁仍属于本模块、且该激活自身要求开启实验时，第二次激活保留已安装的补丁，而不是停止它。它不安装第二个包装，不注册窗口事件，也不打开窗口，自己的会话结束时也不释放任何东西，因为窗口属于安装方激活；它不报告 `enabled`，而是报告 `incompatible` 与原因 `patch-owned-elsewhere`：进程补丁存在、由其他激活持有，本激活无法独立驱动窗口。该原因只说明窗口不由本激活打开，不说明本会话的压缩绝不会被改写：安装方的窗口关闭时，本会话的压缩使用原生期限；窗口打开期间，进程内所有匹配数值范围的调用，包括本会话的压缩，同样被延长。记录的激活 cwd 只用于诊断，不参与比较，因为子代理可能在同一配置下运行于其他目录。保留补丁是已声明的单 owner 范围，不是冲突。

安装方激活结束自己的会话时，该进程不把补丁留给后来的激活。`session_shutdown` 结束它打开的窗口，并且只在 `AbortSignal.timeout` 仍是本模块安装的包装时还原原生函数；registry 留下 `owner-stopped` 形式的有界终态，记录该进程的补丁已由其 owner 释放。已经退出的激活不再被当作活跃 owner。该进程不安装新补丁、不接管、也不重新竞争 owner：配置一致的后续激活遇到该终态时报告该终态而不是安装补丁，因此该调整恢复到该进程需要重启 OMP，从 owner 退出到重启之间没有任何会话获得延长。`session_switch` 属于同一激活继续服务新会话，只结束当前窗口。

组件在状态被查询时从进程 registry 解析压缩状态，而不是重复某一次激活的结果。当本模块的包装由其他激活安装时，状态报告归属；该激活停止补丁之后，状态报告记录的原因；其他扩展替换了 `AbortSignal.timeout` 时，报告 `patch-overwritten`。会话不会把无法由自己驱动的补丁持续显示为 `enabled`。

当 OMP 提供受支持的请求级超时设置或 hook 时，改用该接口并停止全局机制。同一期限策略不保留两个 owner。

### 文档与版本证据

在组件自身的 `docs/` 中提供中英文对照的逐项说明，并由两个 README 相互链接：原生行为与关闭扩展时的表现；为什么需要调整、核对过哪些原生配置或 hook；介入位置以及配置如何影响行为；副作用、取消与失败行为；何种上游变化会使该调整不再必要；源码基线所用的 OMP 版本与提交；自动检查与真实 OMP CLI 运行各自验证过的版本；适用条件与边界。

已核实的结论按调整项分开记录。包级的 peer 范围是关于宿主 API 的元数据，不是对任何调整项的验证；阅读源码也不等于运行。没有真实会话运行的项目记为未验证。

## 考虑过的替代方案

- **为每项调整分别发布扩展包。** 在选择打包方式时考虑。收益是独立发布与独立故障；代价是配置、兼容性、迁移与检查分散在三处安装中，而三项调整共享同一宿主基线。单个包让这些入口集中。
- **使用带独立解析器的专用配置文件。** 在选择配置来源时考虑。所需设置可以由 OMP 插件设置表达，另建解析器、优先级规则与更新路径会带来额外维护，而调整本身并不需要这些能力。
- **替换原生压缩流程。** 在判断期限控制需要多大权限时考虑。它能直接控制请求选项，但把压缩协议、历史替换、重试与回退路径交给本组件，其中还包括生成会话所依赖摘要的路径。
- **推迟压缩调整，等待 OMP 暴露请求级接口。** 在评估隔离性时考虑。它避免进程级副作用并降低维护量，但保留固定期限；本决定改为把受约束的全局机制做成显式、默认关闭的实验，并给出上述替换条件。
- **只记录这三个限制，不提供扩展。** 在提出组件之前考虑。它不增加代码与兼容性负担，但每个场景仍需用户或模型反复介入，而这正是各项调整要减少的情况。
- **保留原有的归属规则并说明其后果。** 在决定是否改动组件时考虑。这样只要启动过子代理，所有运行中的进程都不再有该调整，实验实际上只对从不委派的会话有效。
- **改宿主，让会话不再重复激活进程级扩展。** 在权衡修复位置时考虑。按会话绑定是刻意设计：每个 `Extension` 闭包持有本会话的 cwd、事件总线与 runtime，只有受限子会话这条路径不加载扩展。改该模型会影响所有扩展，而不只是本调整；本组件也无法在不重建宿主的情况下验证结果。
- **让最新的激活接管包装。** 在选择冲突行为时考虑。这样配置快照与已安装补丁不同的会话可以就地替换补丁，正是本决定拒绝的「覆盖」。
- **共用补丁，并让每个激活各自注册窗口钩子。** 在决定再次激活可以深入到什么程度时考虑。那样多个会话会打开与关闭同一个窗口，而归属规则把属于其他会话的窗口视为归属不明确，该进程的实验将因此停用。
- **对保留补丁的激活报告 `enabled`，把限制留给文档说明。** 在决定再次激活可以声明什么时考虑。那样会话会被读成已被完整服务，而补丁实际服务于另一个激活的事件。
- **owner 退出后由下一次匹配激活安装新补丁。** 在选择恢复路径时考虑。这样该进程不必重启就能重新获得该调整，而且新补丁由仍然存活的激活持有。代价是「该进程当前是否启用该调整」取决于之后是否还有激活出现，状态在 owner 退出后也没有确定的终态可报。
- **识别请求归属，让窗口只作用于持有它的会话。** 在评估能否消除窗口副作用时考虑。包装的调用点拿不到会话或请求身份，要按会话判断就得改变压缩调用链的类型与宿主接口，超出本组件的范围；本决定已接受窗口内无关 timeout 被延长的副作用。
- **只接受宿主的中断标记。** 在选择可续跑信号时考虑。它是最精确的信号且不需要状态判断，但没有工具调用在途的中断、以及其他无状态且无结论的失败仍保持原生行为。
- **只接受无状态且无结论的情形。** 作为唯一条件考虑。它不依赖标记即可覆盖这一类错误，但让标记闲置，于是同时带状态的中断（例如工具调用流式输出中的 500）仍保持原生行为。
- **在扩展内匹配中断措辞。** 在寻找分类器覆盖不到的信号时考虑。这样可以覆盖宿主词汇表不认识的中继，但把服务端措辞放进组件，与「错误措辞由分类器负责」的规则相冲突，并且每当有中继用不同说法描述关闭的 socket 都需要维护。
- **只提供配置，让用户自行选择 `unclassified`。** 作为该中断的交付方式考虑。它不改代码，但该范围同时接受带 HTTP 状态而无结论的错误，因此会超出中断这一类，把一项刻意设定的默认值变成逐用户的绕行方案。
- **改为在宿主中扩展分类词汇表。** 在权衡修复位置时考虑。这样组件无需改动，但宿主是另一个项目，改动要等待发布，而且无状态错误没有可供匹配的措辞。

## 结果

- 一个组件让三项调整共享一次发布、一份锁文件和同一个检查入口。破坏其中一个模块的宿主变化也会影响整个组件能否按原样安装，单次依赖升级影响三者。
- 自动检查无法确立宿主行为。每项调整都需要自己的真实会话证据，而在超过原生期限的远端压缩成功完成并随后仍能正常发起模型请求之前，压缩实验的收益仍未证实。
- 调整依赖不带兼容承诺的宿主细节：内置工具描述与空窗结构、`stopReason: "error"` 与公开分类器以及它为被中断轮次写入的 `stopDetails.type` 标记、`AbortSignal.timeout` 的身份，以及压缩生命周期事件的顺序。标记按值比较，无状态条件读取的是字段缺失，因此宿主某次发布若不再写该标记，或开始携带状态，只会静默收窄可接受的集合，而不会直接失败。各模块被写成在识别失败时保持不生效并说明原因，而不是猜测，因此宿主升级可能停用某项调整而不会破坏会话，重新核对之后才再次信任该调整。
- 续跑会重发会话内容并消耗服务额度，重新运行的轮次可能重复失败轮次中的副作用。次数上限、固定排除清单与宿主上限减小了暴露面，但不承诺恰好一次的行为。
- 范围扩大在默认配置下即时生效，因此此前会在无状态中断处停止的会话，现在会为它消耗到续跑次数上限。分类器无法识别的客户端失败在同一条条件下也会被续跑，而每轮都复现的服务端故障会比以前更晚被用户看到，直到次数上限用尽。
- 等待期限到达后仍有工作继续运行，而模型可能已不再关注它们。结果会说明期限已到，模型下一步需要重新检查。
- 压缩实验在窗口打开期间会延长同一进程中无关工作的命中期限，而窗口的开启事件并不指明将被计时的请求。清理无法缩短已经创建的期限，且一个进程只有一个包装。
- 保留补丁的会话不驱动窗口，也不因此获得自己的压缩被延长的保证。状态行与文档是唯一说明这件事的地方，因此状态缺失或缓存的会话会被读成已被完整服务。
- 生效配置快照是已安装补丁与未安装它的会话之间的唯一门槛。若给生效配置新增字段却没有同步更新该比较，复用范围会无声扩大，某个会话可能在它从未选择的配置下被保留。
- 安装方激活退出后，该进程在重启之前不再延长任何压缩期限，状态也一直报告已被释放的补丁。这是选定的终态：释放补丁而不让后续激活重新安装，代价是该进程的剩余生命周期没有该调整。
- 文档针对固定的宿主基线维护，因此宿主升级时需要重新阅读引用的源码并更新受影响的章节，而不是扩大声明的 peer 范围。

## 变更

### 2026-09-22：第四个模块与原生历史重放

`omp-qol` 现在同时发布 `replay` 模块，独立开关的第四个模块，让恢复的进程仍以原生重放形式发出第一条请求。开关为 `replayEnabled`，在组件总开关 `enabled` 之下默认开启。它在进程内包装一次 `Map.prototype.set`，对宿主为 `openai-responses` 提供方创建的状态设置 `nativeHistoryReplayWarmed`，其余写入原样交给被替换的函数。`/qol` 报告该模块的生效开关与被包装改写过的状态写入次数。

它的归属规则来自「没有窗口」这一事实。效果覆盖整个进程，且不依赖安装包装的激活，因此后续同包版本、同模块开关的激活保留该包装，并把模块报为 `enabled`，而不是压缩实验对无法驱动的补丁报告的 `patch-owned-elsewhere`。安装方会话结束后包装保留：它变热的状态可能仍属于运行中的会话，且同一进程的下一个会话否则会退回重编码形态。设置关闭该模块、设置不可读或被拒绝的激活释放包装并报告原因；`patch-overwritten` 表示函数在此之后被其他扩展替换。注册表槽位是本版本无法读取的布局，或运行时未接管该包装时，模块拒绝安装并给出原因。压缩实验保留自己的释放规则与终态记录。

组件版本随之升到 `0.3.0`，模块的文档、README 双语对、包描述与设置 schema 在同一变更中命名它。该调整的实测效果、依赖的宿主事实与边界记录在组件自身的 `docs/adjustments.md` 中。

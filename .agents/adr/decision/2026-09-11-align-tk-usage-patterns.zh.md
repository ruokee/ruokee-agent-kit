# ADR 决定：统一 tk 使用模式

## 动机

tk 需要一套共同规则来建议、采用和维护四种内置使用模式，并需要为描述这些模式的公开页面明确归属与双语一致要求，使 Agent 和用户对模式会增加什么、需要维护什么，以及每项合同由哪个页面负责，形成一致理解。

[Skill 模式参考](../../../projects/tk/skills/tk-zh/references/patterns.md)与 [Skill 设计](../../../projects/tk/docs/design/skill.zh.md)给出四种模式。本决定确定上述共同规则与归属规则，并重述[已归档的文档维护决定](../archived/2026-08-29-maintain-tk-documentation.zh.md)中所有仍然有效、覆盖公开文档集合及其维护方式的规则。

## 分析

[已归档的文档维护决定](../archived/2026-08-29-maintain-tk-documentation.zh.md)将 `scratchpad` 固定译为“临时记事区”，与“草稿纸”作为模式中文名称冲突。

## 决定

### 四种使用模式

为普通任务材料定义四种内置使用模式：

| 英文名称 | 中文名称 | 默认材料 |
| --- | --- | --- |
| Records | 记录 | `records/YYYY-MM-DD-topic.md` |
| Deep research | 深度调研 | `research/report.md` 和 `research/README.md` |
| Iterative design | 迭代设计 | `revision_<N>/README.md` 及该版本目录内的材料 |
| Scratchpad | 草稿纸 | `scratchpad/` 下的文件和子目录 |

一个任务可以组合采用四种模式，也可以都不采用。正式决定遵守项目指定的机制和位置。

模式约束 Agent 行为与普通材料的组织方式，不增加 tk 元数据、schema 字段、`extra` 约定、运行时状态、命令或自动目录生成机制。

### 采用与共通维护

- 只在模式信号已经出现后建议该模式，并说明会增加哪些材料、以后维护什么。用户采用后，在 `TASK.md` 正文中简要声明，并链接已有入口材料。用户明确要求采用某种模式时，该请求就是采用授权，无需重复确认。
- 模式采用不替代创建任务或改变生命周期所需的授权。普通材料的日常创建和编辑沿用既有权限。删除、移动材料，或覆盖归属或含义不明的材料，须符合适用授权；采用模式不授予清理权限。
- 项目规则和已有材料结构可以覆盖默认路径。只为已经发生的工作创建材料，不预建空目录、不补造过去活动、不创建未来日期记录，也不为了匹配示例迁移已有任务。
- `TASK.md` 保存当前事实、当前决定和重要入口。普通材料保存可复用的详细内容。WAL 即 Work Activity Log，通过 tk 追加简洁的持久事件摘要。三者通过链接配合，不整篇复制材料。

### 记录

当实质调查、实施、验证或决策活动已经发生在第二个本地自然日时，可以建议记录模式。同日任务以及仅计划以后继续的工作不满足该信号。

只为有实质活动的本地日期维护记录。每份记录保存背景、动作、证据入口和当时结论。保留先前判断，后续更正写入后续材料，`TASK.md` 指向当前结论。稳定设计、参考资料和来源保存在各自的材料文件中，记录可以链接这些材料。记录不替代 WAL 或正式决策记录。

### 深度调研

工作要求收集、保存或交叉核验外部来源，或已经形成来源清单和来源材料时，可以建议深度调研模式。只读一个已知文档或回答普通 API 用法问题不满足该信号。

使用 `research/report.md` 保存结论，`research/README.md` 导航已有调研材料。计划、来源地图、主张核验及其他支撑材料按需增加。只有任务专属来源需要本地留存时，才创建 `research/sources/`。

持续维护来源来历与访问日期、关键主张对应的证据、来源之间的冲突、尚未核验的部分和结论适用边界。`TASK.md` 提供报告的直接入口。只有来源列表不足以说明证据支持了什么，未核验的推断须与事实区分。

### 迭代设计

出现两次以上相互替代的大幅改版、旧方案被整体推倒，或主要边界持续变化时，可以建议迭代设计模式。增量补充、措辞调整和普通评审修正不需要新版本。

每轮设计在 `revision_<N>/` 下自包含。其 `README.md` 说明背景、目标、主要方案和材料入口。只有新的大幅改版才创建下一轮，普通修正继续编辑当前版本。

被替代的版本保留当时状态。`TASK.md` 只把当前版本作为设计入口。需要解释取代关系时，将说明放在新版本中，不通过改写旧设计抹去先前判断。

### 草稿纸

尚未整理的片段、笔记、输出、小脚本或其他临时文件需要持久保存时，可以建议草稿纸。稳定结论应进入整理后的普通材料，无需留存的简短问答不需要草稿纸。

`scratchpad/` 内可使用任意文件和子目录，不强制模板、文件名或层级。有价值的内容稳定后，整理到合适的普通材料，`TASK.md` 只保留必要的当前结论和入口。失效内容须与当前事实区分。删除和移动遵守适用授权规则。

### Skill 与合同归属

四个权威 Skill 目录分别是 [tk](../../../projects/tk/skills/tk/SKILL.md)、[tk-zh](../../../projects/tk/skills/tk-zh/SKILL.md)、[tk-cli](../../../projects/tk/skills/tk-cli/SKILL.md) 和 [tk-cli-zh](../../../projects/tk/skills/tk-cli-zh/SKILL.md)。每个目录都自包含，并保留完整的模式参考文件。同语言 tools 与 CLI 的参考内容相同，中英文语义对应。Skill 文件的引用留在各自组件内。

[Skill 设计](../../../projects/tk/docs/design/skill.zh.md)负责 Agent 行为合同，[术语表](../../../projects/tk/docs/design/GLOSSARY.zh.md)负责四种名称及其含义，[文档设计](../../../projects/tk/docs/design/documentation.zh.md)负责译名维护，[验证合同](../../../projects/tk/docs/design/validation.zh.md)负责可观察验收。这些合同及其语言对应页与 Skill 参考一并维护。

### 公开文档集合

公开 tk 文档位于 `projects/tk/docs/`，包含：

- 英文和中文用户指南；
- 英文和中文设计索引；
- system、data-model、runtime、tool-api、cli-reference、harnesses、installation、skill、validation、documentation 和 GLOSSARY 的双语对应页面；
- 组件[英文 README](../../../projects/tk/README.md) 和[中文 README](../../../projects/tk/README.zh.md)，它们介绍 tk 并链接指南和设计页面，不重复详细命令或规范性合同；
- 仓库根 README 和中文 README 中的 tk 入口，链接到组件入口页；
- `decision/` 下当前英文和中文 tk ADR。

评审记录、修订号、任务路径、分支状态、实现日志和本地材料不进入公开页面。

### 主题归属

每项行为只有一个主要归属页面。system 负责产品边界和不变量。data-model 负责任务格式和持久化。runtime 负责进程和失败行为。tool API 负责逻辑请求与结果。CLI reference 负责命令拼写和退出行为。Harness integration 负责组件形式和适配器。installation 负责组件生命周期。Skill 负责 Agent 行为与材料模式。validation 负责可观察验收。documentation 负责维护规则。术语表只负责项目特殊术语和固定译法。

参数表、算法或规范字段定义只出现在归属页面。其他页面链接到该页面，只陈述读者所需的上下文。

ADR 保存长期决定、替代方案和结果。它们链接当前公开合同，不复制完整命令、字段或测试清单。

### 最终状态写法

公开文档只陈述当前正式合同，就像产品从一开始便按该形式实现。文档不叙述设计修订、审查争论、开发阶段废弃命令、未发布格式兼容或 Agent 工作历史。

正式发布后的真实行为变化可以在用户需要时提供迁移说明。只存在于开发阶段的尝试不会形成兼容历史，也不会列为已移除功能。

### 英文与中文

每个 guide 和 design 专题都在一级标题后链接另一语言版本。仓库文件链接使用相对于当前文档的路径。当前目录或子目录中的路径以 `./` 开头，目录外链接使用所需数量的 `../`。

英文和中文页面语义对应。中文使用自然表达，不做逐句机械映射。命令、路径、字段、代码、日志、产品名和标识符保留规定的拼写与大小写。

普通公开 Markdown 页面按照[公开文档决定](./2026-09-07-colocate-bilingual-docs.zh.md)使用同目录 `name.md` 和 `name.zh.md` 配对，组件 README 也如此。不维护分离的语言目录，也不在被取代的路径保留跳转占位文件；页面移动时修复受影响的入站链接和命令示例。

术语表只包含在 tk 中具有特殊含义、需要固定大小写或必须保持稳定译法的术语。普通技术词留在归属文档中。固定中文形式包括 `受管`、`草稿纸`、`人类可读`、`直接切换`、`支持的子命令`、`活动操作标记`、`表示切换`、`续跑令牌` 和 `续跑状态`。

### 组件选择与分发文档

公开文档覆盖 tools 与 CLI 模式、通过 `tk install` 选择英文或中文、四个 Skill 身份、多份 Harness 载荷、两份与 Harness 无关的 CLI Skill 载荷、分离的路由合同、互斥的安装目标，以及有限范围的自定义根目录生命周期。

### ADR 格式与生命周期

ADR 提案和决定使用独立的仓库格式与目录。英文和中文文件对保持语义一致，维护者负责批准或拒绝提案，以及归档决定。当前记录位于 `decision/`，ADR 文件不包含 `Status` 字段。

### 维护

公开行为发生变化时，同一变更必须更新归属设计页面、受影响的指南和 CLI 示例、两种语言、受影响的 Skill 内容、负责该决定的全部当前 ADR，以及对应验证合同。

仓库现有 Markdown、链接、格式和拼写检查与人工双语审查共同使用。在重复维护或实际偏差证明某项机械不变量值得自动化前，tk 不增加自定义文档结构或翻译检查器。

权威维护细节见[文档设计](../../../projects/tk/docs/design/documentation.zh.md)和[术语表](../../../projects/tk/docs/design/GLOSSARY.zh.md)。

## 考虑过的替代方案

**在每个相关页面重复完整合同。** 重复内容会让日常变更需要同步许多位置，也会使读者无法判断哪一份是权威来源。

**在公开设计页面保留实现历史。** 开发过程会遮挡当前合同，并把未发布尝试变成意外兼容承诺。

**把所有技术词都加入术语表。** 大型通用术语表会重复普通技术文档，并增加没有必要的翻译维护。

**构建 tk 专用双语结构检查器。** 结构相似无法证明语义对应或中文自然。现有检查加直接审阅已经足够，直到重复的机械故障证明某项规则值得自动化。

## 结果

读者可以从指南、设计专题、Skill 或 ADR 进入，并通过相对链接找到归属合同。每项规范细节只有一个主要维护位置。

四份自包含 Skill 参考和双语公开合同描述同一套模式。保持它们一致需要同时维护四个 Skill 目录和两种语言；只更新部分文件可能造成规则不一致，让 Agent 遵循的采用或维护规则与用户读到的规则不同。

每次产品变更都需要同步维护双语文档。格式检查、链接检查和 Rust 测试无法证明语义一致、写作质量或 Agent 行为，因此仍需要人工审阅；场景验证通过四个 Skill 分别检查四种模式。

最终状态写法使公开文档保持紧凑，但评审历史和实现证据必须保存在任务材料或其他非公开记录中。ADR 保留理由，但不会变成发布说明或进度日志。

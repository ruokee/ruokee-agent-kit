# ADR 决定：添加 omp-context-pin 扩展

Decision owner: Ruokee
Decision writer: deepseek/deepseek-v4.1-flash

[English](./2026-09-15-add-omp-context-pin.md) | 中文

## 动机

运行到触发压缩的长会话，需要把少量细节逐字保留下来：约定好的接口、文件结构说明、必须按原文执行的命令。压缩会摘要历史，而摘要可能缩短或改写这些内容。事后要求模型自行复现原文同样不可靠。

OMP 实验性的 `context_notes` 为每个分支保存一整本笔记，并按当前路径恢复。它提供整本替换而非条目级操作，上下文构建会把最新笔记插在消息数组开头。编辑这个块会改动请求的靠前部分，缩短可复用前缀。条目级 Pin 操作需要不同的放置策略。

本决定定义第一方 `omp-context-pin` 组件，由它通过公开扩展 API 提供该机制，并确定其记录、交付与维护路径必须满足的契约。文中宿主行为的源码核对基线为 [OMP 18.1.16 的固定提交](https://github.com/can1357/oh-my-pi/tree/61b1b8aef634334eaf1412afd003a763e1d1b9c1)，包括 [context notes](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/tools/context-notes.ts) 和[会话上下文构建](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-context.ts)。源码核对用于确认下文所述的宿主行为，不代表实机验收通过。

## 决定

### 组件与范围

按[第一方能力边界](./2026-08-20-establish-first-party-capability-kit.zh.md)和[组件自包含契约](./2026-08-24-keep-components-self-contained.zh.md)，在 `projects/omp-context-pin/` 添加第一方包 `@ruokee/omp-context-pin`。该包通过 `package.json` 的 `omp.extensions` 元数据声明扩展入口，运行时、检查以及双语 `README.md` 和 `README.zh.md` 都位于组件目录内，并且只使用公开的 OMP 扩展 API。它不导入宿主私有模块，不修改上游源码或已安装的二进制，也不依赖其他仓库组件中的文件。

该包只注册一个斜杠命令 `/ctx-pin` 和一个原生工具 `ctx_pin`。`/pin` 是内置保留命令名，用于切换会话在恢复列表中的置顶状态，OMP 会过滤重用保留名的扩展命令并记录冲突警告，因此本扩展使用不同名称。

不带参数的 `/ctx-pin` 打开当前分支的条目列表，提供创建、查看、编辑和删除，创建项固定在第一项，随后按创建顺序排列条目，最后是关闭项；每行以 `#<id>` 显示条目编号，并给出由正文派生的摘要，因此不需要保存标签。每行按对话框实际的宽度截断，列表长于可显示行数时，宿主自带的输入筛选保持可用。`/ctx-pin add <正文>` 直接提交创建。未知子命令或缺少正文时只显示简短用法、不发送消息；`add` 之后的一个分隔空格起，其余内容就是正文，不做 shell 式分词、引号去除、转义处理或空白规范化。内联的查看、编辑和删除不在首版范围内。两个创建入口复用同一个提交函数，因此由宿主在空闲时选择普通发送、运行中作为 steering 进入，而不是在异步等待前先读一次空闲状态。宿主会先处理整段输入（包括外侧 trim），逐字保持以扩展实际收到的正文为边界；需要精确首尾空白的正文使用多行编辑器。

多行正文使用宿主的编辑对话框。`ctx_pin` 通过 `action` 参数分发：

| action | 作用 | 主要输入 |
| --- | --- | --- |
| `list` | 列出当前条目及其 id、来源、revision 和体积 | 无 |
| `get` | 返回完整正文及其 id、来源、revision 和体积 | `id` |
| `create` | 固定一段新的文本正文 | `content` |
| `update` | 替换已有正文 | `id`、`content`、`expectedRevision` |
| `delete` | 取消固定条目 | `id`、`expectedRevision` |

schema 保持稳定，不枚举当前条目。工具使用 `loadMode: "essential"`，使已启用的 `ctx_pin` 保持在顶层工具清单中。Pin 操作不改变工具定义。`update` 和 `delete` 要求已有的 `id` 以及调用者观察到的 revision。未知 id 或 revision 不匹配时拒绝写入。任何 action 都不执行隐式 upsert 或改名式的创建。空正文被拒绝；已接受的正文保留空白和字符，不做 trim 或规范化。

条目 id 和操作号都是会话内的正整数。条目 id 在首次成功创建时分配，同一会话内不复用；内部操作身份在每次用户提交或每次新的 Agent 写调用时分配，该提交或调用重试时复用，允许出现空号。扩展对外发布的整数只有条目编号：列表、回执和工具结果都以 `#<id>` 指称条目，工具的 `id` 参数直接使用该整数，不接受数字字符串。一次写入提交在内部靠扩展交给宿主的那段文本识别，因此不为它发布编号。宿主 tool call id 仍只是内部幂等键，模型不生成、不填写也不解释它。

工具对所有 action 声明最低审批档 `read`。在没有显式 per-tool 策略时，`always-ask`、`write` 和 `yolo` 都不会因 Pin 操作发起询问；用户显式把 `ctx_pin` 标记为 `prompt` 或 `deny` 时仍按其配置执行，扩展不写用户配置，也不自行增设授权、确认或来源准入。类型、条目存在性、revision、容量和记录完整性校验保留：它们让操作作用于正确的数据，而不是限制谁能调用。

Pin 的含义是：条目的正文以原文形式持续出现在当前会话分支的后续普通模型请求中，直到该条目被更新、取消固定，或分支上下文被重置。压缩不结束 Pin；每次提交后的压缩都会从扩展自身的记录中恢复正文。

被接受的操作会立即改变有效集合；对 `/ctx-pin` 而言，这一时刻是宿主消费用户确认的消息时，而不是对话框关闭时。已经发布的旧正文可以继续留在历史中，直到压缩将其归并到新的基准快照。条目 id、revision 和删除记录表达哪些内容仍然有效。下一份快照只包含最新的活跃正文，不包含已删除条目。

首版固定由用户或 Agent 提供的文本正文。它不读取文件、不抓取 URL、不监听内容变化，也不固定任何在没有操作的情况下就会变化的正文。

### 交互与接受

`/ctx-pin` 是用户浏览和编辑的入口：打开当前分支的条目列表，展示正文与 revision，并提供创建、编辑和删除。`/ctx-pin add <正文>` 不打开对话框直接写入，因为发出这条命令本身就是确认。列表、正文查看和草稿编辑都是只读操作：不发送消息、不改变 Pin 状态，也不中断正在执行的轮次；放弃编辑不留任何痕迹。

确认的写入会变成一条普通用户消息，消息内容就是这次操作要固定的文本，不再附加标记。扩展通过公开的消息接口提交正文并逐字保留，因此被固定的正是用户写下的那段文本。进程仍持有该提交时，扩展通过把消息与它交给宿主的文本对齐来识别这条消息，因此正文内部没有保留位置，不解析任何标签，用户自己的措辞也不需要改写。匹配只限本进程持有的提交，以及当前的会话、分支与重置周期；身份从不靠时间戳、数组位置或 `input.source` 推断。与某条待处理提交文字相同的无关消息会被认领一次并随即结算，这是让消息保持可读、可编辑所付出的代价。删除没有待固定正文，因此是一条简短的管理语句，其文本由同一套匹配登记。会话空闲时宿主按普通 prompt 执行这条消息，运行中则作为 steering 进入；这条消息既是请求，也是用户发出内容的可见记录。正文中的明确任务照常执行，背景材料正常回应或澄清，Pin 失败不会因此取消同一条消息里彼此独立的请求。

操作在宿主消费这条消息、并由扩展通过校验之后生效。消费之前，入口报告该操作处于待处理状态；只有规范状态一节所述的校验（当前进程仍持有该提交、载体与登记文本相符、观察到的会话、分支和重置周期仍然有效、条目存在、revision 仍与打开草稿时一致）通过后，被接受的集合才发生变化。接受时把宿主消费的消息与本进程仍持有的提交对齐，action、目标、观察到的 revision 和正文必须一致才会写入；宿主始终未消费的消息、被取消的草稿，以及保留现有正文的冲突，都不改变任何内容。

宿主消费这条消息并执行校验后，入口向用户报告结果：已接受、无变化，或未应用及原因。消费该提交的请求携带它所改变条目对应的结果，因此模型能看到这次变更被接受、没有产生变化还是被拒绝，也不需要为同一操作再写一次才能让已接受的命令生效。这句话只针对该 Pin 操作，不禁止同一请求需要的其他工具工作。结果与正文分开表达，不重复正文，不自行启动轮次，也不增加持久化保证。承载结果的记录不携带 Pin 状态，重放时忽略。

Agent 在它已经执行的轮次中通过 `ctx_pin` 工具管理 Pin，工具结果就是它的回执。用户也可以在普通消息里要求执行 Pin 操作，例如“把刚才约定的接口固定下来”；此时预期 Agent 像调用该请求所需的其他工具一样调用 `ctx_pin`。扩展不会把自然语言解析成 Pin 操作，两条路径也都不保证模型选出正确的工具、参数或时机，操作以工具调用实际产生的结果为准。Agent 通过这种方式执行的操作记录为 `source: agent`，因为决定来源的是入口，而不是请求背后的意图。

### 规范状态

规范状态是会话日志中的追加式操作日志，通过 `appendEntry` 以自定义类型 `omp-context-pin` 写入。每个被接受的写操作追加一条记录：

| 字段 | 含义 |
| --- | --- |
| `schemaVersion` | 记录的载荷版本，当前版本为 `2` |
| `operationId` | 一次用户提交或一次 Agent 写调用的正整数，重试时保留，也用于匹配投影 |
| `action` | `create`、`update` 或 `delete` |
| `entryId` | 创建时分配的正整数，同一会话内不复用 |
| `revision` | 从 1 开始，每次被接受的更新或删除递增 1 |
| `body` | `create` 和 `update` 的完整新正文 |
| `source` | `user` 或 `agent`，记录由哪个入口写入 |

有效集合通过 `getBranch()` 读取当前分支，按时间顺序重放其最近一次 `reset_boundary` 之后的记录计算得出。创建记录确定条目展示的来源，后续操作的作者不会改变它。`list`、`get`、正文未变化的 `update`、被拒绝的操作以及容量检查失败都不追加记录。先校验身份和 revision，再判断 no-op。 编号分配通过公开的 `getEntries()` 读取整个会话，恢复两个序列的高水位，其中包含本进程仍持有但尚未消费的提交所预留的编号，以及宿主已持有的记录占用的编号；这次扫描只分配编号，不把其他分支的正文、回执或操作应用到当前分支。会话或扩展重载会重建分配状态，普通 `/tree` 与 `/clear` 不会降低计数。有效集合仍只通过 `getBranch()` 重放得出。

一次确认的用户提交或一次 Agent 写调用对应一个固定的 `operationId`。一条消息被宿主消费一次就追加一次操作；携带同一身份重新提交属于该操作的重试，而不是写入第二条。重试已接受的调用时返回其回执，不追加第二次操作；Agent 重试通过内部 tool call id 在持久化日志中找回已被接受的记录，并核对调用内容一致，而不是先分配新身份。新的 `create` 调用创建独立条目，即使正文与其他条目相同；新的用户提交只与它提交的文本对齐。交付重试复用已接受操作的身份。

编号超出安全整数范围，或无法可靠建立分配状态时，给出明确错误，不回绕，也不悄悄从 1 重新开始。早期候选写入的会话使用字符串身份；当前版本在其有效范围内把这些记录报告为不支持的格式，不与整数混用，并采取干净切换：旧记录不做迁移，用户新建会话或重置范围后开始新的编号，旧字符串身份不参与新格式的整数计数。损坏范围的处理见容量与重置一节。

操作被接受意味着它已出现在宿主的内存分支日志中。公开的 `appendEntry` 没有返回值，也不确认持久化。跨请求、会话切换和恢复时均以分支重放为准；工具结果是回执，不是状态存储。回执不得宣称宿主尚未确认的落盘保证。非持久会话中的 Pin 只在当前进程内存续，两个入口都须明确展示该限制。

### 会话持久化与责任边界

规范记录位于宿主维护的会话日志中。创建会话文件、写入、退出时保存、恢复以及复制其中的消息都属于宿主职责。Pin 读取宿主提供的分支，并重放其中的记录；它不自行创建、修复、迁移或写入该文件，也不承诺宿主没有报告的结果。

两个入口都拿不到宿主的写入确认：公开的 `appendEntry` 没有返回值，公开的消息接口也不返回交付回执。因此回执说明的是扩展已经提交或已经接受了什么，而不会宣称宿主已经保存。公开的会话接口同样没有暴露持久化操作，扩展无法确认落盘；在核对的源码中，会话文件由宿主侧路径创建（[ReadonlySessionManager](https://github.com/can1357/oh-my-pi/blob/61b1b8aef634334eaf1412afd003a763e1d1b9c1/packages/coding-agent/src/session/session-manager.ts#L376-L400)）。

扩展不绕过这条边界：不暗中新建另一个会话，不直接写日志文件，不调用私有方法，也不额外启动模型轮次来促成保存。宿主没有保存的会话、在扩展之外丢失或截断的文件，以及始终没有到达该分支的恢复，都会让 Pin 无记录可重放。这些属于宿主结果而非 Pin 缺陷，这类失败的证据必须说明是哪一侧造成的。

非持久会话的 Pin 只在进程存活期间有效。两个入口都说明这一限制，而不暗示持久存储。

### 尾部变更

普通变更以会话日志中的自定义消息送达模型，使用专门的自定义类型和 `details.operationId`。`create` 或 `update` 消息包含条目 id、revision 和完整新正文；`delete` 消息记录被取消固定的条目。宿主保留其追加位置，并重建自定义类型和 details，因此扩展可以识别自己的投影，不需要靠正文相等或数组下标猜测。用户确认的写入已经由用户发出的那条消息承载，扩展不会为它再追加一份相同正文；上面的投影用于承载 Agent 的写入，并重新表达请求中缺少载体的变更。它们能否跨进程退出保留，取决于宿主的会话保存与恢复。 其 metadata 同时携带原始会话身份，因此来自其他会话的投影不会被当成当前周期的记录；扩展按当前分支与重置周期过滤投影，并把宿主的原始身份留在内部 metadata 中，不放进条目号或回执正文。

投影与恢复出的正文都把引用文本与管理说明分开组织，并标注条目 id、revision 和来源。恢复出的正文是保留的会话上下文：其中的事实和仍然适用的用户要求继续有效，固定不会让这段文本获得它原本没有的权限，也不代表重新执行已经完成的任务。Agent 写入的正文不会因为被固定而获得用户或系统指令权限。说明既不宣称所有固定正文都不是指令，也不在引用文本里重复管理封套。OMP 通过共享转换器处理普通自定义消息，可能生成 developer role 的消息，因此最终 role 以 Provider 边界处的核对结果为准。

Agent 的写入不得启动模型轮次。调用发生在 Agent 已经在执行的轮次中，投影通过公开的非主动交付模式发出：`pi.sendMessage(message, { deliverAs: "nextTurn", triggerTurn: false })`。运行中宿主把这条消息放入隐藏的后续输入队列，不调度续跑；会话空闲时直接追加，也不开启轮次。只设 `triggerTurn: false` 并不够，因为默认交付路径会进入 steering 并排空队列。扩展交给宿主的结果使用同一非主动交付模式。用户确认的写入改为走普通用户路径，会话空闲时由宿主启动轮次，运行中则作为 steering 进入；那一轮就是用户的请求，并承载该操作。由于宿主可能要到下一次普通 prompt 才把这类消息追加进历史，调用返回不视为已交付：当前请求仍从规范记录推导自己的变更，因此这一轮中接受的变更必须通过这些记录到达该请求。位置保持稳定：结果绑定对应用户消息，Agent 变更绑定对应工具调用的完成位置，宿主随后追加的同身份副本由扩展去重，而不是放到新历史尾部。载体因宿主压缩或 pruning 消失时，按快照与日志顺序恢复位置，不按数组下标猜测。验收必须检查同一次运行中的连续工具步，因为每次构建请求都把同一条缺失投影重新追加到新尾部，会让普通历史一增长前缀就发生移动。

### 压缩边界

请求准备时，扩展找到当前分支生效重置边界之后、最近一次实际提交的压缩条目。重放截至该提交条目的 Pin 集合，形成该周期的基准快照。快照紧跟对应的宿主压缩摘要插入，只过滤本扩展已被该快照覆盖的投影。边界之后接受的变更留在尾部。

边界取自分支上已提交的条目，不取压缩前通知，也不依赖压缩后回调是否已经执行。提交前接受的操作并入快照，提交后接受的操作留在尾部。被弃用、失败及取消的推测压缩不推进边界。Provider 原生远端压缩的不透明载荷保持原样；扩展快照必须在 Provider 有效输入中位于对应重放之后。仅在 context 钩子中插入不能证明最终位置，还须在实际请求中核对转换、规范化及后续处理器的影响。

没有已提交的压缩边界时，扩展不生成基准快照，由尾部消息单独表达当前集合。

快照携带边界身份和 Pin 内容，不含当前时间、请求计数、随机值或按请求产生的估计值，因此状态不变时投影逐字节一致。由于投影在每次请求时从分支重新计算，回调丢失、通知脱离或压缩后重启都不会丢失基准。

### 缓存行为

- 读操作和正文未变化的更新不改变规范 Pin 状态与已发布投影。普通工具调用及结果仍可增加宿主历史。
- 被接受的写入出现在尾部：Agent 的写入以扩展投影的形式出现，用户的写入以用户提交的那条消息出现。已发布的消息保持原位置，更早的指令不被改写。
- 基准快照只在已提交的压缩边界变化，而此时宿主已经重建了历史。
- 工具定义、工具清单及其 schema 与当前 Pin 集合无关。
- 除约定的压缩归并和过期队列过滤外，扩展不改写更早的系统、工具和历史内容。

验证比较 Provider 可见的有效上下文；宿主发送链式增量时，还要纳入前序请求。单独归因宿主自身的变化，检查 Pin 是否引入可避免的前缀改写。

### 容量与重置

- 通过 `/ctx-pin` 任一形式写入的操作 `source` 为 `user`；通过 `ctx_pin` 写入的操作 `source` 为 `agent`。`list` 和 `get` 报告创建时记录的来源。Agent 在普通用户消息要求下执行的操作 `source` 为 `agent`：决定来源的是入口，而不是请求背后的意图。
- 容量按 UTF-8 字节计算，由两个入口在任何状态变更之前执行：单条正文上限 16,384 字节，同一分支活跃条目合计上限 65,536 字节。超过任一上限的操作被拒绝，不改变任何状态，并报告上限和当前用量。两个上限都是组件 README 中说明的常量。
- 成功执行 `/clear` 后，宿主追加 `reset_boundary`，当前 Pin 集合随之结束。状态重放、压缩边界选择和排队消息过滤均以该边界之后的周期为准。`/new` 新建独立会话，使用自己的空集合。`/fresh` 只重置 Provider 流状态、不清空本地历史，因此不清空 Pin。跳转到另一分支时重建该分支自己的周期。
- 校验与追加通过同一条同步路径完成。工具路径在真正接受之前校验；`/ctx-pin` 在宿主消费确认消息时校验。两个入口都将观察到的会话、分支、重置周期和条目 revision 与当前状态比较。草稿保留开始编辑时显示的 revision，并在消费时比较；工具传入 `expectedRevision`。任何 await 之后都重新核对，revision 过期时拒绝操作，而不是覆盖期间发生的编辑。消费之前被编辑、放弃或取消的草稿不写入任何内容；接受之后取消不回滚操作，也不产生第二次写入。 两个命令形式都通过同一个提交函数和同一条同步校验路径，草稿与打开时的 revision 比较。
- 生效重放范围内出现未知 `schemaVersion`、损坏记录或非法操作序列时，有效状态不可用。关闭该范围的写操作、新快照及恢复投影，保留已有日志记录和已发布消息，并输出受限诊断。读取报告状态不可用，不能返回看似完整的部分集合或空集合。不得跳过损坏的更新或删除后，将旧 revision 当成当前状态。当前分支或重置周期变化后重新判断。 早期候选写入的字符串身份按不支持的格式报告，不当作整数读取，见规范状态一节。

## 考虑过的替代方案

- 继续使用宿主自带的 `context_notes` 作为机制。在判断是否需要新组件时考虑过。它按分支保存一整本笔记并沿当前路径恢复，但没有条目级操作，每次写入都替换整本笔记，而且最新笔记被插在消息数组开头，每次编辑都会移动此前稳定的字节。启用实验模式还会改变自动上下文维护方式。
- 每次变更后在前部重新发布完整 Pin 集合。在决定变更放置位置时考虑过。它是最简单的完整可见做法，并作为对照基线保留，但每次编辑都会缩短请求中可复用的前缀。
- 只追加尾部消息，不生成基准快照。在决定固定文本如何跨压缩存续时考虑过。仅靠尾部追加会让固定文本完全受压缩影响，只有日志还留有模型已经看不到的正文。
- 采用更广泛的上下文管理扩展。在比较检索、归档查询、历史折叠、完整上下文规划与条目级 Pin 需求时考虑过。这些额外职责超出本组件范围。将现有第三方能力引入本仓库，也会违反第一方所有权边界。
- 接管宿主的压缩流程。在决定扩展需要对摘要掌握多少控制时考虑过。这样做可以自行撰写摘要，但原生 remote、snapcompact、handoff、soft 和 shake 各有自己的语义，扩展改为读取已提交的边界。
- 在 `/ctx-pin` 对话框确认时直接写入状态。在决定用户操作何时生效时考虑过，早期候选也采用过。它的回执即时返回，但操作在消息到达宿主之前就已生效，因此排队、被编辑或撤回的消息可能留下用户从未发送的变更，运行中的轮次也不会把它作为 steering 收到。
- 由扩展解析自然语言请求并执行管理操作。在考虑普通消息如何在不依赖模型的情况下管理 Pin 时考虑过。它需要命令语法、与普通叙述的优先级规则和自己的错误路径，而工具已经为 Agent 提供了该操作，因此请求交给模型处理。
- 启动模型轮次以促使宿主保存会话。在绕过初始 fresh 会话的文件边界时考虑过。它会花掉用户没有要求的轮次来处理宿主职责，而且仍然不会返回写入已发生的确认。

- 保留生成的 UUID 字符串作为条目与操作身份。在重新审视身份格式时考虑过。已有观察中没有出现由 UUID 引起的模型异常，因此改用整数的理由是易读与上下文占用：整数更易读、在列表里更容易挑选，也在每条携带它的消息里更短。
- 给确认消息追加身份标记。在简化消息结构时考虑过，早期候选也用过。标记把操作号与作用域标记放在消息里，扩展因此不必匹配文本；但它让消息与用户写下的话不一致，要求用户保留一个自己没写过的标签，并让删除语句读起来像机器输出。改为把消费到的消息与扩展交给宿主的文本对齐后，消息保持可读可编辑，文本没有被持有的提交不会被接受。
- 保留持久化的 `title` 作为列表标签。在调整条目呈现方式时考虑过。标题会与它所标注的正文脱节，而整数 id 加正文派生的摘要已经足以区分条目，因此删除该字段，也不再需要重复标题的去重规则。
- 把写操作声明为 write 档。在确定工具审批分类时考虑过。这会让 `always-ask` 下对一次不涉及文件、进程或网络资源的创建发起询问，而宿主策略本已管辖该工具，因此所有 action 统一声明最低档。
- 继续用默认发送路径加 `triggerTurn: false` 交付 Agent 变更。在确定交付路径时考虑过。宿主会把这类消息归入 steering 并排空队列，可能增加轮次或取消同批工作；因此改用显式的非主动交付模式。

## 结果

- 规范记录与它的模型投影是两件事：记录存在而投影缺失时，固定文本会从请求中消失；恢复也可能重复交付，或在快照之后交付更旧的 revision。跨重启、排队和压缩的恢复路径保留在验收范围内。
- 压缩边界取自分支上已提交的条目。被弃用的推测压缩不推进边界，边界选错则会丢失已接受的变更，或让已被取代的 revision 重新生效。
- 其他扩展可能在宿主压缩摘要周围插入消息，或由后序处理器丢弃快照；最终 Provider 转换也可能改变钩子中看似正确的顺序。验收须检查被测扩展组合的最终请求。
- Provider 原生远端压缩让部分历史保持不透明。扩展保持该载荷原样，并让快照与它正确排序，不声称已经对不透明内容去重。
- 固定正文与累计 revision 消耗上下文。字节上限约束的是活跃正文，不约束 token、元数据或旧尾部消息，完整请求仍可能在压缩后溢出。
- 保留的上下文可能被理解为授予权限，会话内整数也可能跨会话冲突或从错误范围恢复。来源标注、说明措辞与会话级高水位是控制手段，Provider 边界的最终 role 以核对结果为准。
- 非主动交付可能把变更推迟到下一次普通 prompt，因此当前请求始终从规范记录推导自身的变更。
- 请求采集可能泄露凭据；采集在写盘前排除敏感传输字段，且不改动实际发给模型的请求。
- 一次提交靠扩展交给宿主的那段文本识别，与它文字相同的消息在被持有期间认领一次，并随提交结算。
- 组件检查纳入 `pnpm check`；自动检查不能代替在受支持运行时上的实机验收。

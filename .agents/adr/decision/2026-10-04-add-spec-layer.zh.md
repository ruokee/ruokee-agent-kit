# ADR 决定：增加规格层

Decision owner: Ruokee
Decision writer: OMP Claude Opus 5.5

[English](./2026-10-04-add-spec-layer.md) | 中文

## 动机

在 `.agents/spec/` 下维护中英双语规格（spec），描述每个组件和仓库领域当前的目标状态，ADR 继续记录决策及其理由。

仓库里原本没有一类文档专门从整体上说明每个组件应该做成什么样。这些信息分散在现行决定、决定中按日期追加的 `变更` 条目和组件文档里。例如，`omp-system-prompt` 的目标由[只用模板决定](../archived/2026-10-04-use-system-prompt-template-only.zh.md)、[模型级提示词规则决定](../archived/2026-09-14-add-model-prompt-rules.zh.md)和组件的 README 文件对共同构成。读者必须把这些来源合在一起，才能知道当前目标。Skill 体系和仓库约定的规则同样分散在现行决定、[AGENTS.md](../../../AGENTS.md) 和[仓库 README](../../../README.zh.md) 中。

ADR 本来就不承担这个职责。[ADR 指南](../README.zh.md)把 ADR 定义为持久决定的理由和契约，后继决定"不复制组件的实现规格"。组件文档面向安装和使用组件的人，仓库说明和 README 面向在仓库中工作的贡献者。它们都没有为维护者和 Agent 提供一份关于组件、Skill 体系或仓库约定的目标、边界和验收的当前说明。

## 分析

以下现行决定与规格层有关。它们都与规格层不冲突，因此本决定不反转任何决定。

- [同目录维护中英文公开文档](./2026-09-07-colocate-bilingual-docs.zh.md)要求普通公开页面使用同目录、互相链接的 `name.md` 和 `name.zh.md` 文件对，入口页面使用 `README.md` 和 `README.zh.md`。仅面向维护者的材料只在目标读者需要时翻译。spec 面向维护者和 Agent，让 spec 保持双语在该决定允许的范围内。该决定中详细命令、参数和规范行为留在其所属页面的规则同样适用于 spec。
- [明确 ADR 机制与内容边界](./2026-09-23-clarify-adr-content-boundaries.zh.md)规定 ADR 必须包含的内容。它写明迁移一条约束性条款并不取消它，指向持续变化的当前文档不能替代历史契约。spec 直接修改、不保留历史，所以不能替代决定中记录的契约。ADR 的内容规则、生命周期和术语表保持不变。
- [保持可分发组件自包含](./2026-08-24-keep-components-self-contained.zh.md)禁止组件内部引用组件以外的文件，并允许组件目录以外的仓库级文档引用组件。`.agents/spec/` 下的 spec 属于这类文档。该决定的 `变更` 条目把每个组件的维护声明留在组件内部。
- [以共享的 Skill 参考文件源码统一 tk 使用模式](./2026-10-04-share-tk-skill-references.zh.md)为每项 tk 行为指定 `projects/tk/docs/` 下的一个主要所属页面，包括系统边界、不变量和验证。tk 的 spec 如果复述这些内容，就会出现第二个所属页面，所以 spec 改为链接到所属页面。
- [建立第一方 Agent 能力工具集](./2026-08-20-establish-first-party-capability-kit.zh.md)只在有真实组件时才增加新的顶层结构。`.agents/` 已经存在，规格层不增加顶层区域。

## 决定

### 位置与覆盖范围

spec 放在 `.agents/spec/`，与 `.agents/adr/` 并列。该目录根部有一对 README，说明 spec 的写法，以及 spec、ADR 和组件文档如何分工。

`projects/` 下的每个组件都有 spec，`projects/tk` 作为整体也有。Skill 体系（包括 `skills/` 和 `variants/zh/skills/` 下的中文变体）有 spec，仓库级约定和宿主兼容策略也有。spec 文件清单由 spec README 维护。spec 依据现行决定和组件文档编写。归档决定不是当前依据，不搬入 spec。

### spec 格式

每份 spec 是同目录的一对 `name.md` 和 `name.zh.md`，互相有语言链接。两种语言在同一次变更中更新，描述同一目标。

spec 按适用情况使用以下小节：目标、非目标、公共面、不变量、宿主下限、验收标准、相关 ADR。不适用于该对象的小节省略，例如仓库约定没有宿主下限。

spec 描述当前的目标状态，直接在原文上修改，不保留修订历史、审查记录或任务记录。

### 分工

spec 说明对象应该做成什么样。ADR 记录持久选择、理由、替代方案和后果。组件文档告诉用户如何安装和使用组件。

spec 不复述组件文档或现行决定所拥有的内容。命令和参数参考、设置表、文件格式以及组件的维护声明，spec 都链接到所属页面，只写读者需要的上下文。相关 ADR 以链接列出。

spec 不得与现行决定冲突。如果改变目标会与现行决定冲突，先走 ADR 流程，再修改 spec。不改变持久选择的 spec 修改不需要 ADR，是否需要 ADR 仍按现有规则判断。ADR 保持现有内容规则：决定可以链接 spec，但链接不能替代决定所记录的契约。

改变组件目标的变更，在同一次变更中同时更新 spec、组件和组件文档。

### 引用方向

引用只能单向。spec 可以链接组件文件、组件文档和 ADR。可分发组件内部的任何文件都不链接 `.agents/spec/`、不写出其中的路径，也不依赖它，因此安装后的组件不需要仓库也能使用。

spec 是说明性文档。可分发组件的运行、构建和分发都不依赖 spec。仓库检查继续遵循现行规则，不为 spec 新增检查或其他读取机制。

### 仓库入口

仓库中指引读者阅读 ADR 规则的说明和入口文档，同时写出 `.agents/spec/` 及其用途。

## 考虑过的替代方案

**继续把目标状态放在 ADR 和现有文档中。** 这是原有做法，不增加需要维护的文件。读者仍需合并现行决定、其 `变更` 条目和组件文档或仓库文档，才能知道组件、Skill 体系或仓库约定的目标。

**把每份 spec 放进对应组件目录。** 这在选择位置时考虑过。spec 会紧挨它描述的代码，但会随组件分发，把用户不需要的维护者材料带给用户。Skill 体系和仓库约定也没有单一的组件目录可以放它们的 spec。

**spec 只用英文编写。** 这在权衡新文档集的翻译成本时考虑过。它能把这部分成本减半，但用中文审阅目标时，就没有其他公开文档和 ADR 所具备的、可独立阅读的成对副本。

**把现行决定中的规格段落替换为指向 spec 的链接。** 这在需求分析中被提出，用于在有了 spec 之后去掉重复内容。它与 ADR 机制决定中"指向持续变化的当前文档不能替代历史契约"的规则冲突，需要反转该决定。规格层的需求不要求这样做。

## 结果

维护者和 Agent 可以找到每个组件、Skill 体系、仓库约定和宿主兼容策略的一份当前说明，包含目标、边界、不变量和验收，并链接到拥有细节的决定和文档。

spec、现行决定和组件文档可能描述同一目标。之后的变更只更新其中一处时，其余几处就会过时，按过时文本工作的维护者或 Agent 会朝错误的目标实现，或报告不存在的冲突。链接到所属页面能缩小重叠，但不能消除，也没有机械检查能证明它们一致。因此改变目标的变更在同一次变更中更新 spec。

如果某份 spec 漏掉了决定后来的变更，或带入了归档决定中的规则，它描述的目标就没有现行决定支持，按它工作可能删掉现行决定仍然要求的行为。spec 与现行决定不一致时以现行决定为准，并修正 spec。

同一份 spec 的中英文版本可能逐渐不一致，两种语言的读者会按不同的目标工作。两个版本在同一次变更中修改，并一起审阅。

增加或删除组件，或者增加需要单独 spec 的仓库领域时，同时更新 spec README 中的 spec 清单。

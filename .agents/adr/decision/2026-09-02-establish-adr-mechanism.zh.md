## 动机

仓库需要一个长期且可检索的位置，保存架构、职责归属、宿主接入、持久化格式、分发和仓库流程决定。它们的理由不能依赖对话、Task 材料、临时分支，或从代码和 Git 历史中反推。

此前的 Agent Note 机制建立了这个位置，但它的术语和单一文档状态模型不符合实际使用。提案和决定具有不同用途，rejected 和 archived 分别描述这两类文档的终止状态，而不是另外两种文档类型。

仓库还需要让提案先进入 `main` 再开始实现，明确更新或反转当前决定的规则，限制文件名长度，永久保留生命周期目录，并避免用虚构的替代方案和风险填充章节。

## 决定

### 术语和位置

使用 **ADR** 作为架构决策记录的主要术语。本仓库使用 `.agents/adr` 作为 ADR 根目录。

使用 `proposal` 和 `decision` 作为两类文档。`proposal/` 保存活跃提案，`rejected/` 保存被拒绝的提案，`decision/` 保存当前决定，`archived/` 保存归档决定。目录表达类型和状态，因此 ADR 文件头不包含 `Status`。

英文使用 `Create decision`、`Update decision` 和 `Reverse decision` 作为动作短语。`Reverse decision` 是动词短语，不是名词标签。新决定在文件头元数据块中使用 `Reverses` 链接归档决定，归档决定在同一位置使用 `Reversed by` 链回新决定。

在 ADR 根目录维护 `glossary.md` 和 `glossary.zh.md`。第一版术语表只包含 ADR、提案、决定、更新决定和反转决定。每项只有一段简明定义，并注明另一种语言中的对应术语。新增术语前，维护者必须明确确定其含义。

### 需求接入与提案合入

规划新需求前，先搜索活跃提案和当前决定。判断需求是增加无关能力、无冲突地扩展当前决定，还是与当前决定冲突。

除非维护者要求其他拆分方式，一项需求创建一份提案。一份提案可以创建多项决定、反转多项决定，或同时执行两种操作。

实现开始前，将获准提案作为独立变更合入 `main`。实现从更新后的 `main` 创建新的短期分支。实现完成后，在实现变更中创建新决定、更新没有冲突的决定、反转冲突决定，并删除已落实的提案。Git 历史保留独立合入的提案。

### 格式与双语维护

每项 ADR 由同目录的英文和中文文件对表示，并保留双向语言链接。两份文件在语义上具有同等权威，并且一起移动。语义冲突会阻止合入，直到维护者解决该冲突。

英文提案使用 `# ADR proposal: <title>`，中文提案使用 `# ADR 提案：<标题>`。正文包含 `Motivation`、`Proposal`、`Alternatives considered`、`Acceptance criteria` 和 `Risks`。被拒绝的提案增加 `Rejection reason`，然后冻结。

英文决定使用 `# ADR decision: <title>`，中文决定使用 `# ADR 决定：<标题>`。正文包含 `Motivation`、`Decision`、`Alternatives considered` 和 `Consequences`。归档决定保留该格式，修复关系链接和事实链接后冻结。

两类文件都保留 `Decision owner` 和 `Draft writer`。owner 是负责维护者，draft writer 记录最初起草者，后续维护时不改变。关系和生命周期元数据位于 `Draft writer` 之后、双向语言链接之前。路径、命令、API 名称、元数据字段和代码标识符在两种语言中都保留仓库原有拼写。

`Motivation` 或 `动机` 是第一个必需正文章节，并准确说明考虑或采用这项选择的具体理由。描述性的三级标题可以整理必需章节，但不能替换必需的二级标题。

包括日期、语言后缀和扩展名在内的完整文件名不得超过 60 个字符。

### 更新和反转决定

新增内容与当前决定没有冲突时，使用更新决定。将内容追加到最后的 `Changes` 或 `变更` 章节，并使用带日期的三级标题。新增内容值得单独成为 ADR 时，链接另一项决定。

冲突选择使用反转决定。先合入一份提案，列出需要反转的每项决定。实现完成后，将每项旧决定仍然有效的规则和获得接受的提案整合成完整的新决定。在新决定的文件头元数据块中增加 `Reverses`，在归档决定的文件头元数据块中增加 `Reversed by`，并在同一变更中将旧文件对移动到 `archived/`。

归档决定在文件头元数据块中增加 `Archived: YYYY-MM-DD`，并将它放在可选的 `Reversed by` 之前。归档决定不再是当前权威，当前文档不得将它作为当前决定引用。

### 编写和维护

只记录 ADR 编写前真实存在，或讨论中实际考虑过的替代方案。风险只记录可能造成的不良结果。适用章节没有内容时写 `None` 或 `无`。

即使目录内已有 ADR 文件，也使用 `.gitkeep` 将 `proposal/`、`decision/`、`rejected/` 和 `archived/` 保存在 Git 中。

维护者负责批准或拒绝提案，以及归档决定。Agent 可以在授权工作中研究、起草、实现和评审 ADR 变更，但未经明确授权不能作出这些生命周期决定。

事实路径、名称或验证入口变化时，保持当前决定准确。事实维护不能表达冲突选择。

依靠评审、仓库搜索和 Git 历史，不增加专用 ADR Skill、分类体系、翻译 sidecar、归档 manifest 或自定义检查器。只有重复维护或实际错误证明某项机械约束确有必要时，才增加最小检查。

完整编写规则见 [ADR 指南](../README.zh.md)、[英文版本](../README.md)和双语术语表。

## 考虑过的替代方案

**保留 Agent Note 作为主要术语。** 这样可以保留旧路径和大量现有文本，但会继续使用掩盖提案与决定差异的单一文档状态模型。

**只写英文或只写中文。** 任一选择都会让部分仓库受众失去审计入口。公开仓库需要英文，维护者需要完整中文材料。

**将两种语言写进同一文件。** 单文件不会漏建对应文件，但每位读者都必须加载两种语言，并且两个章节之间仍可能出现语义偏差。

**只在普通文档和 Git 历史中保存决定。** 这样不需要专用机制，但不能稳定地区分提案、当前决定、被拒绝的提案和归档决定，也无法一致保存理由。

**立即采用分类体系、sidecar、manifest 和自定义验证。** 这些机制在规模更大时可能有用，但仓库尚未出现足以证明其维护成本合理的失败。

**现在将 ADR 维护制作成 Skill。** 该机制仍在使用中发生变化。此时分发 Skill 会在规则尚未稳定时将它们固化。

## 结果

仓库拥有一个可检索的双语位置保存提案和决定，目录名直接表达文档类型和生命周期状态。

提案和实现需要两个分支以及两次主线提交。这增加了一道评审边界，但可以防止实现暗中定义本应由它遵循的理由。

两份权威语言文件可能发生偏差。同一变更审查和双向链接可以降低风险，但无法机械证明语义一致。

反转决定需要重新组成完整的当前合同。评审必须对照归档决定和获得接受的提案，避免遗漏仍然有效的规则。

ADR 的查找依赖简短文件名和仓库搜索，而不是中央索引。只有活跃目录已经明显难以检索时，才增加结构。

术语表刻意保持精简。普通用词和尚未确认的近义词不会成为合同术语。

## 变更

### 2026-09-03：细化替代方案与风险的编写规则

Agent 不得为了填充必需章节而编造替代方案或风险。替代方案必须真实进入过选择范围，并描述另一种做法，而不是事实、要求、约束、验收标准、实现细节或对当前方案的复述。风险必须写明提议或遗漏可能造成的可信不良后果，不能把事实、要求、约束、不变量、验收标准或待办改称为风险。没有合格条目时，只写 `None` 或 `无` 的章节就是完整章节。

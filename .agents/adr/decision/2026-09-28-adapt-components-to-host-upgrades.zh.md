# ADR 决定：宿主内组件随宿主升级保持适配

Decision owner: Ruokee
Decision writer: OMP DeepSeek V4.1 Flash

[English](./2026-09-28-adapt-components-to-host-upgrades.md) | 中文

## 动机

把宿主维护责任与版本门禁分开，并记录第一方宿主组件跨宿主升级所遵循的规则。

第一方组件把代码加载进宿主进程运行，既要随宿主升级继续可用，又要保留受维护旧宿主所需的行为。维护责任、实现选择与验证证据需要各自明确，不能用同一个版本范围代替，因此这些组件遵循统一规则：组件在自身文档中声明维护下限，宿主 peer 声明继续列出宿主包但不承载该下限，更新保留受维护旧宿主原有的结果，验证强度随实际行为影响确定，提高下限只能通过独立决定。本决定不要求这些组件采用相同实现。

## 分析

peer 范围参与依赖解析，不是纯维护说明。例如，npm 默认安装 peer 依赖，无法解析的冲突可能导致安装失败（[npm package.json 文档](https://github.com/npm/cli/blob/latest/docs/lib/content/configuring-npm/package-json.md)）。将维护下限放进 peer 范围，可能阻止实际可用的宿主安装组件；具体结果取决于安装路径，不能把 npm 的行为当作所有宿主上的实测结果。

## 决定

### 适用范围

本决定适用于本仓库所有将代码加载进宿主进程运行的组件。仅作为说明或配置分发、不在宿主进程内执行代码的材料不属于兼容对象。不同宿主使用各自的版本线，各组件独立声明维护下限。

组件依赖的独立协议保留自身合同。宿主维护下限不替代协议兼容要求与安全检查。

与升级无关的新功能在其自身需求中决定。本决定不要求组件采用新的宿主 API，兼容工作以用户可见结果衡量，而不以使用了哪个宿主 API 衡量。

### 在组件 README 中声明最低维护版本

每个组件在自身 `README.md` 与 `README.zh.md` 的兼容性小节声明最低维护宿主版本，这一小节是维护下限的权威说明。组件只声明下限，不设置维护版本上限，仓库不维护受支持版本白名单或公开支持矩阵。

下限表达维护责任。它不承诺后续宿主版本继续可用，不声称下限及以上的每个版本都经过验证，也不为下限以下增加维护承诺。低于下限的宿主不被阻止：能够运行的组件可以在那里运行，只是没有维护承诺。

下限依据交付组件的加载条件、必要能力和行为确定。API 首次出现的记录与已有验证可以提供依据，但都不能单独证明整个组件的兼容范围。开发依赖版本与最近实测版本不能直接充当维护下限。首次声明须经维护者确认；证据不足时记录缺口，不发布猜测值。

### 宿主 peer 不承载维护范围

宿主 peer 声明继续列出组件实际使用的宿主包，其范围不按维护下限收窄，也不添加维护版本上限。安装条件、自定义元数据字段和运行时版本检查同样不承载维护限制。已经以不带版本限制的形式声明宿主包的组件保持该写法。

独立演进的普通依赖保留真实约束。开发依赖保持锁定以提供可复现的检查环境，不成为声明。组件实际需要的能力或语义差异由适配实现与自身检查处理，不用来恢复宿主 peer 上的数值范围。本决定不新增仓库检查器、兼容管理器或受支持版本表，生产代码也不读取组件文档来决定如何运行。

### 保留受维护旧宿主所需的行为

在下限范围内，更新保留旧宿主原有的结果。一套实现能同时覆盖时复用同一套；确有差异时同时保留各宿主需要的实现，并记录选择它们的具体条件。宿主发行版提供原生能力时，先比较用户可见结果、配置和失败行为；等价的原生路径可以替换包装实现，而其他受维护宿主仍然需要的包装继续保留。

仍受维护宿主需要的行为保留下来；承担该行为的实现可以重构、合并或替换，只要行为仍在并按改动验证。仅为维护范围之外的宿主服务、且不承担其他行为的代码可以直接清理，不必等待下一次提高下限。组件独立新增的功能自行决定可用条件，可以说明只在部分宿主可用；本决定不要求各宿主具有相同的功能集合。

### 隔离宿主实现与组件行为

业务规则依赖组件需要的操作与数据，而不依赖宿主 API 的具体形态。适配实现承担宿主 API、数据转换，以及入口与实际宿主的绑定；接口围绕组件需求设计，不重述宿主的整套 API。已有边界直接复用；确有差异或转换需要时再补，普通函数、参数或对象即可满足。只是镜像一次调用的转发不值得增加边界。

宿主耦合随改动逐步整理。同一差异只有一个归属，避免多个调用点各自判断同一件事；组件文档说明每项差异的原因、位置、选择条件、失败行为和验证依据。组件保持自包含：不建立跨组件兼容库，组件不链接其他组件，也不链接仓库外层材料。

### 按能力选择实现，版本判断需要证据

实际能力或输入结构足以区分行为时，由它们决定。只有形态无法区分、且存在有记录的语义差异时，才使用版本范围；即便如此，它也是适配实现内部的局部判断，而不是组件层面的通用门禁。函数存在并不能证明事件顺序、字段含义、投递或持久化没有变化。

稳定接口可以在入口绑定宿主时选择。动态输入、设置、会话状态以及进程级补丁的所有权，按各自生命周期读取和检查。组件不把所有假设冻结为激活时的快照，也不对不会变化的假设在每次调用时重新解析。

### 加载与失败边界保持局部

兼容分析覆盖生产入口及其传递导入，因为运行时探测无法修复在工厂执行之前就失败的模块解析。已知稳定存在的模块可以继续静态导入。存在真实跨版本差异、且缺失时组件仍需工作的模块，把加载失败纳入该适配项自身的边界；把未变化的静态导入挪到别处不算处理。

失败按能够安全隔离的最小功能单元处理，使相互独立的功能继续工作。必要前置条件在宿主允许的范围内先于副作用完成。注册或安装中途失败时，停止后续动作并释放组件自己拥有的资源，不承诺宿主没有提供的原子注册或完整回滚。没有等价实现时，受影响功能保留宿主原生行为，或通过现有诊断通道报告不可用，给出有界、可定位的原因，不假报成功。安全停用是故障处置而不是兼容，本身也不解除维护责任。

### 验证强度随改动确定

验证强度由实际行为影响决定，不设行数或比例阈值，代码类别本身也不是验证门槛。小修改完成相称检查即可通过，不统一要求重跑旧宿主实机；重大行为修改必须在相关真实宿主场景中验证，即使只改了几行。各组件既有发布合同保持原有强度。

仓库不规定固定的验证版本组合。可以选择下限、目标版本或独立适配路径的代表环境，只要证据足以支撑结论。

验证记录写明证据类型、所用版本、场景和未覆盖范围。模拟接口只验证组件自身的逻辑、分支与失败处理，不能代替真实宿主加载；真实宿主包、模板与 CLI 的观察也须分别说明。涉及事件、工具可见性、UI、消息投递、持久化或进程补丁时，检查用户可见结果，而不只看处理函数的返回值。

测试环境依赖较新宿主内部模块而无法运行，不等于生产入口不兼容。既有验证结果保留原有版本和场景，不改写为维护承诺；仓库既有检查仍须执行。

### 提高下限通过独立决定完成

默认保留现有下限。组件确实无法同时服务两个宿主版本，或者同时兼容需要大幅改造而提高下限所需改动明显更小时，才可以提出；提案需要写明组件、现有与建议下限、具体冲突或改造及其投入比较、合理的替代方案、证据，以及用户将失去的旧宿主支持。维护投入是维护承诺本身要求的工作，不作为额外成本，任何时候也不列为风险。

每次提高下限都是维护者决定的独立 ADR，并在同一次变更中更新声明、实现、测试和必要的迁移说明。一个组件提高下限不移动其他组件的下限，决策之外的批准不能代替 ADR。提高下限也无法恢复宿主发行版已经删除的能力。

### 本决定改变的现行决定

现行决定中有两项条款与本决定不能同时成立，由完整后继决定反转，各自合同的其余部分保持不变：

**状态栏的数值宿主声明。** [状态栏决定](../archived/2026-09-24-use-omp-status-bar-widget.md)把直接宿主导入声明为范围 `>=18.1.8 <19` 的 peer 依赖、把 OMP 18.x 写为目标，并由此得出 Package 与该范围绑定的结果。承担维护责任的数值范围会继续替能够正常服务的宿主决定能否安装，两者不能同时成立。[后继决定](./2026-10-02-scope-token-metrics-to-conversation.zh.md)保留该合同的其余内容：Widget、Provider 契约、内置清单、推测估计及其限制，以及每次发布打标签前执行的真实 TUI 检查；维护下限改在组件 README 中声明。

**QoL 的期限机制。** [QoL 决定](../archived/2026-09-22-recover-interrupted-turns.md)要求宿主提供受支持的请求级超时接口后，组件使用该接口并停用进程级机制，没有为仍然受维护、但不具备该接口的宿主保留条件。无条件停用与本决定要求保留受维护旧宿主所需行为之间不能同时成立。[现行 QoL 决定](./2026-10-04-align-remote-compaction-cache.zh.md)按实际宿主选择期限实现，沿用本决定的原则，并保留该决定的其他规则。

其余现行决定经核对后保留：

- [系统提示词决定](./2026-09-30-render-system-prompt-from-host-template.md)已经声明不受限制的 peer，禁止读取宿主版本来决定安装资格、激活、转换、诊断或回退，并保留结构检查与证据边界。补充文档化的维护下限不改变其中任何一条。
- [模型提示词规则决定](./2026-09-14-add-model-prompt-rules.md)沿用上述决定的 peer 合同。文档化的下限是声明，不是回到版本条件。
- [Pin 决定](./2026-09-15-add-omp-context-pin.md)没有记录版本门禁。其激活逻辑读取宿主的公开 API，这一点保持不变，声明部分按本决定处理。
- [tk 集成决定](./2026-09-02-integrate-tk-tools-with-harnesses.md)保留独立 runtime 协议及其 `runtime_compat`、CLI 与驱动合同、组件格式、预检校验、预检失败时注册数为零的结果，以及后续 `registerTool` 失败时唯一的一条有界诊断。宿主维护下限不是 runtime 协议变更。
- [组件自包含决定](./2026-08-24-keep-components-self-contained.md)要求每个组件的文档和材料随组件分发，因此下限写在组件内，不建立仓库级表格。
- [现行 QoL 决定](./2026-10-04-align-remote-compaction-cache.zh.md)保留按调整项分别记录验证的做法，以及宿主升级时重新阅读引用源码、更新受影响章节的义务；修改声明的下限不能替代这些工作。

## 考虑过的替代方案

### 用数值范围声明维护责任并限制使用

维护下限可以继续放在 peer 依赖中，或作为激活条件。这样能提前拒绝范围外的宿主，但会同时拒绝具备必要能力、实际可用的宿主，不能满足维护下限不阻碍使用的要求。

### 每次都验证下限与目标宿主

固定组合能统一验证步骤，但会对行为不受影响的小修改施加相同要求，也不能覆盖组合之外的独立适配路径。因此按实际影响选择验证范围，并保留组件既有发布要求。

### 仅在实施记录中批准提高下限

这一方式保留维护者批准，却不为每次支持范围缩减留下独立的公共理由。因此每次提高下限仍需独立 ADR。

## 结果

- 取消数值门禁后，原先被拒绝的宿主可以进入加载与运行流程。若能力与行为检查漏掉真实不兼容，组件会在使用时失败，而不是在安装时失败。
- 维护下限表达的是维护责任而不是验证。下限及以上的宿主仍可能存在未验证的差异，因此这份重量由证据记录与逐次改动的验证承担，而不是由数值承担。
- 为不同受维护宿主保留的多套实现可能在后续维护中分别演进，使旧宿主上的配置含义或失败行为偏离同一功能的合同。
- 保留下限会推迟提高下限本可换来的精简改动，而每次提高都需要独立决定与评审；组件可能为某个本可放弃的宿主版本承担兼容工作。
- 本决定不新增检查器、兼容管理器或受支持版本表，因此声明没有任何机械手段强制执行，只能靠评审与组件文档保持准确。

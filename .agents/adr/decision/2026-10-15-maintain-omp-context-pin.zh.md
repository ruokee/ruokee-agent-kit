# 维护 omp-context-pin 扩展

Decision owner: Ruokee
Decision writer: OMP DeepSeek V4.1 Flash
Reverses: [添加 omp-context-pin 扩展](../archived/2026-09-15-add-omp-context-pin.zh.md)

[English](./2026-10-15-maintain-omp-context-pin.md) | 中文

## 动机

把 omp-context-pin 扩展作为第一方宿主组件继续维护，让固定文本在压缩后逐字保留，并把它的容量取值留在组件里，而不是留在本决定里。

组件已经存在，它的公开用法记录在组件 README 中，[组件规范](../../spec/omp-context-pin.zh.md)陈述它的目标、不变量与验收标准。本决定沿用其中仍然有效的规则，并记录一处变化：容量取值离开决定，成为组件的默认值。归档记录保留了当时的分析、原来的替代方案，以及取值当时的样子。

## 决定

### 组件范围

- 第一方包 `@ruokee/omp-context-pin` 位于 `projects/omp-context-pin/`，通过 `package.json` 的 `omp.extensions` 元数据声明扩展入口，并且只使用公开的 OMP 扩展 API。它不导入宿主私有模块，不修改上游源码，也不依赖其他仓库组件。
- 该包只注册一个斜杠命令 `/ctx-pin` 和一个原生工具 `ctx_pin`。`/pin` 由宿主保留，因此组件使用不同名称。
- 工具通过 `action` 参数分发列出、读取、创建、更新与删除。它的 schema 保持稳定，不枚举当前条目，工具定义也不随 Pin 集合变化。更新与删除要求已有的条目 id 和调用者观察到的 revision；未知 id、过期 revision 与空正文都被拒绝。任何 action 都不执行隐式 upsert 或改名式的创建。
- 条目 id 和操作号都是会话内的正整数。条目 id 在首次成功创建时分配，同一会话内不复用。操作号在每次用户提交或每次新的 Agent 写调用时分配，该提交或调用重试时复用，因此允许出现空号。
- 所有 action 声明最低审批档 `read`。组件不写用户配置，也不自行增设授权、确认或来源准入；类型、存在性、revision、容量与记录完整性校验保留，因为它们让操作作用于正确的数据，而不是限制谁能调用。

### 交互

- `/ctx-pin` 打开当前分支的条目列表，提供创建、查看、编辑与删除。`/ctx-pin add <正文>` 直接提交创建，因为发出这条命令本身就是确认。列出、查看与起草都是只读操作：不发送消息，不改变 Pin 状态，也不中断正在执行的轮次。
- 确认的写入会变成一条普通用户消息，消息内容就是这次要固定的正文，不附加标记。扩展把宿主消费的消息与它交给宿主的文本对齐，因此消息保持可读可编辑；在持有该提交期间，与它文字相同的无关消息会被认领一次。匹配只限本进程持有的提交，以及当前的会话、分支与重置周期；身份从不靠时间戳、数组位置或输入来源推断。
- 操作在宿主消费这条消息、并由扩展完成校验之后生效。入口随后报告已接受、无变化或未应用及原因，结果与正文分开表达，也不自行启动轮次。
- Agent 在它已经执行的轮次中通过 `ctx_pin` 管理 Pin，工具结果就是它的回执。用户也可以在普通消息里要求执行 Pin 操作，此时预期 Agent 像调用该请求所需的其他工具一样调用该工具；扩展不会把自然语言解析成 Pin 操作，两条路径也都不保证模型选出正确的工具、参数或时机。
- 入口决定来源：通过 `/ctx-pin` 写入的操作记录为 `user`，通过 `ctx_pin` 写入的操作记录为 `agent`，条目保留创建时记录的来源。

### 规范状态

- 规范记录是会话日志中的追加式操作日志，通过宿主的公开条目接口、以组件自己的自定义类型写入。每个被接受的写操作追加一条记录，携带记录版本、操作号、action、条目 id、revision、正文与来源。
- 有效集合通过读取当前分支并按时间顺序重放其最近一次重置边界之后的记录计算得出。其他分支的记录不会应用到当前分支。
- 被接受意味着操作已进入宿主的内存分支日志。公开的追加接口没有返回值，也不确认持久化，因此回执只说明扩展提交或接受了什么，不宣称宿主已经保存。
- 编号分配通过读取整个会话恢复两个序列的高水位，其中包括本进程仍持有但尚未消费的提交所预留的编号。这次扫描只分配身份，不把其他分支的正文、回执或操作应用到当前分支。重载会重建分配状态，普通的树跳转与 `/clear` 不会降低计数。
- 编号超出安全整数范围，或无法可靠建立分配状态时，给出明确错误，不回绕，也不悄悄从 1 重新开始。早期候选以字符串身份写入的记录按不支持的格式报告，不当作整数读取；旧记录不做迁移，在这一点之后新建的会话或重置周期从新的编号开始。
- 生效重放范围内出现未知记录版本、损坏记录或非法操作序列时，该范围不可用：写入与新的快照被拒绝，已有记录与已发布消息保留，并输出受限诊断。读取报告该状态，不返回看似完整的部分集合或空集合；被重置取代的那段周期里的损坏记录不会阻断当前范围。
- 组件不自带持久化。它不创建会话文件，不写日志文件，不调用私有方法，不新建第二个会话，也不启动轮次来促成保存。会话文件及其写入、退出时保存、恢复与复制都属于宿主。宿主不持久化的会话只在进程存活期间保留 Pin，两个入口都说明这一限制，而不暗示持久存储。

### 尾部变更

- 被接受的变更以会话日志中的自定义消息送达模型，使用自己的自定义类型，并在 details 中携带操作号。用户确认的写入由用户发出的那条消息承载；投影承载 Agent 的写入，并重新表达请求中缺少载体的变更。投影能否跨进程退出保留，取决于宿主的会话保存与恢复。
- Agent 的写入不得启动模型轮次：它通过公开的非主动交付模式发出，会话空闲时直接追加，运行中入队但不调度续跑。用户确认的写入走普通用户路径，会话空闲时由宿主启动轮次，运行中则作为 steering 进入。
- 位置保持稳定。回执绑定对应用户消息，Agent 变更绑定对应工具调用的完成位置，宿主随后追加的同身份副本被去重，而不是放到新的尾部位置。载体因宿主压缩或 pruning 消失时，按快照与日志顺序恢复位置，不按数组下标猜测。
- 投影与恢复出的正文把引用文本与管理说明分开组织，并标注条目 id、revision 与来源。恢复出的正文是保留的会话上下文：其中的事实和仍然适用的用户要求继续有效，固定不会让这段文本获得它原本没有的权限，也不代表重新执行已经完成的任务。Agent 写入的正文不会因为被固定而获得用户或系统指令权限。宿主可能通过共享转换器把普通自定义消息生成为 developer role，因此最终 role 以 Provider 边界处的核对结果为准。

### 压缩边界

- 请求准备时取当前分支生效重置边界之后、最近一次实际提交的压缩条目。重放截至该条目的记录，形成该周期的基准快照。快照紧跟对应的宿主压缩摘要插入，只过滤本扩展已被该快照覆盖的投影；边界之后接受的变更留在尾部。
- 边界取自分支上已提交的条目，不取压缩前通知，也不依赖压缩后回调是否已经执行。被弃用、失败及取消的推测压缩不推进边界。Provider 原生远端压缩的不透明载荷保持原样，快照在其对应重放之后排序。
- 快照携带边界身份与 Pin 内容，不含当前时间、请求计数、随机值或按请求产生的估计值，因此状态不变时逐字节一致。由于投影在每次请求时从分支重新计算，回调丢失、通知脱离或压缩后重启都不会丢失基准。
- 没有已提交的压缩边界时，组件不生成基准快照，由尾部消息单独表达当前集合。

### 缓存行为

- 读操作与正文未变化的更新不改变规范状态与已发布投影。它们的普通工具调用及结果仍可增加宿主历史。
- 被接受的写入出现在尾部：Agent 的写入以组件投影的形式出现，用户的写入以用户提交的那条消息出现。已发布的消息保持原位置，更早的指令不被改写。
- 基准快照只在已提交的压缩边界变化，而此时宿主已经重建了历史。
- 工具定义、工具清单及其 schema 与当前 Pin 集合无关。
- 除约定的压缩归并和过期队列过滤外，扩展不改写更早的系统、工具和历史内容。
- 验证比较 Provider 可见的有效上下文；宿主发送链式增量时，还要纳入前序请求。单独归因宿主自身的变化，并检查 Pin 是否引入可避免的前缀改写。

### 容量

- 两个入口在任何状态变更之前按 UTF-8 字节校验单条正文与分支活跃正文合计。超过任一上限的操作被拒绝，不改变任何状态，并报告上限、当前用量以及该操作会达到的大小。
- 当前取值是组件自身的默认值，由组件 README 说明。调整取值属于组件变更，本决定不固定它们。
- 成功执行 `/clear` 后，宿主追加重置边界，当前 Pin 集合随之结束；状态重放、边界选择与排队消息过滤随后以该边界之后的周期为准。`/new` 新建独立会话，使用自己的空集合。`/fresh` 只重置 Provider 流状态、不清空本地历史，因此不清空 Pin。跳转到另一分支时重建该分支自己的周期。
- 校验与追加通过同一条同步路径完成。工具路径在真正接受之前校验，`/ctx-pin` 在宿主消费确认消息时校验。两者都将观察到的会话、分支、重置周期与条目 revision 与当前状态比较，并在任何 await 之后重新核对，revision 过期时拒绝操作，而不是覆盖期间发生的编辑。消费之前被编辑、放弃或取消的草稿不写入任何内容；接受之后取消不回滚操作，也不产生第二次写入。

### 宿主维护

- 组件按 OMP 18.5.0 的下限维护，不设维护版本上限，并在组件 README 的兼容性小节声明，该小节是这一下限的权威说明。该下限不参与安装或激活，组件也不保留只为更早宿主存在的代码路径。
- 组件检查纳入仓库检查入口。自动检查不能代替在真实宿主上的验收。

## 考虑过的替代方案

组件早先选择所考虑过的替代方案保存在归档记录中。反转本身有过这些选择。

- 保留本决定里的容量取值，每次调整取值时反转决定。在判断取值该放在哪里时考虑过。每次调整都要带一份提案、一份后继决定和一次归档，比一个随用法而定的默认值所需的记录更多。
- 用 `## 变更` 追加一条记录来移除取值。作为更轻的机制考虑过。追加内容只在不与决定冲突时允许，而撤回现有条款约束力的记录与之冲突，因此这条路不成立。
- 把取值写进规范层。在核对哪一层持有取值时考虑过。组件规范陈述目标、不变量与验收标准，并把体积上限指向组件 README。在那里重复可调取值会多出一处需要同步的地方。

## 结果

- 固定正文与累计 revision 消耗上下文。字节上限只约束活跃正文，不约束 token、元数据或更早的尾部消息，完整请求仍可能在压缩后溢出。
- 上限不再出现在本决定里，组件 README 成为它们唯一的说明来源，调整取值的组件变更与这里记录的内容不冲突。
- 活跃正文超过当前上限的分支仍能列出与读取条目，但在合计降到上限以内前拒绝新的写入；取消固定不受容量约束，因此这样的分支可以自行回到限内。
- 规范记录与它的模型投影是两件事：记录存在而投影缺失时，固定文本会从请求中消失；恢复也可能重复交付，或在快照之后交付更旧的 revision。跨重启、排队和压缩的恢复路径保留在验收范围内。
- 边界选错会丢失已接受的变更，或让已被取代的 revision 重新生效。其他扩展可能在宿主压缩摘要周围插入消息，或由后序处理器丢弃快照，最终 Provider 转换也可能改变钩子中看似正确的顺序，因此验收须检查被测组合的最终请求。
- Provider 原生远端压缩让部分历史保持不透明。组件保持该载荷原样，不声称已经对不透明内容去重。
- 保留的上下文可能被理解为授予权限，会话内整数也可能跨会话冲突或从错误范围恢复。来源标注、说明措辞与会话级高水位是控制手段，Provider 边界的最终 role 以核对结果为准。
- 非主动交付可能把变更推迟到下一次普通 prompt，因此当前请求始终从规范记录推导自身的变更。
- 一次提交靠扩展交给宿主的那段文本识别，与它文字相同的消息在被持有期间认领一次。
- 请求采集可能泄露凭据；采集在写盘前排除敏感传输字段，且不改动实际发给模型的请求。
- 组件检查纳入仓库检查入口，不能代替在真实宿主上的验收。

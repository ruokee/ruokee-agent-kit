# ADR 决定：按范围执行开发检查并保留完整合并门禁

## 动机

开发与审查使用受影响检查，每个最终合并候选使用完整检查，除独占的串行说明文档工作外均使用独立 worktree。

Markdown 与 Rust 基础检查无法发现 TypeScript 组件或原生适配器中的失败，因此仍需要明确的完整入口。但每次审查前都运行完整检查，也会为文档与单组件工作准备无关环境并重复无关检查。将完整验证安排在最终候选上，可以减少重复工作，不从任何合并结果移除覆盖。

工作目录隔离、依赖准备和检查选择解决不同问题。worktree 保护并行改动，不意味着需要每个组件的依赖。Markdown 也可能是运行时、打包或测试输入，扩展名本身不能确定仅格式检查的范围。

## 决定

### 入口、覆盖与门禁

根 [package.json](../../../package.json) 提供开发和审查使用的 `pnpm check:changed`、完整自动化入口 `pnpm check`、Markdown 与 Rust 基础入口 `pnpm check:base`，以及选择回归测试入口 `pnpm check:selector`。请求审查前，提交任务改动、保持工作树干净，并通过覆盖分支的受影响检查。

完整入口只执行一次基础序列：Markdown 格式、Rust 格式和 Rust 测试。随后按[覆盖与命令参考](../../../README.zh.md#完整合并验证)维护的顺序执行全部明确列出的 OMP 目标，每个目标先检查类型，再运行测试。之后依次执行 tk 原生适配器测试、Skill 生命周期测试和选择器回归测试。根聚合复用组件脚本并明确列出目标，不递归发现组件。

所有审查修改完成后、合并前，必须对干净且已提交的最终候选完整验证。候选必须包含目标 `main`。记录候选提交与 tree、目标提交、命令及结果。新增受跟踪变更、待提交内容、候选变化或目标前进，都使原成功结果失效，需要对新的最终状态完整验证。已授权的 squash merge 必须使用未变化的目标，并产生已验证的 tree。

受影响成功不是完整合并验证，也不授予合并或推送权限。保留[分支工作流决定](./2026-08-20-use-trunk-based-squash-workflow.zh.md)规定的短期分支与 squash 授权边界。自动化成功不能证明真实模型行为、交互界面正确性或实机行为；现有组件场景验证义务继续生效。

### 受影响范围与失败行为

从 `HEAD` 与本地 `main` 或明确指定基线 ref 的 merge base 选择路径。范围包含已提交、已暂存、未暂存和非忽略的未跟踪变更、删除路径及重命名两端。选择器只读 Git，不 fetch 或改变状态。

由仓库维护显式映射。已知范围选择必需检查的并集，不重复执行，并保留完整入口中的相对顺序。仍存在的变更 Markdown 接受仓库 Prettier 检查。已知消费者优先于说明文档规则：组件源码与测试 Markdown 选择对应组件，tk 打包树选择 tk 检查，安装文档选择 Skill 生命周期检查。未知组件和未知 Markdown 不假定为仅格式检查。

共享检查输入、选择器变更、未知范围、不可靠的基线或历史，以及不可靠的路径收集，选择一次完整检查，而不是局部执行。缺少 Git、checkout 无效或 index 存在未解决冲突时直接失败。缺失必需可执行文件或选中范围本地依赖也失败，不能用全局工具掩盖本地准备缺失。删除说明文档可以无需格式命令，但缺失必需输入不能跳过。

报告基线、路径来源、选中范围与命令、回退原因及失败位置。检查按顺序执行，保留子命令输出，并在首次失败时以非零状态停止。前面的成功不能掩盖后续失败。完整回退不递归调用选择器。

### 工作目录与环境归属

代码、配置、脚本、并行任务和无法确认独占的任务使用独立 worktree。只有主工作目录干净、没有并行工作且能够确认独占时，串行说明性 Markdown 或 ADR 任务才可以使用主工作目录。编辑前切到短期分支，不直接在 `main` 上编辑或提交。

运行时模板是源文件，不是说明文档。被测试消费的说明文档仍可以适用目录例外，但保留消费者检查。范围超出例外或失去独占条件时，先停止共享目录编辑，并在继续前将已有工作保存在独立 worktree 中。选择器不确认独占，也不管理分支和 worktree。

环境准备仍是显式步骤。使用声明的 pnpm 版本及其支持的 Node.js、Git，选中 tk 时使用包含 `rustfmt` 且满足 tk 构建前提的 Rust，以及兼容所选组件锁文件的 Bun。开发阶段准备根锁定依赖和选中环境，完整检查或回退准备全部环境。保留独立组件依赖树和锁定版本。[准备矩阵](../../../README.zh.md#检查前置条件)定义命令与系统前提，包括完整 Skill 生命周期覆盖所需的 Git 和非 root 环境。

包管理器内容缓存可以在同一信任边界内复用，不同分支不共享可写依赖目录或构建输出。检查不安装依赖、格式化源码或升级工具。成功检查保持受跟踪源码与配置不变；构建和测试可以创建自身正常使用的临时与生成文件。pre-commit 格式化钩子保留其职责。

### 维护与兼容

新增组件、调整必需自动化检查或引入文档消费者时，同步更新明确的完整聚合、选择器映射和回归测试。[README.md](../../../README.md)、[README.zh.md](../../../README.zh.md) 和 [AGENTS.md](../../../AGENTS.md) 描述相同的门禁、准备边界、目录例外和成功失效条件。组件文档与实际调用的命令保持一致。

本决定反转旧检查决定中的审查前完整检查条款，并保留其完整覆盖、明确顺序、基础入口、独立依赖树、可见失败传递、非修改性检查和场景义务。[Markdown 格式化决定](./2026-09-02-format-markdown-with-prettier.zh.md)继续有效。本次变更不迁移组件布局，不新增 workspace、任务图依赖、CI 平台、覆盖率阈值、测试框架、模型服务调用或 Harness 安装操作。

## 考虑过的替代方案

**保留审查前完整检查，只在开发阶段使用受影响检查。**这保留原门禁，但审查迭代会重复无关准备与检查。完整检查安排在最终状态，不从合并结果移除。

**所有任务都使用 worktree，按范围准备依赖。**这保留最简单的隔离规则，也仍是无法确认独占时的回退。但串行说明文档仍需要新建目录并准备根工具。

**迁移 workspace 或引入任务图工具。**这些工具提供包图和受影响任务，但会改变独立锁文件、环境准备和仓库结构，超出需要。显式范围复用已有检查。

**所有 Markdown 只检查格式，不追加消费者检查。**这更简单，但运行时模板、打包内容和受测试约束的安装步骤可能直到最终验证才暴露回归。受影响范围保留已知消费者。

**保留基础入口，另行记录手动完整序列。**这让缺失检查可见，但每个调用者仍须记住序列。明确的完整入口让成功结果具有完整含义。

## 结果

文档和局部组件工作可以在开发与审查时仅准备和执行受影响环境。共享或未知变更仍需要全部完整前提。每个合并结果保留完整自动化门禁，无关组件失败仍可能阻塞文档合并。

消费者映射是需要维护的知识，不是自动语义依赖分析。遗漏关系可能在最终验证前漏掉回归，显式映射、选择测试、保守回退与强制完整检查限制该损害。

目录例外与最终候选比对依赖操作者确认。错误独占可能暴露并行编辑，过期成功结果可能放行未经测试的合并内容。worktree 回退及候选、目标和 tree 核对是必要条件；选择器不提供合并服务或持久成功凭据。

## 动机

仓库通过双语 ADR 提案与决定保存长期选择，明确理由、必要契约、生命周期与反转依据。

问题出现在单条记录内部：读者有时无法仅凭记录辨认选择及其理由，修订会带入属于组件文档或代码的实现材料，而正常演进曾通过反转一份范围很广的决定来处理，原因只是旧记录把文档数量、内部机制或阶段性不做事项固定成了永久约束。

## 分析

现有规则已经排除进度日志和复制的实现清单，[tk 文档决定](./2026-09-11-align-tk-usage-patterns.zh.md)也将详细契约交给所属页面。这些规则没有说明何种技术细节对决定必不可少，也未要求开头在不依赖标题的情况下说明所做的工作。

按现行规则作反转，仍可能留下过窄的承诺。归档的 QoL 决定（[2026-09-20](../archived/2026-09-20-add-omp-qol.zh.md)、[2026-09-21](../archived/2026-09-21-reuse-a-matching-compaction-patch.zh.md)）中，一份记录在进程已登记其他所有者时停用进程级调整，其后续决定允许匹配的激活保留已安装的补丁。后者确实改变了一条明确规则，因此需要反转。tk 文档的后续决定则把一处固定译法当作必须重述整套文档政策的冲突，使反转范围超过了实际变化的术语。

本次记录的清理还碰到了前一决定中的一条限制。前一决定的[格式与双语维护](../archived/2026-09-02-establish-adr-mechanism.zh.md#格式与双语维护)冻结了被拒绝的提案，并且对归档记录只允许关系链接和事实链接修复。即使调整结构与措辞保留了全部已记录含义，仍然超出该规则的授权，因此本决定只为该次清理增加一次例外，并把前一决定其余仍然有效的规则一并承接。

需要分别判断新选择是否违背已采纳的规则，以及原规则是否需要写到这样的细节程度。反转更少本身不能说明决定更好，既有明确约束在被正式改变前仍然有效。

## 决定

### 术语和位置

使用 **ADR** 作为架构决策记录的主要术语。本仓库使用 `.agents/adr` 作为 ADR 根目录。

使用 `proposal` 和 `decision` 作为两类文档。`proposal/` 保存活跃提案，`rejected/` 保存被拒绝的提案，`decision/` 保存当前决定，`archived/` 保存归档决定。目录表达类型和状态，因此 ADR 文件头不包含 `Status`。

使用 `Create decision`、`Update decision` 和 `Reverse decision` 作为动作短语。`Reverse decision` 是动词短语，不是名词标签。新决定在文件头元数据块中使用 `Reverses` 链接归档决定，归档决定在同一位置使用 `Reversed by` 链回新决定。

在 ADR 根目录维护 `glossary.md` 和 `glossary.zh.md`。第一版术语表只包含 ADR、提案、决定、更新决定和反转决定。每项只有一段简明定义，并注明另一种语言中的对应术语。新增术语前，维护者必须明确确定其含义。

### 需求接入与提案合入

规划新需求前，先搜索活跃提案和当前决定。判断需求是增加无关能力、无冲突地扩展当前决定，还是与当前决定冲突。

除非维护者要求其他拆分方式，一项需求创建一份提案。一份提案可以创建多项决定、反转多项决定，或同时执行两种操作。

实现开始前，将获准提案作为独立变更合入 `main`。实现从更新后的 `main` 创建新的短期分支。实现完成后，在实现变更中创建新决定、更新没有冲突的决定、反转冲突决定，并删除已落实的提案。Git 历史保留独立合入的提案。

### 格式与双语维护

每项 ADR 由同目录的英文和中文文件对表示，并保留双向语言链接。两份文件在语义上具有同等权威，并且一起移动。语义冲突会阻止合入，直到维护者解决该冲突。

英文提案使用 `# ADR proposal: <title>`，中文提案使用 `# ADR 提案：<标题>`。正文包含 `Motivation`、`Proposal`、`Alternatives considered`、`Acceptance criteria` 和 `Risks`，并可在 `Motivation` 与 `Proposal` 之间加入可选的 `Analysis`。被拒绝的提案增加 `Rejection reason`，然后冻结。

英文决定使用 `# ADR decision: <title>`，中文决定使用 `# ADR 决定：<标题>`。正文包含 `Motivation`、`Decision`、`Alternatives considered` 和 `Consequences`，并可在 `Motivation` 与 `Decision` 之间加入可选的 `Analysis`。归档决定保留该格式，修复关系链接和事实链接后冻结。

提案记录 `Draft owner` 和 `Draft writer`，决定记录 `Decision owner` 和 `Decision writer`。owner 是负责维护者，writer 记录最初起草者，后续维护时不改变。关系和生命周期元数据位于起草者字段之后、双向语言链接之前。路径、命令、API 名称、元数据字段和代码标识符在两种语言中都保留仓库原有拼写。

包括日期、语言后缀和扩展名在内的完整文件名不得超过 60 个字符。

### 编写记录

`动机` 是第一个必需正文章节，并准确说明考虑或采用这项选择的具体理由。其首句必须说明对象及具体问题、拟作出的变更或目标，不依赖标题、链接或后文才能理解。新增能力不必被包装成缺陷。反转提案开头说明拟作出的改变，后继决定则说明它记录的完整选择。

可选的 `分析` 章节位于 `动机` 之后、`提议` 或 `决定` 之前；没有实质分析时省略。分析只包含影响选择的观察、证据、约束、推导和不确定性，不能成为实施计划或调研笔记的副本，也不与动机或替代方案章节相互重复。

ADR 记录一项完整且连贯的长期选择、理由、必要边界与归属、重要公开承诺，以及重大的兼容、安全、成本和失败后果。仅当省略某项技术细节会妨碍读者理解选择或重要取舍，或丢失必须保留的契约时，才将它写入 ADR，并只写必要片段。配置权威、身份不可变性或进程级副作用，即使需要具体标识符说明，也可能是必需内容。完整的 API 与配置表、schema、命令参考和持续维护的清单，归所属公开文档。内部函数名、算法步骤、逐文件修改、执行计划、测试命令与验证日志，归实现文档、代码、测试或任务材料。验收标准描述外部可观察的结果，不列测试操作步骤。ADR 链接可访问的公开契约，不把忽略的任务材料作为公开依据。

移走一条有约束力的条款，不等于取消它，必须保留其含义和可访问的引用；历史记录应保留足以解释当时选择的原有细节，指向持续变化的当前文档不能替代历史契约。

区分有意封闭的协议、归属规则或安全边界，与示例和可增长的清单。优先链接清单的所属页面，而不固定数量或穷举文件树；确实需要封闭集合或禁止事项时，说明受保护的边界和理由。当前范围限制或首个版本不需要的选项，不自动成为永久禁令，应在起草决定时说明区别。不能事后把既有禁令降格以绕开它，也不能仅为让文案可扩展而预建抽象或配置。防御规则应针对实际操作及其危害：普通校验、损坏修复、生命周期变化和重复激活可能需要不同前提，保留身份、权限和副作用保护，不用与保护边界无关的全面限制取代它们。

只记录 ADR 编写前真实存在，或讨论中实际考虑过的替代方案；风险只记录可能造成的不良结果。替代方案必须描述另一种做法，而不是事实、要求、约束、验收标准、实现细节或对当前方案的复述。风险必须写明提议或遗漏可能造成的可信不良后果，不能把事实、要求、约束、不变量、验收标准或待办改称为风险。适用章节没有内容时写 `None` 或 `无`。描述性的三级标题可以整理必需章节，但不能替换必需的二级标题。

### 更新和反转决定

新增内容与当前决定没有冲突时，使用更新决定。将内容追加到最后的 `Changes` 或 `变更` 章节，并使用带日期的三级标题。新增内容值得单独成为 ADR 时，链接另一项决定。纯表达维护没有形成新选择，不需要反转。

冲突选择使用反转决定。先合入一份提案，列出需要反转的每项决定，并指出有效条款、新选择，以及二者为何不能同时成立；代码量、增加功能、增加宿主依赖或文件改名，本身都不足以证明需要反转。实现完成后，将每项旧决定仍然有效的规则和获得接受的提案整合成完整的新决定。后继决定保留该决定范围内仍有效的规则，不复制组件的实现规格。在新决定的文件头元数据块中增加 `Reverses`，在归档决定的文件头元数据块中增加 `Reversed by`，并在同一变更中将旧文件对移动到 `archived/`。

归档决定在文件头元数据块中增加 `Archived: YYYY-MM-DD`，并将它放在可选的 `Reversed by` 之前。归档决定不再是当前权威，当前文档不得将它作为当前决定引用。

### 维护

即使目录内已有 ADR 文件，也使用 `.gitkeep` 将 `proposal/`、`decision/`、`rejected/` 和 `archived/` 保存在 Git 中。

维护者负责批准或拒绝提案，以及归档决定。Agent 可以在授权工作中研究、起草、实现和评审 ADR 变更，但未经明确授权不能作出这些生命周期决定。

事实路径、名称或验证入口变化时，保持当前决定准确。事实维护不能表达冲突选择。

归档决定在修复关系链接和事实链接后冻结，被拒绝的提案在修复事实链接后冻结。产生本决定的获准清理，对清理开始时已有的中英文 ADR 配对作一次性例外，允许在不改变已记录的选择、理由、约束、不确定性、历史能力范围、作者、日期和反转关系的前提下调整结构与措辞。该例外不解除其他记录的冻结，也不改变任何有约束力的承诺。它只适用于该次清理，不构成对其他提案的批准，也不是持续修改冻结记录的许可。

依靠评审、仓库搜索和 Git 历史，不增加专用 ADR Skill、分类体系、翻译 sidecar、归档 manifest 或自定义检查器。只有重复维护或实际错误证明某项机械约束确有必要时，才增加最小检查。

完整编写规则见 [ADR 指南](../README.zh.md)、[英文版本](../README.md)和双语术语表。

## 考虑过的替代方案

**保留 Agent Note 作为主要术语。** 这样可以保留旧路径和大量现有文本，但会继续使用掩盖提案与决定差异的单一文档状态模型。

**现在将 ADR 维护制作成 Skill。** 该机制仍在使用中发生变化。此时分发 Skill 会在规则尚未稳定时将它们固化。

## 结果

仓库拥有一个可检索的双语位置保存提案和决定，目录名直接表达文档类型和生命周期状态。

提案和实现需要两个分支以及两次主线提交。这增加了一道评审边界，但可以防止实现暗中定义本应由它遵循的理由。

两份权威语言文件可能发生偏差。同一变更审查和双向链接可以降低风险，但无法机械证明语义一致。

反转决定需要重新组成完整的当前合同。评审必须对照归档决定和获得接受的提案，避免遗漏仍然有效的规则。

区分必要契约与实现材料是判断，而不是机械检查。迁移一条条款，只有在其含义和可访问引用都保留时才成立。

要求在反转前指出具体不相容之处，会收窄反转的适用范围。没有冲突的新增记入带日期的 `变更` 条目，需要时链接独立决定；纯表达维护不形成新选择，既有约束仍然有效。

ADR 的查找依赖简短文件名和仓库搜索，而不是中央索引。只有活跃目录已经明显难以检索时，才增加结构。

术语表刻意保持精简。普通用词和尚未确认的近义词不会成为合同术语。

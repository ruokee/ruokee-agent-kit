## 动机

把 `@ruokee/omp-smart-cache` 作为一个扩展维护，力求避免 OMP 请求出现意料之外的缓存未命中，同时保持普通请求与原生请求路径不变。

[组件 README](../../../../../projects/omp-smart-cache/README.zh.md) 就是这样描述本包，并让各项优化各自成节。[归档决定](../../../archived/2026/10/10-r1-remote-alignment.zh.md)把本包记录为一项优化的归属，组件级条款都写在一份以该能力为主题的决定里。Handoff 缓存对齐属于同一个包，因此组件需要一份记录扩展本身、能力模型及共同维护下限的决定，把每项优化留给各自的决定。否则描述组件的现行文本只覆盖一项能力，第二项能力要么去扩展那份决定的主题，要么让组件级条款没有现行归属。

同一个包里的两项优化还需要一条让它们互不干扰的边界。Remote 对齐与 Handoff 对齐改写的请求不同，协议规则不同，证据各自独立，共享实现不能变成共享合同。

## 决定

### 扩展自包含

在 `projects/omp-smart-cache` 维护自包含包 `@ruokee/omp-smart-cache`，使用自己的原生 `omp.extensions` 入口、设置、检查及中英文文档。遵循[第一方边界](../08/20-first-party-capabilities.zh.md)与[自包含组件合同](../08/24-component-self-containment.zh.md)。不从 QoL 或本地原型导入运行时代码、设置读取器或文档。

本包只维护第一方能力，其携带的每项能力都读取同一份原生设置来源。

### 能力模型

本包携带的每项优化都有自己的决定、自己的原生开关、自己的运行状态与分阶段原因、自己的计数和自己的验收。[Remote 对齐](./10-remote-alignment.zh.md)与 [Handoff 对齐](./12-handoff-alignment.zh.md)是本包携带的两项能力，各有自己的决定。

各项能力共享本包、进程协调器、逐会话登记，以及每个原生方法的一层包装。它们按能力分派，不共享协议规则、载荷形状、原因码或收益证据。一项能力拒绝请求或发现接口不可用时，另一项能力继续工作。每项能力都按需启用，交付前不提供占位开关、模式或接口。

记录能力模型不等于交付能力。本决定既不集成 Handoff 对齐，也不替换已安装的 Handoff 试用扩展；[Handoff 对齐](./12-handoff-alignment.zh.md)记录该能力及其经授权的切换。

### 状态命令

`/smart-cache` 是本包的状态命令，保持一条命令。它不启动模型 turn，按能力分节报告，每节给出该能力的状态、分阶段原因和有界计数。

组件文档以双语维护详细设置与命令、适用性、副作用、原生关闭表现、固定源码基线、实际运行版本及原生替换条件。源码检查、真实 CLI 覆盖、客户端对齐、原生采用和 Provider 测量分别标注。

### 宿主维护下限

遵循[共同 OMP 维护下限](../09/28-host-maintenance.zh.md)，当前为 `18.5.0`。组件 README 双语页拥有下限声明，不设上限或版本白名单。宿主开发依赖锁定共同下限，不收窄宿主 peer，也不增加安装或激活版本门槛。下限只通过该共同决定变更，该决定约束所有面向 OMP 的组件。

### 决定反转

本决定反转[由 smart-cache 提供 remote 对齐](../../../archived/2026/10/10-r1-remote-alignment.zh.md)。那份决定把一项能力作为组件的主题，而 ADR 规则不允许改写现行决定来表达冲突选择。冲突条款如下：

- 组件主题：一份决定同时记录组件与 remote 对齐。冲突：本决定记录扩展，每项能力各有自己的决定。同一份决定不能既是组件合同又是一项能力的合同。
- 组件与公共配置：本包、入口、检查、文档及设置来源都写在 remote 决定里。冲突：这些条款移到本决定，组件级条款归这里；remote 的设置仍归 remote 对齐。
- Handoff：该次迁移既不批准 Handoff 集成，也不替换已安装的 Handoff 原型，且 remote V2 规则不用于 Handoff。冲突：承载 Handoff 能力是本包的主题，[Handoff 对齐](./12-handoff-alignment.zh.md)记录其开关、边界及试用扩展的替换条件。remote V2 规则不用于 Handoff 这条规则留在 [remote 对齐](./10-remote-alignment.zh.md)，也不新增 Handoff 占位接口。

归档决定中所有不冲突的规则继续有效，现在分别落在本决定与 [remote 对齐决定](./10-remote-alignment.zh.md)。对[维护 QoL 模型提示词](../../../archived/2026/09/20-r8-omp-qol.zh.md)的反转随所属条款迁移，由 remote 决定承载。

## 考虑过的替代方案

无

## 结果

- 同一个协调器里的两项能力可能互相干扰。为一项能力所做的改动可能改变共享包装、逐会话生命周期或另一项能力的诊断，于是其中一项的回归会与另一项的改进一起发布。搬移现有能力规则时不改写，并在发布前重跑其验收，是应对手段。
- 本地试用扩展与正式能力可能包装同一批会话方法。若在试用扩展仍被发现时启用某项能力的开关，一个包装可能顶掉另一个，使对齐报冲突停止，或者形成重复同一改写的包装循环。保守的冲突报告与按重启切换限制了影响，但用户仍可能同时安装两者。

## 动机

通过内部 `maintain-spec` Skill 维护完整、独立于实现的双语规格。

删除原实现及其说明资料后，读者仍须能据规格确定要构建什么功能、哪些结果表示符合要求。[前驱](../../../archived/2026/10/04-r2-specifications.zh.md)允许仓库链接，并将详细要求委托给组件页面，使目标依赖那些页面，无法满足独立重建。

当前决定及带日期变更解释持久选择，规格包含完整当前要求。组件指导保持独立可用，设计解释实现，验证记录方法和证据。同一行为可能需要面向各类读者分别表达，避免相近措辞不能成为删除必要要求的理由。

[早期规格决定](../../../archived/2026/10/04-r1-specifications.zh.md)将完整维护方法归给 Spec README。方法继续由 Skill 持有，README 提供项目补充和导航。

## 决定

### 位置

规格位于 `.agents/spec/`，与 ADR 和规则并列。`projects/` 下每个组件都有完整规格集合，tk 作为整体覆盖。对外分发 Skill、仓库约定和宿主兼容也有规格。一个完整主题可采用文件对或多个要求专题，不按内部模块决定拆分。[非规格索引](../../../../spec/README.zh.md)标明每个完整集合，提供双语及相关决定导航。增加或删除对象时同次更新索引。

[maintain-spec](../../../../skills/maintain-spec/SKILL.md) 是 `.agents/skills/` 下的英文内部项目 Skill。仓库规格覆盖它和内部 ADR 维护 Skill。公开 Skill 规格覆盖 `skills/` 与 `variants/zh/skills/`，内部维护不增加公开安装源或翻译分发包。

### 目标权威

规格完整表达当前目的、必要能力、输入条件、可观察结果、失败、边界和验收。已经确认且影响外部合同的命令、参数、设置、格式、文件约定、数值、默认值、上限和兼容承诺都要保留。技术标识本身不使要求成为实现细节。

规格不描述实际实现的内部函数、算法、状态容器、存储或构建组织，也不保存执行和验证记录。混合内容保留必要行为，不强制其机制。不同内部实现可以满足同一规格集合。

当前目标就地修改，不保留修订历史、审查记录、任务记录、会话信息或类似 ADR 的生命周期。编写者读取已确认需求、包含 `Changes` 的当前决定，以及必要文档和实现，以恢复事实和发现遗漏。这些来源不是规格读者的前提。已有实现本身不批准要求。档案解释历史，不代表当前目标。

规格不能与当前决定冲突。改变目标前识别冲突条款，并遵循 ADR 机制。不形成持久选择的变更不需要 ADR。决定可以链接规格，但不能用链接替代自身必要合同。目标变化时同次更新规格、组件及受影响文档。

### 维护归属

Skill 持有[结构](../../../../skills/maintain-spec/SKILL.md#write-the-current-target)、[职责分工](../../../../skills/maintain-spec/SKILL.md#division-of-work)，以及新增、调整、移除、边界澄清的方法。适用章节保持目标、非目标、公共面、不变量、宿主下限、验收标准的顺序，不适用章节省略。相关决定导航放在规格正文之外。

项目补充要求同目录英文和中文配对，描述相同的完整目标，同次维护。语言链接放在非规格索引，不进入规格正文。普通文档仍保留双向语言链接。语言与 Git 政策是项目选择，不是 Skill 的统一要求。

Agent 入口与 Skill 描述在加载前说明适用工作。规格维护、审查或功能工作影响长期目标时加载 Skill，读取有效决定及变更、相关提案、项目补充和必要组件来源，保留未受影响要求并检查结果。只读请求保持只读。

任务 Goal 可以提供已确认需求，但本 Skill 不形成、访谈、修订、重命名或保存 Goal，也不管理任务生命周期。已有 `spec.md` 任务文件仍属于任务材料。工作需要不同职责时使用 `maintain-adr`。

### 引用方向

规格正文不含仓库文件链接，包括组件文件、源码、文档、其他规格、ADR、规则或语言对应页。裸路径、模糊的文档上限和当前实现引用不能替代要求。路径本身属于已确认外部接口时，可以连同完整必要行为出现。非规格索引保存导航，不承接正文省略的功能要求。

其他仓库文档可以链接规格。可分发组件不链接、不写出 `.agents/spec/` 路径，也不在运行、构建或分发时依赖它。内部项目 Skill 可读取所维护的项目文档，不放宽组件自包含要求。

规格仍是 Markdown 检查处理的说明性文档，不新增专用检查器或运行时读取方。维护 Skill 使用原生项目发现，其 Markdown 属于已知文档检查范围。未知文件和共享检查输入仍执行完整验证。

### 验收

按主题核对已确认要求和有效决定，覆盖未链接来源。在所属维护材料中记录要求保留、遗漏补全和实现描述移出。保留数值、条件、例外、权限、兼容性和失败行为。原始要求与当前决定冲突时由维护者裁决，不能从实现推导新目标。

不读取实现和说明资料，只读完整规格集合。读者必须能够重建功能基本一致的实现，并在选择不同内部方法时判断是否符合要求。同时拒绝委托要求和改名为目标的实现描述。核对双语等价、零仓库文件链接、完整外部导航、入站引用及片段。格式检查不能单独证明这些语义性质。

## 考虑过的替代方案

把每份规格放进其组件目录。这样规格靠近代码，但会分发用户不需要的维护者材料。对外分发 Skill 和仓库约定也没有承载整体规格的单一组件目录。

完整维护规则留在 Spec README，Skill 只给步骤。这把方法拆在流程和规则来源两处；所选归属将完整方法保留在一个 Skill 中。

## 结果

读者获得独立于原实现的完整当前要求集合，组件用户保留独立可用的指导。Skill 持有维护方法，非规格索引持有导航和项目补充。

必要行为因不同用途同时出现在规格和用户参考中。变更只更新其中一处，可能产生相反指令或验收，因此受影响文档必须同次维护。过时规格、遗漏决定变更或将历史规则当作当前权威，都可能把实现引向错误目标。实际维护必须确认正确加载、使用来源、保全要求及文档结果；格式不能证明语义一致或 Skill 行为成功。

## 变更

### 2026-10-23 来源范围

读取当前 [ADR 机制](../08/22-adr-mechanism.zh.md)实际保留的记录类型。提案类型移除后，不再寻找活跃 ADR 提案，来源读取要求本身不要求保留该类型。继续读取已确认需求、有效决定及其变更、项目补充和必要来源。任务讨论可以说明批准或建议目标，但本身不批准要求。规格仍以完整、独立于实现为目标。

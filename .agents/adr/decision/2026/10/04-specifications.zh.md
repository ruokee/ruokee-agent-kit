## 动机

在 `.agents/spec/` 下维护中英双语规格（spec），描述每个组件和仓库领域当前的目标状态，ADR 继续记录决策及其理由。

仓库里原本没有一类文档专门从整体上说明每个组件应该做成什么样。这些信息分散在现行决定、决定中按日期追加的 `变更` 条目和组件文档里。例如，一个此后被移除的组件的目标由[只用模板决定](../../../archived/2026/09/07-r4-omp-system-prompt.zh.md)、[模型级提示词规则决定](../../../archived/2026/09/14-r1-model-prompt-rules.zh.md)和组件的 README 文件对共同构成。读者必须把这些来源合在一起，才能知道当前目标。Skill 体系和仓库约定的规则同样分散在现行决定、`AGENTS.md` 和[仓库 README](../../../../../README.zh.md) 中。

ADR 本来就不承担这个职责。[ADR 指南](../../../README.zh.md)把 ADR 定义为持久决定的理由和契约，后继决定"不复制组件的实现规格"。组件文档面向安装和使用组件的人，仓库说明和 README 面向在仓库中工作的贡献者。它们都没有为维护者和 Agent 提供一份关于组件、Skill 体系或仓库约定的目标、边界和验收的当前说明。

## 分析

以下现行决定与规格层有关。它们都与规格层不冲突，因此本决定不反转任何决定。

- [同目录维护双语公开文档](../08/20-bilingual-docs.zh.md)要求普通公开页面使用同目录、互相链接的 `name.md` 和 `name.zh.md` 文件对，入口页面使用 `README.md` 和 `README.zh.md`。仅面向维护者的材料只在目标读者需要时翻译。spec 面向维护者和 Agent，让 spec 保持双语在该决定允许的范围内。该决定中详细命令、参数和规范行为留在其所属页面的规则同样适用于 spec。
- [明确 ADR 内容边界](../08/22-adr-mechanism.zh.md)规定 ADR 必须包含的内容。它写明迁移一条约束性条款并不取消它，指向持续变化的当前文档不能替代历史契约。spec 直接修改、不保留历史，所以不能替代决定中记录的契约。ADR 的内容规则、生命周期和术语表保持不变。
- [保持可分发组件自包含](../08/24-component-self-containment.zh.md)禁止组件内部引用组件以外的文件，并允许组件目录以外的仓库级文档引用组件。`.agents/spec/` 下的 spec 属于这类文档。该决定的 `变更` 条目把每个组件的维护声明留在组件内部。
- [以共享的 Skill 参考文件源码统一 tk 使用模式](../08/29-tk-documentation.zh.md)为每项 tk 行为指定 `projects/tk/docs/` 下的一个主要所属页面，包括系统边界、不变量和验证。tk 的 spec 如果复述这些内容，就会出现第二个所属页面，所以 spec 改为链接到所属页面。
- [建立第一方 Agent 能力工具集](../08/20-first-party-capabilities.zh.md)只在有真实组件时才增加新的顶层结构。`.agents/` 已经存在，规格层不增加顶层区域。

## 决定

### 位置

spec 放在 `.agents/spec/`，与 `.agents/adr/` 并列。该目录根部有一对 README，说明 spec 的写法，以及 spec、ADR 和组件文档如何分工。

`projects/` 下的每个组件都有 spec，`projects/tk` 作为整体也有。Skill 体系（包括 `skills/` 和 `variants/zh/skills/` 下的中文变体）有 spec，仓库级约定和宿主兼容策略也有。spec 文件清单由 spec README 维护。spec 依据现行决定和组件文档编写。归档决定不是当前依据，不搬入 spec。

### spec 格式

spec 的写法、使用的小节与顺序，以及 spec 就地修改这一条，由 [规格层入口页](../../../../spec/README.zh.md#编写-spec)拥有。

### 分工

spec、决定、规则、组件文档、仓库文档与 `AGENTS.md` 的分工，以及 spec 修改与现行决定的关系，由 [规格层入口页](../../../../spec/README.zh.md#分工)拥有。

### 引用方向

引用方向以及 spec 作为说明性文档的性质，由 [规格层入口页](../../../../spec/README.zh.md#引用方向)拥有。

### 仓库入口

仓库中指引读者阅读 ADR 规则的说明和入口文档，同时写出 `.agents/spec/` 及其用途。

## 考虑过的替代方案

**继续把目标状态放在 ADR 和现有文档中。** 这是原有做法，不增加需要维护的文件。读者仍需合并现行决定、其 `变更` 条目和组件文档或仓库文档，才能知道组件、Skill 体系或仓库约定的目标。

**把每份 spec 放进对应组件目录。** 这在选择位置时考虑过。spec 会紧挨它描述的代码，但会随组件分发，把用户不需要的维护者材料带给用户。Skill 体系和仓库约定也没有单一的组件目录可以放它们的 spec。

**spec 只用英文编写。** 这在权衡新文档集的翻译成本时考虑过。它能把这部分成本减半，但用中文审阅目标时，就没有其他公开文档和 ADR 所具备的、可独立阅读的成对副本。

**把现行决定中的规格段落替换为指向 spec 的链接。** 这在需求分析中被提出，用于在有了 spec 之后去掉重复内容。它与 ADR 机制决定中"指向持续变化的当前文档不能替代历史契约"的规则冲突，需要反转该决定。规格层的需求不要求这样做。

## 结果

维护者和 Agent 可以找到每个组件、Skill 体系、仓库约定和宿主兼容策略的一份当前说明，包含目标、边界、不变量和验收，并链接到拥有细节的决定和文档。

spec、现行决定和组件文档可能描述同一目标。之后的变更只更新其中一处时，其余几处就会过时，按过时文本工作的维护者或 Agent 会朝错误的目标实现，或报告不存在的冲突。链接到所属页面能缩小重叠，但不能消除，也没有机械检查能证明它们一致。因此改变目标的变更在同一次变更中更新 spec。

如果某份 spec 漏掉了决定后来的变更，或带入了归档决定中的规则，它描述的目标就没有现行决定支持，按它工作可能删掉现行决定仍然要求的行为。spec 与现行决定不一致时以现行决定为准，并修正 spec。

同一份 spec 的中英文版本可能逐渐不一致，两种语言的读者会按不同的目标工作。两个版本在同一次变更中修改，并一起审阅。

增加或删除组件，或者增加需要单独 spec 的仓库领域时，同时更新 spec README 中的 spec 清单。

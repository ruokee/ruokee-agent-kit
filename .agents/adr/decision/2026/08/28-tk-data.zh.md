## 动机

保留文件承载的任务身份，采用可配置日期布局、显式引用更新和持久扫描报告。

[tk 产品架构](./21-tk-architecture.zh.md)把项目文件作为唯一权威的任务状态，因此载体发现、身份、路径、生命周期、关系、表示、写入、迁移、清理、open 与 closed 任务的名称修复，以及基于文件系统的引用报告都需要明确规则。

## 分析

载体发现把有效任务、普通材料和损坏的受管数据区分开，普通操作要求目标通过严格发现。rename 还负责修复已有字符串名称和可识别生成式目录后缀。若要求旧名称先完整通过校验，运行时就无法执行这项修复，而 UUID 仍是身份，路径仍只是定位器。

closed 任务同样需要名称维护。重新打开是有原因和授权要求的生命周期转换，也无法作为恢复路径：严格加载会在处理生命周期分支之前就以旧名称损坏为由拒绝。名称损坏的 closed 任务会因此没有任何公开恢复路径。

引用报告应当描述用户实际保留的文件，而不是工作树的暂存状态。从 Git 索引枚举候选会漏掉实际存在的未跟踪 Markdown；索引仍有记录、文件已不在工作树的条目又会让整个扫描在 dry-run 或执行开始前失败。

工作区汇聚多个项目的任务时，按天组织能减少月份目录中的条目。monthly 保持缺省，延续已有根目录。普通发现只使用一种配置布局，使导入或部分移动的目录具有明确的受管边界。

路径变化同时影响传入引用和被搬文件内的链接。共享映射和扫描让 rename 与布局操作一致地报告这些影响。显式更新把历史文字的处理留给调用方，持久报告在预览或失败后继续可用。

## 决定

UUIDv7 是权威身份：路径用于定位任务，名称用于描述任务。关系只能存在于同一个任务根目录内，任务不能关联自身，`depends_on` 不能形成环。

普通写入不使用锁、租约、compare-and-swap 或自动合并。多目标操作返回已完成项、未完成项和原始错误，不自动回滚。

关闭和重新打开需要非空原因和当前明确授权。

rename 承担普通改名，以及修复不规范、为空或超长的字符串名称和与元数据不一致的可识别生成式目录；它只容忍这些旧状态缺陷，其他命令继续使用严格发现。

`task_layout` 选择 monthly `YYYY/MM/DD-NN--slug` 或 daily `YYYY/MM/DD/NN-slug`，monthly 为稀疏缺省。普通发现、创建、读取、搜索、check、修复和元数据操作只使用选中布局。子任务放置和发现保持既有规则。

布局 switch 双向转换当前根，最后保存配置。布局 migrate 适配已经导入当前根、显式选中的规范顶层目录，保留配置、元数据模式和 schema。两者保留源日期、序号、slug、身份、元数据、子树和 WAL。最终图验证合并必要的源、目标或选中子树，先按物理目录去重，再检查 UUID、序号、载体、目标和关系。冲突保留已有数据。

rename 和两个布局操作默认保留引用原文。`--update-references` 显式启用改写，可重复的 `--extend-scan` 接受额外 Markdown 文件或目录，支持外部绝对路径。共享规则覆盖 Markdown 目的地、图片、定义、完整任务根路径双链和文本路径。仅文件名双链保持原文。相对链接同时考虑移动后的源和目标，编辑路径区间外内容保留。

有效项目中的每次调用都在受管变化前保存独立不可变 JSON 扫描报告，包括 dry-run、无变化和规划失败。报告包含映射、引用、范围和诊断。摘要及错误另行表达实际完成情况。报告存储失败停止受管变化。`<task_root>/.tk-tmp/reports` 下的报告保留至用户清理，操作收尾及项目 GC 保留该真实目录。报告是辅助快照。

提交顺序为目录移动、可选引用替换，最后提交 switch 配置或 rename 元数据和 WAL。migrate 保留配置。受管写入前复检输入快照及引用扫描。部分 switch 在最终写入前保留源配置，因此已移动任务可能暂时从普通视图中消失。新调用根据当前文件重新规划，借助前次报告核对先前移动。操作不自动回滚。

完整格式和操作细节见[数据模型](../../../../../projects/tk/docs/design/data-model.zh.md)与 [CLI 参考](../../../../../projects/tk/docs/design/cli-reference.zh.md)。

## 考虑过的替代方案

**只支持 split 或 embed。** split 便于直接检查元数据，embed 可以把一个任务保存在单个文件中。两者能够承载相同 schema，不需要把其中一种降为次要表示。

**使用锁、事务或持久恢复计划。** 这些机制会增加协调逻辑和第二个操作状态机。原子替换、完整预检、明确的部分提交结果、活动操作标记和从当前受管文件重试已经覆盖目标工作方式。

**默认改写引用。** 自动编辑可能修改有意保留的历史文字。默认保留并提供显式更新，让调用方决定，同时使用同一次扫描完成报告及改写。

**继续只在 `subtasks_dir` 下发现子任务。** 这种方式缩小扫描范围并保证生成式路径，但改变放置偏好会隐藏有效载体，使导入的子任务无法访问。

## 结果

任务状态保持人类可读，并能跨接口移植。改变 `subtasks_dir` 不再改变可见性，导入或重新组织后的有效子任务载体仍然可用。

任务下完全有效的载体即使原本只是示例，也会成为任务。仓库不应把完整受管载体复制到普通材料中。把有效载体移动到另一个有效任务下，也会在不修改元数据的情况下改变推导父级、关闭阻塞项和同级编号。`check` 和 rename 会显示解析出的父级与路径，便于诊断。

递归发现会比配置路径发现读取更多目录。固定深度和目录上限避免无界工作，但大型或不可读材料树可能让全项目操作以显式错误失败。由于没有永久索引，发现、check、关系校验、迁移、表示切换和修复计划可以使用与候选数量成比例的内存。

rename 可以恢复符合条件的名称，但不会让 read、search、update、生命周期、迁移或表示切换获得宽松加载权限。修复计划需要维护第二种校验模式，且只容许旧名称和可识别后缀缺陷。无效受管祖先可能让后代候选因无法安全确定父级而不能修复。

closed 任务在名称修复中保持生命周期状态。选中扫描范围外的引用，包括非 Markdown 文件，可能被遗漏。显式扩展根允许调用方纳入原本位于外部的 Markdown。

文件系统遍历包含生成或无关 Markdown。显式更新因此可能改写调用方希望保留的历史路径文字。调用方可以在启用更新前检查报告。资源上限及必要 I/O 失败仍明确中止规划。

部分布局提交可能在源配置下暂时隐藏已搬任务。报告保留此前映射供检查，新 switch 计划处理剩余源根。持久报告会积累至用户清理。

普通并发写入采用最后完成写入者语义。多目标失败可能留下合法的部分结果，调用方必须检查已完成项和未完成项后再重试。目录已移动但元数据失败时，活动标记清理后根据当前受管文件重新规划。进程退出后不存在隐藏续跑状态，也不自动回滚。

每个正式发布的 schema 转换都会成为长期维护代码。支持两种表示也要求两条路径具有等价的验证、迁移、正文保留和名称修复行为。

## 变更

### 2026-09-05 创建正文输入

`TASK.md` 仍是由 Agent 维护的普通内容，因此 create 不接受通过 `tk create task --body` 或子任务 item 传入的正文。运行时创建任务时自动生成 `# <规范化名称>` 作为初始正文：split 模式下单独存在，embed 模式下位于受管 frontmatter 之后。创建之后由调用方维护正文，rename 和子任务重试匹配不把正文作为输入或匹配条件。调用方在创建完成后用普通文件操作写入 `TASK.md`。`tk log --body` 保持不变，因为 WAL 条目不属于任务正文。持久元数据 schema 和组件格式均未变化。

### 2026-09-05 WAL 访问

`tk read` 按调用方设置的预算返回最近 WAL，上限为 50 条、16000 字节；字节数按紧凑 JSON 的 UTF-8 编码计算。`summary` 默认使用 5 条和 4000 字节，并省略 WAL 正文。`detailed` 默认使用 50 条和 16000 字节，并包含 WAL 正文。两种视图都返回完整的当前任务正文。`minimal` 不读取正文或 WAL。运行时从最新条目开始选择完整的返回条目，静默省略其余条目且不返回截断标记，最后按时间正序返回。完整历史仍保存在普通的 `wal/YYYY-MM-DD.md` 文件中。

`tk check` 不再通过有界读取路径校验 WAL。流式检查器按固定顺序读取每个普通的每日 WAL 文件并校验其中全部条目，不设置固定的历史总量上限，也不在内存中保存完整 WAL 历史。必要 I/O 失败和取消会使检查不完整，有效 WAL 的规模本身不会产生错误。

### 2026-10-19 任务名称排版

保存名称和生成式后缀可以仅在普通空格 `U+0020`、连字符和下划线的使用或省略上不同。忽略这些字符后，其余文字必须逐字相同。NFKC、非空文字及其他字符要求仍然有效，生成式后缀不含空白。这让项目格式化器可以增加易读空格，而不要求修复名称或移动目录。

每个保存名称和生成式后缀分别按实际字符串遵守 32 个终端显示列上限，包括每个分隔符。排版对应不豁免宽度，也不改变身份、搜索匹配或任务合并。

创建和显式 rename 保留请求规范化及无空格生成路径。普通读取、检查、更新和表示切换接受合法排版，不改写它。子任务创建重试在应用既有创建名称比较前忽略新增普通空格，仍保留原先不同规范化请求的区分。

rename 仍以具体的规范化名称和适用路径为目标，只有两者都精确匹配时才返回无变化。排版对应不替代损坏名称窄修复、closed 状态保留、目标冲突、引用扫描及显式更新控制、提交前精确复检或部分提交报告。目录已移动但元数据失败时，任务可能合法且可读，重试仍须完成请求目标。完整规则归[数据模型](../../../../../projects/tk/docs/design/data-model.zh.md#任务名称)维护。

### 2026-10-23 要求归属

[数据模型](../../../../../projects/tk/docs/design/data-model.zh.md)和 [CLI 参考](../../../../../projects/tk/docs/design/cli-reference.zh.md)完整陈述必要的数据和操作行为，包括格式、上限、失败及验收。设计解释其实现。这些组件页面拥有要求，不改变任务数据或操作语义。

### 2026-11-14 metadata 报告

表示切换和 schema 迁移保存逐次独立、不可变的执行前报告，包括 dry-run、无变化及有效项目中的规划失败。报告持久化完成后才开始受管变化。文件计划描述载体创建、重写、删除及 schema 转换，表示切换的配置变化单独保留为最后一步。错误保留文件级部分完成及未知结果。GC 和 check 保留报告，供人工检查。按操作表达明细，metadata 变化保留自身的文件及版本信息。[数据模型](../../../../../projects/tk/docs/design/data-model.zh.md#扫描报告)规定报告格式。

## 动机

所有面向 OMP 的组件按共同维护下限 OMP 18.13.3 维护，并保留统一的宿主适配规则。

第一方组件把代码加载进宿主进程运行，需要随宿主升级继续可用。维护责任、实现选择与验证证据需要各自明确，不能用同一个版本范围代替，因此这些组件遵循统一规则：组件在自身文档中声明维护下限，宿主 peer 声明继续列出宿主包但不承载该下限，更新保留受维护旧宿主原有的结果，验证强度随实际行为影响确定，提高下限只能通过决定。本决定不要求这些组件采用相同实现。

面向 OMP 的组件是 `omp-qol`、`omp-smart-context` 和 `omp-status-bar`，共同从 18.5.0 转到官方 18.13.3。该基线支持原生 CLI/SDK 请求对齐的延迟加载及恢复、wait 的原生中断处理，以及按模型区分的 Responses 重放。继续维护第二套旧宿主基线，会保留这些组件在选定目标上不再需要的兼容工作。

旧源码通过 `compat/omp-18.12.3` 保留。它固定仓库快照，不形成长期维护分支，也不备份宿主二进制、配置或会话。名称不证明每个组件均已在 18.12.3 完整实测。

## 分析

peer 范围参与依赖解析，不是纯维护说明。例如，npm 默认安装 peer 依赖，无法解析的冲突可能导致安装失败（[npm package.json 文档](https://github.com/npm/cli/blob/latest/docs/lib/content/configuring-npm/package-json.md)）。将维护下限放进 peer 范围，可能阻止实际可用的宿主安装组件；具体结果取决于安装路径，不能把 npm 的行为当作所有宿主上的实测结果。

OMP 18.13.3 初始化[原生重放状态](https://github.com/can1357/oh-my-pi/blob/v18.13.3/packages/ai/src/providers/openai-responses.ts#L466-L496)时，区分普通模型与连接绑定的 Responses 模型。进程级覆盖所有冷状态也会覆盖宿主有意选择的重建。[QoL 后继决定](./20-omp-qol.zh.md)单独采用原生策略及其支持损失；提高共同下限本身不授权删除能力。

共同基线以完整组件适配为前提，包括实际宿主加载、请求传输、持久化和终端行为。公开源码与包级检查提供的证据不同于这些运行观察。旧验证保留原有版本和范围。

## 决定

### 适用范围

本决定适用于本仓库所有将代码加载进宿主进程运行的组件。仅作为说明或配置分发、不在宿主进程内执行代码的材料不属于兼容对象。不同宿主使用各自的版本线，各组件独立声明维护下限。

组件依赖的独立协议保留自身合同。宿主维护下限不替代协议兼容要求与安全检查。

与升级无关的新功能在其自身需求中决定。本决定不要求组件采用新的宿主 API，兼容工作以用户可见结果衡量，而不以使用了哪个宿主 API 衡量。

### 维护声明

每个组件在自身 `README.md` 与 `README.zh.md` 的兼容性小节声明最低维护宿主版本，这一小节是维护下限的权威说明。组件只声明下限，不设置维护版本上限，仓库不维护受支持版本白名单或公开支持矩阵。

下限表达维护责任。它不承诺后续宿主版本继续可用，不声称下限及以上的每个版本都经过验证，也不为下限以下增加维护承诺。低于下限的宿主不被阻止：能够运行的组件可以在那里运行，只是没有维护承诺，并且可能失去为旧宿主删除的代码原本提供的行为。

### 共同 OMP 下限

每个将代码加载进 OMP 的组件都把 OMP 18.13.3 声明为维护下限。纯指令或纯配置分发没有宿主代码维护下限；向其他宿主加载代码的适配器保留各自宿主的独立声明。

OMP 下限是共同的维护基线，即组件实际开发和验证所用的 OMP 版本。它为所有面向 OMP 的组件统一选定，而不是按每个组件仍能服务的最旧宿主分别推导。组件对 `@oh-my-pi/*` 有开发依赖时使用该版本，测试 fixture 和真实宿主检查以该版本的宿主行为为基线。

只为低于共同下限的 OMP 宿主存在的代码路径、探测、fixture、测试和文档段落都删除。下限及以下版本引入的宿主行为继续支持，例如 18.5.0 的 subagent footer tail。

### 其他宿主下限

面向其他宿主的组件，其下限依据交付组件的加载条件、必要能力和行为确定。API 首次出现的记录与已有验证可以提供依据，但都不能单独证明整个组件的兼容范围。开发依赖版本与最近实测版本不能直接充当这类下限。首次声明须经维护者确认；证据不足时记录缺口，不发布猜测值。

### 宿主 peer

宿主 peer 声明继续列出组件实际使用的宿主包，其范围不按维护下限收窄，也不添加维护版本上限。安装条件、自定义元数据字段和运行时版本检查同样不承载维护限制。已经以不带版本限制的形式声明宿主包的组件保持该写法。

独立演进的普通依赖保留真实约束。开发依赖保持锁定以提供可复现的检查环境，不成为声明。组件实际需要的能力或语义差异由适配实现与自身检查处理，不用来恢复宿主 peer 上的数值范围。本决定不新增仓库检查器、兼容管理器或受支持版本表，生产代码也不读取组件文档来决定如何运行。

### 维护行为

在下限范围内，更新保留受维护旧宿主原有的结果。一套实现能同时覆盖时复用同一套；确有差异时同时保留各宿主需要的实现，并记录选择它们的具体条件。宿主发行版提供原生能力时，先比较用户可见结果、配置和失败行为；等价的原生路径可以替换包装实现，而其他受维护宿主仍然需要的包装继续保留。

仍受维护宿主需要的行为保留下来；承担该行为的实现可以重构、合并或替换，只要行为仍在并按改动验证。仅为维护范围之外的宿主服务、且不承担其他行为的代码可以直接清理，不必等待下一次提高下限。组件独立新增的功能自行决定可用条件，可以说明只在部分宿主可用；本决定不要求各宿主具有相同的功能集合。

### 宿主适配

业务规则依赖组件需要的操作与数据，而不依赖宿主 API 的具体形态。适配实现承担宿主 API、数据转换，以及入口与实际宿主的绑定；接口围绕组件需求设计，不重述宿主的整套 API。已有边界直接复用；确有差异或转换需要时再补，普通函数、参数或对象即可满足。只是镜像一次调用的转发不值得增加边界。

宿主耦合随改动逐步整理。同一差异只有一个归属，避免多个调用点各自判断同一件事；组件文档说明每项差异的原因、位置、选择条件、失败行为和验证依据。组件保持自包含：不建立跨组件兼容库，组件不链接其他组件，也不链接仓库外层材料。

### 能力选择

实际能力或输入结构足以区分行为时，由它们决定。只有形态无法区分、且存在有记录的语义差异时，才使用版本范围；即便如此，它也是适配实现内部的局部判断，而不是组件层面的通用门禁。函数存在并不能证明事件顺序、字段含义、投递或持久化没有变化。

稳定接口可以在入口绑定宿主时选择。动态输入、设置、会话状态以及进程级补丁的所有权，按各自生命周期读取和检查。组件不把所有假设冻结为激活时的快照，也不对不会变化的假设在每次调用时重新解析。

### 加载边界

兼容分析覆盖生产入口及其传递导入，因为运行时探测无法修复在工厂执行之前就失败的模块解析。已知稳定存在的模块可以继续静态导入。存在真实跨版本差异、且缺失时组件仍需工作的模块，把加载失败纳入该适配项自身的边界；把未变化的静态导入挪到别处不算处理。

失败按能够安全隔离的最小功能单元处理，使相互独立的功能继续工作。必要前置条件在宿主允许的范围内先于副作用完成。注册或安装中途失败时，停止后续动作并释放组件自己拥有的资源，不承诺宿主没有提供的原子注册或完整回滚。没有等价实现时，受影响功能保留宿主原生行为，或通过现有诊断通道报告不可用，给出有界、可定位的原因，不假报成功。安全停用是故障处置而不是兼容，本身也不解除维护责任。

### 验证

验证强度由实际行为影响决定，不设行数或比例阈值，代码类别本身也不是验证门槛。小修改完成相称检查即可通过，不统一要求重跑旧宿主实机；重大行为修改必须在相关真实宿主场景中验证，即使只改了几行。各组件既有发布合同保持原有强度。

仓库不规定固定的验证版本组合。可以选择下限、目标版本或独立适配路径的代表环境，只要证据足以支撑结论。

验证记录写明证据类型、所用版本、场景和未覆盖范围。模拟接口只验证组件自身的逻辑、分支与失败处理，不能代替真实宿主加载；真实宿主包、模板与 CLI 的观察也须分别说明。涉及事件、工具可见性、UI、消息投递、持久化或进程补丁时，检查用户可见结果，而不只看处理函数的返回值。

测试环境依赖较新宿主内部模块而无法运行，不等于生产入口不兼容。既有验证结果保留原有版本和场景，不改写为维护承诺；仓库既有检查仍须执行。

### 下限变更

共同的 OMP 下限由所有面向 OMP 的组件一起移动，每次提高都是独立决定。任务记录现有与建议下限、证据、合理的替代方案，以及用户将失去的旧宿主支持。获准选择形成正式决定，保留这些理由和支持损失；变更同时更新每个面向 OMP 的组件的声明、实现、测试和必要的迁移说明。

面向其他宿主的组件默认保留现有下限。组件确实无法同时服务两个宿主版本，或者同时兼容需要大幅改造而提高下限所需改动明显更小时，才可以提出。任务记录组件、现有与建议下限、具体冲突或改造及其投入比较、合理的替代方案、证据，以及用户将失去的旧宿主支持。采纳的决定保留这些依据。这类组件提高下限不移动其他组件的下限。

维护投入是维护承诺本身要求的工作，不作为额外成本，任何时候也不列为风险。每次提高下限都由维护者决定。批准和待实现安排可以由任务跟踪，但决定之外的批准不能代替公开 ADR，正式决定随已完成的下限变更一起集成。提高下限也无法恢复宿主发行版已经删除的能力。

### 组件契约

18.13.3 切换结束对 OMP 18.5.0 至 18.13.2 的维护。继续使用旧宿主的用户保留 `compat/omp-18.12.3` 对应组件，不跟随新主线。该 tag 固定源码与依赖声明，不承诺回补，也不改变快照自身的 18.5.0 维护声明。

[QoL](./20-omp-qol.zh.md) 退役强制原生历史重放，并要求移除 `replayEnabled`。[请求对齐](../10/22-request-alignment.zh.md)保留正常 CLI/SDK 会话、延迟加载、恢复，以及独立的 Remote 与 Handoff 行为。状态栏保留渲染和提供方合同，Pin 持久化继续归宿主控制。

此前 18.5.0 切换继续有效，不恢复系统提示词默认块路线、`hub` 等待路径或状态栏动态投机区间估算。其历史选择保留在[前驱](../../../archived/2026/09/28-r3-host-maintenance.zh.md#组件契约)中。

## 考虑过的替代方案

### 逐组件 OMP 下限

这是采用共同下限之前的规则。凡是代码仍能服务的宿主，它都保留到各组件原有的下限，但六个组件会停在彼此不同、且低于开发宿主的下限上，组件也要继续维护只在旧宿主上工作的默认块路线和投机区间估算。

### 保留 18.5.0 下限

保留旧下限可以继续维护既有用户，但需要同时针对旧宿主行为及 18.13.3 目标开发和适配。选择共同提高下限，为旧用户保留明确源码锚点，不继续保留两套受维护基线。

## 结果

- 取消数值门禁后，原先被拒绝的宿主可以进入加载与运行流程。若能力与行为检查漏掉真实不兼容，组件会在使用时失败，而不是在安装时失败。
- 为不同受维护宿主保留的多套实现可能在后续维护中分别演进，使旧宿主上的配置含义或失败行为偏离同一功能的合同。
- 继续使用 18.5.0 以前 OMP 版本的用户更新组件后，会在没有提示的情况下失去被删除的行为：在 18.3.0 以前的宿主上，除非用户选择模板，系统提示词策略不再生效；在带 `hub` 的宿主上，总期限等待不再生效；在 18.4.0 以前的宿主上，投机区间指示器变为静态字形。
- 共同的 OMP 下限只能通过覆盖所有面向 OMP 的组件的决定移动，因此本可更早放弃旧宿主的组件要等待下一次共同提高，而每次提高都需要覆盖所有面向 OMP 的组件的决定与评审。
- OMP 18.5.0 至 18.13.2 用户更新到源码锚点之后的版本便失去维护。无限制 peer 仍允许加载，因此旧宿主可能在使用时失败，而不是拒绝安装。保留旧快照可以避免跟随这一不受维护的组合，但不会自动获得回补。

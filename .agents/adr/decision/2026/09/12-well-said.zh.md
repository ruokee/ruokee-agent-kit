## 动机

保留 `well-said` 作为指导自然、直接表达的双语 Skill，来源署名写在仓库根 README，许可与来源事实写在本决定。

[上一版本](../../../archived/2026/09/12-r2-well-said.zh.md)把署名与许可文件放在写作指令旁边。这两个位置都不适合这类材料。Skill 里的文件会作为指令进入 Agent 上下文，或与指令一起被宿主和 Agent 当作同一个组件读取，法律通知对写作会话没有意义，还可能被读成能力规则的一部分。署名与许可信息服务于仓库的读者，由仓库把它们记在 Skill 树之外。

重写从能力最原始的需求和原始资料出发。旧 Skill 只作辅助参考，不作为验收清单。章节覆盖或范围不同，本身不能说明重写稿有问题。

记录须区分 Ruokee 对 well-said 的作者归属，以及 Lauren Tan 对复用的 unslop 材料的作者归属。

## 决定

### 能力范围

保留 `well-said` 作为独立编写、可由模型调用的 Skill。适用说明为"输出任何内容时使用"，包括回复、文档、代码注释和 Agent 交流。继续支持明确调用。应用写作规则不增加修改文件或可执行内容的权限。

每个语言组件的 `SKILL.md` 提供完整的英文或中文写作指南，按写作流程、文风模式、防御性表述、可见的编写会话残留、文章写作和作者声音组织。两种语言都保留原意，以及作者真实的观察与判断。两个版本均不依赖其他 Skill 或仓库支持文件。

将防御性表述视为文字问题，也视为可能尚未完成工作的信号。覆盖证明姿态、认知边界和未执行工作的交代。两种语言都列出中英文代表表达，说明危害和处理方式。这些表达用于提示判断，不构成禁用词表。

区分表述问题和工作问题的处理方式。只是措辞过于保守时，把已有依据的结论说清楚。工作缺失或结果有误时，在授权范围内补做或返工。工作本身没问题时，按读者需要重写有用段落，删除空洞段落。保留事实、实际风险、重要未知、授权条件、必要论证，以及用户或适用流程要求的状态报告。

### 组件布局

英文组件继续位于 `skills/well-said/`，中文组件继续位于 `variants/zh/skills/well-said/`。两者都是自包含分发组件，只包含 `SKILL.md`，其中提供写作指令，并在 frontmatter 的 `metadata.version` 中声明版本。

Skill 正文不重复来源署名、许可文本或版本号。来源署名由仓库根 README 的条目承载，上游路径、固定版本与许可由本决定记录。

使用 `1.0.0` 作为正式发布的起始版本。后续发布遵循仓库版本政策。普通 Skill 不增加包 manifest、检测器、plugin 或运行时依赖。

[第一方能力决定](../08/20-first-party-capabilities.zh.md)区分 well-said 主体归属和复用材料的作者归属。文风章节大幅保留来源措辞、示例与有效组织，并作必要衔接和补充。保留的原文来自 [Cursor plugins / pstack](https://github.com/cursor/plugins/blob/99559f2f52047978602ef365589275831e76af07/pstack/skills/unslop/SKILL.md)，版本为 `99559f2f52047978602ef365589275831e76af07`，采用 [pstack MIT 许可](https://github.com/cursor/plugins/blob/99559f2f52047978602ef365589275831e76af07/pstack/LICENSE)，版权人为 Lauren Tan，年份为 2026。后续复用其他材料时，须在分发前核实来源、权限、署名和通知。

完整写作指南保持在一个文件中。只有实际内容与加载测量表明有必要时，才移出篇幅可观的低频补充材料。日常写作仍由 `SKILL.md` 中的完整规则支持。

### 编辑权限

可执行代码和配置不属于编辑范围。混合文件中的注释与可执行内容分别处理。引文、命令、标识符、原始日志、录制输出及其他字面材料，在其用途或用户请求要求逐字保留时保持原样。

Skill 不增加文件修改权限。审阅请求在未获编辑授权时保持只读。处理范围遵循用户指定的文件、文本和结构。

- 面向只拥有成品及其可访问来源的读者写作。遵循当前有效要求，清除已舍弃的概念、纠错标签和只有编写会话中才能理解的引用。
- 让事实、观察、判断和有用行动成为正文主线。必要理由与来源放在其支持的主张旁边。
- 清除空泛服从证明、泛化自保、重复核验旁白、冗词、黑话和机械表达。保留作者真实的语气、观察与判断。
- 保留事实、数字、条件、否定、义务、不确定性、来源和因果强度。不为让文字更像人或更具体而编造经历、立场、测量结果或行为主体。
- 已经清楚的文字优先原样保留。按请求交付文章、回答、诊断或编辑结果，不附送未经请求的清理报告。保留有用的完成信息、真实阻塞和用户要求的解释。

unslop 的明确禁令保持强制性。直接列出关键标点要求：不用破折号，不以括号、短破折号或连字符替代同类插入表达，弯引号换成直引号。详细规则和例子放在同一文件中。字面材料保护继续适用。

允许在授权范围内调整结构，包括重排段落、合并重复、重写开头和结尾。调整非常广泛时，Agent 可以询问是否整篇重写；已有授权即可执行，不设置人为改动比例门槛。保留固定结构与逐字要求。

对照原始信息和当前请求复核结果。尤其不能把未测试环境写成不支持环境、把义务写成已经完成的行为、把假设设计写成已有能力。保留具体未知，查证有实际影响的矛盾，不以流畅改写掩盖问题。

### 加载

将 Skill 应用于输出前，取得完整 `SKILL.md`。描述、摘要或截断片段不能代替完整指南；宿主未提供的内容需要补齐。当前上下文已有完整正文时复用，不为每次回复重复读取。上下文丢失导致所需内容不可用时，恢复该内容。

起草和编辑时综合应用相关章节。纠正、撤销和替换要求时检查当前有效需求及会话残留；润色请求关注文风；反复自证时检查证明姿态。这些信号用于在已有正文中确定关注点，不触发额外文件读取。普通输出同样遵循完整的适用规则，已经清晰的文字可以不改。

加载失败时，使用已有规则与保护边界，必要时说明受影响的检查范围，不宣称已经应用缺失内容。分别验证宿主发现、完整加载与规则遵循；仅有完整加载不能证明写作质量。

### Agent 交流

写作范围明确包括 Agent 之间的自然语言消息：委派、任务交接和评审反馈。这类消息面向将要执行任务的 Agent，也面向之后阅读它的人。

- 传递任务、材料、授权与范围限制、影响继续工作的实际状态以及验收标准。简短消息只需包含会改变接收方行动的项。
- 省去发送方的重试、等待、批次调度和上下文整理叙述，除非它们改变接收方的下一步行动。
- 保留阻塞、权限缺失、未核实或部分完成的写入、未满足的依赖，以及防止重复副作用所需的信息；不把未完成或未知状态写成已完成。

### 验证要求

1. 两个语言组件提供完整写作指南，范围、规则、例外、示例和版本一致。仓库能力索引描述相同的适用方式。
2. 防御性表述规则说明危害和处理方法，区分工作问题与文字问题，保留会影响读者判断或行动的信息。两种语言均提供中英文代表表达。
3. 每个组件只包含自己的 `SKILL.md`。署名区分 well-said 与复用材料的作者归属。来源署名和法律通知不出现在 Skill 正文；仓库根 README 与本决定承载它们。
4. 两份入口声明相同的 `metadata.version`，并遵循上方发布策略，正文不重复版本号。完整组件可独立安装，不依赖其他组件或仅仓库内存在的材料。
5. 实机 Harness 测试在真实模型上运行，分别覆盖两个模型，并实际使用两个语言组件。记录候选版本、实际模型与 Harness 版本、相关指令、输入、输出和加载证据。提案或仓库自动检查不能代替行为验证。
6. 测试覆盖普通起草、已有文本清理、只读审阅、授权文件编辑、长文结构、作者声音、字面保护、有用解释与历史，以及多轮新增、纠正、撤销、替换和临时要求。同时检查漏清理与有害误改。
7. 测试完整入口加载、已有内容复用、上下文丢失后的恢复、内容不完整或不可用、明确调用和普通宿主发现。覆盖普通输出及文风、泄露、证明姿态混合场景，不要求读取专项文件。区分加载失败与加载后未遵循规则。
8. 宿主支持时，以相同输入比较有无候选的结果。记录现有写作规则的干扰，区分独立行为与共存行为。宿主无法提供独立条件时，明确报告限制，不宣称已验证独立效果。
9. 使用人工语义判断，允许多种合格改写。文风改善不能抵消事实误改、义务或限定丢失、虚构经历及越权编辑。各模型与语言分别判断。
10. 保存失败输出，判断其对实际使用的影响。实机测试用于暴露问题，不要求发布前解决所有观察到的问题。整体指南可用时，可以记录剩余问题，依据实际使用数据继续改进。规则修改需由维护者同意。经批准修改后，复测失败和邻近保护场景，并在两个模型上运行完整适用集。冻结候选后测试新输入。用于调整规则的输入转入回归集。重复高风险和曾失败场景，报告波动，不挑选最好输出作为结论。
11. 执行仓库要求的自动检查。分别报告实机结果与剩余限制，不向未测试的模型、文本或环境推导效果。
12. 仓库指引和第一方能力决定明确区分能力主体归属与第三方来源使用。该原则普遍适用，包括 architect 与 well-said，不能仅凭使用第三方内容认定 fork。复用材料保留来源归属，并满足适用许可与署名要求。

## 考虑过的替代方案

- 继续修改旧 Skill。选择从原始需求和资料重写时，已否定这一路线。该方案仍以旧文本为起点，没有采用所选的重写稿。
- 将来源署名、法律通知和版本保留在 Skill 正文。这是被替代决定采用的布局，会把分发信息混入写作指令。正文版本也会与 frontmatter 声明重复。
- 将署名与许可文件保留在写作指令旁边。这是上一版本采用的布局，也是本决定取代的布局。它把法律通知放在宿主和 Agent 把 Skill 当作一个组件读取的位置。
- README 署名同时写出许可名称与固定版本。这是选择署名承载内容时考虑过的方案。它会在面向读者的索引里重复本决定已用固定版本记录的内容。
- 在仓库层面另建复用材料的通知文件。这是选择仓库记录复用的位置时考虑过的方案。它为本仓库并不单独分发的材料增加一份文件，而 README 署名与本决定已经写出来源、版本与许可。
- 由现有 unslop Skill 继续处理一般文风，另建泄露清理 Skill。能力边界选择时考虑过这一方案。它分开了需要共同保护语义的规则，无法提供选定的统一写作行为。
- 短核心加三份按需加载的专项指南。文件布局比较中考虑过这一方案。低频专项材料较多时可能节省上下文，但增加了信号识别、文件读取和多指南综合处理。完整单文件省去日常写作中的这些依赖；实际上下文节省和行为差异尚未测量。
- 入口只保留导航，每次输出用户可见文本都读取完整 unslop 指南。确定强制禁令的可见位置时考虑过这一方案。它增加读取步骤，入口自身也无法完整提供统一写作规则。
- 将 unslop 的明确禁令放宽为默认建议，并允许文风例外。规则强度选择时考虑过这一方案。选定的文风偏好保留禁令，同时保护字面材料与含义。
- 仅作局部措辞修改，结构调整前一律询问。编辑范围选择时考虑过这一方案。证明姿态清理可能需要重组文本，该方案会为已有授权的结构调整增加确认。

## 结果

过度清理可能删除限定、迁移义务、证据、有用历史或作者声音，产生流畅但误导的文字。共同保护规则以及应该保留和应该修改的配对案例需要约束所有章节。

完整加载可能让当前回复不需要的细节占用上下文，较长文件也可能使关键规则更容易被忽略。测量实际内容和加载行为，保持结构清楚，同时检查漏清理与有害误改。

Agent 可能未发现 Skill、只取得部分正文、在上下文中丢失内容，或没有遵守已经读取的规则。单文件省去专项读取步骤，但不保证完整加载与遵循；需要同时检查加载证据与实际输出来定位失败。

Skill 内部规则与现有写作指令可能重叠或冲突，导致修改不一致。现有规则还可能掩盖候选的缺陷，造成效果被高估。

针对熟悉样例调整规则，可能只改善这些样例，对新文字无效。需要新输入测试与回归检查暴露这一问题。

未核实来源和许可就复制文本，可能遗漏必要署名或未经许可分发材料。新组件的归属不能解决这些义务。

署名如今放在仓库根 README 与本决定里，而不是写作指令旁边，后续改动需要让两处保持准确。

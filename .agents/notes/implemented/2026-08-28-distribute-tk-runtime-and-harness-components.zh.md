# Agent Note: 分发 tk 运行时与 Harness 组件

## 动机

[tk 产品架构](./2026-08-21-define-tk-product-architecture.zh.md)包含一个用户级运行时，以及面向 Codex、Claude Code、Pi 和 OMP 的自包含组件。运行时安装和 Harness 集成属于不同职责。组件使用运行时前，必须先安装可执行文件。组件安装必须保持确定性、离线、可检查和可撤销，同时不维护第二个安装数据库。

各 Harness 的目标位置和官方生命周期 API 不同。分发仍需要为安装、更新、无变化、干净卸载和部分失败定义一套统一结果边界。

## 决定

### 运行时安装

Linux 运行时是位于 `$HOME/.local/bin/tk`、具有 Unix 执行位的常规可执行文件。发布流程或用户安装把可执行文件放到该路径。Harness 组件生命周期会验证和启动它，但不会安装、更新或删除它。

运行时只有一个路径和一个可执行版本。Harness 组件不包含第二份运行时、包装器或私有二进制文件。

### 构建期组件组装

`projects/tk/build.rs` 是唯一的组件组装器。Cargo 在 `OUT_DIR` 下为每个受支持 Harness 构建一个自包含组件树、确定性 `tar.zst` 归档和 manifest。可执行文件使用 `include_bytes!` 内嵌全部归档和 manifest。

组装过程读取权威英文 Skill 和所选 Harness 自己的源码，并验证自包含性和仓库相对链接。生成的组件树和归档不提交到 Git，也不存在 Python 或第二条发布组装路径。

manifest 记录组件格式、Harness、组件版本、`runtime_compat`、`source_revision`、允许的相对路径、文件类型、Unix 权限和内容摘要。设置 `TK_SOURCE_REVISION` 时使用其值，否则使用 `package-v<CARGO_PKG_VERSION>`。构建脚本不调用 Git。

安装只读取内嵌字节。持久写入前，归档验证会拒绝不支持的格式、不兼容的运行时范围、绝对或逃逸路径、symlink、特殊文件、重复项、缺失或多余项、权限不匹配和摘要不匹配。安装不访问网络、不下载发布产物、不运行 `curl`，也不接受本地归档来源。

### Harness 组件内容

Codex 组件包含英文 Skill 和 MCP 注册。Claude Code 组件是包含英文 Skill 和 MCP 配置的自包含 Plugin。Pi 和 OMP 分别使用包含英文 Skill 和原生适配器的独立自包含 Package。

组件不包含运行时、中文 Skill、其他 Harness 文件、评审记录或产品源码。工具和适配器行为由 [Harness 集成 Agent Note](./2026-08-28-integrate-tk-with-harnesses.zh.md)负责。

### 生命周期

公开组件命令要求显式指定 Harness：

```text
tk install --harness <codex|claude|pi|omp> [--dry-run]
tk uninstall --harness <codex|claude|pi|omp> [--dry-run]
```

`tk install` 根据内嵌组件、固定 tk 专用目标和共享配置中的 tk 配置项选择安装、更新或无变化。`tk uninstall` 选择卸载或无变化。生命周期不会从进程或目录推断 Harness，也不接受语言、force、组件版本、项目、actor、网络来源或本地归档选项。

生命周期规划不使用所有权清单、安装历史、部分卸载状态或旧内容摘要数据库。它只读取当前固定目标、共享配置中的 tk 配置项和当前内嵌组件。

Harness 提供官方 install 或 uninstall API 时，tk 使用这些 API。否则只管理固定 tk 专用目标，以及共享结构化配置中的固定 tk 配置项。具体命令、路径和配置键属于驱动实现细节。

dry-run 和实际执行使用相同完整预检，覆盖运行时、内嵌组件、兼容性、Harness 可用性、官方接口、目标可读性、共享配置解析、计划变更和活动操作标记。

安装和更新先在 tk 临时位置准备内容，再次验证目标和共享配置，提交专用组件目标，添加或替换 tk 注册，删除已被取代的 tk 目标，最后删除临时内容和标记。配置不会指向暂存位置。

### 干净卸载与失败

干净卸载使 Harness 恢复为从未安装过 tk 的状态，同时保留无关内容。

固定 tk 专用路径会被完整删除，包括其中的用户修改和额外文件。编辑共享配置前必须完整解析。直接编辑只删除 tk 对应的结构化配置项，并保留其他全部配置项。删除配置项后，只有该共享文件由 tk 在当前生命周期中创建且已经为空时才删除；其他情况都保留文件，包括合法的空文件。

组件操作在提交前完成全部读取和预检，再按确定顺序写入。错误或取消会停止操作，并返回已完成项、未完成项和原始错误。操作不会自动回滚，也不返回续跑令牌。后续调用根据当前目标重新规划。

GC 可以删除操作进程退出后遗留的组件临时内容和活动操作标记。它不会继续安装、更新或卸载，也不会修改规范 Harness 目标或配置。

完整用户和驱动合同见[安装设计](../../../projects/tk/docs/design/installation.zh.md)与[用户指南](../../../projects/tk/docs/guide.zh.md)。

## 考虑过的替代方案

**通过每个 Harness 组件安装运行时。** 这会让可执行文件出现多个所有者和版本。把固定运行时作为前置条件，可以分离运行时分发与 Harness 注册。

**下载发布产物或接受本地来源。** 网络和来源选择会给已经由可执行文件携带的组件增加身份、信任、可用性和版本耦合问题。

**维护所有权清单和安装历史。** 历史状态会成为另一个数据库，并可能在人工修改后与当前目标冲突。固定目标和当前配置已经足以形成计划。

**在仓库中保留生成组件树或 Python 组装器。** 多条源码和组装路径可能产生不同载荷。单一 Rust 构建路径使发布、安装和验证使用相同字节。

**保留 tk 专用目标中的修改文件。** 这会留下无法构成可用组件的碎片，也不符合干净卸载结果。

## 结果

运行时可执行文件携带四个组件归档和 manifest，因此其体积包含这些载荷。更新组件内容需要重新构建并分发运行时。

组件安装不依赖网络或源码检出。当固定目标和注册与内嵌组件一致时，重复安装收敛为无变化。

干净卸载会删除 tk 专用目标中的全部文件，包括用户修改。无关共享内容保留在该边界之外。Harness API 或配置发生变化时，需要更新驱动并针对真实 Harness 验证。

删除运行时是独立的用户或发布操作。卸载全部 Harness 组件不会删除 `$HOME/.local/bin/tk`。

# Agent Note: 添加 tk 作为持久项目工作能力

Status: proposed
Decision owner: Ruokee
Draft writer: OMP GPT-5.6 Sol

[English](./2026-08-21-add-tk-persistent-task-capability.md) | 中文

## 动机

`ruokee-agent-kit` 需要一项第一方能力，用来让项目工作跨越 Agent 会话和不同 Harness。对话会结束，上下文会压缩，模型也会切换。一项工作只要不能在一次对话中结束，就需要自己的身份、当前状态、材料和历史。

旧 Task Plugin 已经证明这种工作方式有用，但也暴露了构建、元数据文件和公开名称上的问题。它使用 Python/Nuitka 构建 standalone 程序，冷构建慢到会打断日常维护。构建缓存占用磁盘，还可能被清理，无法消除冷构建成本。`TASK.md` 同时包含生成的 frontmatter 和人工编写的 Markdown，元数据更新因此必须重写用户维护的文件。公开名称 `task` 含义宽泛，并且与 OMP 的子 Agent 工具重名。

这项能力还要同时接入 Codex、Claude Code、Pi 和 OMP。过去出现过 wrapper 与 runtime 版本不匹配、生成 schema 漂移等问题。即使源码测试通过，也不能据此认定实际安装的工具彼此一致。

tk 保留 Task 模型和实际使用积累的经验，同时更换实现、文件所有权边界、名称和公开合同。它不会为了兼容而保留旧 Python runtime 或旧公开 API。

## 提议

### 架构

在 `plugins/tk/` 下添加 tk Plugin，并在 `packages/tk/` 下提供 OMP/Pi 原生 Package。两个路径使用同一份 Rust 实现和同一份生成合同。

共享逻辑使用 Rust 实现。替换 Python/Nuitka 的首要原因是冷构建速度；继续调缓存只能改善热构建，还会增加磁盘占用。迁移时必须记录 Rust 的冷构建耗时、产物大小和启动耗时，并与 Nuitka 基线比较，不能预先假定重写一定更快。

发现、身份、关系、生命周期规则、路径边界、受管理元数据、WAL 格式、请求校验和结构化错误都由同一个 Rust 程序处理。这些规则不能随着调用宿主变化。宿主 adapter 只转换工具注册和调用传输格式。tk Skill 说明创建授权、恢复、记录和关闭行为，不讲解实现布局。

所有宿主 schema 都从 Rust 类型定义生成。Package 元数据、wrapper、runtime、生成 schema 和 Skill 必须报告相同版本与 protocol。即使 Rust 构建正确，过期的 wrapper 或 schema 仍可能和它一起发布，因此发布检查必须调用实际安装的宿主包。

### 领域

Task 是一项有限的工作，需要稳定的身份、材料和活动历史。它可以从用户明确保存的早期想法开始，经过规划和执行，最后因为完成、放弃、不可行或被替代而结束。只有用户决定保存某个具体想法时，它才成为 Task。tk 不负责排列 Task 优先级，也不提供队列、看板或筛选流程，因此不会成为 backlog、todo 管理器、Issue 跟踪器、Agent 调度器、工作流执行器或知识索引。

命令、Package、Plugin 和工具 namespace 使用 `tk`。保存下来的对象仍叫 Task，领域术语继续使用 Task ID 和 `TASK.md`。只改工具名称就能避开 OMP `task` 冲突，无需改动领域对象或文件名。

### 生命周期

Task 只有 `planning`、`open` 和 `closed` 三种状态。允许的转换是 `planning -> open`、`planning -> closed`、`open -> closed` 和 `closed -> open`。`open` 不能回到 `planning`。任何祖先仍为 `closed` 时，Task 都不能重开；用户需要先重开祖先链，或者在 closed 树外创建新 Task。

`planning` 表示一项工作在执行前正被记录、调研或整理。没有使用 `proposed`，因为这个词更像等待批准，而且已经用于 Agent Note 的生命周期。旧 `paused` 状态与保持 `open` 并记录阻塞相比没有新增行为，`archived` 相对 `closed` 也没有新增行为。关闭时必须写 `reason`，用来区分完成、放弃、不可行和被替代，不必再为这些结果增加更多终态。

创建和每次生命周期转换都会自动追加 WAL 事件，恢复因此不依赖 Agent 是否记得记录状态变化。关闭和重开还要求 `reason`。普通关闭要求所有后代 Task 和所有 `depends_on` 目标都已 `closed`，否则父任务可能在必要工作仍未结束时声称完成。`related_to` 只表示上下文关系，不代表必要工作，所以不会阻塞关闭。只有用户明确要求时，force close 才能绕过这些检查，并且不得修改其他 Task。

### Agent 行为

创建默认使用 `open`，因为多数新 Task 会直接进入执行。只有 inbox 事项、计划、想法、简短记录或以后再完善的工作等明确的提前保存意图，才使用 `planning`。如果内容目前无法执行，且用户是否想保存并不明确，Agent 必须询问，而不是把普通想法当作持久工作保存。`planning` 取代旧 Inbox 字段、固定 Inbox 文件以及独立的 capture、start、abandon 流程。

在已经授权且仍处于活动状态的 Task 树内创建子任务，不需要再次取得顶层持久化授权。子任务的初始状态仍遵循普通 `open` 和 `planning` 规则。在已关闭的父任务下创建子任务时，应遵循生命周期一节中的 closed 规则，不能隐式重开任何 Task。

完成当前请求、Goal、一次执行或 Agent 会话，都不代表可以关闭对应 Task。一项 Task 可能跨越多个此类边界。Agent 判断 Task 已经结束时，应先展示依据和拟采用的关闭 `reason`，再询问用户。没有得到用户在当前对话中针对这次关闭的同意，Task 就继续保持 `planning` 或 `open`。得到同意后，普通关闭仍须满足后代和依赖约束。

用户给出明确 Task 路径或目录、明确要求创建或查找 Task，或者项目采用 permissive 创建策略且当前工作明显可执行并需要持久化时，Skill 才介入。它不能根据 Git branch、工作目录、worktree、`continue` 一词或对话长度绑定 Task。这些信号并不稳定，而且一次会话可能同时涉及多个仓库和 Task root。任何创建策略都不得在缺少明确提前保存意图时把工作捕获为 `planning` Task。

Catchup 是 Skill 中的只读恢复阶段，不是专用工具。复合请求完成恢复后还要继续处理后续要求。closed Task 仍保持只读；新工作通常创建一个与旧 Task 相关的新 Task，只有用户明确选择时才重开旧 Task。这样可以保留原来的完成边界。

上下文压缩前，Agent 应尽力保留精确 Task 目录或 `TASK.md` 路径。通用的近期文件列表可能漏掉 Task 入口，所以 Skill 要直接写明路径。也可以保留下一步需要的 Task 材料路径。tk 不注册压缩钩子，也不管理对话历史，因为不同 Harness 的相关机制并不一致。

### 公开操作

`tk` 可执行文件提供以下 CLI 操作：

- `tk search` 查找项目内 Task 候选，并应用下文定义的过滤条件；
- `tk read` 解析一个精确 Task，并返回 metadata、summary 或 detailed 视图，同时限制 WAL 读取量；
- `tk create` 创建一个顶层 Task，或者在同一父任务下批量创建子任务，只有全部输入通过校验后才写入；
- `tk update` 修改受支持元数据，并且最多执行一次生命周期动作；
- `tk log` 追加一条持久活动事件；
- `tk init` 初始化项目 Task root 和可选的稀疏项目配置；
- `tk check` 执行只读检查，并报告配置、项目或 Task 诊断；
- `tk rename` 按受管理的路径规则修改 Task 名称和目录；
- `tk --version` 不访问项目，只报告 runtime 版本与 protocol。

所有命令都调用同一份 Rust 合同并返回结构化错误。CLI 不会定义 Harness 工具缺少的另一套行为。

### Harness 接入

Codex 和 Claude Code 通过随包发布的 MCP server 接入。MCP 提供六个工具：

- `tk_read` 解析一个精确 Task，并返回 metadata、summary 或 detailed 视图，同时限制 WAL 读取量；
- `tk_search` 查找项目内候选，并应用下文定义的过滤条件；
- `tk_create` 创建一个顶层 Task，或者在同一父任务下批量创建子任务，只有全部输入通过校验后才写入；
- `tk_update` 修改受支持元数据，并且最多执行一次生命周期动作；
- `tk_log` 追加一条持久活动事件；
- 受限 `tk_exec` 只接受 `--version`、`init`、`check` 和 `rename` 参数数组，不调用 shell。

Pi 和 OMP 支持原生扩展，因此对应 Package 直接把这六项操作注册为原生工具，不再启动 MCP server。MCP 和原生工具的 schema 都从 Rust 类型生成。Adapter 只映射名称、注册、传输、`cwd` 和宿主可以提供的 actor 上下文，不增加领域行为。

Agent 应使用当前 Harness 对应的接入方式：Codex 和 Claude Code 使用 MCP，Pi 和 OMP 使用原生工具。正常工作的工具入口不能被 CLI 绕过。只有首选入口缺失或调用失败时，Agent 才可以把 Harness 的 Bash 工具作为最后手段，执行等价的 `tk` CLI 命令。回退后仍须遵守相同的授权、发现、校验和生命周期规则，也不能因此直接编辑 `tk.toml`。

每个发布的 Skill 语言变体都包含本地 `references/troubleshooting.md`。该文档说明如何检查工具注册和版本一致性、运行 `tk check`、选择等价 CLI 命令、安全传递结构化参数，以及恢复后切回 Harness 工具。CLI 回退成功只能证明 runtime 可以工作，不能证明出现故障的 MCP 或原生接入已经恢复。

用户意图允许持久化后，其他领域 Skill 可以使用相同的 Task 操作。通用合同已经足够组合；各 Skill 专用命令、回调和第三方 schema 会让 tk 依赖不属于它的工作流。

### 受管理文件

每个 Task 目录包含 `tk.toml` 和 `TASK.md`。tk 负责 `tk.toml` 中的结构化状态，人和 Agent 负责 `TASK.md` 中的纯 Markdown。拆开两个文件后，元数据更新无需解析和重写用户文本。`tk_create` 初始化这两个文件。`tk_update` 不接受正文或通用 Markdown patch 字段，因此 `TASK.md` 和普通材料只能通过宿主文件工具编辑。受管理文件缺失或无效时，tk 必须报错，不能编造内容。

Agent 日常修改 `tk.toml` 时必须使用 tk 操作，因为直接编辑会绕过关系、生命周期和路径校验。如果文件已损坏，并且没有 tk 操作能够表达修复，Agent 只有在说明具体改动并取得用户在当前对话中的明确授权后，才能直接编辑。修复后必须使用 tk 验证结果，并通过 `tk_log` 记录修复。

当前 `tk.toml` 元数据是权威来源。WAL 只记录活动，不是可重放的日志，因此 tk 不会用它重建当前状态。WAL 保存决定、纠正、可恢复里程碑、验证结果、已核实的协作结果和阻塞。创建和生命周期操作自动写入各自的事件；Agent 通过 `tk_log` 记录其他值得保留的事件。已有条目只能追加，纠正通过新条目表达，不能改写历史。成果正文、工具调用噪音、聊天记录和例行会话摘要都不进入 WAL。

### Task 材料

`TASK.md` 只回答三个恢复问题：这项 Task 要做什么，哪些结论仍然有效，下一步应该去哪里读。它是导航入口，不存放工作成果或进度历史，而且应当保持简短。可以写入当前目的与边界、仍然有效的结论与约束、稳定的后续方向和重要材料链接。只有预计到下一次会话或移交时仍有用，并且会持续有效到后续决定取代它的事实，才适合写入。整体阶段顺序可能符合这个条件，当前失败的测试或正在执行的子步骤不符合。这些是内容规则，不是必需标题或固定模板。

具体计划、调研、设计、调查过程、checkpoint、handoff、命令输出、验证证据和变化中的进度，如果后续会话可能需要，就写入普通材料文件。临时执行状态留在当前对话中。`TASK.md` 可以说明某份材料为什么重要并链接到它，但不能复制材料正文。具有独立价值、包含支撑证据或多步推导，或者会独立变化的内容，都应保存在单独文件中。tk 保存恢复工作所需的结果，不保存 Agent 产生这些结果的聊天过程。

导航采用渐进式披露，避免每次材料文件变化都要修改 `TASK.md`。规模小而且稳定时，可以直接链接每份文档并说明用途。集合变大或经常变化后，`TASK.md` 只介绍整个集合，并指向对应目录或有用的局部索引。文件级导航留在下一层。例如，三篇记录可能适合逐篇链接；十几篇记录可能更适合用一条说明指向 `records/`。这里的数量只用于说明选择，不是固定阈值。

当前事实变化时，Agent 应直接替换 `TASK.md` 中的旧说法，事件时间线由 WAL 保存。单次工具调用、进度变化、WAL 事件，或者一个已经介绍过的材料集合增删文件，都不足以单独触发更新。准备写入细节或很快过时的进度前，应把可复用内容移到普通材料，只留下稳定摘要和入口。没有后续价值的内容不需要保存。如果 `TASK.md` 已经堆积了细节、短期状态或完整文件清单，下一次相关编辑应移动或压缩这些内容，同时保留其中仍可复用的信息。tk 不为普通材料规定固定清单、文件名、行数限制或 schema。

### 材料模式

每个发布的 tk Skill 语言变体都包含本地 `references/material-patterns.md`，说明四种可选的普通 Task 材料参考模式：

- 按日期记录，用于跨本地日历日期持续积累的实质性工作；
- 深度调研，用于收集来源、保存出处、交叉验证和限定结论边界；
- 迭代设计，用于会取代先前版本而非仅调整措辞的重大设计；
- 实验，用于保存变量、基线、重复运行、结果和决策标准。

这四种模式来自已有 Task 的实际用法，但不是完整清单。它们只是 Skill 指引，不是受管理元数据、生命周期状态、必需目录或 runtime 规则。reference 文档说明各模式的适用信号、不适用迹象、默认组织方式，以及采用后需要承担的维护工作。

适用信号出现时，Skill 先说明建议结构和维护成本，再询问用户是否采用。项目规则已经要求该模式，或者现有 Task 已经使用该模式时，无需重复询问。只有同名目录，并不表示 Skill 可以补建缺失结构。一次性工作不应套用模式，也不能预建空材料。项目规则可以增加、替换或限制模式、目录名称和维护规则，并且优先于 reference 中的通用指引。

采用模式后，`TASK.md` 仍只保留有用的顶层入口。它不会增加正式 pattern 字段，也不枚举每篇记录、每个设计版本、每项来源或每次实验。详细导航留在普通材料中，这样材料变化时无需重写 Task 入口。

### 项目配置

tk 提供内建默认值和可选的项目配置 `.agents/tk_config.toml`。不同项目确实需要不同的 root、子任务目录、Git 策略和创建策略，但目前没有实际场景需要用户级配置或项目外存储。因此 tk 不提供用户级配置、detached mode、全局 registry 或 `data_dir`。

默认值是：

```toml
task_root = ".tk"
subtasks_dir = ""
git_policy = "none"
creation_policy = "strict"
```

`strict` 只在用户当前对话中明确要求或确认持久化后创建顶层 Task。`permissive` 可以为用户已经决定推进、明显需要持久化、多阶段或跨会话的工作主动创建顶层 Task，并在同一轮告知用户。任何策略都不能在缺少明确早期保存意图时把未决定工作捕获为 `planning`。

项目配置只保存与默认值不同的字段，让配置文件记录项目做出的选择，而不是复制默认值。缺失字段继承内建值。未知字段、错误类型、非法枚举值和非法路径都属于错误。尚无项目级调整 WAL 读取预算的需求，因此它继续使用内建值或单次调用参数。

### 初始化

没有项目配置时，不带参数运行 `init` 会创建默认 `.tk` root，不创建配置文件。已有合法配置但解析出的 root 不存在时，`init` 创建对应 root。传入非默认参数时，创建或重写稀疏的 `.agents/tk_config.toml`，并创建解析后的 root。root 本身就是初始化标记，因为后续操作真正需要的是这个目录。单独的 marker 会重复表达同一事实，而配置文件可以先于 root 合法存在。

已经初始化的项目再次运行 `init` 会报错，除非用户传入 `--force`。强制初始化只修改配置。它重写稀疏差异，所有值恢复默认时删除配置文件，并确保新解析出的 root 存在。它不会清空、覆写、迁移或删除 Task 数据。root 改变时，旧 root 保持原样，结果同时报告新旧路径。此后的自动发现使用新 root，旧 root 仍可通过显式路径访问。从明确项目目录执行时，`init --force` 可以替换无效配置。把 force 限制在配置恢复范围内，可以避免初始化命令变成数据迁移或删除命令。

### 版本管理策略

目标项目使用 Git，因此 tk 只理解 Git，`git_policy` 也是唯一的版本管理字段。

`git_policy = "track"` 要求项目位于 Git worktree，并要求 Task root 和 `.agents/tk_config.toml` 都对 Git 可见，不能被 ignore。tk 不要求所有文件已经 staged 或 committed，也不要求工作树干净。

`git_policy = "ignore"` 要求 Task root 实际被 Git ignore，但不限制项目配置本身是 tracked、untracked 还是 ignored。`git_policy = "none"` 完全不检查 Git，也不要求项目使用 Git。

tk 可以调用 `git rev-parse`、`git check-ignore` 和 `git ls-files` 等只读命令。直接询问 Git，可以避免重新实现嵌套 ignore 规则、仓库 excludes、用户 excludes 和 worktree 行为。tk 不执行会修改工作树、index、配置或历史的 Git 命令，也不编辑 `.gitignore`。

除 `init` 和不访问项目的操作外，每个项目相关操作都必须在读写 Task 状态前完成 Git 策略预检。读取也不能例外，否则配置的存储规则只剩提示作用，同一个 root 的读写还会采用不同策略。状态不匹配时，操作直接拒绝并返回具体诊断。`init` 可以在策略不满足时先创建 root，因为 root 不存在时后续操作也无法满足策略。它会报告策略尚未就绪；在用户修复 Git 状态前，后续操作继续被拒绝。

### 自动发现

Task 路径由 tk 在代码中解析，不交给 Agent 猜测。显式 Task 目录、`TASK.md`、`tk.toml` 或材料路径优先于工具调用的 `cwd`。材料路径先解析到最近的、包含 Task `tk.toml` 的祖先目录，tk 再确定所属 Task、root、项目配置和 Git 策略。显式路径优先，是因为实际工作经常跨仓库，例如 Task 保存在笔记项目中，而代码位于另一个项目。

一个 prompt 或会话可以通过独立工具调用访问任意多个 Task root。tk 不保存 current Task、current project 或 actor 绑定，因为工作一旦切换仓库或 Agent，这类状态就会失真。裸 Task ID 或名称只能在显式项目目录或工具调用 `cwd` 解析出的 root 内查找。tk 不扫描兄弟仓库、用户目录或全局 registry。

搜索和顶层创建等没有 Task 主目标的操作优先使用显式项目目录，否则使用 `cwd`。向上发现不能越过当前 Git root。没有上层 Git root 时，基于 `cwd` 的发现只检查 `cwd` 本身，不向任意祖先目录查找。这些边界可以防止嵌套调用方误用无关祖先目录中的配置。位于非 Git 项目子目录中的调用方必须提供显式项目目录或 Task 路径。找到项目配置但其解析出的 root 不存在时，应报告项目未初始化，不能借用父项目的 root。

### 项目边界

`task_root` 必须是非空的项目相对路径，不能是项目根、绝对路径、包含 `..`，也不能通过符号链接解析到项目外。`subtasks_dir` 可以为空，表示子任务直接放在父任务下。非空值在父任务内遵循相同的相对路径和符号链接规则。受管理的 Task、材料和 WAL 访问不能越出解析后的 root。这些检查防止项目内操作因为配置或符号链接而读写无关位置。

tk 没有能够解析和维护跨项目目标的全局 registry，因此结构化 `parent`、`depends_on` 和 `related_to` 关系只能位于同一个 Task root。写操作以目标 Task 的 root 为准，拒绝 self relation、未知的新目标、依赖环和来自其他 root 的引用。更新可以移除目标已经缺失的现有关系。项目规则允许时，Markdown 可以链接到其他项目中的工作。tk 把链接视为普通文本，不扫描、验证或维护引用，也不对其应用生命周期规则。

### 搜索

`tk_search` 默认返回 `planning` 和 `open` Task，避免已完成历史挤占当前工作结果。明确搜索历史或指定状态时才包含 `closed`。精确 Task 目录、`TASK.md` 路径或完整 ID 可以读取 closed Task；明确查找某个 Task 时，如果活动候选没有匹配，可以继续查找 closed。普通搜索只排除已关闭父任务下同样处于 `closed` 状态的后代。force close 留下的活动后代仍然可见，因为隐藏它会让尚未结束的持久工作从普通恢复流程中消失。结果必须标明已关闭的祖先。

搜索匹配 ID、名称、目录名、路径、受支持元数据和可选 `extra` 过滤条件。已有项目确实使用自定义分类，因此保留 `extra`。创建可以设置初值；更新对顶层 key 执行浅层 set 和 remove；搜索使用 AND 语义精确比较所有给定的顶层 key 与 value，嵌套 value 作为一个完整结构比较。当前需求只有元数据和路径候选搜索，因此不提供 dot path、deep merge、范围运算符、包含运算符、模糊匹配或查询 DSL。搜索候选不能授权修改；写操作只接受精确引用。

### 并发

多个 Agent 可以读写同一个 Task root。目前多数场景只有一个 Agent，而且 Agent 做出决定需要数秒，写入受管理文件只需要毫秒。实际碰撞风险不足以支撑锁、compare-and-swap、合并规则和恢复协议的复杂度。因此 tk 接受 last-writer-wins 风险，也不承诺跨进程隔离。

每个请求仍须在写入前校验全部输入，因此一批子任务中只要存在非法输入，就不会写入其中任何一项。这只能避免单次请求写入一半，不能协调不同进程。原子文件替换可以避免元数据文件写到一半，但不提供事务隔离。每次成功的 WAL append 会写入一个完整条目，并发追加仍有相同限制。读取时报告无效条目，不能用 WAL 猜测当前状态。

### 验证

验证必须覆盖每个实际安装入口，不能只测试 Rust 二进制。先通过打包后的可执行文件运行五个高频 CLI 命令和管理命令，再通过 Codex 与 Claude Code 调用全部六个 MCP 工具，并通过 Pi 与 OMP 调用全部六个原生工具。过去发布包曾让 wrapper 使用错误的 runtime 版本，也曾让 adapter schema 拒绝合法的批量输入，因此每种入口都要比较报告的版本与 protocol，并且真正调用安装包内的 runtime。

冒烟场景覆盖有限 WAL 读取视图、持久日志追加、受限管理命令、同一父任务下的子任务批量创建，以及发现任一非法输入后整批不写入。还要覆盖初始化、发现、受管理文件诊断、生命周期转换和自动 WAL 事件、默认 `open`、force close 留下的活动后代、closed 过滤、`extra` 精确搜索、关系规则、关闭检查、Git 策略拒绝，并确认 `branch`、`paused`、`archived`、Inbox 行为、迁移入口和旧 `task_*` 别名没有残留。

Skill 场景审查覆盖 planning 授权、Goal 成功后的显式关闭授权、复合 catchup、closed Task 处理、取得授权后修复损坏的 `tk.toml`、拒绝未经授权的直接修复、只把 `TASK.md` 用作导航入口、不写入很快过时的进度、对不同规模的材料集合采用渐进式披露、清理 `TASK.md` 时保留可复用内容、材料模式采用、项目规则覆盖、不适用迹象、压缩时保留精确 Task 路径、选择 Harness 入口，以及拒绝绕过工作正常的工具。受控的工具缺失或调用失败场景必须遵循 `references/troubleshooting.md`，通过 Bash 执行等价 CLI 命令，同时保留原始接入错误。在 OMP 中使用 Luna 执行一个有代表性的真实 Agent 冒烟场景。不同宿主的模型措辞无需逐字一致，但可观察到的决定和工具行为必须一致。

## 考虑过的替代方案

**保留 Python/Nuitka runtime，继续优化缓存。** 这样不用重写，但无法消除冷构建。缓存还会占用磁盘，并且可能被清理。冷构建等待已经影响日常维护，因此本提案更换构建方式，不再继续调缓存。

**继续把 Task 元数据放在 `TASK.md` 中，或者让 `TASK.md` 可选。** 受管理 frontmatter 会让 tk 和人编辑同一个文件。改成可选，可以让只有元数据的 Task 避开这项冲突，却会失去稳定的可读入口。要求两个独立文件，才能让双方各自只负责一个文件。

**继续使用 `task` 作为公开名称。** 这个名称熟悉，但含义过于宽泛，而且与 OMP 的子 Agent 工具重名。把工具改名为 `tk`，比要求每次对话都区分两个无关操作更简单。

**保留旧 Inbox、状态和 branch 字段。** Inbox 与每个 Task 都代表已经决定推进的工作这一前提互相矛盾。现在由 `planning` 保存用户明确要求保留的早期工作。`paused` 和 `archived` 没有独立行为，branch 则属于项目上下文，不是 Task 身份。

**通过持久 current Task、branch、工作目录或 `continue` 绑定工作。** 一次会话跨仓库、Task 保存在笔记项目中或者 branch 改变时，这些捷径都会失效。显式路径和项目内查找无需隐藏会话状态，每次操作都能说明自己解析到了哪里。

**保存完整对话上下文，或者依赖 Harness 的压缩钩子。** 这样会保留更多聊天内容，却不一定留下另一个 Agent 真正需要的决定和材料。各宿主的钩子机制也不一致。tk 把可复用结果写入 Task 材料，并要求 Skill 在压缩时保留精确 Task 路径。

**保留用户级配置、detached 存储、全局 registry 和受管理的跨项目关系。** 当前没有实际场景需要这些能力。它们会引入隐式查找，还会让项目行为取决于机器级状态。项目内 root 和显式路径足以覆盖现有工作；Markdown 可以链接其他项目，但 tk 不会把这类链接当作受管理的生命周期关系。

**允许读取跳过版本管理预检。** 写入仍然强制该策略，读取却可以在存储规则已经不满足时成功。这样配置规则只剩提示作用，同一个 root 的读写还会采用不同策略，因此读取同样被拒绝。

**增加锁、compare-and-swap 或冲突解决。** 目前主要是单 Agent 使用，而且受管理文件的写入时间远短于 Agent 思考时间。提案接受现有碰撞风险，不为尚未出现的问题增加协调和恢复协议。

**迁移旧 Task 数据，并同时支持两种格式。** 只有目标格式稳定后，才能设计迁移。新的 `.tk` 默认路径会保留旧 `.task` 数据，后续可以单独审查迁移方案，不必让每个 tk 操作都背上兼容分支。

**当前 Goal 或会话成功后自动关闭 Task。** 一项 Task 可能跨越多个 Goal 和会话。只有用户能决定这项持久工作是否已经结束，因此关闭必须经过明确授权。

**所有 Harness 都使用 MCP。** 这样可以减少 adapter 形式，但 Pi 和 OMP 已经提供原生扩展 API。在这些宿主中再启动 MCP server，只会增加一个进程和一层 protocol，不会增加 Task 行为。

**让 Agent 默认通过 Bash 调用 CLI。** CLI 在各宿主都可用，但 shell 调用缺少工具级 schema，也更容易出现结构化参数转义错误，还可能掩盖损坏的 MCP 或原生安装。因此 Bash 只作为最后的恢复手段。

**只运行 Rust 测试和实现二进制。** 过去的发布包已经证明，源码测试通过后，wrapper、runtime 版本和生成 schema 仍可能不一致。实际安装入口的冒烟场景负责覆盖这个边界。

## 验收标准

1. `plugins/tk/` 与 `packages/tk/` 使用同一份 Rust 实现和生成合同。迁移记录 Rust 冷构建耗时、产物大小和启动耗时，并与 Nuitka 基线并列比较。
2. 每个 Task 都有稳定身份、权威 `tk.toml`、必需的纯 Markdown `TASK.md`，以及本文定义的三状态生命周期。创建和生命周期变化会自动追加 WAL 事件。
3. CLI 提供 `tk search`、`tk read`、`tk create`、`tk update`、`tk log`、`tk init`、`tk check`、`tk rename` 和 `tk --version`。在同一父任务下批量创建子任务时，必须先校验全部输入，再写入任何一项。
4. Codex 和 Claude Code 通过 MCP 暴露 `tk_read`、`tk_search`、`tk_create`、`tk_update`、`tk_log` 和受限 `tk_exec`。Pi 和 OMP 把相同六项操作注册为原生工具。所有 schema 都来自 Rust 合同，Skill 只包含 Agent 可观察规则，adapter 不包含另一套领域行为。
5. Agent 使用当前 Harness 支持的 MCP 或原生入口。只有该入口缺失或调用失败时，才能通过 Bash 执行等价 CLI 命令；回退时必须遵循本地 `references/troubleshooting.md`，也不能把 CLI 成功当作 Harness 接入正常的证据。
6. tk 不暴露 `TASK.md` 正文编辑参数。受管理文件缺失或无效时必须返回诊断，不能猜测内容。日常 `tk.toml` 修改使用 tk 操作；直接修复必须取得用户明确授权，并在修复后使用 tk 校验和 `tk_log` 记录。元数据更新不得重写 `TASK.md`。
7. Skill 把 `TASK.md` 保持为简短的导航入口，不写入很快过时的进度，按渐进式披露组织链接，把详细结果放进普通材料，就地更新当前摘要，并在移动已堆积细节时保留可复用内容。
8. 请求、Goal、执行或会话成功结束都不能自动关闭 Task。只有用户在当前对话中针对这次关闭明确同意，才能执行关闭，并且仍须遵守生命周期约束。
9. 每个发布的 Skill 语言变体都包含语义一致的本地指引，介绍按日期记录、深度调研、迭代设计和实验。这些模式可选，也不是完整清单。项目规则可以增加、替换或限制模式，并在冲突时优先。
10. 创建策略、稀疏配置、初始化、强制配置覆写、路径边界、Git 策略和发现行为符合本文定义。
11. 结构化关系强制同 root、目标存在、禁止 self relation 和禁止依赖环。tk 把跨项目 Markdown 引用视为普通文本。
12. `tk_search` 默认过滤出活动工作，保留 force close 留下的活动后代，并精确匹配顶层 `extra` 字段。修改操作必须使用精确引用。
13. 每个请求都在写入前拒绝非法输入。tk 不承诺元数据或 WAL 具有基于锁或事务的隔离。
14. tk 不包含旧数据迁移、Python 兼容路径、旧 `task_*` 别名、detached registry 或用户级配置。
15. Package、wrapper、runtime、schema 和 Skill 的版本与 protocol 一致。
16. 打包后的 CLI、Codex 和 Claude Code MCP 入口，以及 Pi 和 OMP 原生工具通过端到端冒烟场景，包括任一子任务输入非法时整批拒绝，以及已删除行为检查。
17. OMP 与 Luna 通过一个有代表性的 Agent 行为冒烟场景。不同宿主的模型措辞可以不同，但决定和工具行为必须一致。
18. tk 不增加跨 Task 优先级或筛选、todo 管理、Agent 编排、Issue 跟踪、工作流执行或知识索引。

## 风险

用户可能把 `tk` 与 Tcl/Tk 混淆。Package 名、README 首句、Skill description 和 `tk --help` 必须说明它是持久项目工作能力。

root 目录本身就是初始化标记，因此配置路径上的无关目录可能看起来已经初始化。Agent 对该目录执行操作前，诊断必须报告解析出的项目与 root。

Git 规则变化后，配置的策略可能不再满足，并同时阻塞读写。tk 不修复 Git 状态，因此诊断必须指出失败的策略和路径。

并发写入可能丢失元数据更新，跨进程 WAL 事件顺序也没有定义。进程崩溃或磁盘写满可能留下不完整的尾部条目。读取时应把它报告为无效，而不是隐藏或修复。

`git_policy = "none"` 不提供版本管理或备份保证。项目需要自行保护 Task 数据。

Agent 仍可能把短期进度写进 `TASK.md`，或者在依据不足时套用材料模式。Skill 场景必须覆盖这两类错误。

Bash 回退可能掩盖损坏的 MCP 或原生安装，也更容易出现参数转义或 payload 错误。Skill 只允许在工具入口缺失或调用失败时回退，必须保留原始错误，也不能把 CLI 成功算作 Harness 验证通过。

Rust 合同正确，不代表打出来的包一定正确。过期 wrapper 或生成 schema 仍可能和 runtime 一起发布，因此发布检查必须调用实际安装包，不能只测源码二进制。

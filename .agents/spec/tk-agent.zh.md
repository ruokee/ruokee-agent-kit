# tk Agent 行为

## 目标

指导 Agent 使用 tk 保存持久工作，不虚构任务范围、生命周期权限或运行时规则。英文和中文变体提供等价行为，源码和安装后 Skill 均无需其他组件即可理解。

## 公共面

### 触发

用户明确提及任务 ID、名称、路径、分支或 tk 操作时使用 tk。在 permissive 项目中，也为明显需要跨步骤或会话保存的工作创建或复用任务。不能仅因 tk 可用，就为简单问答、普通 TODO、小型一次性修改和随意想法建立任务。

两个 CLI Skill 的全部操作都使用公开 CLI，各自包含所需完整命令参考。源码和安装后的全部文件引用都在自身 Skill 内解析。

### 任务选择

新会话默认不绑定任务。唯一完整引用可以直接读取；名称、前缀、文本、材料路径、目录名或分支先搜索，再选精确引用。已有信息仍对应多个候选时，展示候选并询问用户。当前对话保留已解析任务，不会在任务元数据中持久保存会话绑定。

单独 catchup 只读。读取 summary、`TASK.md` 入口和必要材料，报告目标、状态、依赖、既有结论、阻塞和下一步，然后停止。同时授权继续的请求可以恢复工作。上下文恢复不重复已完成操作，也不产生新权限。

### 创建

创建前搜索现有工作，避免重复。名称表达整体预期结果，不只表达首个准备步骤。倾向避免分析、评估、规划等准备性词语，但保留用户指定名称和明确的仅研究范围。名称中的词不能决定生命周期状态。

`planning` 保存仍在形成的想法、调查或计划，`open` 表示活动工作，`closed` 表示工作结束，包括完成、放弃、不可行或被替代。状态不表示优先级。

strict 创建需要真实的当次确认，重要性本身不构成确认。permissive 可以保存值得保留的工作，只有用户明确希望保存早期材料时才使用 planning，已经开展活动工作时使用 open。创建后在同一回复报告任务名称、状态和路径。

只在活动父任务下创建子任务，不隐式重开 closed 父任务。批量子任务代表同一父任务下真实、独立的工作单元，不用于导入整个 backlog。planning 子任务确认及数据规格中的批次边界仍然有效。

### 材料

`TASK.md` 保持简洁，只保存当前目标、范围、约束、稳定采用的决定、重要材料入口和活动阻塞。详细调研、设计、执行证据和其他普通材料写入任务目录，不把 `TASK.md` 变成聊天记录、命令日志、长报告或旧计划档案。

普通正文编辑遵循用户当前权限，受管元数据通过公开 tk 操作修改。一级标题可选，可不同于名称和目录，不受 32 列限制。在正文编辑权限内直接修改，不要求 rename 或目录移动。rename 不同步标题。可读时倾向使用普通空格，同时保留明确措辞和有意义的标识符。初始生成标题无需额外清理写入。closed 任务保留只读边界。

### 日志

事实成为持久决定、纠正、可恢复里程碑、验证结果、协作结果或阻塞后，及时记录，再开始其他分支工作。使用非空单行摘要、可选详细 Markdown 正文，以及当前可得的最具体模型或 Harness 归属。

不记录普通读取、命令轨迹、暂定计划、猜测，也不重复运行时已经记录的生命周期事件。WAL 警告后先读取当前任务和日志，只补缺失事件，不重跑已提交修改。

### 生命周期

通过 update 改变关系、extra 或生命周期前读取当前任务。关闭前确认工作确实结束、后代和依赖满足关闭规则、`TASK.md` 保留当前结果和入口，以及必要决定和验证结果已记录。

使用 `tk update <task_ref> --start` 时不传原因参数。`--close <reason>` 和 `--reopen <reason>` 各自携带非空原因，不使用独立的原因选项。

close 和 reopen 分别要求非空理由及用户当次明确确认。只有明确请求时使用 force。不从会话完成推断关闭，也不为写日志而重开。新工作通常使用关联任务，只有用户确认仍属于原工作时才重开原任务。rename 和符合条件的修复不授权其他 closed 任务写入。

### 修复

普通变更使用公开 tk 操作。受管元数据损坏且 tk 无法表达修复时，先说明精确字段和最终内容，取得当次明确授权，只做这些最小修改，运行 `tk check`，恢复可用后在 WAL 记录修复。不编辑元数据、清理状态或 Harness 配置来绕过运行时拒绝。

决定是否重试前，读取稳定错误代码、类别、details 和 completed/uncompleted 项。部分失败后，根据当前规范状态及用户目标发出新的完整命令，不假定回滚或续做。只询问真实用户决定，不询问工具或材料可提供的事实。

### 材料模式

记录、深度调研、迭代设计和草稿纸四种模式可选，可以组合。它们只组织普通文件，不增加 schema、元数据、extra 键、运行时状态、命令或自动目录。项目约定可以覆盖默认路径。

只有信号出现后才主动建议模式，说明增加哪些材料及维护成本。用户明确要求采用本身就是采用授权，不受主动建议反例阻止。采用后在 `TASK.md` 简述选择并链接现有入口材料。不建空占位、不虚构过去活动、不写未来日期记录，也不只为符合示例迁移现有任务。采用不授予任务创建、生命周期、删除或移动权限。

记录模式 Records 可以在第二个本地日历日已有实质调查、实现、验证或决定活动后建议。同日工作或计划以后继续不足以触发。默认文件为 `records/YYYY-MM-DD-topic.md`。保留当时上下文、行动、证据和判断，后续纠正写入后续材料。从 `TASK.md` 可访问当前结论。记录不替代 WAL 或正式决定。

深度调研模式 Deep research 可以在外部来源需要收集、保存或交叉核对，或已有来源列表和材料时建议。一个已知文档或普通 API 问题不足以触发。默认入口为 `research/report.md`、`research/README.md`，按需保存来源材料。保留来源归属、访问日期、主张证据、来源冲突、未验证点和结论边界。`TASK.md` 直接链接报告。

迭代设计模式 Iterative design 可以在两次以上重大重设计、整体推翻方案或主要边界持续变化后建议。增量功能、措辞修改和普通审查修正不要求新修订。默认入口为 `revision_<N>/README.md` 及该修订材料。每个修订自足，旧修订保留原内容。新的重大重设计开启下一修订，普通修正更新当前修订。`TASK.md` 只暴露一个当前设计入口。

草稿纸模式 Scratchpad 可以在未完成笔记、输出、片段、小脚本或临时文件需要保留时建议。无需保留的简短交流不创建材料。默认位置为 `scratchpad/`，文件组织自由。稳定内容进入合适的普通材料，过时笔记保持可与当前事实区分。清理仍需要删除或移动权限。

正式决定使用项目指定机制和位置，材料模式不替代它。

## 验收标准

已安装 Skill 场景必须证明英文和中文行为等价：

- strict 与 permissive 创建、真实 planning 意图、保留用户范围的名称、避免重复，以及同回复报告创建结果。
- 精确和模糊选择、歧义候选、只读 catchup，以及只有有效权限下才继续。
- 稳定 `TASK.md` 内容、独立正文标题、及时有用的 WAL，以及追加失败后不重复已提交工作的恢复。
- close、reopen、force 和手工修复的当次授权，不隐式写 closed 任务，不绕过运行时拒绝。
- 任务操作使用公开 CLI 及规定的命令、默认值、结果和错误。
- 每种模式的信号、反例、明确采用、有用材料、历史保留和清理权限，不增加运行时字段或空架子。

静态 Markdown 或编译检查不能证明这些 Agent 结果。Skill 验证须在 Harness 场景中观察已安装候选。
